# LearnTGVaultsV6: the accounting guard

The scholarship vault that comes after V5, with self-enforcing accounting. It is **written and
tested but not deployed**: it lives apart from the contracts in production so that nothing here
is mistaken for live code.

| | |
|---|---|
| Contract | `apps/contracts/contracts/next/LearnTGVaultsV6.sol` (`VERSION = 6`) |
| Tests | `apps/contracts/test/next/LearnTGVaultsV6.test.ts` (11) |
| Deploy | `cd apps/contracts && bin/next/deployLearnTGVaultsV6` (operator) |
| ABI | `apps/web/abis/next/LearnTGVaultsV6.json` (generated by `pnpm compile`) |
| Requirement | https://github.com/pasosdeJesus/learn.tg/issues/221 §Findings |

Everything else under `apps/contracts/contracts/` and `apps/contracts/test/` is the code and
the tests of the deployed versions; a `next/` subfolder means "not deployed yet". The project
keeps one Hardhat app and one `pnpm compile` (Hardhat compiles a single source root), so a
separate package would duplicate the config and the dependency tree for no isolation gain: the
deployed ABIs are only the ones published in `apps/contracts/deployments/` and synced to
`apps/web/abis/`.

## Why

`LearnTGVaultsV5` keeps one token balance but **per-course bookkeeping**:

- `recordCourseFunds` adds to `vaults[courseId].balanceUsdt/Slearn` (only the SLEARN
  contract can call it).
- `payScholarship` requires **that course's** recorded balance to be ≤ the contract's
  **whole** token balance, then pays and subtracts.
- `setVaultBalance` (a migration helper, `onlyOwner`) sets a course's balance requiring
  only **that amount** ≤ the whole balance. It never looks at the sum of the courses.
- `emergencyWithdrawUSDT/SLEARN` move tokens out **without touching** the per-course
  balances. This is not hypothetical: on 2026-06-02 `emergencyWithdrawUsdt(8248137)` moved the
  whole balance of `LearnTGVaults` V2 (`0x4AE3…33D7`) to the owner as the first step of the
  V3 migration, and the books of the retired course 106 kept their 8 USDT.

So the recorded balances can add up to more than the contract holds. On Celo mainnet
(2026-10-28, block ≈ 81 410 000) they do:

| | Recorded (sum of courses) | Held | Difference |
|---|---|---|---|
| USDT | 21.236402 | 13.195492 | **−8.040910** |
| SLEARN | 819.23 | 834.29 | +15.06 |

The gap is the retired course **106** ("W e b 3 e IBU --retirado"), which carries a
recorded balance of **8 USDT** and a per-guide amount of 0.000001. Those 8 USDT were real:
`deposit(106, 10000000)` put 8 USDT into V2 on 2026-01-13 (block 56 437 513). They left V2 on
2026-06-02 with `emergencyWithdrawUsdt(8248137)` (block 68 480 390), which transferred the whole
V2 balance to the owner and left the per-course books untouched. That was the first
half of the V3 migration: 3 s later the same 8.248137 USDT were sent to V3, and the same pattern
repeats in every migration (V3 swept 11.418021 into V4 on 2026-06-09, V4 swept 12.224915 into
V5 on 2026-08-12), so the tokens never left the fund. What travelled without the tokens was the
number: every migration copied the books with `setVaultBalance` (V5:
**2026-08-12 14:36:25 UTC**) and no `CourseFundsRecorded` event exists for 106. The same stale
number is in **V3** (`0x34b0…4728`) and **V4** (`0x42dc…0479`).

The V5 setup shows exactly how the gap is written and why a guard is needed: it received
**12.224915 USDT** and then declared **20.262753 USDT** of course balances with
`setVaultBalance` (8.037838 more than it held; course 106 alone is 8), so the sum was above the
money from the first minute. A `totalRecordedUsdt` updated by these setters and compared against
`token.balanceOf(address(this))` would have reverted the migration that day.

Impact: nobody is owed that money (the course is retired and pays 0.000001 per guide),
but the books overstate the fund, and a course whose recorded balance exceeded the global
balance would make `payScholarship` **revert**. The invariant `Σ recorded ≤ held` is the
one to enforce.

## What V6 implements

**Decision (operator, 2026-10-22): one contract per course is not practical; the fix is to do
the accounting well in the contract.** The contract is written in
`apps/contracts/contracts/next/LearnTGVaultsV6.sol` (`VERSION = 6`, **not deployed**) with its
tests in `apps/contracts/test/next/LearnTGVaultsV6.test.ts`; it keeps a single vault and makes the books
self-enforcing.

1. **Two accumulators.** `uint256 public totalRecordedUsdt; uint256 public
   totalRecordedSlearn;`, changed only by the four functions that touch `vaults[]`:
   `recordCourseFunds` (`+=`), `payScholarship` (`-=` exactly what it deducts),
   `setVaultBalance` (`total - old + new`) and `retireCourse` (`-=` the removed amounts).
   Each one ends with

   ```solidity
   function _assertSolvent() internal view {
       require(totalRecordedUsdt <= usdtToken.balanceOf(address(this)), "Accounting: USDT");
       require(totalRecordedSlearn <= slearnToken.balanceOf(address(this)), "Accounting: SLEARN");
   }
   ```

   O(1): do **not** iterate `vaults` (there is no course list and the gas would be unbounded).
2. **`emergencyWithdraw*` can only take the unallocated float:** `require(amount <=
   balanceOf(this) - totalRecordedX, "Withdrawal would break accounting")`. For a real
   emergency add `forceEmergencyWithdraw*` with an explicit `bool`, which sets
   `accountingBroken = true`, emits it, and makes `payScholarship` revert until the owner
   reconciles. A migration therefore zeroes the books first (`setVaultBalance` or
   `retireCourse`), withdraws, and declares the balances again in the new vault; the contract
   cannot silently keep paying against money that left.
3. **`retireCourse(courseId, bool sendToOwner)`**: retires the course and cleans its books in
   one call, so the second half cannot be forgotten (this is exactly the course 106 case). Since
   there is **one** token balance, "the course's money" is its recorded balance and it can only
   be paid from the float left after covering the other courses: it sends
   `min(recorded, float)` to the owner when `sendToOwner` is true, writes off whatever has no
   tokens behind it, or (with `false`) leaves the backed part in the pool as float. It keeps
   `exists = true`, zeroes the per-guide amounts and emits
   `CourseRetired(courseId, sentUsdt, sentSlearn, unsentUsdt, unsentSlearn)`.
4. **A view for the off-chain check.** `accountingState() returns (heldUsdt, heldSlearn,
   totalRecordedUsdt, totalRecordedSlearn, accountingBroken)`, read by
   `apps/web/bin/check-vault-balances.mjs` (target `make vault-check`); the script must also
   **fail when the accumulator differs from the scanned per-course sum**, because that is a
   contract bug, not rounding.
5. **Tests** (Hardhat, `apps/contracts/test`): a migration that declares more than it holds
   reverts; an emergency withdrawal above the float reverts; `forceEmergencyWithdraw` sets the
   flag and blocks `payScholarship`; `retireCourse` keeps the invariant and blocks payment of
   that course; the totals stay exact across `recordCourseFunds` + `payScholarship`.
6. **Migration script.** Deposit into the new vault, `createVault` + `setVaultBalance` per
   course, `retireCourse` for the courses that no longer exist, assert `accountingState()`
   on-chain and run `make vault-check` before and after.

### What the counter does and does not fix

It fixes the drift that exists today: from V6 on, no `setVaultBalance`, `recordCourseFunds`,
`payScholarship`, `retireCourse` or `emergencyWithdraw*` can leave the books above the tokens, so
a migration that declares 20.26 while holding 12.22 reverts instead of shipping, and the
retired-course phantom becomes impossible once `retireCourse` is used. What it does not do is
give each course its own tokens: the guard checks the **sum**, so a migration can still assign
the pool to different courses while the total matches. **That limit is accepted**: a contract
per course (or a clone per course) would be the only true segregation and was discarded as
impractical — deploy and migration per course, a `courseId -> vault` registry, and more
addresses to verify. A per-course balance inside one contract is not possible with a single
ERC-20 balance, and a hash of the totals would be only an audit anchor, not enforcement.

## Until V6 is deployed

- Deploy with `cd apps/contracts && bin/next/deployLearnTGVaultsV6` (writes
  `deployments/LearnTGVaults/V6/<network>.json`); the operator runs it.
- **Do not call `setVaultBalance` outside a migration.** It is not a general admin tool.
- After **any** `setVaultBalance` or `emergencyWithdraw*`, run
  `cd apps/web && make vault-check ARGS="--network celo"` and require it to pass.
- Clean up the known phantom with `setVaultBalance(106, 0, 0)` (V6: `retireCourse(106, true)`); that
  leaves a **0.040910 USDT** residual (0.037838 declared above the tokens in the V5 setup plus
  0.003072 of rounding), accepted by the script's built-in tolerance (0.05 USDT / 0.50 SLEARN,
  in `apps/web/bin/check-vault-balances.mjs` — it is deliberately not a flag).
- The guard is also the reason the script exists: without it, only a post-migration check
  can catch a bad migration. The script already understands V6: it accepts `VERSION` 5 or 6
  and, on V6, compares `accountingState()` with the scanned sum and fails when the contract
  reports `accountingBroken`.
