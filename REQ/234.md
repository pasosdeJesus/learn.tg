## 1. Objective

Convert `learn.tg` into a **Progressive Web App (PWA)** that works **offline-first** in low-connectivity contexts (Seria/Falaba, Sierra Leone), while enabling **pluggable tools built as packages** — with **`gdcluster` as the first real tool** to be integrated.

The PWA must:

1. **Work offline** for core learning activities (reading guides, completing crosswords, signing auth locally)
2. **Synchronize** with the server when a connection is available
3. **Load tools dynamically** from packages (motors, per R-#35), starting with `gdcluster`
4. **Support `gdcluster`'s own tools offline**: country/cluster funds, rankings, cluster formation, and student ranking for program director selection
5. **Respect the Two-Layer Strategy** (E-#177): Celo today, Cardano in the future
6. **Preserve user privacy** in persecution contexts (pseudonyms, encrypted storage)

---

## 2. Motivation

The current app assumes a stable internet connection. Users in Seria/Falaba experience:

- **Unstable electricity** — devices can't stay charged
- **Intermittent signal** — no internet for hours at a time
- **Two SIMs (Orange/Africell)** — users choose whichever works at the moment
- **High data costs** — every byte matters

Without a PWA, learn.tg is unusable in these contexts. With a PWA, the core learning experience can happen offline, and synchronization can happen when the opportunity arises.

Additionally, the ecosystem already has a **real tool built as a package**: `gdcluster` (R-#35). This tool includes:

- Country/cluster funds (donations, balances)
- Ranking of countries and clusters
- Cluster formation (invite, join, manage)
- Ranking of students for program director selection (R-#226)

The PWA must be able to load `gdcluster` **dynamically** and let it work **offline-first** with its own data.

## 3. Design

### 3.1 PWA Core Principles

| Principle | Description |
|-----------|-------------|
| **Offline-first** | The app works without connection; the network is a bonus |
| **Cache-first** | Static assets are cached; the app loads instantly |
| **Background sync** | Data is synchronized when the connection returns |
| **Installable** | Users can add learn.tg to their home screen |
| **Pluggable tools** | Tools (engines) are loaded dynamically from packages |
| **Lightweight** | The core bundle stays small; tools are loaded on demand |

### 3.3 The `gdcluster` Tool

|---------|-------------|-----------------|

| **Ranking of countries/clusters** | Public rankings (transparency) | ✅ Read cached |

| **Student ranking** | Ranking for program director selection (R-#226) | ✅ Read cached; scores computed offline |

**Offline behavior for `gdcluster`:**

| Action | Online | Offline |
|--------|--------|---------|
| **View country/cluster funds** | ✅ Fresh from server | ✅ Cached (last known) |
| **View rankings** | ✅ Fresh from server | ✅ Cached (last known) |
| **Create a cluster** | ✅ Immediate | ⏳ Queued; synced later |
| **Invite a pastor** | ✅ Immediate | ⏳ Queued; synced later |
| **Accept/reject an invitation** | ✅ Immediate | ⏳ Queued; synced later |
| **View student ranking** | ✅ Fresh from server | ✅ Computed from cached data |

### 3.4 Service Worker Strategy

| Resource Type | Caching Strategy | Rationale |
|---------------|------------------|-----------|
| **Static assets** (HTML, CSS, JS, fonts) | Cache-first | App loads instantly, even offline |
| **Guide content** (Markdown, images) | Cache-first with network update | Content is read-only |
| **Tool assets** (gdcluster JS chunks) | Cache-on-first-use | Tools are loaded on demand; cached after first load |
| **API responses** (GET) | Network-first with cache fallback | Data may change; prefer fresh when online |
| **API mutations** (POST, PUT, DELETE) | Network-only with offline queue | Mutations require connection; queue when offline |

### 3.5 IndexedDB Structure

| Store | Purpose | Encryption |
|-------|---------|------------|
| **session** | NextAuth session (JWT in cookie + fallback in localStorage) | No |
| **in_app_wallet** | In-App Wallet private key (R-#184) | AES-256-GCM + PBKDF2 (user PIN) |
| **progress** | Course progress (guides, crosswords) | No |
| **pending_actions** | Offline queue (mutations to sync) | No |
| **tool_data_gdcluster** | Data cached by gdcluster (funds, rankings) | No |

### 3.6 Offline Queue for `gdcluster`

When the user performs a mutation offline (e.g., creates a cluster, invites a pastor):

1. The action is stored in `pending_actions` (IndexedDB) with `type: 'gdcluster_create_cluster'`, etc.
2. The UI shows a "pending sync" indicator.
3. When the connection returns, the Sync Manager processes the queue.
4. The server validates each action and responds.

**Example:**

```typescript
interface PendingAction {
  id: string;
  type: 'gdcluster_create_cluster' | 'gdcluster_invite' | 'gdcluster_accept' | ...;
  payload: any;
  createdAt: number;
  retries: number;
  status: 'pending' | 'syncing' | 'failed';
}
```

### 3.7 Sync Manager

```typescript
// lib/pwa/sync-manager.ts
export class SyncManager {
  async processQueue(): Promise<void> {
    const actions = await getPendingActions();
    
    for (const action of actions) {
      try {
        await this.syncAction(action);
        await removePendingAction(action.id);
      } catch (error) {
        await markActionAsFailed(action.id, error);
      }
    }
  }
  
  private async syncAction(action: PendingAction): Promise<void> {
    // Route to the appropriate API endpoint based on action.type
    switch (action.type) {
      case 'gdcluster_create_cluster':
        await fetch('/api/gdcluster/create', { method: 'POST', body: JSON.stringify(action.payload) });
        break;
      case 'gdcluster_invite':
        await fetch('/api/gdcluster/invite', { method: 'POST', body: JSON.stringify(action.payload) });
        break;
      // ...
    }
  }
}
```

### 3.8 Offline Fallback Page

When the user navigates to a route that is not cached and there's no connection, the Service Worker serves `app/offline/page.tsx`:

> *"You are offline. This page is not available right now. Your progress has been saved locally and will sync when the connection returns. [Go to cached content]"*

### 3.9 Detection of Offline Status

```typescript
// lib/pwa/useOfflineStatus.ts
export function useOfflineStatus() {
  const [isOffline, setIsOffline] = useState(!navigator.onLine);
  
  useEffect(() => {
    const handleOnline = () => setIsOffline(false);
    const handleOffline = () => setIsOffline(true);
    
    window.addEventListener('online', handleOnline);
    window.addEventListener('offline', handleOffline);
    
    return () => {
      window.removeEventListener('online', handleOnline);
      window.removeEventListener('offline', handleOffline);
    };
  }, []);
  
  return isOffline;
}
```

The UI must show a clear indicator when the user is offline:

- **Banner:** "You are offline. Your progress will be saved locally and synced when connection is available."
- **Icon:** A small cloud-off icon in the header.

### 4.2 Tool Loading

Tools are loaded dynamically using **dynamic imports**:

```typescript
// lib/pwa/tool-registry.ts
export async function loadTool(toolName: string): Promise<void> {
  const manifest = await fetchToolManifest(toolName);
  
  if (manifest.offline?.cacheable) {
    // Cache the tool's assets
    await cacheToolAssets(manifest);
  }
  
  // Register the tool's routes and API endpoints
  registerToolRoutes(manifest);
}
```

**For `gdcluster`, the tool loads:**

- The cluster management UI (`/cluster/*`)
- The funds/ranking UI (`/cluster/ranking`, `/cluster/funds`)
- The API endpoints (`/api/gdcluster/*`)

## 9. Example: `gdcluster` Offline Flow

**Scenario:** A pastor in Seria/Falaba wants to create a cluster while offline.

1. The pastor opens `learn.tg` (PWA) — the app loads from cache.
2. The pastor navigates to `/cluster` — `gdcluster` is loaded dynamically.
3. The pastor creates a cluster (name, pseudonym, invitations) — the action is queued in `pending_actions`.
4. The pastor sees a "pending sync" indicator.
5. Later, the pastor's device connects to the internet.
6. The Sync Manager processes the queue — the cluster is created on the server.
7. The pastor sees a "synced" indicator.

**Scenario:** A visitor wants to see the ranking of clusters in Sierra Leone while offline.

1. The visitor opens `learn.tg` (PWA) — the app loads from cache.
2. The visitor navigates to `/cluster/ranking` — `gdcluster` shows the cached ranking (last known).
3. The visitor sees a "cached data" indicator.
4. When the connection returns, the ranking is refreshed.
