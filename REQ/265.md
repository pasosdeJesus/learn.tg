# R-#265: Several wallets per user

Let one learner own **several wallets** (in-app + external, or an old and a new one)
without getting a separate account, progress, scholarships or credentials for each.

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/265
**Created:** 2026-09-24
**Status:** **Draft** — refined 2026-10-06 with the operator's decisions (a credential follows the wallet that completed it, payouts follow the connected wallet, bonuses the last used wallet); nothing implemented yet.
**Type:** Feature / Identity
**Priority:** Medium-High — today the same person with the in-app wallet and an external
wallet ends up with two accounts and the work of one of them is invisible from the other
(the operator asked for it on 2026-09-23, while testing offline on Android: "we should
allow one user to have several wallets").
**Dependencies:** R-#227 / R-#233 (session-only auth), R-#244 / R-#245 / R-#246 (in-app
wallet), R-#259 (per-user privacy switches), R-#256 (offline copies are per wallet),
R-#163 (referral program), R-#153 (data at rest), R-#260 (learner/geo base model in `m`),
R-#250 (session lifetime/revocation, §3.8), R-#248 (wallet auto-lock model, §3.8), and the
`m` identity core **`m/REQ/47`** / `m/doc/identidad-multibilletera.md` (N wallets + invitations).

---

## 1. Objective

The platform authenticates with a wallet, but the identity is the **user**, who may own
**N wallets** (in-app + external, or an old and a new one); any of them can sign in to the
same account. This requirement adds the missing piece: the **account**, not a single
wallet, is what holds progress, scores, credentials and privileges.

1. **Link a wallet from inside the account**: signed in with wallet A, the learner signs
   a message with wallet B (SIWE) and B is added to the same account.
2. **Sign in with any linked wallet**: wallet B alone reaches the same account (same
   progress, scores, credentials, privacy switches, referral code).
3. **No principal wallet in the core**: there is no stored "main" address. Payouts go to
   the connected wallet, credentials to the wallet that completed the course and bonuses
   to the last used wallet (see §3.3); a consumer that needs a single public address uses
   the oldest linked wallet or its own column.
4. **Unlink** a secondary wallet, with the rules and the consequences stated in the UI.

## 3. Design (to be refined by the operator)

### 3.1 Model

- Keep `billetera_usuario` as the wallet ↔ user map and **keep the unique wallet**
  (a wallet can never belong to two people).
- **No principal wallet**: the core stores no "main" address (no core operation uses one).
  A consumer that needs a default public address uses the oldest linked wallet or adds its
  own column. `m/doc/identidad-multibilletera.md` is the detailed design.
- Record the destination of every credential: `credential_emission.billetera` (or an FK
  to `billetera_usuario.id`). The table stores `usuario_id` + `course_id` + `token_id` and
  **no address**, so today the profile cannot tell which wallet holds each SBT nor where
  to revoke and re-mint.
- Optionally `billetera_usuario.linked_at` / `linked_by` for audit in `userevent`.

### 3.2 Linking and unlinking

- **Link**: authenticated as the account + SIWE with the new wallet (`POST /api/wallet/link`,
  session cookie + signature; no new `usuario` is created).
- **Sign-in**: `authorize()` keeps creating an account for a genuinely new wallet (that is
  how the platform onboards), **but** when the SIWE arrives signed in as another account the
  route offers "link" instead. Open question: on a plain sign-in with an unknown wallet, do
  we offer to link it to the account the browser already has a session for?
- **Unlink**: only a secondary wallet, never the last one; what happens to the SBTs already
  minted to that address is an operator decision (they stay on-chain; the profile can stop
  showing them or keep them as historical).

### 3.3 What follows the user and what follows the wallet (operator decides)

| Data | Options |
|---|---|
| Progress (`guide_usuario`), scores, verification, privacy switches, referral code | **Per user** (they follow the account; that is the point of the requirement) |
| SBT / credential | **To the wallet that completed the course** (the one the learner signed with). The public profile aggregates **all** the credentials held by **every** wallet of the account |
| Scholarships / UBI | **To the connected wallet** (the one signing the claim). The contract checks per address, so N wallets could claim N times: the anti-abuse decision is (a) accept it, or (b) the backend marks the guide as paid per user and refuses a second claim |
| Bonus (referral payout, `pastor_bonus`, …) | **To the last used wallet** |
| Referral | Referrer/referred are users; linking must not create a self-referral (A links B and then B "refers" A) — needs an explicit rule |
| Offline copies | `belongsToWallet` accepts any wallet of the account; the record should also store the `usuario_id`; cleanup when the last wallet goes away |
| Church roles | Per user and per church (unchanged); decide what happens when a linked wallet was already a pastor |

### 3.4 Limits and abuse

- Maximum wallets per user (suggested 2-3) and rate limit on linking.
- Linking does **not** merge two verified profiles: if the second wallet already had an
  account with progress, the operator decides whether to (a) refuse, (b) migrate
  `guide_usuario`/`transaction`/`credential_emission` to the surviving account, or (c) keep
  both accounts and only allow signing in with either.
- Self.xyz / verifier checks: per user, not per wallet.

### 3.5 Admin

- The admin UI lists every wallet of a user and allows linking/unlinking (both actions
  logged in `userevent`).
- The admin can **revoke a credential held by a compromised wallet and re-mint it to
  another wallet** of the same user (both actions logged).

### 3.6 Privacy: switching wallets and transfers that cannot be traced (operator, 2026-09-24)

Operator notes for when this functionality exists, thinking about the privacy of whoever has
to protect their affiliation (R-#259) or simply does not want a public observer to tie their
activity across wallets:

1. **Recommend switching wallets.** With several wallets per user, and even with several
   wallets inside the in-app wallet, the app can **suggest** using a different wallet for the
   activity that should be detached from the main identity (e.g. claiming UBI, donating or
   completing a sensitive course), explaining what follows the person (progress,
   scholarships, credentials) and what stays on the address.
2. **Safe transfer between in-app wallets, hard or impossible to trace.** Offer a function to
   move funds from one in-app wallet to another that uses **timing** mechanisms (e.g. a
   delay/execution window, batches or normalised amounts) and **platform** mechanisms (the
   wallet itself as intermediary, signing and broadcasting from the platform) so an observer
   cannot tell **which wallet sent to which**. Its honest limit must be stated: the trace
   exists on-chain, so the goal is that it is **not attributable** with public information,
   not that it is undetectable. It requires a decision on custody at transfer time, amount
   limits, accounting traceability (transparency) and how it combines with the anti-abuse
   rules of §3.3 and §3.4.

### 3.7 Resilience: a lost or compromised wallet (operator, 2026-10-06)

Decision: **credentials do not travel with a stored default wallet**, so losing access to
one wallet (or having it compromised) is not catastrophic.

- **Credentials follow the wallet that completed the course.** SBTs are soulbound: an
  attacker who gets the key cannot move them, only hold them and appear as their holder.
- **The public profile shows the credentials of every wallet of the account**, so losing
  the wallet that holds an SBT does not hide it from the profile.
- **The admin can revoke and re-mint**: revoke the credential on the compromised address
  (`credential_emission.revoked_at` already exists) and mint it again to another wallet
  of the user.
- **Funds are the accepted loss**: a compromised wallet can lose money, but not the
  account's identity, progress or credentials. Payouts therefore go to the connected
  wallet (see §3.3), not to a stored default address.

### 3.8 Session lifetime and key lock (R-#250, R-#248)

The refactor changes the identity surface these two requirements govern, so settle both
**here** instead of touching `auth-options.ts` / `authenticateUser` twice.

**R-#250 (session lifetime and revocation) — do it with this requirement.** Today the
NextAuth session is the only credential (R-#233): a JWT whose `sub` is the wallet, with no
explicit `maxAge` (30 days by default) and no server-side revocation (`doc/siwe-auth-flow.md`,
`doc/api-security.md`). With several wallets the session must identify the **user**, and the
wallet becomes a changeable attribute:

- The session shape changes to session ↔ user (plus which wallet is connected for the current
  request). `walletAddress` stays an untrusted hint that must belong to the account, not the
  identity.
- Add an explicit `session.maxAge` + `updateAge` and a per-user `session_epoch` so the operator
  can cut **every** session of a user with one `UPDATE` (lost or shared phone: the measured
  audience is on shared phones). See R-#250 §4.
- Write down the rule that becomes central with N wallets: **the session identifies the user;
  the unlocked wallet authorizes value** (signed in + wallet locked = read, not write), and cover
  it with a test.

**R-#248 (configurable inactivity auto-lock) — settle the model, keep the selector optional.**
The wallet key lives in memory and locks after `INACTIVITY_LOCK_MS` (one hour,
`lockReason: 'idle'`, never signs the user out). With N wallets fix the model once:

- Decide whether the timeout is a **device** preference (R-#248 §4: device-scoped, never
  synced) or per wallet. Suggestion: keep it **per device** (one timeout), so the learner does
  not juggle N unlocks, but lock **all** keys together on idle.
- Unlocking one wallet must not silently unlock another; the L1 gesture funds gate (a fresh
  gesture before `eth_sendTransaction` / `eth_signTypedData_v4` / `eth_signTransaction`) stays
  **per transaction** and independent of the timeout, so a longer timeout cannot make a transfer
  silent.
- The lock is `'idle'`: it never signs the user out (that is R-#250's job).
- The selector itself ("1 min / 1 h / 4 h / 1 day / never") stays optional: build it only if
  users ask, and "never" only with a passkey enrolled (R-#248).

## 4. Acceptance criteria (draft, to refine)

- [ ] A signed-in learner can link a second wallet by signing a SIWE message with it; the
      wallet appears in the account and the session keeps working.
- [ ] The linked wallet can sign in by itself and reaches the same account: same progress,
      scores, privacy switches, referral code and credentials list.
- [ ] A wallet still belongs to **one** user only (`UNIQUE (billetera)` kept); no API can
      move it without the signature of that wallet and the session of the receiving account.
- [ ] Linking never duplicates progress or a scholarship for the same guide in the
      database (`guide_usuario` one row per user and guide) and the anti-abuse decision of
      §3.3 about the on-chain checks is implemented and documented.
- [ ] A credential is minted to the wallet that completed the course (recorded in
      `credential_emission.billetera`); the public profile lists the credentials held by
      every wallet of the account.
- [ ] Scholarship and UBI payouts go to the connected wallet and bonuses to the last used
      wallet.
- [ ] The admin can revoke a credential held by a compromised wallet and re-mint it to
      another wallet of the same user (both actions logged).
- [ ] Unlinking a secondary wallet is possible and safe (the account keeps at least one);
      the UI states what happens to the credentials already minted to it.
- [ ] The offline store accepts any wallet of the account and is cleaned when the last
      wallet is unlinked or deleted.
- [ ] The admin can see and manage the wallets of a user.
- [ ] Migrations reversible, `make type` and the affected `make test*` targets green,
      `node bin/audit-api-auth.mjs` at `0 failed` for the new route(s).
- [ ] The session identifies the **user**, not the wallet: `session.maxAge`/`updateAge` are
      explicit and a per-user `session_epoch` lets the operator revoke every session of a user
      with one `UPDATE` (R-#250, §3.8).
- [ ] With N wallets the idle lock (R-#248 model) locks every key together without signing the
      user out, unlocking one wallet does not unlock another, and the L1 gesture funds gate still
      fires per transaction (§3.8).
- [ ] User guide and `ARCHITECTURE.md` updated (how to link, what follows the user, what
      stays in the wallet).

## 5. Open questions for the operator

1. Do we offer "link this wallet to my account" to anyone who signs in with an unknown
   wallet while having a session, or only from an explicit screen in the profile/settings?
2. Claiming goes to the connected wallet (decided); may a person claim with several
   wallets (the contract is per address), or does the backend enforce one claim per user?
3. If the second wallet already has an account with progress, do we merge, refuse or keep
   two accounts?
4. What happens to SBTs minted to a wallet that is later unlinked (keep them in the public
   profile, hide them, offer to re-mint to another wallet of the account)?
5. How many wallets per user, and is the in-app wallet always one of them?

## 6. Out of scope

- Changing the wallet's cryptographic role: it stays a signing device, and the **session
  identifies the user** (§3.8), not the wallet.
- Multi-signature accounts or shared accounts between different people.
- Anonymous/pseudonymous credentials (R-#259 §5 keeps that separate).
- Adopting the `m` base model in learn.tg (R-#260 Part B). The N-wallets relation itself is
  already the `m` identity core (`m/REQ/47`, `m/doc/identidad-multibilletera.md`); what is out
  of scope here is learn.tg's migration to it.
