# R-#288: Link a new in-app wallet to an existing verified account and delete the duplicate

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/288
**Created:** 2026-10-22
**Status:** **Implemented (2026-10-22)** — app core, routes, UI, unit/route/component tests;
the E2E spec is written but its two-device run is pending an environment with
`ulimit -d` ≥ 7G (see §15.5). The engine operation announced in §9 was implemented in the
app core instead (see §15.1); `m#50` can absorb it later.
**Type:** Enhancement (account identity and multi-wallet).
**Priority:** High — users with an existing verified account create a second account with
the in-app wallet and ask for their old account back.
**Related:** https://github.com/pasosdeJesus/learn.tg/issues/265 (one account, N wallets),
https://github.com/pasosdeJesus/learn.tg/issues/276 (wallet panel and invitations),

## 1. Objective

Add the **in-app wallet** to the learner's existing, verified account and **delete the
duplicate account** the in-app wallet created. Nothing is merged: the verified account
keeps all its history (`transaction`, SBTs, profile, `nusuario`, referrals, church, privacy
switches) and the duplicate contributes only its wallet.

## 2. Context

The current invitation (R-#265 §3.2, R-#276 §7) attaches an address that **has never
signed in**:

- `inviteWallet` rejects an address already in `billetera_usuario`
  (`packages/generated/wallet/src/wallet-link.ts`);
- `linkWallet` refuses a wallet of another account (`WalletOwnedByOtherError`);
- `acceptInvitation` cannot move a wallet between accounts.

Creating the in-app wallet ends in SIWE (`apps/web/components/WalletDialog.tsx`,
`signInWithInAppWallet`), so the address always gets its own `usuario` row. That duplicate
is what this requirement deletes.

**Operator's data (2026-10-22), authoritative:**

- The verifier has not verified any user who uses the in-app wallet. In practice an in-app
  account has **one wallet**; note that `POST /api/wallet/link` does not check the inviter,
  so a second wallet is technically possible in the same browser: the handover moves **all**
  wallets it finds. It holds at most a GoodDollar date and a proposed interview date,
  **which are ignored**; it cannot have a Self passport (`passport_name`/
  `passport_nationality`) because only the operator verifies. Today the in-app account
  **cannot verify GoodDollar** at all.
- It cannot have `transaction` rows (no scholarship, purchase, UBI or referral payout) and
  there is no scenario of two accounts of the same user with half the progress.

So the duplicate **has nothing to contribute**: delete it, keep its wallet(s).

## 3. Definitions

- **Verified account**: the existing account (external wallet). Same trust bar as
  `apps/web/lib/wallet-invite-policy.ts`: profile score ≥ 50, or a Self passport, or a
  verified church relationship.
- **Duplicate**: the account created by the in-app wallet. Normally one wallet and no value;
  it is deleted.

## 4. Flow

1. Signed in with the **in-app wallet**, the learner chooses *"I already have a verified
   account"* / *"Ya tengo una cuenta verificada"*, enters the **old wallet address** and
   sends a **handover request** (`billetera_invitada`, mode `handover`). The app warns that
   accepting **closes this account** and deletes its data (which is ignored).
2. The learner signs in with the **old wallet** (or already is). Because that account
   exists, the sign-in succeeds; the app must surface the **received** request (see §8).
3. The old wallet **accepts** and signs a fresh SIWE (domain, chain and nonce policy of
   `lib/siwe-server.ts`).
4. In one transaction the engine links the in-app wallet to the verified account, marks the
   request used and **deletes** the duplicate (`usuario` row and its remaining rows).
5. The verified account lists both wallets; the in-app device signs in with its wallet and
   lands in the verified account. The duplicate no longer exists.

## 5. Preconditions

Duplicate (the requester):

- authenticated session (`authenticateUser`) and the session account is the duplicate;
- **not verified** (score < 50, no passport, no verified church relationship);
- **any** number of wallets (normally one); all of them move to the survivor;
- **no monetary value**: no `transaction`, `premium_course_usuario` or
  `credential_emission`; and no church row, reputation or cluster row created under it, and
  no `referralrelationship` (the operator resolves those by hand). If any exists, **refuse**
  with a readable reason; money and on-chain proofs are never destroyed silently.
- Its other rows (`guide_usuario` progress, `notifications`, `userevent`, `verification_log`,
  `referralcode`, pending `billetera_invitada`) are **deleted** as part of discarding the
  account; their counts are recorded in the audit event.
- it is not the same account as the old wallet's, and it is not a verifier wallet.

Verified wallet (the approver):

- signs the SIWE of the accept;
- its account is verified (§3) and is not the duplicate;
- no other pending handover request exists for the duplicate (one at a time).

## 6. Effects (one database transaction)

| Step | Rule |
|---|---|
| Link | Move **all** `billetera_usuario` rows of the duplicate to the survivor (`usuario_id`); `billetera`, `linked_at`, `linked_by` and `answer_fib` are preserved. |
| Request | Mark the handover `billetera_invitada` row `used_at = now()`. |
| Duplicate rows | Delete its `guide_usuario` progress, `notifications`, `userevent`, `verification_log`, `referralcode`, other `billetera_invitada` rows and any other child row listed by the §9.1 pre-check (all empty in the normal case). |
| `usuario` | Delete the row after the moves. Sessions die with it; `session_epoch` is bumped first as a belt-and-braces measure. |
| Survivor | Untouched: `profilescore`, `nusuario`, profile, privacy switches, history. No score recalculation and no credential minting. |

## 7. Security and anti-abuse

- **The verified wallet signs**: only whoever controls the old wallet can authorize the
  deletion of the duplicate. A stranger's duplicate cannot do anything without that
  signature.
- **The duplicate must be valueless** (§5): no monetary history is ever deleted; the engine
  refuses instead of relying on `ON DELETE CASCADE`.
- **Atomicity**: one transaction; a failure leaves both accounts untouched.
- **Race/idempotency**: a second accept of the same request fails cleanly; the request
  cannot be replayed after the duplicate is gone.
- **Audit**: `userevent('account_handover')` on the survivor (wallet moved, duplicate id,
  no PII) and a `verification_log` entry.
- **Spam**: one pending request at a time; the verified account can ignore or cancel it;
  it expires in 30 days (existing rule).

## 8. Received requests must be surfaced (gap found 2026-10-22)

Invitations are only discovered **after a failed sign-in**: `lib/wallet-invitations.ts`
probes the invitation when the credentials POST is rejected, which only happens for wallets
**without** an account. A verified wallet signs in successfully and never sees the request.

Required:

- `GET /api/wallet` (session) returns the **received** requests of the account's wallets
  (today it returns only the ones the account sent), or a dedicated
  `GET /api/wallet/invitations/received`.
- The wallet panel (Accounts tab) and the profile show them with the accept action; the
  accept signs a fresh SIWE with the session wallet.
- Only the account that owns the invited address sees the request; anonymous callers get
  nothing.

## 9. API and engine

- The operation lives in the **app core** (`apps/web/lib/wallet-handover.ts`): it moves the
  wallets with one `UPDATE` (preserving `answer_fib`, `linked_at`, `linked_by`) and deletes
  the duplicate in one transaction. It is not in the `wallet` engine because it must delete
  `usuario` and enumerate the 31 consumer foreign keys, which the engine does not own; `m#50`
  can absorb it later.
- `POST /api/wallet/invite` with `mode: 'handover'`.
- `POST /api/wallet/accept` with `confirm: true` runs the handover atomically and answers
  `handover: true` with the verified account data.
- `GET /api/wallet` also returns `receivedInvitations` and `verified` (§8).
- **No `mode` column:** the mode is inferred at accept. A `link` invitation can never target
  an address that already has an account (the engine rejects it), so a pending invitation
  for a linked address is a handover.
- `apps/web/m-engine.json` declares `billetera_invitada` again (the app now writes the
  request and reads received ones).

### 9.1 Foreign keys: verify, move, then delete

`usuario` is referenced by **31 foreign keys** (`apps/web/db/structure.sql`). Two are
`ON DELETE CASCADE` and would erase history silently:

- `credential_emission.usuario_id` (SBT emissions);
- `transaction.usuario_id`.

The implementation must therefore enumerate the references of the duplicate, **refuse**
when a row exists outside the allowed empty set (§5), and only then delete `usuario` after
moving the wallet. Never rely on the cascade.

## 10. UX

- In-app device: *"I already have a verified account"* / *"Ya tengo una cuenta
  verificada"*, with the old address field and an explicit warning: accepting closes this
  account and deletes its data.
- Verified device: *"A wallet asks to join your account"*, listing the address and the
  consequence; accepting requires that wallet's signature.
- After: the account lists both wallets; the in-app device signs in and sees the inherited
  history.
- Errors in the learner's language: not verified, duplicate has value, request expired,
  already accepted.

## 11. Tests

- Engine unit: eligibility matrix, refusal when the duplicate has any value, atomicity,
  FK order (the cascade cannot fire), idempotency, race, audit event, no PII in logs.
- Route unit: auth, validation, 403/409 messages; received requests only for the addressed
  account.
- DB integration: wallet moved, duplicate deleted, survivor untouched, no orphan rows,
  duplicate cannot sign in.
- E2E two devices: in-app account requests; verified wallet accepts on its device (request
  surfaced); duplicate disappears; survivor lists both wallets; in-app device signs in to
  the survivor; the old history is intact.
- Regression: the existing invitation of a never-signed-in address still works.

- [x] The verified account keeps its history, profile, `nusuario` and privacy switches

## 13. Out of scope

- Merging progress, credentials, referral relationships or profile data from the duplicate.
- The reverse outcome (the in-app account surviving).
- Merging two accounts with `transaction` rows.
- Transferring or re-minting SBTs on-chain.
- An admin UI for handovers.
- More than one duplicate per verified account.

## 15. Implementation (2026-10-22)

What was built, where it lives, how it differs from the plan and what was measured.

### 15.1 Where it lives

The operation is in the **app core**, as §9 decided (it needs `usuario`, session
invalidation and the full foreign-key catalog, which the published `wallet` engine does not
own):

- `apps/web/lib/wallet-handover.ts` — eligibility, reference scan, the transaction, the
  request and the received list; it reuses `wallet-invite-policy.ts` for the verified bar.
- `apps/web/lib/wallet-account.ts` — `fetchWalletOverview`, `requestHandover`,
  `cancelHandoverRequest`, `acceptHandoverRequest` and the server-code → UI-reason map.
- `apps/web/lib/siwe-sign.ts` — one SIWE signature for the accept (the session wallet or
  the unlocked in-app wallet).
- `apps/web/components/HandoverWalletControl.tsx` — the two sides in EN/ES; mounted by
  `components/AccountWalletActions.tsx`, so it appears in the profile and in the wallet
  panel's **Accounts** tab.
- `apps/web/app/api/wallet/{invite,accept,cancel}/route.ts` and `wallet/route.ts` (git
  submodule): `mode: 'handover'`, the inferred mode at accept, `receivedId` on cancel and
  the `receivedInvitations`/`verified` fields.
- `apps/web/m-engine.json` — declares `billetera_invitada` for `generated-wallet`.

### 15.2 Behaviour as implemented

- **Request.** `POST /api/wallet/invite` with `mode: 'handover'` requires the session
  account to be the duplicate; the target address must belong to a **verified** account and
  the duplicate must pass the eligibility check. The row goes to `billetera_invitada` with
  the existing 30-day rules (partial unique index → `already-pending`).
- **Accept.** `POST /api/wallet/accept` looks the signer's address up: if it already
  belongs to an account the accept is a handover (a `link` invitation can never target a
  linked address, so no column is needed). `confirm` is required; the code answers 403 for
  a non-verified target, 400 for `target-not-linked`/`no-wallets` and 409 otherwise.
- **One transaction.** Eligibility is re-checked inside it, all `billetera_usuario` rows
  move with one `UPDATE` (preserving `billetera`, `linked_at`, `linked_by`, `answer_fib`),
  the duplicate's rows in `guide_usuario`, `notifications`, `userevent`,
  `verification_log`, `referralcode` and `billetera_invitada` are deleted, then
  `userevent('account_handover')` and `verification_log('wallet_handover')` are written on
  the survivor (no PII: ids, wallet addresses and counts), `session_epoch` is bumped and
  the `usuario` row is deleted. If the `UPDATE` moves **zero** wallets (a concurrent
  accept won the row locks after our check), the transaction refuses with
  `already-completed` instead of deleting anything.
- **Refusals.** `duplicate-not-found`, `duplicate-verified`, `duplicate-disabled`,
  `duplicate-is-verifier`, `duplicate-has-value` (with `table.column (count)`),
  `survivor-not-found`, `survivor-not-verified`, `survivor-disabled`, `same-account`,
  `target-not-linked`, `target-not-verified`, `already-pending`, `no-wallets`. The
  reference list comes from `pg_constraint`, so a new foreign key to `usuario` defaults to
  **refuse**, never to delete.
- **Received requests.** `GET /api/wallet` (session) returns pending, unexpired rows whose
  `direccion_invitada` is one of the account's wallets, plus `verified`. The verified
  account can **dismiss** one with `POST /api/wallet/cancel` (`receivedId`), which matches
  the id **and** that the addressed wallet belongs to the session account. Anonymous
  callers get the same 401 as before; the route audit reports no change in exposure.
- **The request row is not marked `used_at`**: it is deleted with the duplicate, which is
  stronger than a flag and makes a replay impossible.
