# R-#287: Build fingerprint for the in-app wallet (Phase 1)

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/287
**Created:** 2026-10-21
**Status:** Proposal — design only; nothing implemented.
**Type:** Security / Transparency (supply chain)
**Priority:** Medium — the in-app wallet sources are open and live entirely outside `/api/`, so the frontend can be made verifiable without touching the closed backend. This is Phase 1 of a multi-phase plan.

## 1. Objective

Expose a deterministic, signed build fingerprint of the in-app wallet frontend, so a third party (including an AI auditing agent) can verify **which source commit the deployed wallet was built from**, without depending on the operator's word and without requiring full reproducible builds.

The in-app wallet lives entirely outside the closed API backend. All its sources are open. The closed backend (`/api/`) is **out of scope** for this requirement.

## 2. Why this phase exists

The previous conversation established that a full reproducible build attestation is complex and, for the closed backend, impractical. Phase 1 takes the simplest verifiable step: make the build ID deterministic and expose it, so an agent can at least confirm **the site declares serving commit X**, and the operator can later add a signature over that declaration.

Full reproducible builds (byte-for-byte comparison of a third-party rebuild) are **Phase 2+**, not this requirement.

## 3. Design (Phase 1)

### 3.1 Deterministic `buildId` from the git commit

Configure Next.js to use the git commit SHA as the build ID, instead of the random default.

```js
// apps/web/next.config.js
module.exports = {
  generateBuildId: async () => {
    return process.env.GIT_HASH // set by the deploy pipeline
  },
}
```

The `GIT_HASH` environment variable must be set by the build/deploy pipeline (e.g. `GIT_HASH=$(git rev-parse HEAD)` before `next build`). If unset, the build should **fail**, not fall back to a random ID, so a misconfigured deploy cannot silently produce an unverifiable build.

### 3.2 Expose the build ID

Next.js embeds the `buildId` in the HTML and in `__NEXT_DATA__`. The agent can read it with a simple HTTP request to the dev site, or from the browser via Chrome.

Optionally, add a tiny endpoint `GET /__version` that returns JSON:

```json
{ "buildId": "<git-sha>", "builtAt": "<timestamp>" }
```

The endpoint is optional in Phase 1. The HTML/`__NEXT_DATA__` route is sufficient and requires no new code.

### 3.3 Deploy pipeline sets `GIT_HASH`

The deploy script (the one that runs `make all` / `make prod`) must export `GIT_HASH` before building. No change to the runtime server is needed.

## 4. What this achieves

An agent (or a human) can:

1. Fetch `https://learn.tg:9001` and extract the `buildId`.
2. Compare it with `git rev-parse HEAD` in the clone being audited.
3. If they match, the audit covers the deployed code (for the frontend).
4. If they do not match, the agent reports the discrepancy and does not claim coverage.

This removes the assumption "the clone is what is deployed" and gives the audit report an objective anchor.

## 5. What this does **not** achieve (explicitly out of scope)

- **No signature yet.** The build ID is a declaration, not a proof. A server with access could change it. Signing the build ID (e.g. with Cosign) is **Phase 2**.
- **No reproducible build.** The agent cannot rebuild the frontend and compare bytes. That is **Phase 2/3**.
- **No backend verification.** The closed API at `/api/` is not covered, by design.
- **No protection against a malicious server** that serves different content to different visitors. The fingerprint is a transparency measure, not a tamper-proof seal.

## 6. Acceptance criteria

- [ ] `generateBuildId` in `apps/web/next.config.js` returns `process.env.GIT_HASH`, and the build fails if `GIT_HASH` is unset.
- [ ] The deploy pipeline exports `GIT_HASH=$(git rev-parse HEAD)` before building.
- [ ] The dev site (`learn.tg:9001`) exposes the `buildId` in the HTML or `__NEXT_DATA__`.
- [ ] A verification script (or the audit agent) can read the `buildId` from the dev site and compare it with the clone's `HEAD`.
- [ ] The R-#278 and R-#265 tests remain green (no regression).
- [ ] `make type` and the affected suites green; `node bin/audit-api-auth.mjs` at 0 failed if routes changed.

## 7. Testing

- Build twice with the same `GIT_HASH`: the `buildId` must be identical.
- Build with `GIT_HASH` unset: the build must fail.
- Fetch the dev site after deploy: the `buildId` must match the deployed commit.
- The audit agent script (a simple `curl` + `grep`/`jq`) must report `match` or `mismatch`.

## 8. Phase 2 (not this requirement)

- Sign the `buildId` with Cosign in the deploy pipeline, publish the signature bundle, and have the agent verify it with the public key. This turns the declaration into a signed provenance statement.
- A `hashes.txt` of the frontend bundle (SHA-256 of each file) for a lighter form of reproducibility checking.

Phase 2 is **not** part of R-#287. This requirement is deliberately minimal so it can be implemented and verified quickly.

## Notas para aplicarlo

1. **`GIT_HASH` debe fallar si no está.** Esto es crucial: si el pipeline no lo exporta, el build debe abortar, no caer a un `buildId` aleatorio. De lo contrario, un deploy mal configurado produce un build que parece verificable pero no lo es.
2. **El endpoint `/__version` es opcional.** El `buildId` ya está en el HTML/`__NEXT_DATA__`; el endpoint es una comodidad, no un requisito. Si lo añades, recuerda que debe ser público (sin auth) y no debe filtrar nada más que el `buildId` y el `builtAt`.
3. **No toca el backend cerrado.** La billetera vive fuera de `/api/`; este REQ solo toca `apps/web/next.config.js` y el pipeline de deploy.
4. **La Fase 2 (firma Cosign) queda explícitamente fuera.** Si el operador quiere firmar el `buildId`, es un REQ nuevo o una revisión posterior de este.
