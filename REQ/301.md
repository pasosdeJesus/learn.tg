# R-#301: Course feedback — students send suggestions to pdJ about a course or a guide

> **Draft.** The operator publishes it with `cd apps/web && bin/m req:sync-to-repo 301` (the
> repository assigns the IID; if it is not 301, rename this file and its link).

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/301
**Created:** 2026-11-15
**Status:** Proposal
**Type:** Feature / platform (any course) + verifier dashboard
**Priority:** Medium — today a student can only report a bug by writing outside the app; there is no
channel that reaches pdJ with the course and guide already identified.

## 1. Objective

A student who is taking a course can send **one short suggestion** about the course or about one of
its guides, and pdJ can read it, mark it and answer it **in the app**. It is private feedback for
pdJ, not a public review: nothing of it is published, rated or shown to other students.

## 2. Model

New table `course_feedback` (migration `bin/m db:mig:make course_feedback`):

| Column | Type | Notes |
|---|---|---|
| `id` | serial PK | |
| `usuario_id` | int NOT NULL | author (`usuario`), FK ON DELETE CASCADE |
| `course_id` | int NOT NULL | `cor1440_gen_proyectofinanciero.id` (any course, not only GD) |
| `guide_suffix` | varchar(40) NULL | the guide page (`guide2`, `guia2`); NULL = about the whole course |
| `kind` | varchar(20) NOT NULL DEFAULT `'suggestion'` | CHECK `suggestion` \| `problem` \| `praise` |
| `body` | text NOT NULL | 10–2000 characters after `trim()`, control characters collapsed |
| `rating` | smallint NULL | 1–5, optional ("how useful was it") |
| `status` | varchar(20) NOT NULL DEFAULT `'new'` | CHECK `new` \| `read` \| `resolved` \| `archived` |
| `response` | text NULL | pdJ's answer, ≤ 2000 characters |
| `read_by` / `read_at` | int / timestamptz | who of pdJ opened it |
| `responded_by` / `responded_at` | int / timestamptz | who answered |
| `lang` | varchar(5) NOT NULL | `en` / `es` of the page it was sent from |
| `created_at` | timestamptz NOT NULL DEFAULT now | |

Indexes: `(status, created_at)`, `(course_id, guide_suffix)`, `(usuario_id)`. **No** unique
constraint: the same student may send several suggestions over time. Nothing is deleted: closing a
suggestion is `archived`.

## 3. Endpoints

| Method | Path | Class | Who / what |
|---|---|---|---|
| POST | `/api/course-feedback` | authenticated | The student, with `{ courseId, guide?, kind, body, rating? }`. Requires **access to the course** (free, or paid by that account; the same check `/api/guide` uses) — 403 otherwise, so it cannot be used to spam a course the account cannot read. Answers `201 { id }` |
| GET | `/api/course-feedback/mine?courseId=` | authenticated | The student's own suggestions **with pdJ's answer**, so the reply is visible where it was sent |
| GET | `/api/admin/course-feedback?status=&courseId=&guide=` | **admin-only** | pdJ: list with `nusuario` (never the real `nombre`) and the course/guide title |
| PATCH | `/api/admin/course-feedback/[id]` | **admin-only** | `{ status }` (mark read/resolved/archived) and/or `{ response }`; answering notifies the student |
| DELETE | `/api/course-feedback/[id]` | authenticated | The author, only while `status = 'new'` (a wrong send is withdrawn, not edited) |

- **Rate limit** (anti-abuse, in the POST route): at most **5 suggestions per account per hour** and
  **20 per day**, answered `429 feedback_rate_limited`; the limit is per `usuario_id`, not per wallet.
- **Answer notification**: `notifications(type = 'course_feedback_answer', link = /{lang}/{course}/guideN)`,
  one per answer, so the student finds it where the guide is.
- **No public surface**: no route in `PUBLIC_ENDPOINTS`, no field of it in any public response, no
  ratings aggregate published. The admin list is the only reader of the whole table.

## 4. UI

- **At the end of every guide page** (all courses, after the "Action" section) a discreet line:
  *Send a suggestion to pdJ* → a dialog with kind (suggestion / problem / praise), a textarea, an
  optional 1-5 rating and, when the course is GD, the guide already selected. Only for a student with
  access to the course.
- **The same entry point on the course page**, with `guide_suffix` NULL ("about the course").
- The dialog shows the previous suggestions of that course **and pdJ's answer** when it exists
  (`GET /api/course-feedback/mine`), so the conversation stays in one place.
- **Verifier page** `/{lang}/admin/feedback`: table with course, guide, kind, `nusuario`, date and
  status; filters (course, status, guide); the full text in a panel; buttons *Mark read*,
  *Resolve* and a reply box. A dashboard widget with the count of `new` follows the existing widgets.

## 5. Privacy and content rules

- Suggestions are **for pdJ**, not published; the student is told so in the dialog ("this goes to the
  pdJ team, it is not published").
- The admin list shows `nusuario`, never the real name (rule 3 of `doc/api-security.md`).
- No PII in logs: the routes log the id and lengths, never the body.
- The body is stored as plain text and rendered as text (no markdown, no HTML): it is not worth a
  sanitizer and it keeps the surface small.

## 6. Acceptance criteria

- [ ] `POST` without a session → 401; with a session but without access to the course → 403.
- [ ] Body shorter than 10 or longer than 2000 characters → 400 `feedback_invalid`; `kind` outside
      the three values → 400; `rating` outside 1-5 → 400.
- [ ] The 6th suggestion in an hour (and the 21st in a day) → 429 `feedback_rate_limited`.
- [ ] pdJ lists it, marks it read, answers it, and the student sees the answer in the dialog and gets
      the in-app notification.
- [ ] The author can withdraw it while it is `new`; afterwards only pdJ can archive it.
- [ ] No public endpoint exposes the table or an aggregate; `audit-api-auth` stays at 0 failed with
      the new routes classified (POST/GET mine authenticated, admin ones admin-only).
- [ ] Unit tests for the validation and the rate limit; one browser spec for send → answer → read.

## 7. Out of scope

Public reviews, star ratings shown anywhere, moderation of abusive content beyond the length and
rate limits, email/WhatsApp replies, voting or sorting by usefulness, feedback on content that is not
a course (guides of the church directory, campaigns).
