# R-#269: Improve usability of in-app wallet

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/269

---

## 1. Report

The operator, testing the in-app wallet on the phone (2026-09-28), found two rough
edges in the create/import dialog:

1. **The password cannot be read back.** The field shows dots and there is no way to
   check what was typed. The password cannot be recovered (only the 12 words restore
   the wallet) and it is asked again on every unlock and on the biometric enrolment,
   so a typo is expensive.
2. **Enrolling the fingerprint is easy to miss.** The option was a checkbox inside the
   12-words screen, below the list of words, so it went unnoticed. Expected instead:
   right after typing the password the dialog asks **how to unlock the wallet** and
   offers the gesture (fingerprint/Face ID) as the **default** when the phone supports
   it, leaving "only with the password" as the explicit alternative and keeping the
   password as the backup in both cases.

## 2. Changes

| Report | Change |
|---|---|
| 1 | New `apps/nextjs/components/PasswordInput.tsx`: the field plus a button with the eye. It is `type="button"` (never submits the form), carries `aria-pressed` and the accessible name from `passwordShow`/`passwordHide`, and the icon is inline SVG (`EyeIcon`, with the slash when the password is visible) so no icon dependency is added. `pr-10` keeps the text clear of the button. Used for the three fields of the dialog: create, confirm and the biometric enrolment. |
| 2 | `apps/nextjs/components/WalletDialog.tsx`: the checkbox of the 12-words screen (`wallet-create-biometric`) is gone. After the password the dialog shows the explicit step `wallet-protect` with two radios: `wallet-protect-gesture` ("with my fingerprint or Face ID (recommended)", **checked by default**) and `wallet-protect-password`. The gesture seals the wallet with the passkey using the password already in memory (`createPasswordRef`), so it is never typed twice; create then continues to the 12 words and import signs in directly. When the device cannot verify the user, or a passkey is already enrolled, the step is skipped and the password-only path is unchanged. If `enableBiometric` fails, the step stays open with `wallet-protect-notice` (the password option still works, and it is the fallback), instead of failing silently. |

New strings (EN/ES): `passwordShow`, `passwordHide`, `protectTitle`, `protectHint`,
`protectGesture`, `protectPassword`, `protectContinue`.

Docs synced with the change (Documentation Sync Policy): `doc/wallet-auth.md` (the
`PasswordInput` field and the `wallet-protect` step), `doc/pdJ-wallet.md` and
`doc/pwa-user-guide.md` (the create/import walkthrough for the student, now six
steps), `doc/e2e-testing.md` and `doc/pdj-wallet-testing.md` §3 (the helper and the
local recipe), and `apps/nextjs/CONTRIBUTING.md` (suite counts).

## 3. Tests

`apps/nextjs/components/__tests__/WalletDialog.test.tsx` (27 tests) covers the toggle
(`shows and hides the password`), the gesture as the default
(`enrolls the fingerprint during creation when the device supports it`, which asserts
the gesture radio is already checked), the explicit password-only choice
(`continues with the password only when that is chosen`), the failure of the enrolment
(`tells the user when the fingerprint could not be saved during creation`) and the same
step after importing (`asks how to unlock after importing`), plus the unchanged
password-only path when the device cannot verify the user.

`apps/nextjs/e2e/helpers/in-app-wallet.mjs` gained `chooseWalletProtection(page, {
gesture })`, tolerant with builds where the step does not exist (it returns `false`).
The five specs that create the wallet in the browser answer the step:
`in-app-wallet`, `in-app-wallet-payments`, `donate-unlock-dialog`,
`header-wallet-dialog` and `biometric-unlock` (this one keeps the gesture for its own
second step and answers "password only" during creation).

## 5. Not fixed here (environment, noted for the operator)

- `donate-unlock-dialog.spec.mjs` cannot run against the local server: the "Donate to
  this course" button only renders on a **course** page whose vault exists
  (`sData.vaultCreated`) and the local database has no vaults, so the spec stops
  before the wallet dialog. Its creation part (the new step) passed. On the dev site
  the spec still depends on that page continuing to render the button (commit
  `64559c2e` removed it from the language page, which is why the spec's fallback URL
  `/en` no longer helps).
