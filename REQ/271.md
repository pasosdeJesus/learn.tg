# R-#271: GoodDollar claim and verification with the in-app wallet

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/271

**Status:** In progress (2026-10-01)
**Created:** 2026-10-01
**Type:** Bug / compatibility (in-app wallet)
**Priority:** High — the in-app wallet is the default way to operate with learn.tg (R-#270) and GoodDollar is one of the two UBIs the Web3 & UBI course teaches.

---

## 1. Problem

With the **in-app wallet** GoodDollar cannot be claimed, and the button blames the wrong cause:

- `apps/nextjs/components/GoodDollarClaimButton.tsx` loads the GoodDollar identity/claim SDK; when the SDK is not ready it shows `testnetUnavailable` ("Not available on testnet" / "No opera en testnet"), **assuming** the network is testnet (`:95-99`, the `hintText` ternary). On **Celo mainnet** with the in-app wallet the user therefore reads a false reason: the network is not the problem.
- The same SDK runs the **face verification**, so with the in-app wallet the learner also cannot complete the verification that gives **7 profile points** (`lastgooddollarverification`, `apps/nextjs/lib/score-rules.ts:38`) and shows as ✅ on the profile (`app/[lang]/profile/page.tsx:997`).
- Consequence today: a learner who signed in with the in-app wallet (the recommended path) is left without GoodDollar unless they also use an external wallet, while the platform tells them the network is to blame.

**Operator report (2026-10-01):** "en mainnet el botón dice Not available in testnet" while claiming with the in-app wallet.

## 2. Why it fails (hypotheses to confirm with the real SDK)

1. The GoodDollar SDK expects an EIP-1193 provider in `window.ethereum` and probes it (accounts, chain, `personal_sign`). The in-app wallet exposes itself as the injected provider **only while unlocked** (`provider.isPdJWallet`, `packages/pdj-wallet/src/provider.ts`; the key lives in memory and a reload locks it), so an SDK that probes before/without an unlock finds nothing.
2. The SDK may require a wallet it recognises (or a specific `eth_chainId`), and the in-app wallet declares its chain only after `wallet_switchEthereumChain` or creation on that network (R-#266).
3. Signing goes through the **L1 gesture gate** (`requireFundsConfirmation`): if the SDK signs without a user gesture the flow cannot complete, and the error is swallowed.
4. The button degrades silently: the real error never reaches the user, so the wrong message is the only feedback.

## 3. Objective

1. The GoodDollar **claim** works with the in-app wallet, on Celo Sepolia and on Celo mainnet.
2. The GoodDollar **verification** (face verification, the 7 profile points) works with the in-app wallet.
3. When something really blocks the flow, the button says **why** (no wallet, wallet **locked**, provider not supported, network not supported, GoodDollar service down) in EN and ES, never "testnet" by assumption.

## 4. Scope

**In scope**

- `components/GoodDollarClaimButton.tsx` (reason selection, locked-wallet state, i18n) and the GoodDollar block of the profile page.
- The provider bridge the SDK needs: `packages/pdj-wallet` (core provider) and `packages/pdj-wallet-next`, exposing what the SDK asks for while unlocked (accounts, chain, `personal_sign`) and a clear error when locked.
- Tests: unit for the reason picker; E2E that creates/unlocks an in-app wallet and exercises the button.
- Docs: `doc/wallet-auth.md` and the course guide 4.

**Out of scope**

- The GoodDollar protocol or its own app (`gooddapp.org`).
- Removing the external-wallet path: it must keep working.
- Merging GoodDollar and self.xyz into one verification.

**Meanwhile (not a blocker):** the Web3 & UBI course now presents **learn.tg-UBI (CELO) as the main UBI** and describes the identity path as **self.xyz (with a passport) + the verifier interview** (content change of 2026-10-01 in `resources/{en/web3-and-ubi,es/web3-e-ibu}`), so a learner with the in-app wallet still earns UBI and profile points.

## 6. Testing plan

- **Unit:** the reason picker as a pure function (inputs: wallet absent/locked/external, chain, SDK ready/error) and the SDK-availability detection against a mocked provider.
- **E2E (Puppeteer, dev site):** create and unlock the in-app wallet, open guide 4, press the button, assert that the flow starts (verification) or that the reason is truthful; a **locked** wallet must offer the unlock dialog.
- **Manual (operator, mainnet):** the only way to see a real claim, since it needs an already verified GoodDollar identity.

## 7. Risks and notes

- GoodDollar may not support the provider shape the in-app wallet can offer. If the SDK cannot be adapted, the honest fallback is to keep GoodDollar **external-wallet only** and say so in the button and in the course, with learn.tg-UBI as the in-app path (that is already the course direction).
- **The `citizen-sdk` is an active gate, not just a helper** (measured 2026-10-01, §10.4): a whitelisted, entitled address was **blocked from claiming** because the SDK demanded a fresh FaceTec verification, while the protocol itself paid the moment the check was bypassed. So a **third-party client-side policy** can deny a student a benefit they are entitled to, and it can change without notice. It also makes learn.tg depend on GoodDollar's services (`goodid.gooddollar.org` for the verification, `goodserver.gooddollar.org` for the whitelist sync): if either is down, the button cannot complete even for an already-verified learner. Mitigation (protocol lib written, wiring tracked in https://github.com/pasosdeJesus/learn.tg/issues/275): claim **directly on-chain** whenever `getWhitelistedRoot != 0` and `checkEntitlement > 0`, and use the SDK/GoodID only when verification is genuinely required; the CLI `apps/nextjs/scripts/claim-gooddollar-ubi.mjs` is the reference implementation of that path.
- The in-app wallet locks on reload and after an hour of inactivity (R-#246): the UBI buttons must treat "locked" as a normal state, not an error.
- The GoodDollar claim is an on-chain transaction signed by the wallet: it inherits the gas rule (a little CELO for the network fee).
- Small cosmetic bug seen while writing this: the profile label ends with a stray `')'` after the ✅/❌ (`app/[lang]/profile/page.tsx:1002`).

## 10. Reference implementation: `github.com/GoodDollar/GoodWallet` (analysed 2026-10-01)

A clone lives at `/var/www/adJ-ia/GoodWallet` (Next.js 2.1.2, the official
GoodDollar browser wallet). It is a working reference of "claim GoodDollar from a
browser wallet" and it answers the open hypotheses of §2.

**It does not use `@goodsdks/citizen-sdk`.** It implements the claim against the
contracts directly with `@gooddollar/goodprotocol` ABIs + ethers v6
(`src/gooddollar/`).

### 10.1 The four steps

| Step | What it does | Where |
|---|---|---|
| 1. Whitelist check | `IdentityV2.getWhitelistedRoot(address)`; whitelisted iff `!= 0x0`; also `getWhitelistedOnChainId(address)` | `src/gooddollar/stores/identityStore.ts` |
| 2. Verification (face) | `generateGoodIDLink(signer, firstName, chainId, rdu)`: signs a **fixed message** (`FV_IDENTIFIER_MSG2`) → `fvsig`, then `window.open('https://goodid.gooddollar.org?account&chain&fvsig&firstname&rdu&isDelta=true', '_self')`; on return `parseGoodIDRedirectUrl` reads `verified=true` / `reason`; then `syncWhitelist(address)` → `GET https://goodserver.gooddollar.org/syncWhitelist/{address}` | `src/gooddollar/methods/goodid.ts`, `sections/GoodDollar/components/Claim/ClaimView.tsx` |
| 3. Claim | `UBIScheme.checkEntitlement(whitelistedRoot)` (>0 → claimable, 0 → already claimed) plus `currentDay/periodStart/getDailyStats/dailyCyclePool/paused`; tx = `encodeMethodCall(UBIScheme, 'claim')` → sign + `provider.broadcastTransaction` | `src/gooddollar/stores/ubiStore.ts`, `src/ethers-utils/utils.ts` |
| 4. Attribution | appends the Divvi `GD_DATASUFFIX` to the calldata and `POST https://api.divvi.xyz/submitReferral` | `src/gooddollar/methods/divvi.ts` |

The face capture itself is **FaceTec** (link in `RequireWhitelist.tsx`) and happens
on GoodID's site, not in the caller's page.

### 10.2 What it means for learn.tg

1. **The claim does not need the citizen-sdk.** What it needs from the wallet is
   `personal_sign` of a fixed message and one contract write (`UBIScheme.claim()`).
   The in-app wallet provides both while unlocked, so the provider-shape hypothesis
   (§2.1) is not the only path: the GoodWallet flow is a proven one.
2. **GoodDollar UBI is mainnet-only, confirmed by the SDK itself:** both GoodWallet
   (`GOODDOLLAR_NETS`) and `@goodsdks/citizen-sdk@1.2.7` (`SUPPORTED_CHAIN_IDS`,
   `isSupportedChain`) list exactly Fuse (50), XDC (122) and **Celo (42220)**.
   **Celo Sepolia (11142220) is not supported** (the only Sepolia id anywhere is
   Ethereum's 11155111). → §3 objective 1 must be corrected: on Celo Sepolia the
   truthful state is "GoodDollar UBI is on Celo mainnet; here use learn.tg-UBI
   (CELO)", which is what the reason picker now renders (supported list 50/122/42220).
3. **Verification is a redirect**, not an in-page SDK call: GoodID + FaceTec + the
   `goodserver` whitelist sync. The current `IdentitySDK`/`ClaimSDK` usage hides
   that, which is why the button could only guess the reason.
4. Addresses come from `@gooddollar/goodprotocol/releases/deployment.json`, network
   key `<env>-celo` for Celo; **G$ has 18 decimals on Celo** (2 on Fuse).
5. Any signer with `signMessage` + `signTransaction` works (GoodWallet's own
   `EVMSigner`); it does not rely on `window.ethereum` being any particular wallet.

### 10.3 The citizen-sdk is not the problem (corrected)

Inspecting the installed `@goodsdks/citizen-sdk@1.2.7` after this analysis says the
SDK does fit the in-app wallet:

- its bundle has **no wagmi** (`wagmi` is a peer dependency of the companion
  `@goodsdks/react-hooks`, not of the core classes); the classes are viem-only;
- `IdentitySDK` / `ClaimSDK` take exactly the `{ account, publicClient, walletClient,
  env }` learn.tg already builds, and expose `generateFVLink` / `getWhitelistedRoot` /
  `checkEntitlement` — the same GoodID redirect and contract reads GoodWallet does
  by hand;
- so the observed failure was **the locked in-app wallet** (`walletClient` null), not
  a rejected provider.

**Recommendation (revised):** the citizen-sdk is not rejected by the provider — the
observed failure was the locked in-app wallet. **Superseded by §10.4 and
https://github.com/pasosdeJesus/learn.tg/issues/275:** the SDK leaves the claim path and the
GoodWallet flow is used directly, because the SDK adds a verification-freshness gate the
protocol does not have. What must not come back is the wrong reason: the button
distinguishes locked / unsupported provider / network / SDK error.
