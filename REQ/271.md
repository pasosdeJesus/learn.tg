# R-#271: GoodDollar claim and verification with the in-app wallet

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/271

**Status:** Proposal (this file replaces the 2026-10-01 stub)
**Created:** 2026-10-01
**Type:** Bug / compatibility (in-app wallet)
**Priority:** High — the in-app wallet is the default way to operate with learn.tg (R-#270) and GoodDollar is one of the two UBIs the Web3 & UBI course teaches.

---

## 1. Problem

With the **in-app wallet** GoodDollar cannot be claimed, and the button blames the wrong cause:

- `apps/nextjs/components/GoodDollarClaimButton.tsx` loads the GoodDollar identity/claim SDK; when the SDK is not ready it shows `testnetUnavailable` ("Not available on testnet" / "No opera en testnet"), **assuming** the network is testnet (`:95-99`, the `hintText` ternary). On **Celo mainnet** with the in-app wallet the user therefore reads a false reason: the network is not the problem.
- The same SDK runs the **face verification**, so with the in-app wallet the learner also cannot complete the verification that gives **7 profile points** (`lastgooddollarverification`, `apps/nextjs/lib/score-rules.ts:38`) and shows as ✅ on the profile (`app/[lang]/profile/page.tsx:997`).
- Consequence today: a learner who signed in with the in-app wallet (the recommended path) is left without GoodDollar unless they also use an external wallet, while the platform tells them the network is to blame.

**Operator report (2026-10-01):** "en mainnet el botón dice Not available in testnet" while claiming with the in-app wallet.

## 2. Why it fails (hypotheses to confirm with the real SDK)

1. The GoodDollar SDK expects an EIP-1193 provider in `window.ethereum` and probes it (accounts, chain, `personal_sign`). The in-app wallet exposes itself as the injected provider **only while unlocked** (`provider.isPdJWallet`, `packages/pdj-wallet/src/provider.ts`; the key lives in memory and a reload locks it), so an SDK that probes before/without an unlock finds nothing.
2. The SDK may require a wallet it recognises (or a specific `eth_chainId`), and the in-app wallet declares its chain only after `wallet_switchEthereumChain` or creation on that network (R-#266).
3. Signing goes through the **L1 gesture gate** (`requireFundsConfirmation`): if the SDK signs without a user gesture the flow cannot complete, and the error is swallowed.
4. The button degrades silently: the real error never reaches the user, so the wrong message is the only feedback.

## 3. Objective

1. The GoodDollar **claim** works with the in-app wallet, on Celo Sepolia and on Celo mainnet.
2. The GoodDollar **verification** (face verification, the 7 profile points) works with the in-app wallet.
3. When something really blocks the flow, the button says **why** (no wallet, wallet **locked**, provider not supported, network not supported, GoodDollar service down) in EN and ES, never "testnet" by assumption.

## 4. Scope

**In scope**

- `components/GoodDollarClaimButton.tsx` (reason selection, locked-wallet state, i18n) and the GoodDollar block of the profile page.
- The provider bridge the SDK needs: `packages/pdj-wallet` (core provider) and `packages/pdj-wallet-next`, exposing what the SDK asks for while unlocked (accounts, chain, `personal_sign`) and a clear error when locked.
- Tests: unit for the reason picker; E2E that creates/unlocks an in-app wallet and exercises the button.
- Docs: `doc/wallet-auth.md` and the course guide 4.

**Out of scope**

- The GoodDollar protocol or its own app (`gooddapp.org`).
- Removing the external-wallet path: it must keep working.
- Merging GoodDollar and self.xyz into one verification.

**Meanwhile (not a blocker):** the Web3 & UBI course now presents **learn.tg-UBI (CELO) as the main UBI** and describes the identity path as **self.xyz (with a passport) + the verifier interview** (content change of 2026-10-01 in `resources/{en/web3-and-ubi,es/web3-e-ibu}`), so a learner with the in-app wallet still earns UBI and profile points.

## 5. Acceptance criteria

- [ ] On Celo mainnet with the in-app wallet unlocked, pressing the GoodDollar button starts the claim (or shows the real blocking reason) instead of "Not available on testnet"
- [ ] Same on Celo Sepolia
- [ ] The profile's GoodDollar verification completes with the in-app wallet and sets `lastgooddollarverification` (7 points)
- [ ] A **locked** in-app wallet is a first-class state: the button offers to unlock it (reuse `learn-tg:open-in-app-wallet-dialog`, as the payment modals do) instead of failing
- [ ] Every unavailable state names its cause, EN/ES, with no silent `catch` hiding the error
- [ ] Unit tests for the reason picker; E2E with a real in-app wallet on the development site
- [ ] `make type` and the affected suites green

## 6. Testing plan

- **Unit:** the reason picker as a pure function (inputs: wallet absent/locked/external, chain, SDK ready/error) and the SDK-availability detection against a mocked provider.
- **E2E (Puppeteer, dev site):** create and unlock the in-app wallet, open guide 4, press the button, assert that the flow starts (verification) or that the reason is truthful; a **locked** wallet must offer the unlock dialog.
- **Manual (operator, mainnet):** the only way to see a real claim, since it needs an already verified GoodDollar identity.

## 7. Risks and notes

- GoodDollar may not support the provider shape the in-app wallet can offer. If the SDK cannot be adapted, the honest fallback is to keep GoodDollar **external-wallet only** and say so in the button and in the course, with learn.tg-UBI as the in-app path (that is already the course direction).
- The in-app wallet locks on reload and after an hour of inactivity (R-#246): the UBI buttons must treat "locked" as a normal state, not an error.
- The GoodDollar claim is an on-chain transaction signed by the wallet: it inherits the gas rule (a little CELO for the network fee).
- Small cosmetic bug seen while writing this: the profile label ends with a stray `')'` after the ✅/❌ (`app/[lang]/profile/page.tsx:1002`).
