## 1. Objective

Phase 2 of R-#227: make Rails (`servidor/`) authenticate with the shared session
(or its own mechanism with a separate key/`audience`) and retire the
`billetera_usuario.token` column, so the client no longer needs to persist or send
an API token. This closes the remaining OWASP gaps of R-#227 (credential in the
URL/query and in `localStorage`).

## 2. Why a separate issue

Phase 2 touches the `servidor/` repo and is the highest-risk part; closing R-#227
with Phase 1 + the hardening already meets the original objective (an on-chain
operation is not lost to a 401 and identity is the session).

## 3. Measured scope (small surface)

- Rails: `app/helpers/application_helper.rb`
  (`usuarioBilleteraToken`/`verificaToken`) and **2 endpoints**:
  `cor1440_gen/proyectosfinancieros_controller#index/#show` and
  `usuarios_controller#actualiza_mi_usuario` (6 uses of `request[:token]`).
  **There are no Rails tests** for those routes.
- Next: `authorize()` (`auth-options.ts`), `app/api/auth/token`,
  `lib/authenticateUser.ts` (legacy fallback), `lib/auth-token.ts`, and the
  E2E/non-browser specs of R-#227's "Residual token dependency inventory".

## 8. Operating without Rails (plan)

After Phase 1 + §4.4 + Phase 2 the **runtime of the public site never calls
Rails**. Evidence: no reference to `NEXT_PUBLIC_API_BASE`, `learntg-admin`,
`:3250`, `:3500` or `proyectosfinancieros` in `apps/nextjs/app`,
`apps/nextjs/lib` or `apps/nextjs/components` — those strings remain only in
`apps/.env.example` and in the Rails-targeting smoke specs (`rails-auth`,
`rails-health`).

### 8.1 What Next serves by itself

Course catalog and detail (`/api/course-catalog`, `/api/course-catalog/[id]`),
profile (`/api/profile`), identity photos (`/api/user/id-photo/*`), scholarship,
guides, crossword, referrals, donations (course/vault/campaign), CELO UBI,
transparency, metrics, notifications, and the verifier admin UI
(`/{lang}/admin/*` → Next's own `/api/admin/*` via `lib/admin-fetch.ts`). The
credential is the NextAuth session cookie; there is no token and no Rails
session.

### 8.2 Conditions to run with Rails stopped

1. `NEXT_PUBLIC_API_URL` **must be empty**; otherwise `next.config.ts` rewrites
   `/api/*` to that host (`beforeFiles`) and the whole site depends on it.
2. `NEXT_PUBLIC_API_BASE` is unused by app code — harmless to leave set, but it
   can be unset/removed from the deployed `.env`.
3. Migrations do not need Rails: new schema changes live in
   `apps/nextjs/db/migrations` and are applied with `bin/m db:migrate` (the
   shared PostgreSQL DB is the integration point, not HTTP).
4. `NEXT_PUBLIC_SELF_ENDPOINT` (Self protocol verifier) is an external service,
   independent of Rails.

### 8.4 What still lives in Rails (decision pending)

- The MSIP backoffice UI on `:3250` (prod) / `:3500` (dev) with Devise: the
  interface to MSIP/Cor1440Gen/Mr519Gen/Heb412Gen data (religions, countries and
  municipalities, users, part of the course/guide records). Day-to-day verifier
  work is covered by `/{lang}/admin` in Next; deep data edits would need Rails.
- `usuarios#foto` (serves stored photos). The Next app does not link to it, so it
  is only reachable by direct URL.
- The historical ActiveRecord migrations (Rails migrations stopped around
  2025-10; newer schema changes are Next-side).
- The `rails-auth` (tolerant) and `rails-health` (skips unless `RAILS_CHECK=1`)
  smoke specs.

Plan: keep Rails installed but **not required** — start it on demand for
backoffice work, and treat the public site as Next-only. Follow-ups: make the
`rails-*` smokes skip gracefully when Rails is unreachable, document this mode in
`doc/environments.md`, and decide the long-term fate of `usuarios#foto` and of
the MSIP backoffice (retire it, or narrow it to what Next does not cover).
