# R-#233: Rails per session and remove billetera_usuario.token

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/233

**Status:** Proposal — low-risk intermediate step implemented (2026-09-14); Rails migration pending
**Created:** 2026-09-14
**Type:** Security / Refactor
**Dependencies:** R-#227 (https://github.com/pasosdeJesus/learn.tg/issues/227)
**Moved from:** R-#227 (Phase 2)

---

## 1. Objective

Phase 2 of R-#227: make Rails (`servidor/`) authenticate with the shared session
(or its own mechanism with a separate key/`audience`) and retire the
`billetera_usuario.token` column, so the client no longer needs to persist or send
an API token. This closes the remaining OWASP gaps of R-#227 (credential in the
URL/query and in `localStorage`).

## 2. Why a separate issue

Phase 2 touches the `servidor/` repo and is the highest-risk part; closing R-#227
with Phase 1 + the hardening already meets the original objective (an on-chain
operation is not lost to a 401 and identity is the session).

## 3. Measured scope (small surface)

- Rails: `app/helpers/application_helper.rb`
  (`usuarioBilleteraToken`/`verificaToken`) and **2 endpoints**:
  `cor1440_gen/proyectosfinancieros_controller#index/#show` and
  `usuarios_controller#actualiza_mi_usuario` (6 uses of `request[:token]`).
  **There are no Rails tests** for those routes.
- Next: `authorize()` (`auth-options.ts`), `app/api/auth/token`,
  `lib/authenticateUser.ts` (legacy fallback), `lib/auth-token.ts`, and the
  E2E/non-browser specs of R-#227's "Residual token dependency inventory".

## 5. Two-phase deployment

- **Additive phase:** Rails accepts the shared session (or a dedicated token)
  **in addition to** `billetera_usuario.token`; the column still exists but the new
  path is used. Monitor the `"No token"` / `"Different tokens"` logs for residual
  legacy usage.
- **Subtractive phase:** only once no legacy usage is observed, stop populating the
  column and then remove it (or leave it nullable/unused).

## 6. Audit of other pdJ clients

- Search the sivel and stable-sl repositories for uses of
  `billetera_usuario.token` (and of the token API in general).
- Document the findings and, if any client depends on the token, add a migration
  plan before the subtractive phase.

## 7. Acceptance criteria (OWASP gaps)

- [ ] Rails endpoints accept the **session** (or their own mechanism with a
      **separate key/`audience`**); `NEXTAUTH_SECRET` is not shared.
- [ ] No credential travels in the **URL/query**; if a token is still used, it goes
      in a header. (Closes R-#227 OWASP deviation 1.)
- [ ] The client **does not** persist credentials in `localStorage`. (Closes R-#227
      OWASP deviation 2.)
- [ ] The API token (if it still exists) has **short expiry and revocation**;
      `authorize()` does not rotate it (already the case since 2026-09-14).
      (Closes R-#227 OWASP deviation 3.)
- [ ] `NEXTAUTH_SECRET` is stable (not rotated across deploys/redeploys); rotating
      it invalidates every session and would break the migration.
- [ ] `billetera_usuario.token` is retired (or left nullable/unused) with the
      two-phase deployment of §5 and monitoring of the `"No token"` /
      `"Different tokens"` logs.
- [ ] Audit of other pdJ clients (§6) completed.
- [ ] E2E suite green incl. `premium-course-checkout`, `fresh-wallet-first-connect`,
      donations, and new tests for listing/detail/update-profile.
- [ ] `audit-api-auth.mjs` with no regressions.
