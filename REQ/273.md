## 1. Objective

Take the cluster/country funds from "money can be donated" to "money reaches the cluster": a
visible contact record with Global Disciples, an admin **on-chain release**, rankings that show
the real balances, and — only after the GD pilot — yield on idle funds.

---

## 2. What already exists (do not duplicate)

From https://github.com/pasosdeJesus/learn.tg/issues/155 (phase 1): the `cluster` +
`church_clustergd` tables, `/api/cluster` CRUD, `/api/church`, the `transaction`, `userevent`
and `m_hdi` tables, `ClusterFundsV2.sol` (operational) and `ClusterFunds.sol` (V1), `SLEARN`
with `MINTER_ROLE` granted to ClusterFunds, the `gdcontact` table (migration
`20260805021849`), `/api/gdcluster/donations/verify`, the cluster/country `DonateModal` and the
`[Donate]` entry points on the ranking.

The contract already carries `setClusterVerification()`, `releaseClusterFunds()` and
`releaseCountryFunds()`; what is missing is the API/UI around them.

## 3. Phase 2 — GD contact pipeline

**Goal:** the contact pipeline is visible; **no funds move yet**.

| # | Task | Notes |
|---|---|---|
| 2.1 | `POST /api/gd/contact/mark-sent` | cluster pastor only ("we sent the email to GD") |
| 2.2 | `POST /api/gd/contact/mark-pdj-sent` | admin |
| 2.3 | `POST /api/gd/contact/mark-responded` | admin |
| 2.4 | `GET /api/gd/contact/:clusterId` | derived status (no stored `status` column) |
| 2.5 | Contact status UI on the cluster page | checkboxes + who/when |
| 2.6 | Ranking shows the contact status per cluster | depends on #154 |

Storage stays in `gdcontact`; **the status is derived from the checkboxes**, never stored, and
every action is logged in `userevent`. Contact notes are confidential (R-#153/R-#162): no free
text in entity tables.

---

## 4. Phase 3 — Fund release

**Goal:** pdJ releases → on-chain transfer to the cluster wallet.

- `setClusterVerification()` — admin marks a cluster as verified (function exists, no UI/API).
- `POST /api/gd/contact/release` — admin; triggers `releaseClusterFunds()` (USDT/SLEARN to the
  cluster wallet) and `releaseCountryFunds()` (from the country fund).
- Release UI: admin checkbox → on-chain tx → confirmation.
- `course_completed_at` is set automatically when the cluster finishes the GD course (#161).
- On cluster dissolution, its funds go to the **country** fund.
- Every release records a `transaction` row (`categoria`/`subcategoria`, `crypto`, `amount`,
  `balance_impact`, `hash`) — the single source of truth.

---

## 5. Phase 4 — Ranking integration

- The ranking shows cluster/country **USDT balances** read from `ClusterFunds`.
- HDI data (`m_hdi`) feeds the donation-impact metrics.
- Rank/aggregate caches are refreshed by **DB triggers**, not cron (ARCHITECTURE.md §Cache
  Update Triggers).

---

## 6. Phase 5 — Yield (AAVE V3, post-pilot)

Only after the GD pilot, and as a contract upgrade:

- track `aUSDT` in `ClusterFunds`;
- add `aave_deposit` / `aave_withdrawal` to the `transaction` CHECK;
- auto-withdrawal on `releaseClusterFunds()` (principal + 70 % yield to the cluster, 30 % to the
  pdJ Treasury);
- yield visible in the ranking and the cluster page.

## 7. Acceptance criteria

### Contact & release
- [ ] A cluster pastor can mark "we sent the email to GD" (authenticated, that cluster only)
- [ ] pdJ (admin) can mark "pdJ contacted GD", "GD responded" and "release funds"
- [ ] The status is derived from the checkboxes (no stored `status` column)
- [ ] The ranking shows the contact status per cluster
- [ ] Every checkbox action is logged in `userevent`
- [ ] `releaseClusterFunds()` verifies the cluster is verified before transferring
- [ ] A release creates its `transaction` row

### Contract / funds
- [ ] Country donations split equally among the existing clusters of that country
- [ ] Country donations accumulate in the country fund when there are no clusters
- [ ] `redistributeCountryFunds()` is called by the backend when a new cluster forms
- [ ] `releaseClusterFunds()` / `releaseCountryFunds()` transfer USDT and SLEARN
- [ ] On cluster dissolution, all its funds move to the country fund

### Ranking
- [ ] Country/cluster balances from `ClusterFunds` are visible in the ranking
- [ ] HDI impact metrics use `m_hdi`
- [ ] The caches are refreshed by DB triggers

### Yield (post-pilot)
- [ ] Idle USDT can be deposited into AAVE V3
- [ ] Yield is tracked per cluster/country fund; 70/30 split
- [ ] Yield is visible in the ranking and the cluster page
- [ ] Auto-withdrawal on release sends principal + 70 % yield to the cluster

## 8. Testing plan

  with the ClusterFundsV2 suite.
- **E2E on the development site**: contact checkboxes, a release against a funded contract and
  the ranking balances.
- **Docs**: `doc/admin-guide.md` (admin checkboxes and release) and `doc/church-registration.md`
  as needed.

---

## 9. Risks

- The on-chain release needs the contract to hold funds **and** the backend wallet to have CELO
  for gas; a failed transfer must not lose the contact record (retry path like the crossword
  routing).
- AAVE is explicitly post-pilot; shipping it early adds an upgrade while the pilot is running.
- Privacy: GD contact notes and donor identities stay confidential (R-#153/R-#162), never in
  free-text entity columns.
