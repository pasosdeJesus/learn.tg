# F-#300: The in-app wallet never unlocks on the development site (8 E2E specs red)

> **Draft.** The operator publishes it with `cd apps/web && bin/m req:sync-to-repo 300` (the
> repository assigns the IID; if it is not 300, rename this file and its link).

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/300
**Created:** 2026-11-13
**Status:** Open — **causa raíz identificada** (2026-11-13): el núcleo de billetera de `m`
no puede derivar la frase en el navegador; el arreglo es una versión nueva de `m`
**Type:** Failure / bug (in-app wallet, E2E suite)
**Priority:** Medium — it does not block the GD cluster work, but it leaves the wallet half of the
browser suite red, and the wallet is how a user without MetaMask signs in.

## 1. Symptom

A full run of the browser suite against the development site (`https://learn.tg:9001`,
`make test-e2e-retry`, 2026-11-13) ends with **41 ok, 9 skip, 8 fail**. Every failure is about the
in-app wallet; the cluster, course, admin, auth and donation specs pass:

```
wallet-panel-collectibles.spec.mjs   wallet-link-second-wallet.spec.mjs
in-app-wallet.spec.mjs              in-app-wallet-payments.spec.mjs
in-app-wallet-default.spec.mjs      header-wallet-dialog.spec.mjs
donate-unlock-dialog.spec.mjs       biometric-unlock.spec.mjs
```

The visible failure is always the same: after the create form is filled and **Create** is pressed,
the wallet never reaches the `unlocked` state, so the 60 s wait expires:

```
TimeoutError: Waiting failed: 60000ms exceeded
  at waitForStatus (apps/web/e2e/specs/in-app-wallet.spec.mjs:42:14)
  at main (apps/web/e2e/specs/in-app-wallet.spec.mjs:89:9)
```

`wallet-link-second-wallet` reports it as `No se consiguió una sesión con la billetera de la
aplicación` (no SIWE session with the app wallet), which is the same root: there is no unlocked
wallet to sign with. `header-wallet-dialog`, `donate-unlock-dialog` and `biometric-unlock` also need
that wallet and fail on the same step.

## 2. Root cause (confirmed 2026-11-13)

The chain in the browser is:

```
WalletDialog (apps/web/components/WalletDialog.tsx)
  → useInAppWallet                (@pasosdejesus/m/wallet/next)
  → createWallet()                (m: wallet/wallet.js:113)
  → newMnemonic()                 (m: wallet/signer.js:25)
  → viemAccounts()                (m: wallet/signer.js:8)
  → loadFromProject('viem/accounts', import.meta.url)   (m: util/project-require.js:51)
  → nodeBuiltins() throws         (m: util/project-require.js:16)
```

`loadFromProject()` resolves `viem` from the **project tree** with `createRequire`, which only
exists in Node: `nodeBuiltins()` reads `process.getBuiltinModule` and refuses to run in a browser.
`newMnemonic`, `accountFromMnemonic`, `accountFromPrivateKey` and `keccak` all go through it, so the
wallet cannot be created, imported or used from the browser at all. The user sees the generic error
`wallet dialog error: loadFromProject() resolves a package from the project tree and only works in
Node >= 22.3 (process.getBuiltinModule); this runtime is` and the page stays in `no-wallet`.

**Why it is a regression.** `m` R-#66 (version 0.37.14, 2026-11-06,
https://gitlab.com/pasosdeJesus/m/-/work_items/66) moved `wallet/signer` to `loadFromProject` so the
**global** `m` CLI would use the project's `viem`. That fixed the CLI and broke the browser, which
shares the same module. `m@0.37.17` then replaced the static `node:fs`/`node:module`/`node:path`
imports with `process.getBuiltinModule` so the **bundle builds**, which only moved the failure from
build time to run time. The local recipe of `doc/pdj-wallet-testing.md` (0 failures, 2026-09-28)
predates both versions.

**Where the fix belongs.** In `m`, not here: the signer needs a browser implementation that imports
`viem`/`viem/accounts` **statically** (the bundler resolves it), selected for the client bundle
(e.g. a `browser` field mapping `dist/wallet/signer.js` to a `signer.browser.js`), while the Node
CLI keeps `loadFromProject`. learn.tg then only bumps the catalog
(`pnpm-workspace.yaml` override and `apps/web/package.json`) to the release that carries it. A
workaround here is not viable: the browser cannot emulate `createRequire`/`node:fs`.

## 3. Measurements (2026-11-13)

- The run uses `make test-e2e-retry E2E_RETRIES=2`: the three attempts of each spec fail, so it is
  not the load/timing flakiness documented in `doc/e2e-testing.md`.
- Running the spec **alone** with the machine idle (`make test-e2e-spec SPEC=in-app-wallet`) fails
  identically at the same line with the same 60 s timeout.
- `/en/test/wallet` **is** deployed: the page renders and the form is usable. The spec gets past
  `wallet-password`, `wallet-password-confirm`, `wallet-create` and the protection dialog; it is the
  `wallet-status` element that never becomes `unlocked`.
- The site was redeployed immediately before the run (build visible after 67 s), so this is the
  current `main` working tree, not a stale build.

## 4. What is not the cause

- **Not R-#299.** That change touches clusters (`packages/gdcluster`, `apps/web/app/api/cluster*`),
  the public cluster page and the migration; it does not touch `packages/generated/wallet`,
  `@pasosdejesus/m/wallet` or `/en/test/wallet`, and the 41 green specs include every cluster,
  admin, auth and course check.
- **Not connectivity**: the same browser session signs in with the `apps/.env` wallet (SIWE 200) in
  the other specs of the same run.
- **Not the classic headless KDF slowness alone**: the suite passed before on the same machine and
  the failure repeats with no other spec running.

## 5. Proposed work

1. **Done — make the failure legible**: `apps/web/e2e/specs/in-app-wallet.spec.mjs` now prints, on
   timeout, the real `wallet-status`, the tail of the page log (which shows the wallet error) and the
   browser console/page errors. That is how §2 was found; a silent 60 s wait had hidden it.
2. **In `m`**: browser implementation of `wallet/signer` (static `viem` imports) selected through
   the package `browser` field, keeping `loadFromProject` for the Node CLI; a unit test that the
   browser bundle does not reach `project-require`, and the regression written into `m`'s changelog
   and `REQ/66`.
3. **In learn.tg**: bump the catalog/override to the `m` release that carries the fix
   (`pnpm-workspace.yaml`, `apps/web/package.json`) and note the minimum version in
   `doc/pdj-wallet-testing.md`.
4. Re-run the eight specs (and then the full suite) on the development site.
