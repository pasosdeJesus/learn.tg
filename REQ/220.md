# R-#220: Cluster Formation (Simplified) — built on the existing GD cluster model

Formation of clusters of **at least 3 churches** (lead pastor + 2 invited pastors, with room to grow) for the Global Disciples pilot, **building on the existing GD cluster infrastructure** in the `@learn-tg/gdcluster` engine (https://gitlab.com/pasosdeJesus/m/-/work_items/35 Phase 3, https://github.com/pasosdeJesus/learn.tg/issues/214):

- Tables **`clustergd`** + **`church_clustergd`** (church-based membership) + **`clustergd_history`** (audit) — **NO parallel `cluster`/`cluster_member` tables are created**.
- Existing **`/api/cluster/*`** routes (`POST /api/cluster`, `POST /api/cluster/join`, `GET|PATCH /api/cluster/[id]`, `POST /api/cluster/[id]/leave`) — **extended, not duplicated**.
- Funds: **`ClusterFundsV2`** (`processDonation` → `clusterFunds[cluster_wallet]`) using the `church.cluster_wallet`; cluster ranking already operational.
- Invite candidates: **#163 referral graph** (referred pastors + the referrer if they are a pastor).

**Dependencies:** #161 (GD course — content ⏳, purchase requirement already enforced in `createCluster`), #163 (referrals — ✅), #155/214 (cluster funds — ✅ operational).

---

## 1. Overview

A pastor with the GD course paid (verified in `createCluster`) forms a cluster with **their church + at least 2 invited churches** (3 churches minimum). The cluster may keep growing; the platform does not cap the number of churches. The cluster is the existing `clustergd` entity; membership is churches (`church_clustergd`); the fund is the initiator church's `cluster_wallet` (`ClusterFundsV2`, 80% of GD donations).

### 1.1 Pastor states (user)

| State | What they see |
|-------|---------------|
| **No cluster** | `/{lang}/cluster` with a reference to Guide 2 + "Create a cluster" button |
| **Pending invitation** | Page with the invitation + **Accept** / **Reject** buttons |
| **In a cluster** | Cluster details (name, pseudonym, members) + "Leave cluster" button |

### 1.2 Cluster states (`clustergd.status` — new column)

| State | Condition |
|-------|-----------|
| `pending` | 1–2 member churches (created, invitations open) |
| `active` | 3 or more member churches (cluster formed; no technical maximum) |
| `disbanded` | No member churches left after the initiator leaves, or an admin disbands it |

### 1.3 Size: minimum 3, no technical maximum

Three churches is the **minimum for `active`**, not a ceiling. The platform does
not impose a maximum number of churches, because the size of a cluster is a
**strategic decision**, not a technical one. The cluster proposes the number of
cohorts per year and the number of students per cohort from the membership of
its churches, and fits them to the training capacity. The upper limit is
strategic: it is the number of churches needed to gather enough students to
sustain the program through its three-year funding cycle and beyond, following
GD's methodology and its phase sequence (discipleship/GDT first, then SBD). The
plan does not assume that a cluster can be split later; the cluster starts with
the number of churches it needs. The creation form invites two pastors because
that is what is needed to reach the minimum; after creation, more churches join
with the 6-char code.

**Update (2026-10-26):** cluster creation is open to countries classified as
type 1 (`msip_pais.tipo_region = 1`), replacing the Colombia/Sierra Leone pilot
list. Type 2 and unclassified (`NULL`) remain closed. See the R-#161 revision.

## 2. Creation (pastor without a cluster)

**Page:** `/{lang}/cluster`

1. The pastor sees: *"To form a cluster, you need to invite 2 trusted pastors. Read Guide 2 for more information."* + link to Guide 2 + **"Create a cluster"** button.
2. The form (reuses `POST /api/cluster` with new fields):

| Field | Type | Description |
|-------|------|-------------|
| **Cluster name** | Text | Public (unique per country — existing validation) |
| **Pseudonym** | Text (optional) | For contexts where the public name could expose the pastor; when set, it is what appears in the public ranking (privacy) |
| **Invite pastors** | Multi-select | Candidates (see §2.1) |

3. The pastor selects **2 pastors** (the minimum needed to reach three churches) and submits. More churches can join later with the code; the cluster's final size is not capped by this form.
4. A `clustergd` is created (existing 6-char code + `pseudonym` + `status='pending'`) with the leader's church as the 1st member (`church_clustergd`), and **2 invitations** are generated (`cluster_invitation`). The cluster stays `pending` until the third church joins.

### 2.1 Invite candidates (`GET /api/cluster/candidates`)

Priority (same pilot-country rule as `createCluster`):

1. **Pastors referred** by the leader (#163 referral graph: `referralrelationship` → `usuario` with `church_relationship='pastor'`).
2. The leader's **referrer**, if they are a pastor.
3. (Fallback, if candidates are missing) search by name/cluster code of verified churches in the same country — the cluster can also be completed with the existing **6-char code** (`POST /api/cluster/join`).

Per-candidate constraints: same country as the leader, declared and verified church, no current cluster, not themselves.

The two invitations at creation are a convenience to reach the minimum, not a
maximum: any number of additional churches can join later with the 6-char code.

## 3. Invitation (pastor with a pending invitation)

1. The invitee receives an **in-app notification** (existing `notifications` table): *"You have been invited to join cluster [Name] by [Pastor]."*
2. Opening `/{lang}/cluster`: *"You have been invited to join cluster [Name] created by [Pastor]."* + **Accept** / **Reject**.
3. **Accept** → `POST /api/cluster/invitation/accept`: the pastor's church joins `church_clustergd`; with 3 or more members, `clustergd.status='active'`; the leader is notified and it is recorded in `clustergd_history`.
4. **Reject** → `POST /api/cluster/invitation/reject`: `cluster_invitation.status='rejected'`; the leader is notified (they can invite another candidate).

**Rule:** a pastor/church can only belong to one cluster at a time (existing `getChurchCluster` validation → 409).

## 4. Management (pastor in a cluster)

**Page:** `/{lang}/cluster`

- Name, pseudonym (if set), members (initiator church + at least 2; the cluster may grow), cluster code, and the **cluster wallet** with its change history.
- Text: *"The pastor who created the cluster can edit the details."*
- **"Leave cluster"** button (`POST /api/cluster/[id]/leave`, existing, extended):
  - If the **leader** leaves: leadership is transferred to the oldest remaining member; if no member remains, the cluster is **disbanded** (`status='disbanded'`).
  - If a member leaves and fewer than 3 remain: the cluster returns to `pending` and the leader can invite a replacement (candidates §2.1). A cluster with 3 or more churches stays `active` when a member leaves.

The **initiator** edits name/pseudonym and **sets the cluster wallet**: `PATCH /api/cluster/[id]` (existing, extended).
The wallet is `church.cluster_wallet` of the initiator church (the source of truth for the 10% routing). The
leader sets it from `/{lang}/cluster/[id]`; the UI recommends a **multisig wallet shared by the
cluster's pastors** (e.g. a Safe) and warns that changing it later does not move funds already
credited (the fund is keyed by the old address). Changing it is recorded in `clustergd_history`
(`cluster_wallet_change`) and `userevent`. The verifier keeps the ability to correct it in the
church modal as a support path (`PATCH /api/admin/church/[id]`), not as the normal flow.

## 5. Admin / Verifier

Over the existing data (`clustergd` + `church_clustergd` + `church`), exposed via `/api/admin/clusters/*` (verifier/admin auth, `lib/admin-auth.ts` pattern).

| Role | Access |
|------|--------|
| **Admin** | Create, edit, disband any cluster |
| **Verifier** | View all, edit name/pseudonym/members, cannot disband |

### 5.1 List (`/api/admin/clusters`)

Columns: ID · Name (or pseudonym) · Country · Initiator (initiator church + pastor) · Members (n; minimum 3) · Status (pending/active/disbanded) · Fund (`cluster_wallet` + balance via `ClusterFundsV2`) · Actions (Edit / Disband).

Filters: name, country, status, leader.

### 5.2 Create / Edit (`/api/admin/clusters` POST / `/api/admin/clusters/[id]` PUT)

Fields: name, pseudonym, initiator church (select), members (multi-select of verified churches), status.

### 5.3 Detail (`/api/admin/clusters/[id]`)

Details + members with roles + add/remove member + disband. Admin changes are logged in `userevent` (and `clustergd_history`).

## 6. Database Schema (new migration)

### 6.1 Alter of `clustergd` (existing table)

```sql
ALTER TABLE clustergd
  ADD COLUMN pseudonym VARCHAR(100),              -- privacy (contexts where the name could expose the pastor)
  ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'pending', -- pending | active | disbanded
  ADD COLUMN initiator_church_id INTEGER REFERENCES church(id);  -- initiator church (optional: default = 1st member)
```

> **Funds decision:** the `cluster_wallet` (`ClusterFundsV2` fund) remains the `church.cluster_wallet` of the **initiator church** (current model: the donation route resolves the destination by the member church's `cluster_wallet`). Documented in the migration; the column is not moved in this phase.
>
> **Terminology (2026-10-27):** the role is called **cluster initiator** (`iniciador del clúster`) in the UI, the API and the guides, to avoid confusing it with the **program director** or with the church's **lead pastor**. The schema was aligned by `20261027180000_rename_cluster_initiator`: `clustergd.leader_church_id` → `initiator_church_id` (with its FK constraint) and the `clustergd_history` event `leader_transfer` → `initiator_transfer` (existing rows updated; reversible). The public JSON exposes `initiator_church_id` plus `isInitiator` for the viewer. When the initiator leaves, the role is transferred to the oldest remaining member and the new holder is called the initiator too.

### 6.2 New table: `cluster_invitation`

```sql
CREATE TABLE cluster_invitation (
    id SERIAL PRIMARY KEY,
    clustergd_id INTEGER NOT NULL REFERENCES clustergd(id),
    invited_pastor_id INTEGER NOT NULL REFERENCES usuario(id),
    invited_church_id INTEGER NOT NULL REFERENCES church(id),
    invited_by_id INTEGER NOT NULL REFERENCES usuario(id),
    status VARCHAR(20) NOT NULL DEFAULT 'pending', -- pending | accepted | rejected | expired
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    responded_at TIMESTAMP,
    UNIQUE(clustergd_id, invited_pastor_id)
);
```

> **No new cluster tables:** the original draft's `cluster`/`cluster_member` are discarded; membership remains `church_clustergd` (churches), not users.

## 14. Out of Scope

- Multiple clusters per pastor/church.
- Bulk invitations.
- Email or WhatsApp notifications (in-app only).
- Automatic activation by member count on-chain (the backend activates at 3 or more; on-chain activation is future work).
- A hard maximum number of churches per cluster: the size is a strategic decision with GD, not a platform limit.
- Cluster logo or image.
- Moving `cluster_wallet` from `church` to `clustergd` (future decision; documented in the migration).
