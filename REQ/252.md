## 1. Objective

One place to record refactoring opportunities where code is duplicated, or where a
piece of learn.tg really belongs in the shared **`m`** ecosystem
(https://gitlab.com/pasosdeJesus/m, work item `35`). Two directions:

- **Inside learn.tg** (between engines, `apps/nextjs`, `packages/*`, e2e helpers).
- **Between learn.tg and `m`** (`@pasosdejesus/m`, `@pasosdejesus/mpdj`,
  `@pasosdejesus/usdt`, `@pasosdejesus/edr`, `@pasosdejesus/contract-test`).

The project already has a precedent: `@pasosdejesus/usdt` was a **"1ª graduación
local → shared"** — hooks that started in learn.tg and moved to `m` so sivel3 could
reuse them (`ARCHITECTURE.md` §Web3 Engines). This requirement is where the next
ones get listed and planned.

## 2. Methodology to find opportunities (to be run later)

Write-up only. Framed on the local → shared graduation pattern above.

### Step 0 — Freeze the two inputs

- **learn.tg:** `packages/*` (engines + `pdj-wallet`), `apps/nextjs/{lib,components,db}`,
  `apps/hardhat`, `apps/nextjs/e2e`.
- **m:** `/var/www/adJ-ia/m/packages/*` (`m`, `mpdj`, `usdt`, `edr`, `contract-test`)
  and whatever `@pasosdejesus/m` exports from its `package.json` `exports`.

### Step 1 — Inventory the public surface (both sides)

- List every exported symbol with its signature and doc comment, and tag the
  runtime: **browser**, **node**, or **both**.
- For learn.tg packages use their `README.md`/`ARCHITECTURE.md` "API" tables; for
  `m` use `packages/m/src/index.ts` and the package `exports` map.
- Output: one table per side (`symbol | signature | deps | runtime | owner`).

### Step 2 — Cheap candidate heuristics

Run these and then eyeball the hits; they are signals, not verdicts:

- **Same name** on both sides (`git grep` for the identifier).
- **Same third-party primitive wrapped repeatedly** (`viem/accounts`,
  `keccak256`, `encodeFunctionData`, `siwe`, `qrcode.react`…).
- **Same algorithm re-implemented**: formatting, retries, JSON file with `0600`,
  error mapping, i18n dictionaries.
- **Copy-paste / near-duplicate blocks** between the two trees (diff the candidate
  files; look for identical comments).
- **Pass-through wrappers** that only rename an existing `m` or viem function.
- **Cross-imports already present**: a learn.tg file importing something from `m`
  that is later re-implemented.

### Step 3 — Score each candidate

| Criterion | Question |
|---|---|
| Reuse | Used by ≥ 2 apps/packages (learn.tg + sivel3/stable-sl), or unit-agnostic? |
| Stability | Is the API settled, not a moving MVP? |
| Boundary | Framework-agnostic (no `next`/`react`/`kysely`)? |
| Self-containment | Carries its own tests and no app config? |
| Direction | Points to `m` (shared) or is learn.tg-specific (keep here)? |

### Step 4 — Decide the destination

- **Shared primitive** → `m` (`@pasosdejesus/m` or a package like `usdt`/`mpdj`).
- **App/UX only** → stays in learn.tg; record it as "keep" so it is not re-proposed.

### Step 5 — Plan the graduation (per accepted candidate)

1. Move the code **with its tests** to `m`; publish a new `m` version.
2. Replace the local copy with `@pasosdejesus/m/...`; delete the duplicate.
3. Update the docs of both sides (`README.md`/`ARCHITECTURE.md`) and this file.
4. Verify: unit tests on both sides plus the E2E specs that cover the feature.

### Step 6 — Record the finding here

One subsection per opportunity: files, evidence, destination, effort, risk, status.

> **Do not run this methodology while authoring R-#252.** It is the work for a
> later task/agent.

## 3. Opportunity #1 — wallet primitives (pdj-wallet ↔ m wallet)

*Reported by the operator (2026-09-20).* Functions in `pdj-wallet` and in the `m`
wallet should share their source in `m`.

**Where**

- learn.tg: `packages/pdj-wallet/src/{signer.ts,crypto.ts,storage/file.ts,siwe.ts}`
- m: `packages/m/src/tasks/wallet.ts` (the `bin/m wallet:*` CLI)

**Evidence (same primitives, two homes)**

- Both wrap `viem/accounts`: `generateMnemonic(english)`, `mnemonicToAccount`,
  `privateKeyToAccount`.
- `pdj-wallet/src/signer.ts` exports `newMnemonic`, `normalizeMnemonic`,
  `isValidMnemonic`, `assertValidMnemonic`, `accountFromMnemonic`,
  `accountFromPrivateKey`, `addressFromMnemonic`, `privateKeyFromMnemonic`; the m
  CLI inlines the equivalent work in `cmdGenerate`/`cmdImport`/`cmdDerive`/`cmdSign`.
- **Keystore on disk, written twice:** m `getWalletsDir`/`loadWallet`/`saveWallet`/
  `ensurePermissions` (JSON, `0600`, `~/.m/wallets/`) vs `pdj-wallet`
  `storage/file.ts` `FileStorage` (JSON, `0600`, `FileStorage(path)`). The **adapter
  pattern is the same**; the **payload differs**: `pdj-wallet` stores the
  AES-256-GCM-encrypted record, while the m CLI stores the private key and the
  mnemonic in clear JSON (protected only by file permissions).
- Address resolution (`resolveToAddress`), RPC error formatting (`formatRpcError`)
  and `keccak256` (`cmdKeccak`) exist on both sides.
- **Concrete drift, not hypothetical:** the m CLI derives with
  `mnemonicToAccount(mnemonic, { accountIndex: index, addressIndex: 0 })`, while
  `pdj-wallet` uses `mnemonicToAccount(mnemonic, { addressIndex: index })`; the
  option names and the meaning of the index differ between the two.

**Proposal**

Extract the account/key/keystore primitives into `m` (for example
`@pasosdejesus/m/wallet`), framework-agnostic and Node-safe, with tests; then:

- the `m` CLI consumes them (no behavior change, and it fixes the derivation
  inconsistency), and
- `packages/pdj-wallet` consumes them for the non-browser parts (mnemonic
  normalize/validate, account derivation, file keystore), keeping the browser-only
  pieces local: `crypto.ts` (WebCrypto AES-256-GCM + PBKDF2), `provider.ts` (EIP-1193
  + L1 funds gate), `web-authn.ts` and `biometric.ts` (PRF sealing).

**Risks / boundaries**

- `pdj-wallet` is browser-first: the shared module must not drag `node:fs` into
  browser bundles. `FileStorage` already lives in a `./storage` subpath for exactly
  this reason; keep that split and expose the Node keystore from a subpath.
- `m` is ESM on Node 18+; keep the shared module dependency-light (`viem` only).
- Do **not** move the WebCrypto record format or the provider: those are browser
  concerns, and the m CLI has no wallet encryption today.
- Separate follow-up (its own requirement, not part of the shared primitives):
  consider whether the m CLI should also stop storing plaintext keys and adopt the
  encrypted record; that would be a security improvement but changes the `~/.m`
  keyfile format.

  `apps/nextjs/lib/hooks/useGasEstimation.ts` (a local copy already exists, with

  `apps/hardhat/deployments/*.json`, the ABI sync to `apps/nextjs/abis`.

  `packages/rewards/src/lib/credentials.ts`.
- **Metrics:** `@pasosdejesus/m/wba` vs `apps/nextjs/lib/metrics-server.ts`.
- **i18n:** `@pasosdejesus/m/i18n` vs the app dictionaries, and the near-duplicate
  dictionaries between `components/WalletDialog.tsx` and `pdj-wallet-next/src/i18n.ts`.
- **Test utilities:** `@pasosdejesus/m/test-utils` mocks vs the app's test helpers.
- **Inside learn.tg only:** the three engines share adapter/registry patterns
  (`apps/nextjs/lib/{rewards,gdcluster}-app.ts`, `lib/engines.ts`) that could be one
  generic adapter.
