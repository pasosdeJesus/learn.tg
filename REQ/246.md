### 1. Objective

Stop asking the user to unlock the in-app wallet so often, **without ever
leaving the private key readable at rest**, by using the device's own
authentication (platform authenticator: Face ID / Touch ID / fingerprint /
device passcode) instead of a second app PIN.

### 2. Problem

The in-app wallet keeps the decrypted key in module memory only, so any page
reload locks it again. The operator hit this twice by hand:

- 2026-09-15/16 (`/var/www/adJ-ia/tmp/d.txt`): after signing in, the header went
  back to "Unlock your in-app wallet" on reload.
- 2026-09-16: "quise donar para un curso, se abrió el modal con un botón para
  Unlock Wallet, lo presioné pero no hizo nada". Two defects: `WalletSelector`
  returned the signed-in header without mounting `WalletDialog` (the only
  listener of `learn-tg:open-in-app-wallet-dialog`), and `WalletDialog` re-signed
  the SIWE even when the session cookie already belonged to that wallet, so the
  reload that followed locked the wallet again.

Both are fixed (see §11). What remains is the design question: the PIN is a
secret the user must type, and today it is asked again after every reload.

### 4. Design: three layers

The three mobile wallet browsers in §3 solve the same problem differently; §13
records what they do and which parts of it we can and cannot copy in a web page.

| Layer | Mechanism | Gives | Needs hardware | Key material |
|---|---|---|---|---|
| **L0** (today) | PIN → PBKDF2-SHA256 600k → AES-256-GCM, key in module memory | Works everywhere, offline, no dependency | no | never at rest, never persisted |
| **L1** *gesture gate* | Before a signature, require a WebAuthn assertion with `userVerification: 'required'` and a fresh challenge | A script (XSS) cannot complete the gesture silently: the user sees the prompt. Bounds the window in which a page can sign | platform authenticator | none (assertions are signatures, not keys) |
| **L2** *hardware unlock* | WebAuthn **PRF extension** (`hmac-secret`): the authenticator derives a deterministic secret that never leaves it; the wallet key is wrapped with that secret (HKDF → AES-GCM) | Unlock by Face ID / fingerprint, **no PIN to type**, and nothing readable at rest | `prf` support | wrapped, never plaintext |

Rules:

1. **The passkey is never the only path.** Losing the device must not mean losing
   the funds: the PIN (L0) stays as fallback and the 12 words as recovery.
   This mirrors the decision already documented in `doc/pwa-user-guide.md`.
2. **The device PIN is never read by the page.** "Use the device PIN" is only
   reachable through WebAuthn's user-verification prompt (or the OS keystore);
   there is no API that returns the passcode.
3. **Detect, never assume.** WebAuthn/passkeys are unavailable in many Android
   WebViews; `prf` only exists in Chrome 116+ and Safari 18+. Every layer must
   degrade silently to the one below.
4. **External wallets keep priority on their own browsers.** When
   `window.ethereum` (or an EIP-6963 announcement) exists (environments 3–6) the
   external path is used; the in-app wallet stays an explicit opt-in.
5. **No device is left out.** L0 needs nothing but the PIN, so every measured
   environment works today; L1 and L2 are *improvements* where the runtime happens
   to provide them (see the coverage table below).

**Coverage of the measured environments** (capabilities from §8, 2026-09-18):

| Environment | L0 PIN | L1 gesture | L2 PRF unlock | What the user ends up doing |
|---|---|---|---|---|

| Safari iOS (pending measurement) | yes | yes | likely (iOS 18/26 in use) | In-app wallet; Face ID if `prf`, otherwise PIN |
| Rabby in-app browser (P1) | yes | **no** | **no** | Their Rabby wallet (once §10's EIP-6963 item is done); in-app wallet only with PIN |
| OneKey in-app browser (P2) | yes | **no** | **no** | Their OneKey wallet (once §10's EIP-6963 item is done); in-app wallet only with PIN |
| MetaMask in-app browser (P2) | yes | **no** | **no** | Their MetaMask wallet (once §10's EIP-6963 item is done); in-app wallet only with PIN |

So: **all of them operate**, because the PIN path has no hardware requirement.
What changes per device is the friction (typing the PIN per unlock) and whether
the user even needs the in-app wallet — in items 3–6 they already carry a wallet
that authorizes each signature in its own app.

**Should the in-app wallet be offered inside wallet browsers?** Not as an equal
option — but keep it as an explicit fallback, for these cases:

- The host provider cannot `personal_sign` (MiniPay is the documented example: it
  has no message signing, and the in-app wallet owns its own provider, which is
  why it exists).
- The host provider fails: wrong chain, `-32000 region restricted` (OKX), a stale
  injected provider after an SPA navigation (OKX's documented quirk), or an
  `accountsChanged([])` mid-flow.
- The user deliberately wants an identity separate from the wallet app's account.

Why it must not be the default: the profile, the score, the scholarship and the
referrals are all **per address**, so silently creating a second wallet forks the
user's account; and in those WebViews there is no L1/L2, so it means typing the
PIN on every unlock while the app's own wallet would have asked nothing.

**Prompt policy (what the user is asked, and when)** — this is the usability side
of the tradeoff, and it is what L2 is for:

| Moment | With L2 (Chrome/Brave Android, Safari iOS, desktop) | Without WebAuthn (wallet WebViews, Opera) |
|---|---|---|
| Opening the app (cold page load with a wallet) | **1 biometric gesture** to unwrap the key; cancelling falls back to the PIN | 1 PIN |
| Moving around inside the app (client-side navigation) | nothing: the key stays in module memory | nothing |
| **Moving funds** (donate, buy a course, claim UBI/scholarship, send) | **1 fresh gesture** before the transaction is signed (L1, implemented 2026-09-18) | nothing extra (no WebAuthn): the PIN already unlocked it |
| Zero-value actions (mark a guide complete, crossword answers) | nothing | nothing |
| Back after an hour of inactivity (auto-lock, implemented 2026-09-18; one hour since 2026-09-19) | 1 gesture on the next action | 1 PIN on the next action |
| Hard reload / the OS killed and restored the tab | 1 gesture | 1 PIN |
| Header ✕ (disconnect) | drops the key **and** signs out | same |

> The auto-lock default was **ten minutes** until 2026-09-19: in the operator's
> mobile test the wallet was already locked when donating, less than ten minutes
> after unlocking, and the timer also listened for `visibilitychange` on `window`
> (the event is emitted at `document`, so the listener never ran). It is now
> **one hour** with the activity sources fixed — see §10, and
> https://github.com/pasosdeJesus/learn.tg/issues/248 for a user-chosen value.

Implementation notes for the two new rows:

- The funds gate lives in the provider, not in the UI: any
  `eth_sendTransaction` on the in-app wallet asks for a fresh user-verified
  assertion (`requireFundsConfirmation()` in `packages/pdj-wallet/src/provider.ts`),
  so a script in our origin cannot move money silently either. Cancelling is a
  rejection with code `4001`, like any wallet; without a passkey enrolled the gate
  allows the request (L1 needs hardware).
- **Fixed 2026-09-19:** the gate also covers `eth_signTypedData_v4` and
  `eth_signTransaction` (EIP-3009 authorization, EIP-2612 permit and raw signing
  move funds too). `personal_sign` keeps no gate (it is the SIWE). See the
  acceptance criterion in §10.
- The auto-lock drops the key after `INACTIVITY_LOCK_MS` (one hour) without pointer,
  key, touch, scroll or visibility activity (the visibility event is listened for
  on `document`), and marks `lockReason: 'idle'` so
  `WalletEventListener` **does not** sign the user out (only the ✕ or deleting the
  wallet does).

So on Chrome for Android the PIN is asked **once, at wallet creation**, and as a
fallback when the user cancels the biometric prompt or the passkey is gone; the
daily flow is "open the app → touch the sensor → use it". What repeats is one
**gesture per app open**, not per reload-in-a-tab, not per transaction and not
per navigation. The security price of that window:

- While the tab is open and unlocked, code running in our origin (XSS) or someone
  holding the unlocked phone can sign without any prompt; that window is bounded
  by the auto-lock timer and by the header ✕.
- L1 exists precisely for the case where that window is judged too wide: a fresh
  user-verified assertion before each signature (or above a value threshold)
  makes silent signing impossible, at the cost of one prompt per payment.
- Because `sessionStorage` does not survive closing the app (§8), nothing shortens
  this window by accident: the promise is exactly "one gesture per app open", no
  more and no less, and never "unlocked forever".

### 5. Detection and fallbacks

```ts
// Capability probe; every field must be optional/guarded.
const hasWebAuthn = typeof window.PublicKeyCredential !== 'undefined'
const platformUv = hasWebAuthn
  ? await PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()
  : false
// prf is only reported by creating a credential with the extension
const prfEnabled = creRes.getClientExtensionResults()?.prf?.enabled === true
```

| Situation | Behaviour |
|---|---|
| `prf` enabled | Offer "Unlock with Face ID / fingerprint" (L2); PIN still available |
| WebAuthn with UV, no `prf` | Keep the PIN to decrypt; require an assertion (L1) before each signature |
| No platform authenticator (typical Android WebView) | L0 only |

### 6. Key storage policy

The **stopgap in the tree today** is a tab-scoped entry
`learn.tg:in-app-wallet:unlocked` in `sessionStorage`
(`packages/pdj-wallet/src/session.ts`, added 2026-09-16) holding the **private key
in plaintext**, with a sliding 30-minute TTL, cleared by `lockWallet()` (the
header ✕), `deleteWallet()` and the TTL.

It is the only place where the key exists outside memory and it is exactly what
this requirement is meant to remove. **Measured caveat (§8): `sessionStorage` does
not survive closing the app in any of the tested environments**, so the entry only
saves the PIN for reloads inside a live tab — never for a user who comes back the
next day. Target state:

- L2 available → unlock is a biometric gesture; delete the entry.
- L2 unavailable → L0 (PIN again after a reload) + L1 before each signature.

Interim options if the friction is unacceptable before L2 lands:

| Option | Effect | Against XSS | Against profile theft |
|---|---|---|---|
| **A. Remove it now** | PIN per reload | nothing to steal | nothing to steal |
| **B. Wrap with a non-extractable `CryptoKey`** (AES-GCM key in IndexedDB, ciphertext in `sessionStorage`) | No plaintext at rest, unlock survives reloads | no help (the page decrypts) | good (the key blob is not usable outside the browser) |
| **C. Keep it, TTL 10 min absolute** | Status quo, shorter window | no help | no help |

Recommendation: **A while L2 is not implemented**, then B is unnecessary.
Independent control, same threat model: the app has **no CSP today** (only HSTS,
`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`; see
`next.config.ts` §headers). A strict CSP + Trusted Types is the real mitigation
for XSS, which is the only path that needs **no** privilege on the user's device.
Propose it report-only first on the dev site.

### 7. What an attacker needs (threat model)

| Path to the plaintext entry | Privileges on the user's device | Works? |
|---|---|---|
| XSS / poisoned build in learn.tg | **none** | yes, same origin |
| Browser extension with site-data access | install the extension | yes |
| Process running as the user reading the browser profile | user-level (Android needs root: app sandbox) | yes, if the tab is alive or the session was restored |
| Physical access with DevTools / MITM proxy with its CA | unlocked device | yes |
| Reading the disk without executing code | — | no key is on disk |

The IndexedDB record stays useless without the PIN (PBKDF2 600k), so a profile
thief only gets L0 material. The plaintext session entry is the exception, and
that is why it must go.

### 8. Capability probe (do this first)

**Page:** `apps/nextjs/public/pdj-wallet-probe.html` — a single self-contained

1. Open the URL and read sections 1 and 2, which fill in automatically:
   environment (UA, `window.ethereum` and its flags, EIP-6963 providers),

**What the results change**

1. **L2 is viable exactly where it matters most.** Chrome for Android (P0) reports
   `isUserVerifyingPlatformAuthenticatorAvailable() = true` and a **deterministic
   32-byte PRF secret**, so "unlock with the fingerprint, no PIN to type" can be
   implemented on the priority environment. Brave behaves the same.
2. **L1/L2 are impossible in the wallet WebViews** (items 3–6):
   `PublicKeyCredential` is `undefined` and creation fails with
   `NotSupportedError — Error connecting to Web Authentication service`. On those
   devices the external wallet is the only sensible path (its own app authorizes),
   so §4 must not offer the in-app wallet there as an equal option.
3. **`sessionStorage` does not survive closing the app in any of the six.** The
   stopgap of §6 only saves the PIN for **reloads inside a live tab**; a user who
   closes Chrome/MiniPay the night before types the PIN again. That is one more
   reason for option A (remove it) once L2 exists, and it must be documented in
   the user guide.
4. **IndexedDB survives everywhere** (including the four wallet WebViews), so the
   stored encrypted wallet — and the 12 words as recovery — remain the safety net.
5. **Detection of the injected wallet is a timing/robustness problem, not an
   absence.** The probe read `window.ethereum` once, at page load, and got `NO` in
   Rabby, MetaMask and OneKey (only OKX had it, as `isMetaMask`); their providers
   then arrived as EIP-6963 announcements (`io.rabby`, `io.metamask.mobile`,
   `so.onekey.app.wallet`). **But learn.tg works there today**: the same database
   records successful sign-ins from those browsers (MetaMask 101 sign-ins from 12
   addresses, OKX 40/16, Rabby 32/14 — §3 evidence), which is only possible with a
   provider, so the wallet is found once the user acts, not at first paint. The
   real risk is narrower: nine places decide "external wallet available" from a
   read of `window.ethereum` (`lib/hooks/useAuthAddress.ts`, `useWallet.ts`,
   `useWriteContract.ts`, `useWalletProvider.ts`,
   `components/ConnectWalletButton.tsx`, `WalletEventListener.tsx`,
   `WalletSelector.tsx`) plus one legacy `ethereum#initialized` listener, so a late
   injection can leave the external option hidden (until a reload) and
   `WalletEventListener` unattached. Fix: an EIP-6963 discovery layer used by all
   those readers, listening for `eip6963:announceProvider`, dispatching
   `eip6963:requestProvider` and keeping `window.ethereum` as fallback; decided
   2026-09-18 to keep it **inside this requirement** (see §10 and §12.5) instead of
   opening R-#247. The hook must accept whichever rdns is announced (per wallet
   *and* platform: `io.metamask` vs `io.metamask.mobile`).
  **How to settle the open question without another manual round:** record in
  `userevent` whether the provider came from `window.ethereum`, from an EIP-6963
  announcement or from the in-app wallet; the next real users answer it.
  **Implemented 2026-09-25:** `wallet_source` is stored in `siwe_auth_attempt` and
  `siwe_auth_success` (see §10).

### 12. Open questions

### 13. Prior art: how the wallet browsers handle sessions (research 2026-09-17)

The mobile wallet browsers in §3 items 3–6 were checked against their
sources. The pattern is consistent and it is **not** what this project currently
does:

| | Rabby | OneKey | OKX Web3 |
|---|---|---|---|
| What persists | Per-**origin** permission (`ConnectedSite.isConnected`), in a persisted store dumped from an LRU cache (`src/background/service/permission.ts`: `hasPermission(origin)`, `removeConnectedSite` sets `isConnected:false` **but keeps the record for history**) | Dapp connections in a DB entity (`SimpleDbEntityDappConnection`), scoped to the **built-in browser**: "Account connection will cease once users leave OneKey App and navigate to a site on external browsers" (help.onekey.so) | Per-dapp authorization, with an **inactivity deadline**: the warning for long-inactive authorizations went from 90 to **30 days** (OKX announcement, 2024-09-27) |
| What does **not** persist | The decrypted keys: locked/unlocked lives in **memory**; the vault stays encrypted on disk. `autoLockTime` is a user setting **in minutes** | Same: app password / passkeys gate the app; keys come from `secureStorage` (OS Keychain / Keystore per platform). Data keys in IndexedDB lookups (`dbs/simple/entity/SimpleDbEntityDappConnection.ts`), never the seed | Extension: their own guidance is "lock your extension after each session" |
| Device authentication | WebAuthn credential + **encrypted password** (`biometricUnlockCredentialId`, `biometricUnlockEncryptedPassword`, `biometricUnlockIv`); `unlockPreferredMethod: 'biometric'`. A migration **clears `biometricUnlockPrfSalt`**, i.e. they moved off a PRF-based scheme | **Passkeys (Face ID / fingerprint)** as an alternative to the app password, on top of OS secure storage; biometrics are enabled for a period and fall back to the password when the attempt limit is reached | Lock/auto-lock setting; provider handles the signing prompt |
| Provider lifecycle | EIP-6963 with `rdns`, `isMetamaskMode` compatibility flag | EIP-6963 provider APIs | "OKX's content script reinjects after every navigation, so `window.okxwallet` references can become stale on SPA route transitions — **re-resolve the provider on each connect** rather than caching at module load" (web3.new/protocols/okx-wallet) |

Conclusions that change our design:

1. **Nobody persists the decrypted key in page-readable storage.** They persist
   the *connection* (per origin) and keep the *unlock* short-lived, gated by the
   device. Our NextAuth cookie already is the persisted connection; the
   `sessionStorage` stopgap of §6 is the anomaly and should go (option A).
2. **They can afford "unlock once" because they own native secure storage**
   (Keychain/Keystore) and an app-level lock. A web page has neither: its only
   equivalents are a WebAuthn **gesture** (L1) or a WebAuthn **PRF** secret
   (L2). So on mobile we must not promise the same ergonomics as a native wallet
   app; §8 probe is what decides it.
3. **PRF is not a safe assumption.** Rabby's own history shows a PRF-based
   biometric unlock being replaced by a credential-wrapped password. Treat PRF as
   an optimization with an L1 + PIN fallback, never the only path.
4. **Auto-lock is a user setting in every wallet** (Rabby: minutes; OneKey:
   password bypass options; OKX: lock after each session). We should expose the
   same knob for the in-app wallet instead of hardcoding one TTL.
5. **Connection staleness is expected and should be surfaced**: OKX warns after
   30 days of inactivity; Rabby keeps disconnected sites in history. Our
   equivalent is the NextAuth session expiry; the UI should just say "Conectar"
   again instead of failing silently.
6. **Re-resolve the injected provider per use.** Our
   `apps/nextjs/lib/hooks/useWalletProvider.ts` already reads `window.ethereum`
   on every render (not cached at module load), which is the OKX-recommended
   behaviour: keep it that way and do not memoize it in a module variable.

### 14. Source review of Rabby (2026-09-19)

Read of the actual sources at `/var/www/adJ-ia/Rabby` (v0.94.9, commit `66c312834`),
not just its docs: `src/ui/utils/biometric.ts`, `src/ui/views/Unlock/index.tsx`,
`src/ui/views/BiometricUnlockSetup/index.tsx`,
`src/background/service/autoLock.ts`, `src/background/utils/password.ts` and
`WalletController.lockWallet()` in `src/background/controller/wallet.ts`. Our side
is compared against `packages/pdj-wallet/src/{web-authn,biometric,provider}.ts`.

**Adopt (small, concrete):**

1. **Tell the authenticator a passkey is gone** when the user turns the biometric
   unlock off or deletes the wallet: Rabby calls
   `PublicKeyCredential.signalUnknownCredential({ rpId, credentialId })` when the
   browser exposes it (`biometric.ts` → `cleanupBiometricCredential`). We only drop
   our sealed record (`disableBiometricUnlock`), so the orphan passkey stays in the
   OS list until the user removes it by hand.
2. **Remember the preferred unlock method and do not re-prompt after the first
   unlock**: Rabby keeps `unlockPreferredMethod` and a session-scoped
   `hasUnlockedOnce`, and skips the auto gesture when the user chose the password
   (`Unlock/index.tsx:340-355`, `autoBiometricTriggeredRef`). We auto-trigger the
   gesture every time the dialog opens with a passkey enrolled; adopting the
   preference respects a user who deliberately pressed "use the PIN".
3. **Cancel in-flight value operations on lock**: `lockWallet()` calls
   `cancelAllSignTxPreparations()` before dropping the key. With us, an
   `eth_sendTransaction` that already passed L1 keeps going if the wallet locks
   mid-flight (idle lock or ✕); add an epoch/generation check so nothing signs or
   broadcasts after a lock.
4. **Cancel detection by keyword**: `isBiometricUserCanceledError` treats
   `cancel*`, `notallowederror`, `aborterror` as "the user cancelled". We match only
   `NotAllowedError`, so an abort surfaces as an unknown error.
5. **Parity already reached (no action):** our assertions already send
   `userVerification: 'required'` with `allowCredentials = [credentialId]`
   (`web-authn.ts:147-155`) and we verify that the unsealed key matches the stored
   address, which is Rabby's `equalBytes` check with a different shape.

**Consider (documented trade-off):**

6. **A non-PRF L2 fallback.** Rabby does **not** use the `prf` extension: it creates
   a **resident** credential (`requireResidentKey: true`) and wraps the *password*
   with an AES-GCM key derived by HKDF-SHA256 (`info = 'rabby-biometric-unlock'`)
   from the credential's 64-byte **userHandle**, returned by the authenticator only
   after a user-verified assertion. That works on every platform with a platform
   authenticator, where our PRF path needs Chrome 116+/Safari 18+. The trade-off is
   real: with `prf` the wrapping secret is generated inside the authenticator and
   never leaves it, while a `userHandle` is stored data that the authenticator
   returns (and passkeys, with their user handle, may sync to the cloud), so an
   attacker who obtains it and the ciphertext decrypts the secret offline. Decision
   for a future revision: offer the `userHandle` wrap **only** when `prf` is
   unavailable (L2b), after measuring how many of our phones lack PRF — today the
   priority environment (Chrome Android, and Brave) reports it, and the wallet
   WebViews have no WebAuthn at all.
7. **Auto-lock options**: theirs reach "never" (`useAutoLockOptions`: never, 7 days,
   1 day, 4 h, 1 h) and the stored default is `0` (never) on a desktop extension.
   For a shared phone that default is the wrong end of the spectrum; our one hour
   stands, and R-#248 records the configurable version.

**Do not copy:**

8. **Exporting the vault key into storage while unlocked.** Rabby derives the vault
   key with `@metamask/browser-passworder` and keeps `exportedKey` + `salt` in
   `browser.storage.session` so later writes can re-encrypt without the password
   (`src/background/utils/password.ts`), clearing them on lock. It is convenient for
   an extension (MV3 workers restart), but it keeps key material in storage; our PIN
   is required again for every encryption and nothing is exported. Keep ours.
9. Unverified: the vault KDF parameters live inside `@metamask/browser-passworder`
   (v6.0.0, not vendored in that repo), so they could not be compared offline;
   check the package before drawing conclusions about their work factor.
10. Rabby keeps a "forgot password" path for keyring data saved unencrypted
    (`hasUnencryptedKeyringData`, `src/ui/views/ForgotPassword/`), which only applies
    to some hardware wallets — not applicable to us (our recovery is the 12 words).
