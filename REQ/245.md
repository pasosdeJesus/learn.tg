### 1. Objective

Define the testing strategy for the `pdj-wallet` packages so that tests are fast (<5 min automated), lightweight (<1 GB RAM), and runnable on OpenBSD/adJ. Avoid the 45-minute full E2E suite for wallet-only changes.

### 2. Testing layers

| Layer | Scope | Tool | Time | Memory |
|---|---|---|---|---|
| **Unit (core)** | `pdj-wallet` functions | Vitest | seconds | <1 GB |
| **Unit (next)** | `pdj-wallet-next` hooks/components | Vitest + Testing Library | seconds | <1 GB |
| **Integration (learn.tg)** | `useAuthAddress`, `WalletSelector`, `useWriteContract` | Vitest (existing) | seconds | <1 GB |
| **E2E (minimal)** | In-app wallet flow on dev site | Puppeteer (existing) | ~30 s | <1 GB |
| **Manual (PWA)** | Service worker, offline | Chrome mobile | minutes | — |

### 3. Commands

Both new packages ship their own `vitest.config.ts` (a plain object with an
alias map onto `apps/nextjs/node_modules`), so `pnpm test` is no longer the
blocker it was: the package `test` scripts call
`../../apps/nextjs/node_modules/.bin/vitest` directly and can be run even where
corepack resolves pnpm 11 (the repo is pinned to pnpm 10). Run them from
`apps/nextjs`, which owns the dependency graph:

```bash
cd apps/nextjs

# Core wallet (fast) — verified 2026-09-15: 25 passed, 0 skipped, ~11 s
./node_modules/.bin/vitest run --root ../../packages/pdj-wallet \
  --config ../../packages/pdj-wallet/vitest.config.ts

# Next components (fast) — verified 2026-09-15: 15 passed, 7.5 s
./node_modules/.bin/vitest run --root ../../packages/pdj-wallet-next \
  --config ../../packages/pdj-wallet-next/vitest.config.ts

# Integration in learn.tg (fast) — green: 74 passed / 2 skipped, 44 s
make test-hooks test-components

# Minimal E2E (fast)
CHROME_PATH=/usr/local/bin/chrome make test-e2e-spec SPEC=in-app-wallet

# Offline queue E2E (R-#242, ~3 min: waits for the queue to drain)
CHROME_PATH=/usr/local/bin/chrome make test-e2e-spec SPEC=offline-crossword

# Full E2E (slow, regression only)
CHROME_PATH=/usr/local/bin/chrome make test-e2e
```

Notes (measured 2026-09-15):

- The two blockers of the first draft are **fixed**: the aliases are in
  `apps/nextjs/vitest.config.ts` (`@learn-tg/pdj-wallet-next` before
  `@learn-tg/pdj-wallet`, order matters) and the `useAuthAddress` mocks in
  `lib/hooks/__tests__/useGuideData.test.ts` carry `inAppAddress` /
  `isInAppUnlocked`, so `pnpm typecheck` is clean.
- `packages/rewards` and `packages/gdcluster` still have no `vitest.config.ts`
  and their `package.json` `test` script points to a non-existent file; the same
  fix applies.
- Where the wall time goes: Vitest dominates. `make test-lib` took **56 s** for
  169 tests, of which the run itself reports `tests 281ms`, `environment 35.4s`,
  `setup 5.2s`, `collect 2.1s`. Across the six app targets the actual assertions
  are ~33 s out of 345 s (`environment` ~161 s, `collect` ~66 s). The cost is
  per-test-file environment setup and teardown (jsdom), so the suite is bounded by
  the number of files (79) rather than by the number of tests.

### 5. Minimal E2E spec

**File:** `e2e/specs/in-app-wallet.spec.mjs` — ✅ written and **passing** on the
dev site, which serves this branch since 2026-09-15: the operator's run was 0
failures in 17.7 s (R-#244 §10).

Independent re-runs the same day (agent, while the rest of the suite was idle):

| Run | Result | Time |
|---|---|---|
| 18:42 | ✗ failed at step 3 (60 s timeout waiting for `OK signed in`) right after `make test` finished | 81 s |
| 18:46 | ✅ 0 failures | 12.5 s |
| 18:46 | ✅ 0 failures | 12.2 s |

So the spec is **flaky under load**, not broken: it waits up to 60 s for the SIWE
sign-in and the shared machine was cold when it failed. Re-run it alone before
blaming the code. Each run creates a wallet in the Puppeteer profile, so a fresh
profile is used every time.

Where `/en/test/wallet` is not deployed the spec still self-skips with a clear
message instead of failing.

The steps below are the target. They finish with a real NextAuth **session
cookie** (R-#233 Phase 2 removed the API token), and any Node-side API call must
forward that cookie (as the fixed `verified-city-gate` and `interview-date` specs
now do).

**Steps:**

1. Launch browser.
2. Go to `learn.tg:9001/en/test/wallet`.
3. Create wallet (PIN: `123456`).
4. Get the address.
5. Build SIWE message.
6. Sign with in-app wallet.
7. POST to `/api/auth/callback/credentials`.
8. Verify session cookie set.
9. Go to `/en/profile`.
10. Verify address displayed.

**Time:** ~30 s.

### 6. Test page for manual development

**File:** `app/[lang]/test/wallet/page.tsx` — ✅ created. It drives one single
`useInAppWallet()` instance: create/import with a PIN, unlock, sign in with SIWE,
lock and delete, plus a log area (the recovery phrase is shown once, for
debugging). It uses only data-testid hooks, which is what the E2E spec drives.

**Not for production:** the page renders a "disabled" notice when
`NEXT_PUBLIC_NETWORK === 'celo'`.
