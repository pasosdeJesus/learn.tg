# R-#199: Patrones de Remix IDE y pnpmj aplicables a learn.tg

> *"El sabio oye y aumenta el saber, y el entendido adquiere consejo"* (Proverbios 1:5)

Análisis del código fuente de [Remix Project](https://github.com/ethereum/remix-project)
(`../remix-project`) para identificar patrones de UX y optimización de desarrollo
aplicables a learn.tg.

---

## 1. Patrones de UX — learneth (plataforma educativa de Remix)

`apps/learneth/` es una app React independiente que funciona como plugin iframe dentro
del IDE. Es la fuente más directamente aplicable a learn.tg.

### 1.1 Navegación de cursos

**Patrón**: Hash router + query params para estado de navegación.

```
/ → landing
/home → catálogo de cursos
/list?id=<repo> → syllabus de un curso
/detail?id=<repo>&stepId=<n> → paso actual del tutorial
```

**Aplicable a learn.tg**: learn.tg ya usa Next.js App Router con `[lang]`. No necesita
hash router, pero el patrón de query params (`?course=1&guide=3`) para estado de
navegación dentro de un curso es limpio y bookmarkeable.

### 1.2 Catálogo con filtros

`apps/learneth/src/pages/Home/index.tsx` + `components/FiltersPanel.tsx`:

- **Búsqueda con debounce** (250ms): `useState` + `useEffect` con `setTimeout`
- **Filtros colapsables**: niveles (Beginner/Intermediate/Advanced) + tags extraídos
  dinámicamente de los metadatos de los cursos
- **Indicador de dificultad**: barras de antena (1-3) según nivel
- **Badge de completado**: leído de `localStorage`
- **Sort**: nivel → prioridad → nombre
- **Grid de cards** con imagen, título, descripción, nivel, badge

**Aplicable a learn.tg**: learn.tg tiene listado de cursos en `page.tsx`. Mejoras:
- Debounce en búsqueda (ya tiene search params pero sin debounce)
- Filtros por nivel/dificultad
- Indicador visual de progreso/completado por curso
- `localStorage` para progreso offline (complementa el backend)

### 1.3 Tutorial paso a paso

`apps/learneth/src/pages/StepDetail/index.tsx`:

- **Markdown renderizado**: `react-markdown` + `remark-gfm` + `rehype-raw` + `rehype-sanitize`
- **Bloques de código con botón copiar**: estilizados con header de lenguaje
- **Navegación entre capítulos**: `< >` flechas + "X / N" contador + dropdown de syllabus
- **"Check Answer"**: ejecuta tests automatizados (Solidity unit tests)
- **"Show Answer"**: carga archivo `*_answer.sol` en el editor
- **Animaciones**: `SlideIn` al cambiar de paso
- **Toast notifications**: `react-toastify` para feedback (conectando, cargando, errores)
- **Estados de carga**: `BounceLoader` overlay durante operaciones asíncronas

**Aplicable a learn.tg**: learn.tg renderiza guías en `guide*.md`. Patrones adoptables:
- **"Verificar respuesta"**: en vez de revelar respuesta textual, ejecutar validación
  (quizás contra el backend o contra un contrato)
- **Indicador de paso actual**: "Guía 3 / 8" con flechas de navegación
- **Dropdown de syllabus**: acceso rápido a cualquier guía del curso
- **Animaciones de transición**: entre guías
- **Toast de feedback**: ya tiene `sonner`, consistente

### 1.4 Tracking de progreso

**Patrón**: `localStorage` con key `learneth_completed_tutorials` → `{ [entityId]: true }`.
Se guarda al hacer clic en "Finish tutorial" en el último paso. Se consulta en HomePage
y StepListPage para mostrar badges de completado.

**Aplicable a learn.tg**: learn.tg ya tiene `guidePaid` y `studentCanSubmit` en el
contrato. Podría complementar con `localStorage` para progreso offline/instantáneo
(útil cuando el backend o la wallet están lentos).

### 1.5 Analytics

`trackMatomoEvent` desde `@remix-api` en cada interacción: `load_repo`, `start_workshop`,
`test_step`, `show_answer`, `navigate_next`, etc.

**Aplicable a learn.tg**: learn.tg ya tiene `@vercel/analytics`. Podría agregar
eventos granulares: `course_start`, `guide_complete`, `guide_fail`, `claim_ubi`, etc.

### 1.6 Estructura de workshop (contenido-driven)

Cada workshop/tutorial sigue una convención de directorios:
```
repo/
  config.yml          # metadatos: name, level, tags, language, priority
  README.md           # descripción del curso
  1/
    step.md           # instrucciones del paso
    step_test.sol     # test para validar
    step_answer.sol   # solución (oculta hasta "Show Answer")
    *.sol             # archivos de trabajo
  2/
    ...
```

**Aplicable a learn.tg**: learn.tg ya tiene estructura similar con `guide*.md` +
DB migrations. La diferencia es que Remix es contenido-driven (el workshop vive
en GitHub) y learn.tg es DB-driven (los cursos se crean con migrations SQL).
El enfoque contenido-driven permite iterar cursos sin tocar la app — interesante
para creadores de contenido no-técnicos.

## 2. Patrones de arquitectura — remix-ide

### 2.1 Sistema de plugins

`apps/remix-ide/src/app.ts` — `AppComponent.run()` registra plugins como clases:
```typescript
const editor = new Editor()
const fileManager = new FileManager()
this.engine.register([editor, fileManager, ...])
```

**Perfil de plugin**: cada plugin declara `profile = { name, methods, events, location, icon }`.
La comunicación es RPC: `this.call('pluginName', 'method', ...args)` + eventos `this.emit()`.

**Aplicable a learn.tg**: No necesita un sistema de plugins completo, pero el patrón
de **perfil tipado** para features podría ayudar a organizar módulos: cada feature
(wallet, cursos, verificación, UBI) declara qué expone y qué consume.

### 2.2 Panel system

Paneles fijos (no drag-and-drop): iconos izquierdos → panel lateral, área central,
panel derecho, terminal inferior. `Layout` plugin orquesta visibilidad y resize.

**Aplicable a learn.tg**: learn.tg tiene layout más simple (header + contenido +
footer). Para features futuras (chat, consola, panel de ayuda), el patrón de
paneles colapsables con `localStorage` para persistir estado sería útil.

### 2.3 Registry singleton (DI ligero)

`apps/remix-ide/src/registry.js` — singleton `Registry` con `put/get` para compartir
servicios (editor, fileManager, config) antes de que el engine de plugins esté listo.

**Aplicable a learn.tg**: learn.tg ya tiene `createSiweContext` y `useAuthAddress`.
El patrón Registry podría unificar acceso a servicios core (auth, wallet, DB) sin
prop drilling.

### 2.4 File provider pattern

`FileManager` delega en providers según prefijo de path: `browser://` → FileProvider,
`localhost://` → RemixDProvider, `workspace://` → WorkspaceFileProvider. Un Proxy
transparente (`WorkspaceProviderProxy`) swappea backend sin cambiar referencias.

**Aplicable a learn.tg**: Si learn.tg llegara a soportar múltiples fuentes de
contenido (DB local, GitHub, IPFS), el patrón provider sería ideal.

## 3. Optimización de desarrollo

### 3.1 TypeScript — cambios inmediatos (bajo riesgo, alto impacto)

| Optimización | Archivo | Impacto estimado |
|---|---|---|
| `skipLibCheck: true` | `tsconfig.json` | 2-4x más rápido `tsc --noEmit` |
| `incremental: true` | `tsconfig.json` | re-compilaciones parciales |
| Path aliases para imports | `tsconfig.json` | limpia `../../../` hell |

learn.tg ya tiene `skipLibCheck` en `apps/nextjs/tsconfig.json`. Verificar que
todos los tsconfig del monorepo lo tengan.

### 3.2 Build caching — Nx-style named inputs

Remix usa Nx con `namedInputs` que excluyen `*.spec.*`/`*.test.*`:
```json
"namedInputs": {
  "default": ["{projectRoot}/**/*", "sharedGlobals"],
  "production": ["default", "!{projectRoot}/**/*.spec.*", "!{projectRoot}/**/*.test.*"]
}
```

**Aplicable a learn.tg**: learn.tg no usa Nx, pero turborepo (si se adopta) tiene
`turbo.json` con `"inputs": ["src/**", "!src/**/*.test.ts"]`.

### 3.3 Test sharding por timing histórico

Remix CI (`scripts/plan-shards.js`) usa datos históricos de CircleCI para dividir
tests equitativamente entre nodos paralelos. También re-ejecuta solo tests fallidos.

**Aplicable a learn.tg**: learn.tg tiene 526 tests Next.js + 65 contract tests.
Dividir por timing balancearía la carga. Vitest soporta `--shard=i/n`.

### 3.4 Webpack optimizations (ya resueltas por Next.js)

Next.js maneja code splitting, content hashing, y tree shaking. Los patrones de
Remix (contenthash, TerserPlugin parallel, watchOptions.ignored) ya los provee
Next.js por defecto.

### 3.5 Dynamic imports para dependencias pesadas

Remix usa `await import(...)` para cargar prettier plugins, auth SDKs, y esbuild-wasm
solo cuando se necesitan.

**Aplicable a learn.tg**: `next/dynamic` con `ssr: false` para componentes que usan
librerías pesadas del lado cliente (viem, ethers, @ethereumjs/*). Ya se usa en
algunos lugares — verificar cobertura.

### 3.6 Dev server — watchOptions

Remix webpack configura `watchOptions: { ignored: /node_modules/, aggregateTimeout: 300 }`.
Next.js tiene `watchOptions` en `next.config.js` para optimizar file watching.

### 3.7 CI — cache de dependencias por lockfile checksum

CircleCI: `v1-deps-{{ checksum "yarn.lock" }}`. Con pnpm, usar `pnpm-lock.yaml`.

**Aplicable a learn.tg**: Si se configura CI/CD, cachear `node_modules/.pnpm` con
key basado en hash del lockfile.

4. **"X / N" en navegación de guías** — contador de guía actual en el breadcrumb

### Mediano plazo (1-2 semanas)

6. **Dropdown de syllabus** — acceso rápido a cualquier guía desde la barra de navegación
7. **Transiciones animadas entre guías** — `framer-motion` o CSS transitions

12. **Test sharding en CI** — dividir 526 tests por timing histórico

## 7. Optimización de desarrollo — patrones de pnpmj

`../pnpmj` es un fork de pnpm v10 (~80 paquetes, ~64,000 líneas TypeScript).
Su arquitectura de build y test ofrece patrones directamente aplicables a learn.tg.

### 7.1 esbuild dev mode: sub-second rebuilds

**`pnpm/dev/pd.js`** — script que compila y ejecuta pnpm usando **esbuild** en vez de `tsc`:

```javascript
// Plugin que reescribe @pnpm/* → src/index.ts de cada paquete
build.onResolve({ filter: /@pnpm\// }, ({ path }) => {
  return { path: pathLib.resolve(dirByPackageName[path], 'src', 'index.ts') }
})
// Bundle completo desde src/, sin compilación tsc intermedia
await esbuild.build({ bundle: true, platform: 'node', entryPoints: [...], outfile: '...' })
```

**Resultado**: compilación sub-second vs minutos de `tsc`. El bundle CJS resultante
se ejecuta directamente con `node --enable-source-maps`.

**Aplicable a learn.tg**: para desarrollo local de `@pasosdejesus/m`, `mpdj`, `edr`,
`contract-test` y `apps/nextjs`, crear un script esbuild que:
1. Resuelva `@pasosdejesus/*` → `packages/*/src/index.ts`
2. Bundlee directamente a CJS/ESM
3. Ejecute con source maps

Esto eliminaría el ciclo `tsc → dist → pnpm install → next dev` para cambios en
paquetes del monorepo. Un solo comando: `pnpm dev` con esbuild watch.

### 7.2 TypeScript Project References: compilación incremental

**`__utils__/tsconfig/tsconfig.json`** (base):
```json
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "skipLibCheck": true,
    "strict": true,
    "target": "es2022"
  }
}
```

Cada paquete tiene `tsconfig.json` con `references` manuales a sus dependencias:
```json
{
  "extends": "@pnpm/tsconfig",
  "compilerOptions": { "composite": true, "outDir": "lib", "rootDir": "src" },
  "references": [
    { "path": "../resolving/npm-resolver" },
    { "path": "../fetching/tarball-fetcher" }
  ]
}
```

**Resultados reales en OpenBSD** (Node.js v22, 64k LOC):
| Escenario | `tsc --build` |
|---|---|
| Full build | 2.2s |
| Cache hit | 1.6s |
| Touch 1 paquete (55 líneas) | 2.7s |
| Touch entry point (2198 líneas) | 2.2s |

Solo se recompilan los paquetes modificados y sus dependientes directos.

**Aplicable a learn.tg**: el monorepo `m` (4 paquetes) y `learn.tg` (2 apps) podrían
usar project references. `apps/nextjs` ya usa Next.js con SWC, pero `apps/hardhat`
y los 4 paquetes de `m` compilan con `tsc` → se beneficiarían directamente.

### 7.3 Branch-aware testing

**CI**: `test-branch` ejecuta `pnpm -r _test --filter=...[origin/release/10]` —
solo prueba paquetes cambiados respecto a la rama base. `test-main` corre la suite
completa.

**Aplicable a learn.tg**: con ~600 tests, diferenciar CI en PR (solo tests afectados)
vs main (suite completa). Vitest soporta `--changed` con git.

### 7.4 Shared config como workspace packages

pnpmj centraliza config en paquetes del workspace:
- `__utils__/jest-config/` — preset de Jest compartido
- `__utils__/tsconfig/` — tsconfig base compartido
- `__utils__/prepare/` — helpers de test (`prepare()`, `tempDir()`)

Cada paquete extiende: `"jest": { "preset": "@pnpm/jest-config" }`

**Aplicable a learn.tg**: el monorepo `m` ya tiene `vitest.config.ts` por paquete.
Podría extraerse un `@pasosdejesus/test-config` con preset compartido de vitest:
setup de EDR, timeouts, mocks de DB, etc.

### 7.5 Separación compile-only vs compile

- `compile-only`: solo `tsc --build` (typecheck)
- `compile`: `compile-only` + lint + format

**Aplicable a learn.tg**: separar `typecheck` de `build` completo. En desarrollo,
solo typecheck del paquete modificado; en CI/pre-push, build completo.

### 7.6 Convención `_test` por paquete

Cada `package.json` define `"_test": "jest"`. El root orquesta:
```bash
pnpm run --no-sort --workspace-concurrency=1 -r _test
```

`--workspace-concurrency=1` evita conflictos entre tests que comparten estado
(registry mock, temp dirs).

**Aplicable a learn.tg**: ya se usa `pnpm -r test` en `m`. Agregar `--workspace-concurrency=1`
si hay conflictos de recursos (DB, puertos) entre paquetes.

### 7.7 Temp dirs fuera del proyecto

`__utils__/prepare-temp-dir/` crea directorios temporales en `../pnpm_tmp/`
(fuera del workspace) para evitar que `node_modules` resolution interfiera.

**Aplicable a learn.tg**: los contract tests ya crean providers aislados.
Para tests de integración Next.js que tocan DB, usar `PGDATABASE_TEST`
(ya implementado) con nombre único por test file para paralelismo.

### 7.8 Comparativa: build speed

| Proyecto | LOC | Build tool | Full build | Incremental |
|---|---|---|---|---|
| pnpmj | ~64,000 | tsc --build (project refs) | 2.2s | 1.6-2.7s |
| pnpmj dev | ~64,000 | esbuild bundle | <1s | <0.5s |
| m (4 pkgs) | ~8,000 | tsc (sin refs) | ~5s | ~5s |
| learn.tg apps | ~15,000 | Next.js SWC + tsc | ~30s | ~5s (HMR) |

**Oportunidad**: `m` podría pasar de ~5s a <1s con esbuild dev mode. learn.tg
ya es rápido en HMR gracias a SWC, pero el ciclo completo `cambio en m → build m →
pnpm install → next dev` es lento (~40s). Con esbuild watch + project references,
se reduciría a <5s.
