## 1. Objective

Let the people of the ecosystem talk to each other **inside learn.tg**, privately: churches of a
cluster, clusters with pdJ, and clusters with donors. Messages are confidential by default: they
are **encrypted at rest**, the API never returns plaintext, and the pilot's email/preferences
leftovers from phase 1 are finished here.

## 4. Phase B — internal messaging

### 4.1 Conversation types

| Type | Participants |
|---|---|
| **Cluster** | pastors and delegates of the same cluster |
| **pdJ** | cluster ↔ pdJ (support and verification) |
| **Donor** | cluster ↔ donors (thank-you notes and updates) |
| **GD** | cluster ↔ Global Disciples (future) |

### 4.2 Features

- Threaded conversations (reply in a thread).
- Attachments (documents, images) — reuse the existing upload path, never bypass
  `doc/api-security.md`.
- **Encryption** with the R-#153 pattern (AES-256-GCM with the wallet-derived DEK).
- Read receipts.
- Permission controls: only the participants of a conversation can read or post in it.

### 4.3 Privacy rules (non-negotiable)

- Communications are confidential by default; content is stored **encrypted** and the API
  returns **ciphertext + metadata** (participants, timestamps, status), never plaintext.
- The client decrypts with the wallet-derived key (R-#153). pdJ access, when required, uses the
  ECIES envelope of R-#153.
- No message content, subject or participant identity in logs (doc/api-security.md §1.4).
- Every route authenticates (`authenticateUser`); a conversation is readable only by its
  participants. Run `node bin/audit-api-auth.mjs` after adding routes.

---

## 5. Data model

A `messages`-style table (the phase-2 sketch of #162) with:

- `id`, `sender_id`, `recipient_id` (or a conversation/participants model for the cluster and
  donor threads), `cluster_id`, `subject`, `content` (**ciphertext**), `encrypted`, `read`,
  `parent_id` (threading), `created_at`;
- indexes for the participant/timestamps queries the UI needs;
- the exact shape (single `messages` table vs `conversation` + `message`) is decided at
  implementation, favouring the simplest model that supports the four conversation types.

---

## 6. API endpoints

| Endpoint | Method | Description |
|---|---|---|
| `/api/messages` | GET | conversations of the authenticated user (metadata only) |
| `/api/messages` | POST | send a message (ciphertext) |
| `/api/messages/:id` | GET | one thread (ciphertext + metadata) |
| `/api/messages/:id/read` | PUT | mark as read |
| `/api/notifications/preferences` | GET/PUT | phase-A preferences |

## 7. UI

- A messages entry point in the header (next to the notifications bell) with an unread badge.
- A conversation list and a thread view; the content is decrypted client-side with the
  wallet-derived key.
- The donation flow can offer a thank-you note; the cluster page can offer "message the cluster"
  (participants only).

---

## 8. Acceptance criteria

- [ ] Email notifications are sent when there is an email and the user allowed that type
- [ ] Users can set and change their notification preferences
- [ ] A participant can start a conversation of the four types available in their role
- [ ] Messages are stored encrypted and the API never returns plaintext
- [ ] Threads work (reply shows under its parent)
- [ ] Read receipts work
- [ ] Permissions hold: a non-participant cannot read or post (401/403), and the audit stays at
      `0 failed`
- [ ] Attachments respect the upload rules (no path traversal, size/type limits)

---

## 9. Out of scope

- WhatsApp notifications, group messaging beyond the four types, message search and message
  reactions (kept in #162's original "Out of Scope").

---

## 10. Testing plan

- **Unit/API tests**: permissions (participant vs outsider), ciphertext round-trip, preferences,
  read receipts.
- **Privacy tests**: the API response contains no plaintext; logs carry no content.
- **E2E on the development site**: two wallets exchange a message in a cluster conversation and
  the unread badge updates.
- **Docs**: `doc/api-security.md` (any new route), and a short section in the user-facing guide
  if the flow ships to students.

---

## 11. Risks

- Getting the encryption wrong is worse than not shipping messaging: no plaintext at rest, no
  plaintext in responses, no content in logs, keys derived from the wallet (R-#153).
- A conversation model that does not fit the cluster/donor threads would be reworked later:
  decide the data model before building the UI.
- Email can leak information: it is opt-in, and the content of a private message is never put in
  an email body.
