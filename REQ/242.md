# R-#242: Offline Crossword


**Link:** https://github.com/pasosdeJesus/learn.tg/issues/242

sync on reconnect and the "pending sync" indicator are implemented, the puzzle was

**Created:** 2026-09-15
**Type:** Feature
**Priority:** High

### 1. Objective

Allow users to complete crosswords offline. Answers are saved locally in a queue and synced when connection returns.

### 2. Changes

**Current state:** `app/[lang]/[pathPrefix]/[pathSuffix]/test/page.tsx` already saves crossword state in `localStorage`
(`crossword-state-<address>`) and restores it when the same course+guide is opened
again, **without touching the network** — that is what makes the puzzle loadable
offline today. It is cleared after a successful submission.

**Implemented (nombres reales):**

- Cache crossword data (grid, placements) after first fetch: ✅ already done via
  `localStorage` (kept as is; moving it to IndexedDB would gain nothing for a
  single puzzle and would break the restore-on-return behaviour).
- Load from IndexedDB if offline: ✅ satisfied by the `localStorage` restore above.
- Queue submissions in IndexedDB: ✅ `lib/offline-queue-db.ts` (store `pending` of
  `learn-tg-offline`, with an in-memory fallback), reached through
  `lib/hooks/useOfflineQueue.ts`.
- Sync the queue when online: ✅ `useOfflineQueue()` replays the queue on mount
  and whenever the browser reports it is back online, in page context so the
  NextAuth session cookie authorizes the replay (R-#233 Phase 2: no token is
  persisted). Failed attempts are counted and dropped after five
  (`MAX_ATTEMPTS`), 5xx/network errors are retried.
- Evaluate migration from `next-pwa` to `serwist` if `next-pwa` has problems: ⬜
  pending (nothing has failed so far; the build check is R-#244 step 5).

**Module actually used instead of `lib/offline/queue.ts`:**

```typescript
// lib/offline-queue-db.ts
interface PendingSubmission {
  id: string
  url: string          // e.g. '/api/check-crossword'
  body: unknown        // the payload the page tried to POST
  createdAt: number
  attempts: number
}

export async function enqueueSubmission(url: string, body: unknown): Promise<PendingSubmission>
export async function listPending(): Promise<PendingSubmission[]>
export async function pendingCount(): Promise<number>
export async function dequeueSubmission(id: string): Promise<void>
export async function registerAttempt(id: string): Promise<void>
```

Storing the URL + payload (instead of a typed crossword record) keeps the queue
reusable for any future offline mutation.

**Update `test/page.tsx`:** ✅ done

- On submit, if the request fails **without** an HTTP response (offline), the
  answer is queued and the page shows "Sin conexión: tu respuesta quedó guardada
y se enviará sola cuando vuelvas a tener conexión."
- While answers are queued, the page shows a persistent `N respuesta(s)
guardada(s) sin conexión, pendiente(s) de enviar.` notice (`data-testid="offline-pending"`).
- 4xx/5xx answers keep the previous error behaviour (they are not queued).

**New hook:** `lib/hooks/useOfflineQueue.ts` (not `useOfflineSync`) — listens for
the online state, replays the queue and exposes `pending`.

### 3. Acceptance criteria

- [x] Crossword data cached after first fetch (`localStorage`, existing behaviour).
- [x] Crossword loadable offline (restored from `localStorage` without network).
- [x] Submission offline queues (`lib/offline-queue-db.ts`).
- [x] Queue syncs when online (`useOfflineQueue` replays on mount and on the
  `online` event).
- [x] User sees "Pending sync" indicator (`offlineQueued` warning +
  `data-testid="offline-pending"` counter).
- [ ] Rewards processed after sync (the server does it on replay; the manual
test below can be run on the dev site as it is, because the queue does not need
the service worker — `doc/pdj-wallet-testing.md` §5).
- [x] E2E test of the queue: `e2e/specs/offline-crossword.spec.mjs` fills the
crossword at `/en/gdcluster/guide1/test`, submits it offline, checks the
`offline-pending` indicator, verifies the entry is in the `pending` store of
IndexedDB and waits for the queue to drain when the connection returns.
**Measured 2026-09-15: 0 failures in 40 s** (dev site, `learn.tg:9001`). It does
**not** assert the reward: the grid is filled with placeholder letters, so the
replay is a wrong answer the server rejects (that is the point: the queue is
replayed). The reward path stays in the manual test above and in
`e2e/specs/donate-course-real.spec.mjs` / `pastor-journey.spec.mjs` (online).
- [x] Decision documented on `next-pwa` vs `serwist` (doc/pwa-developer-guide.md, last section).

### 5. Testing plan

**Unit tests** (new): ✅

- `lib/__tests__/offline-queue-db.test.ts` (5): queue, order, dequeue, attempt
  counting and drop after five.
- `lib/hooks/__tests__/useOfflineQueue.test.ts` (5): queue, replay, keep on 500,
  keep with no network, and no send while offline.

**Manual tests** (documented in `doc/pdj-wallet-testing.md` §5 — it needs no
service worker, so a dev server is enough):

1. Open `learn.tg:9001/en/gdcluster/guide1/test` online.
2. Turn off connection.
3. Complete the crossword.
4. Submit: see "Pending sync" message.
5. Turn on connection.
6. Verify submission synced and rewards processed.

**Commands:**

```bash
cd apps/nextjs && make test-hooks                                   # unit (queue + hook)
CHROME_PATH=/usr/local/bin/chrome make test-e2e-spec SPEC=offline-crossword
```

**Measured 2026-09-15:** the E2E spec passes in **40 s** (dev site); the unit
layer is `offline-queue-db` (5) + `useOfflineQueue` (5). The offline *reload* of
the page is not part of it on purpose: on a dev server there is no service worker
caching the HTML, so that half belongs to R-#240 (production build).

**Time:** seconds (unit) + ~40 s (E2E). **Memory:** <1 GB.
