# R-#206: Reduce build time

The production build (`next build --webpack`) on adJ/OpenBSD takes ~43 min.
Root cause: **SWC runs in WASM** on OpenBSD (no native `@next/swc-*` bindings
for `openbsd/x64`), ~10-50x slower than native SWC. Webpack + SWC-WASM is the
bottleneck. Memory is secondary (needs `--max-old-space-size=14336` to avoid
GC thrash into swap).

Measured on this VM: `next build --webpack` (Next 16.3.1) → "Compiled with
warnings in 43.1min", 57 static pages, ~90 API routes.

## Ideas (ordered by impact/effort)

### 1. Build on Linux CI, deploy artifacts to OpenBSD (highest impact)

OpenBSD only needs to *run* (`next start`), not compile. Run `next build` on a
Linux runner (GitLab CI already exists, or GitHub Actions) where SWC is native
→ build drops from ~43 min to ~5-10 min. Deploy `.next/` + `public/` +
`node_modules/` (or better, `output: 'standalone'`, which packages the minimum).

- [ ] Add `output: 'standalone'` to `next.config.ts`.
- [ ] Add a Linux build job to `.gitlab-ci.yml` (or `.github/workflows/ci.yml`).
- [ ] Deploy the standalone artifact to the OpenBSD host (`next start`).

### 2. Reduce the transpilation/minification graph

Build time is proportional to the graph size (~90 API routes, heavy SDKs:
`ethers`, `viem`, `ox`, `@goodsdks/*`).

- [ ] Lazy-load (`dynamic()`) heavy SDKs used only in some routes.
- [ ] Split API routes that import crypto SDKs (each `route.ts` is an entry).
- [ ] Review `lib/engines.ts` / `lib/credentials.ts` crypto imports.

### 3. Webpack / SWC tuning (cheap)

- [ ] Fix the broken filesystem cache: build logs
  `Caching failed for pack: Can't resolve 'next.config.compiled.js'`.
- [ ] Try `swcMinify: false` (Terser, native JS) — may be faster than SWC-WASM
  for minification on OpenBSD.
- [ ] `experimental.workerThreads` / webpack `parallel` for multi-core.

### 4. Long-term

- [ ] Native SWC for OpenBSD: build `swc` (Rust) natively and patch Next.js to
  use it (community effort; removes the root bottleneck).
- [ ] Split into packages/motors to reduce the per-build graph (complements #1/#2) — see "Package split plan" below.

## Package split plan

Based on a source study of `apps/nextjs/` (69 API routes, ~30 `lib/` modules),
`packages/`, `apps/hardhat/`, and `servidor/`.

### Current state

- `apps/nextjs/` — monolith: UI + API + business logic. Heavy SDKs (`ethers`,
  `viem`, `@goodsdks/*`, `@selfxyz/*`) are pulled into most route entries.
- `apps/hardhat/` — Solidity on Celo (unchanged).
- `servidor/` — Rails (MSIP + cor1440_gen) admin/content backend (unchanged).
- `packages/mr519/` — the only extracted package today: an "engine"
  (`DynamicForm` + server routes) registered via a **hardcoded** entry in
  `lib/engines.ts`.

### Domain boundaries

Group `lib/` modules + API routes into bounded contexts:

| Package | `lib/` modules | API routes | Heavy SDKs |
|---|---|---|---|
| `@learn-tg/rewards` | `crypto`, `credentials`, `deployments`, `donate-utils`, `sle-rate`, `pastor-bonus`, `abis/` | `check-crossword`, `claim-celo-ubi`, `add-donation`, `scholarship`, `credential/*`, `ubi-report*` | `ethers`, `viem`, `@goodsdks/*` |
| `@learn-tg/scoring` | `scores`, `score-rules`, `leaderboard-queries`, `metrics/queries`, `user-transactions`, `premium-pricing` | `leaderboard`, `transparency`, `update-scores`, `user-transactions/*`, `metrics*` | — |
| `@learn-tg/content` | `guide-utils`, `remarkFillInTheBlank`, `course-access`, `format` | `guide`, `crossword`, `guide-status`, `courses/*` | `unified`/`remark` |
| `@learn-tg/admin` | `admin-auth`, `admin-fetch`, `caldav`, `ability`, `gd-utils`, `gd-cluster-routing` | `admin/*`, `church*`, `cluster*`, `verification/*`, `self-verify`, `user/*` | — |
| `@learn-tg/core` | `fetchHelpers`, `utils`, `config`, `mobile-detection`, `deeplink`, `metrics-server`, `authenticateUser`, `db/` | shared infra | `kysely`, `pg` |
| `@learn-tg/ui` | `components/*` (shared + `ui/`) | — | `radix`, `recharts` |

Each package ships precompiled `dist/` and is consumed via `exports`. Precompiled
code is NOT re-transpiled by Next.js SWC-WASM — the main build bottleneck.

### How `m` helps

1. **Monorepo model**: `m`'s `packages/*` + `apps/*` layout (each with `dist/`
   + `exports`, `tsc -b` build) is the template for learn.tg's split.
2. **Auto-discovery pattern**: `m`'s `registerCommands` + `mEngine: true`
   (plugin auto-discovery from `package.json`) is the model to replace the
   hardcoded `lib/engines.ts` — each `@learn-tg/*` engine self-registers via
   `registerEngine`, and the app discovers them automatically. **The registry
   itself must be extracted and exported** (see "Infrastructure to export").
3. **Shared modules already in `m`** (do not reimplement in learn.tg):
   `@pasosdejesus/m/i18n`, `@pasosdejesus/m/wba`, `@pasosdejesus/m/test-utils`,
   `@pasosdejesus/m/shadcn-components/*`, `@pasosdejesus/m/debug`,
   `@pasosdejesus/m/e2e`, `@pasosdejesus/m/blockchain/deployments`.
4. **Hooks for cross-cutting logic**: `m-extensions/` + `registerHook`
   (already used for `course_id` in credentials) keeps package-local side
   effects out of the packages themselves.
5. **Tooling**: `m:create` scaffolds the apps/packages layout; `contract-test`
   + `edr` run Hardhat tests on OpenBSD; `tsc -b` + Makefile patterns from `m`.

### Infrastructure to export (engine registry + auto-discovery)

The engine registry must NOT stay inside `apps/nextjs/lib/engines.ts`. Extract
it into a shared, exported package so engine packages can depend on it without
reaching into the app internals:

- **`@learn-tg/engine`** — exports `registerEngine()` / `getEngineHandler()` and
  a `loadEngines()` auto-discovery loader (reads `package.json`, imports
  packages marked `learnTgEngine: true` or `@learn-tg/*`, which self-register
  on import).
- Mirrors `@pasosdejesus/m/plugin` (`registerCommands`/`getPluginCommands` +
  `mEngine: true`) — the same pattern, already proven in `m`.
- Document it in a `doc/` guide (e.g. `doc/creating-a-package.md`): how to
  create a `@learn-tg/*` package, mark it, self-register, and consume it via
  `exports`.

**Coupling to fix today**: `packages/mr519/src/server/register.ts` imports
`registerEngine` from `@/lib/engines` (an app-internal alias), and
`lib/engines.ts` hardcodes `mr519`/`mr519-admin` with `@ts-ignore` workarounds
for `link:` packages lacking their own `node_modules`.

### Migration steps (incremental, keep the app green at each step)

1. Extract `@learn-tg/core` first (pure helpers, no crypto) — lowest risk.
2. Extract the engine registry into `@learn-tg/engine` (export
   `registerEngine`/`getEngineHandler` + `loadEngines`) and write
   `doc/creating-a-package.md`; repoint `mr519` at it.
3. Replace the hardcoded `lib/engines.ts` list with auto-discovery, so `mr519`
   and future engines self-register.
4. Extract `@learn-tg/rewards` (crypto) — biggest build win; precompile and
   consume `dist/`; lazy-load the SDKs only in reward routes.
5. Extract `scoring`, `content`, `admin` as they stabilize.
6. Move cross-package side effects to `m-extensions/` hooks.

### Additional acceptance criteria

- [ ] Each `@learn-tg/*` package ships `dist/` and is consumed via `exports`.
- [ ] `@learn-tg/engine` exports `registerEngine`/`getEngineHandler`/`loadEngines`,
  and `doc/creating-a-package.md` documents how to create a package that uses it.
- [ ] `lib/engines.ts` no longer hardcodes engine names.
- [ ] The main `next build` graph shrinks (fewer route entries import crypto SDKs directly).
