# R-#266: InApp wallet can be created in Sepolia and used in Mainnet

InApp wallet can be created in Sepolia and used in Mainnet

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/266

---

**Created:** 2026-09-27
**Status:** Implemented (2026-09-27) — the in-app wallet **can change networks**: the same key
works on Celo Sepolia and on Celo, so a wallet created on the development site pays on
production. Deployment is pending (this VM does not deploy) as is re-running the E2E that
presses the buy button against the deployed site.
**Type:** Bug fix / Wallet
**Priority:** High — it prevents paying on production for whoever created the wallet on the
development site.
**Dependencies:** https://github.com/pasosdeJesus/learn.tg/issues/236 (provider events and

## 1. Report

While paying for the **Global Disciples** course on **production** (https://learn.tg, Celo
mainnet 42220) with the **in-app** wallet created on the development site (Celo Sepolia
11142220), the operator got the viem error (and the same when donating to course 103, the
donation modal was fixed later, see §3):

```
The current chain of the wallet (id: 11142220) does not match
the target chain for the transaction (id: 42220 – Celo)
```

`ChainMismatchError` (`viem/utils/chain/assertCurrentChain.js`) comes from comparing
`client.chain.id` with the `eth_chainId` the wallet answers. The message does not say what to
do and, worse, there was no way to fix it from the interface: the in-app wallet was **bound to
the network it was created with**.

## 2. Cause (four pieces)

1. **The wallet could not change networks.** `getInAppWalletProvider()` took `record.chain`
   when creating the wallet and `wallet_switchEthereumChain` answered **4902** ("unknown
   chain") for any other network. That was an explicit decision of
   https://github.com/pasosdeJesus/learn.tg/issues/236; this requirement changes it, because
   the private key is the same on any network: the only thing that changes is the network the
   wallet **declares**.
2. **The provider did not see the change.** `getInAppWalletProvider()` captured `info` once,
   when it was built, so even after changing the network `eth_chainId`/`net_version` would
   have kept answering the old network and viem would fail again **in the same payment**.
3. **The SIWE `chainId` and the payment chain came from different sources.** The SIWE message
   took it from `NEXT_PUBLIC_NETWORK` **falling back to `celoSepolia`** (`lib/in-app-siwe.ts`)
   while the server validates `IS_PRODUCTION ? 42220 : 11142220`
   (`app/api/auth/auth-options.ts:129`, and `IS_PRODUCTION` comes from `NEXT_PUBLIC_AUTH_URL`,
   `packages/rewards/src/lib/config.ts`). They are two independent variables: in production
   with `NEXT_PUBLIC_NETWORK` undefined the client would send 11142220 and the server would
   reject it with `siwe_wrong_network`, and the same the other way around in any environment
   where the two do not match. The message now uses the app `chainId`, which is exactly what
   the server expects.
4. **No modal did a network pre-flight** before signing: viem's raw error reached the student.

## 3. Changes

**Engine, `packages/pdj-wallet`**

- `src/wallet.ts:382` — `setWalletChain(chain, storage?)`: changes the network and persists the
  record. It **does not touch the encrypted secret**: the biometric seal only covers
  `cipher`/`kdf`, so the key and the fingerprint unlock stay valid. If the wallet is unlocked,
  it refreshes the in-memory session so the provider sees the new network without unlocking
  again.
- `src/provider.ts:225` — `wallet_switchEthereumChain` maps the requested `chainId` to one of
  the two known networks (`CHAIN_IDS`, `src/types.ts:3`), really switches, emits
  **`chainChanged`** and returns `null`. A network we do not know still answers **4902**
  (EIP-1193).
- `src/provider.ts:245` — `wallet_addEthereumChain` accepts the two networks (they are already
  "added"); injected wallets use it to complete the switch.
- `src/provider.ts:208` — `currentInfo()`: the network is read **on every request**, not once
  when the provider is built (cause piece 2).

**Application, `apps/nextjs`**

- `lib/app-chain.ts:11` — `getAppChain()`: **a single source** for the app network (Celo in
  production, Celo Sepolia in development).
- `lib/ensure-chain.ts:55` — `ensureWalletChain()` + `WrongChainError`: an `eth_chainId` check
  before signing; it asks an external wallet to switch, adds the chain when the wallet does not
  know it, and only when the switch is **not** applied does it throw the typed error (with
  `isInApp` so something useful can be said).
- `components/CheckoutModal.tsx:324` — `handlePay()` does the pre-flight and then pays; the
  message shows in the error block (`data-testid="checkout-error"`) with ES/EN texts
  (`wrongChain`, `wrongChainInApp`). It is declared **before** `if (!isOpen) return null`: a
  hook after that early return changes the number of hooks between renders.
- `lib/hooks/useWallet.ts:10` and `lib/in-app-siwe.ts:37` — use `getAppChain()` instead of
  repeating `IS_PRODUCTION ? celo : celoSepolia` and `CHAIN_IDS[NEXT_PUBLIC_NETWORK]`.
- `components/DonateModal.tsx` — the donation modal was the pending path: it kept the raw
  viem error (2026-09-27/28, operator report: donating to course 103 on production with a
  wallet created on the development site failed with "The current chain of the wallet
  (id: 11142220) does not match the target chain for the transaction (id: 42220 - Celo)").
  It now calls `ensureWalletChain` before both the ERC-20 and the native CELO paths and
  shows `wrongChain` / `wrongChainInApp` (ES/EN) when the switch does not apply.

## 4. Acceptance criteria

- [x] An in-app wallet created on Celo Sepolia can **switch** to Celo from the payment
      (`wallet_switchEthereumChain`) and finish paying.
- [x] The switch is **persisted**: after a reload, the wallet is still on the new network.
- [x] `eth_chainId` and `net_version` answer the new network **on the same provider** already
      created (otherwise viem fails again in the immediate payment).
- [x] `chainChanged` is emitted on a change and is **not** emitted when the wallet was already
      on that network.
- [x] The secret is **not** invalidated: the same password unlocks the wallet after the switch
      and the biometric seal still covers only `cipher`/`kdf`.
- [x] An unknown network still answers **4902**, both in `wallet_switchEthereumChain` and in
      `wallet_addEthereumChain`.
- [x] The `chainId` of the SIWE message is the app's (what the server validates), not the one
      the wallet declares: signing does not depend on the network, so a wallet created on
      Sepolia can sign in on production.
- [x] If the network switch is not applied, the student sees a clear message (ES/EN) and **not**
      viem's raw error — in **both** modals: `CheckoutModal` (premium purchase) and
      `DonateModal` (2026-09-27/28: donations used to keep the raw `ChainMismatchError`).
- [x] The pre-flight **does not get in the way** of the normal path: when the wallet is already
      on the app network (the case of the development site) no switch is requested and paying
      keeps working exactly as before.
- [x] Deployed and the E2E that presses the buy button re-run against the deployed site (see
      §5 and §6): `premium-course-checkout` and `in-app-wallet-payments` pass with 0 failures
      on `https://learn.tg:9001` (2026-09-28).

## 6. Pending / notes

- **Deployment.** Until the operator deploys, a wallet created on the development site does
  **not** pay on production: one has to use an external wallet on Celo or create the wallet on
  the production site. With this deployed, that is no longer needed.
- **E2E.** The specs run against the **deployed** development site (`https://learn.tg:9001`),
  so they cannot cover this change before the deployment: it is worth re-running
  `make test-e2e-two-courses` (it presses the `CheckoutModal` buy button) and, for the same
  path with the in-app wallet, `make test-e2e-spec SPEC=in-app-wallet-payments`. The real
  mismatch cannot be reproduced: the development site runs on the same network the wallet is
  created with, so the pre-flight ends up "doing nothing" (which is precisely what has to be
  confirmed as still working). They can also run against the local instance
  (`doc/environments.md`, "The E2E specs also run against the local instance"), but that needs
  the full stack (Rails + PostgreSQL) and this VM has a single CPU: it was not run in this
  session, and that is why the payment verification rests on the integration test of §5.
- **Scope.** Only the two networks of `CHAIN_IDS` are accepted (Celo and Celo Sepolia). Another
  network is still "unknown" (4902); adding a third one means adding an entry to `CHAIN_IDS`
  and to `getAppChain()`.
- **Donations.** `DonateModal.tsx` used to attempt the network switch with a `catch` that
  ignored the failure, so the raw `ChainMismatchError` reached the donor (report of
  2026-09-27/28: donating to course 103 from production with a wallet created on the
  development site). It now uses `ensureWalletChain` like the checkout, for both the ERC-20
  and the native CELO paths; the 2026-09-19 read failures ("Unsupported method: eth_call")
  are covered by the `in-app-wallet-payments` spec that passes against the deployed site.
