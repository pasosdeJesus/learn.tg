## 1. Objective

Close the two usability gaps the operator found after using the in-app wallet on a
phone end to end, **without** weakening the security model:

1. **Creation asks for the password but never offers the device gesture.** The
   password is the backup and the 12 words the recovery, but a phone user expects
   the flow to offer the fingerprint once (R-#246 L2) while the password is still
   fresh, instead of discovering the option later in the dialog.
2. **The panel is a long single scroll** (address, balances, receive, send,
   collectibles). On a phone, reaching "Send" means scrolling past everything and
   the sections compete for attention.

## 2. What the operator reported (phone session, 2026-09-21)

**Works (kept as evidence for R-#244/R-#246):** created the wallet, claimed CELO
UBI, donated 0.1 CELO from the Lensenia page, earned USDT and SLEARN with a
crossword, and used the SLEARN to buy the Global Disciples course.

**To improve:**

| # | Finding | Decision |
|---|---------|----------|
| 1 | Creating the wallet asks for the password but not for the fingerprint | Ask for both during creation **when the device can verify the user and PRF is available**; a device without it keeps the password-only path (no dead end) |
| 2 | The panel would be clearer with tabs | Tabs **Balances · Receive · Send · Collectibles**, with the address and its copy button kept above the tabs |

## 3. Implementation

### 3.1 Fingerprint during creation

- `components/WalletDialog.tsx` keeps the password used to create the wallet in a
  ref (never in a rendered value) until the backup is confirmed, then, if the
  device supports it and the user left the option on, calls
  `enableBiometric(password)` before signing in.
- The backup step shows the option (default on) with the same wording family as
  R-#246 (`biometricHint`), plus an explicit "the password still works" note.
- If the gesture is cancelled or the device reports `no-prf`/`no-webauthn`, the
  wallet is created anyway and the password remains the only unlock: the failure is
  reported, not fatal.
- The password held in the ref is cleared when the dialog closes and after the
  enrollment attempt.

### 3.2 Panel with tabs

- `components/WalletPanel.tsx` renders the existing sections inside
  `Tabs`/`TabsContent` from `@pasosdejesus/m/shadcn-components/ui/tabs`, in order
  **Balances**, **Receive**, **Send**, **Collectibles** (`wallet-panel-tab-*`).
- The address card and Copy stay above the tabs (they belong to every tab).
- Each section keeps its current `data-testid`s, so the existing unit and E2E
  tests only have to open the tab they exercise.
- Collectibles keep loading on demand (no request while their tab is closed).
- i18n: the tab labels are added in English and Spanish.

## 4. Acceptance criteria

- [x] On a device with a platform authenticator and PRF, creating a wallet offers
      the fingerprint in the same flow, and the wallet unlocks with the gesture
      afterwards; the password still unlocks it.
- [x] On a device without WebAuthn/PRF the option is not offered and creation
      finishes with the password alone (no error shown for the missing feature).
- [x] Cancelling the gesture during creation does not lose the wallet: the flow
      still signs in with the password.
- [x] The password kept for the enrollment is cleared when the dialog closes.
- [x] The panel shows four tabs (Balances, Receive, Send, Collectibles), the
      address card above them, and every existing testid inside its tab.
- [x] Collectibles are only requested when their tab is opened.
- [x] Unit tests updated (`WalletPanel`, `WalletDialog`) and green; `make type`
      green.
