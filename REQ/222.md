# R-#222: Double connect required in Rabby (mobile)

When connecting with **Rabby** (mobile / in-app browser) the user has to repeat
the flow **twice** to become authenticated: (1) connect, (2) sign, (3) confirm —
after the first round the UI still shows "Connect Wallet" and everything has to
be repeated.

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/222

---

## Symptom

1. The user opens learn.tg in the Rabby browser and taps "Connect Wallet".
2. Rabby asks to connect → sign the SIWE message → confirm (3 steps).
3. The page reloads but **there is still no session** (the button shows
   "Connect Wallet" again).
4. Repeating the 3 steps → this time the user stays connected.

## Current flow (`components/ConnectWalletButton.tsx`, `handleConnect`)

1. `eth_chainId` (no prompt) → if different: `wallet_switchEthereumChain` →
   fallback `wallet_addEthereumChain` (https://github.com/pasosdeJesus/learn.tg/issues/216
   covers the Rabby extension case).
2. `eth_requestAccounts` → `accounts[0]` → `getAddress` (EIP-55).
3. `eth_chainId` again → numeric chainId.
4. `GET /api/auth/csrf` → nonce.
5. SIWE `personal_sign` (Rabby: confirm).
6. `POST /api/auth/callback/credentials` (csrfToken+message+signature).
7. Success → `localStorage` `sessionAddress` + `authToken` → `location.reload()`.
   (The `authToken` was removed in R-#233 Phase 2; only `sessionAddress` remains.)

## Hypotheses to verify (they required device logs)

- **H1 — `eth_requestAccounts` resolves before Rabby "unlocks"**: the first call
  returns `accounts: []` (or throws) and the flow dies in
  `getAddress(undefined)` → generic "Connection failed" error; the second attempt
  (wallet already "connected") does return the account. Rabby mobile is known to
  require the second request after the in-app approval.
- **H2 — The session is not established after the first reload**: the callback
  POST answers `ok` but the session cookie (NextAuth JWT) is not readable after
  the reload (mount race / Secure cookie behind nginx `:9001`) → the button stays
  on "Connect Wallet"; the second round "repairs" the cookie.
- **H3 — The callback POST fails the first time** (non-ok status) with Rabby
  because of some detail of the re-signed SIWE message (nonce rotated between the
  CSRF fetch and the callback), and works when retried with a fresh nonce.

## Acceptance criteria

- [x] A single round (connect → sign → confirm) leaves the session active.
- [x] The button shows "Disconnect" after the reload, with no second round.
- [x] Regression: MetaMask mobile/extension and Rabby still connect in one round.

## Resolution (2026-09-14) — cold session, not an extra Rabby prompt

**Confirmed cause:** it was not a second Rabby prompt (H1 ruled out: no 300 ms
retry and no evidence of `accounts: []`). The symptom came from the session/token
layer (H2+H3 family):

- The API token **was the CSRF and rotated on every login**, so the second round
  "repaired" the token stored in `localStorage` (which is why the second attempt
  did work).
- After a client-side navigation the NextAuth session can be **"cold"**
  ([bug #5719](https://github.com/nextauthjs/next-auth/discussions/5719)) while
  the address is already in `localStorage`: the page queried `/api/scholarship`
  **anonymously** and the card showed "cooldown" and 0 % progress with a
  freshly connected wallet.

**Changes applied:**

- **Dedicated random API token** (256 bits) instead of the CSRF, with
  `authenticateUser` authenticating first through the session cookie (`sub` =
  wallet) and using the DB token only as a legacy fallback (`378470c`,
  `5567ea4`; https://github.com/pasosdeJesus/learn.tg/issues/227 phase 1). Both
  the token and the fallback were removed in R-#233 Phase 2.
- Wallet taken from `session?.address || address || localStorage
  (learn.tg.sessionAddress)` (`lib/hooks/useCourse.ts:43-48`,
  `app/[lang]/page.tsx:102-110`): when there are signs of a session the page
  **waits** for the address/token instead of querying anonymously; progress and
  scholarship are never queried without a wallet.
- `components/CourseStatistics.tsx:117` requires `canSubmit === false` (no longer
  `!canSubmit`) to render "cooldown", so an unknown state is not shown as a
  cooldown. Commit `02a189b`.

**Verification:**

- **Field (owner, 2026-09-14):** with a **brand-new** wallet, a single connection
  (connect → sign → confirm) and **without reconnecting**, the owner completed
  the profile, won the crossword, claimed UBI and paid for a course.
- **E2E** `e2e/specs/fresh-wallet-first-connect.spec.mjs` (documented in
  `doc/e2e-testing.md:197`): a new wallet authenticated by SIWE in one round
  (`:113`) plus an assertion that the page does not query `/api/scholarship`
  anonymously and does not show a false "cooldown" (`:179-187`).
