# R-#222: Doble connect requerido en Rabby (móvil)

Al conectar con **Rabby** (móvil / navegador integrado), el usuario debe
repetir el flujo **dos veces** para quedar autenticado: (1) conectar,
(2) firmar, (3) confirmar — tras la primera ronda la UI sigue mostrando
"Connect Wallet" y hay que repetir todo.

**Enlace:** https://github.com/pasosdeJesus/learn.tg/issues/222

---

## Síntoma

1. El usuario abre learn.tg en el navegador de Rabby y pulsa "Connect Wallet".
2. Rabby pide conectar → firmar el mensaje SIWE → confirmar (3 pasos).
3. La página recarga pero **sigue sin sesión** (el botón vuelve a mostrar
   "Connect Wallet").
4. Repetir los 3 pasos → esta vez sí queda conectado.

## Flujo actual (`components/ConnectWalletButton.tsx`, `handleConnect`)

1. `eth_chainId` (sin prompt) → si difiere: `wallet_switchEthereumChain` →
   fallback `wallet_addEthereumChain` (https://github.com/pasosdeJesus/learn.tg/issues/216
   cubre el caso Rabby extension).
2. `eth_requestAccounts` → `accounts[0]` → `getAddress` (EIP-55).
3. `eth_chainId` de nuevo → chainId numérico.
4. `GET /api/auth/csrf` → nonce.
5. SIWE `personal_sign` (Rabby: confirmar).
6. `POST /api/auth/callback/credentials` (csrfToken+message+signature).
7. Éxito → `localStorage` `sessionAddress` + `authToken` → `location.reload()`.

## Hipótesis a verificar (requieren logs del dispositivo)

- **H1 — `eth_requestAccounts` resuelve antes de que Rabby "desbloquee"**:
  la primera llamada devuelve `accounts: []` (o lanza) y el flujo muere en
  `getAddress(undefined)` → error genérico "Connection failed"; el segundo
  intento (billetera ya "conectada") sí devuelve la cuenta. Rabby móvil es
  conocido por requerir el segundo request tras el approve en la app.
- **H2 — La sesión no queda establecida tras el primer reload**: el POST del
  callback responde `ok` pero la cookie de sesión (NextAuth JWT) no es legible
  al recargar (race de montaje / cookie Secure tras nginx `:9001`) → el botón
  sigue en "Connect Wallet"; la segunda ronda "repara" la cookie.
- **H3 — El POST del callback falla la primera vez** (status no-ok) con Rabby
  por algún detalle del mensaje SIWE re-firmado (nonce rotado entre el CSRF
  fetch y el callback) y funciona al reintentar con un nonce fresco.

## Criterios de aceptación

- [x] Una sola ronda (conectar → firmar → confirmar) deja la sesión activa.
- [x] El botón muestra "Disconnect" tras el reload, sin segunda ronda.
- [x] Regresión: MetaMask móvil/extensión y Rabby siguen conectando en una ronda.

## Resolución (2026-09-14) — sesión fría, no un prompt extra de Rabby

**Causa confirmada:** no era un segundo prompt de Rabby (H1 descartada: no hay
reintento de 300 ms ni evidencia de `accounts: []`). El síntoma venía de la capa
de sesión/token (clase H2+H3):

- El token de API era el **CSRF y se rotaba en cada login**, así que la segunda
  ronda "reparaba" el token guardado en `localStorage` (de ahí que el segundo
  intento sí funcionara).
- Tras una navegación cliente la sesión de NextAuth puede venir **"fría"**
  ([bug #5719](https://github.com/nextauthjs/next-auth/discussions/5719))
  mientras el address ya está en `localStorage`: la página consultaba
  `/api/scholarship` **en anónimo** y la tarjeta mostraba "cooldown" y 0% de
  avance con una billetera recién conectada.

**Cambios aplicados:**

- Token de API **dedicado y aleatorio** (256 bits) en vez del CSRF, con
  `authenticateUser` que autentica primero por cookie de sesión (`sub` =
  billetera) y usa el token de BD solo como respaldo legacy (`378470c`,
  `5567ea4`; https://github.com/pasosdeJesus/learn.tg/issues/227 fase 1).
- Billetera tomada de `session?.address || address || localStorage
  (learn.tg.sessionAddress)` (`lib/hooks/useCourse.ts:43-48`,
  `app/[lang]/page.tsx:102-110`): si hay indicios de sesión se **espera** al
  address/token en lugar de consultar en anónimo; nunca se consulta
  avance/beca sin billetera.
- `components/CourseStatistics.tsx:117` exige `canSubmit === false` (ya no
  `!canSubmit`) para pintar "cooldown", de modo que el estado desconocido no se
  muestra como cooldown. Commit `02a189b`.

**Verificación:**

- **Campo (propietario, 2026-09-14):** con una billetera **totalmente nueva**,
  una sola conexión (conectar → firmar → confirmar) y **sin reconectar**,
  completó el perfil, ganó el crucigrama, reclamó UBI y pagó un curso.
- **E2E** `e2e/specs/fresh-wallet-first-connect.spec.mjs` (documentado en
  `doc/e2e-testing.md:197`): billetera nueva autenticada por SIWE en una ronda
  (`:113`) y aserción de que la página no consulta `/api/scholarship` en
  anónimo ni muestra "cooldown" falso (`:179-187`).
