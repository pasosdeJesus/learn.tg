# R-#222: Doble connect requerido en Rabby (móvil)

Al conectar con **Rabby** (móvil / navegador integrado), el usuario debe
repetir el flujo **dos veces** para quedar autenticado: (1) conectar,
(2) firmar, (3) confirmar — tras la primera ronda la UI sigue mostrando
"Connect Wallet" y hay que repetir todo.

**Enlace:** https://github.com/pasosdeJesus/learn.tg/issues/222

---

## Síntoma

1. El usuario abre learn.tg en el navegador de Rabby y pulsa "Connect Wallet".
2. Rabby pide conectar → firmar el mensaje SIWE → confirmar (3 pasos).
3. La página recarga pero **sigue sin sesión** (el botón vuelve a mostrar
   "Connect Wallet").
4. Repetir los 3 pasos → esta vez sí queda conectado.

## Flujo actual (`components/ConnectWalletButton.tsx`, `handleConnect`)

1. `eth_chainId` (sin prompt) → si difiere: `wallet_switchEthereumChain` →
   fallback `wallet_addEthereumChain` (https://github.com/pasosdeJesus/learn.tg/issues/216
   cubre el caso Rabby extension).
2. `eth_requestAccounts` → `accounts[0]` → `getAddress` (EIP-55).
3. `eth_chainId` de nuevo → chainId numérico.
4. `GET /api/auth/csrf` → nonce.
5. SIWE `personal_sign` (Rabby: confirmar).
6. `POST /api/auth/callback/credentials` (csrfToken+message+signature).
7. Éxito → `localStorage` `sessionAddress` + `authToken` → `location.reload()`.

## Hipótesis a verificar (requieren logs del dispositivo)

- **H1 — `eth_requestAccounts` resuelve antes de que Rabby "desbloquee"**:
  la primera llamada devuelve `accounts: []` (o lanza) y el flujo muere en
  `getAddress(undefined)` → error genérico "Connection failed"; el segundo
  intento (billetera ya "conectada") sí devuelve la cuenta. Rabby móvil es
  conocido por requerir el segundo request tras el approve en la app.
- **H2 — La sesión no queda establecida tras el primer reload**: el POST del
  callback responde `ok` pero la cookie de sesión (NextAuth JWT) no es legible
  al recargar (race de montaje / cookie Secure tras nginx `:9001`) → el botón
  sigue en "Connect Wallet"; la segunda ronda "repara" la cookie.
- **H3 — El POST del callback falla la primera vez** (status no-ok) con Rabby
  por algún detalle del mensaje SIWE re-firmado (nonce rotado entre el CSRF
  fetch y el callback) y funciona al reintentar con un nonce fresco.

## Fix propuesto (a confirmar con el diagnóstico)

1. **H1**: tras `eth_requestAccounts`, si `!accounts?.length`, esperar ~300ms y
   reintentar una vez antes de fallar (race de desbloqueo de Rabby).
2. **H2**: usar el estado de `useAuthAddress` (session ∥ localStorage) para
   decidir el botón tras el reload — verificar por qué `showAsConnected` es
   false tras la primera ronda (¿`isWalletAvailable`?).
3. **H3**: si el callback no es `ok`, registrar el cuerpo de la respuesta
   (hoy se descarta) para distinguir 403/CSRF de otros errores.
