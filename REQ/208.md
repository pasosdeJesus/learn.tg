# R-#208: E2E hydration regression — ConnectWalletButton not rendered on Next 16 dev server

The Puppeteer E2E specs (`full-flow.spec.mjs` and the new
`pastor-journey.spec.mjs`) fail at their first step: the `Connect Wallet`
button never appears. `ConnectWalletButton` is a client component that is no
longer hydrating on the dev server after the Next.js 16 upgrade (REQ/205).

---

**Created:** 2026-08-18
**Status:** Resuelto (hidratación + SIWE corregidos en nginx; ver Resolution)

**Related:** REQ/205 (Next.js 16.3.1 upgrade), REQ/207 (vitest 3.2.7)

---

## Symptom

```
── Step 1: Pastor connects wallet ──
✗ Connect Wallet not visible
```

- New spec `apps/nextjs/e2e/specs/pastor-journey.spec.mjs` (pastor Sierra
  Leona) fails at `Connect Wallet not visible`.
- `full-flow.spec.mjs` — which previously passed — now fails at the **same**
  point. This proves the regression is in the dev server, not in the new spec.
- In Puppeteer, `buttonCount: 0` at +5s, +15s and +30s after
  `domcontentloaded`. The page text never contains `Connect Wallet` /
  `Conectar Billetera`.
- The dev server `https://learn.tg:9001` already serves **Next.js 16.3.1**.
- **Confirmado:** el dev server corre en modo dev con `--webpack` (de lo
  contrario no arrancaría). Descartada la hipótesis "falta `--webpack`".

## Root cause (hypothesis, ranked)

`ConnectWalletButton` returns `null` until `useAuthAddress()` reports
`isWalletCheckComplete` (set in a `useEffect` after inspecting
`window.ethereum`). If the client bundle does **not** hydrate, that effect
never runs and the button never paints. Candidate causes:

1. **Compilación on-demand fría y lenta (SWC-WASM) en `next dev`.** Con
   Webpack + SWC-WASM (~10-50× más lento), la primera petición a `/en` compila
   los chunks del cliente bajo demanda. El HTML (SSR) llega, pero el JS del
   cliente puede tardar **minutos** en compilarse/servirse. El test sólo espera
   30 s → la hidratación aún no ocurrió. Coincide con que el fallo apareció
   tras redeplegar (caché `.next` fría).
2. **Error JS durante la hidratación** (React 19 la silencia/reintenta):
   p. ej. `useSession` fuera de `SessionProvider`, un módulo que lanza, o
   mismatch de hidratación ("Text content does not match…").
3. **Chunk del cliente roto/incompleto por SWC-WASM** (el workaround de
   REQ/205 §2.7 deja `node_modules/next/wasm/@next/swc-wasm-nodejs/` vacío si
   no se re-aplica).
4. **Regresión silenciosa de efectos** documentada en Next 16 (ver Research).

## Resolution (confirmed root cause)

The regression was caused by the **nginx reverse proxy in front of the dev
server**, not by the Next.js 16 upgrade itself. Two independent nginx
misconfigurations were fixed, plus one spec race:

1. **HMR WebSocket upgrade not forwarded** — the `@learntgdes` proxy location
   lacked the WebSocket upgrade directives, so `wss://…/_next/hmr` returned
   `HTTP/1.1 200` (the HTML page) instead of `101 Switching Protocols`. In
   Next 16 the dev client blocks hydration when the HMR socket fails, so
   `useAuthAddress`'s `useEffect` never ran and `ConnectWalletButton` stayed
   `null`. Evidence: a raw handshake probe returned `200 OK` with
   `Server: nginx/1.28.0`; after the fix it returns `101` plus the
   `sync`/`isrManifest` HMR messages.

   **Fix (nginx):**
   ```nginx
   location @learntgdes {
       proxy_http_version 1.1;
       proxy_set_header Upgrade $http_upgrade;
       proxy_set_header Connection "upgrade";
       # ...
   }
   ```

2. **SIWE domain mismatch (surfaced once hydration worked)** — the client
   signs `domain = window.location.host` (= `learn.tg:9001`), but `authorize()`
   verifies against `new URL('https://' + host).host`. With
   `proxy_set_header Host $host` (port stripped), the server saw `learn.tg`
   while the client sent `learn.tg:9001` → `siwe` `DOMAIN_MISMATCH` →
   `401 CredentialsSignin`. Reproduced via HTTP: `domain=learn.tg → 200`,
   `domain=learn.tg:9001 → 401`.

   **Fix (nginx):** preserve the port:
   ```nginx
   proxy_set_header Host $http_host;   # instead of $host
   ```

3. **Spec navigation race** — `pastor-journey.spec.mjs` (and `full-flow`) poll
   with `page.evaluate` right after clicking Connect, but `ConnectWalletButton`
   calls `window.location.reload()` on SIWE success, destroying the execution
   context. Wrapped the poll in `try/catch` to tolerate the reload.

After the nginx fixes, `pastor-journey.spec.mjs` passes Steps 1-4
(connect → profile → verifier → UBI). Step 5 still fails: the verifier flow
grants a profile score of 77, but the spec expects > 90 (the 44 SLEARN bonus
threshold) — a separate spec-expectation issue, not a hydration regression.

## Research (internet)

Patrón "componente `'use client'` que devuelve `null` hasta un `useEffect` y
nunca re-renderiza" es una clase de fallo conocida en Next 16 / React 19:

- **vercel/next.js#95932** — `useEffect` no se ejecuta en dev (Turbopack);
  el mismo código funciona en `next build && next start`. Efecto saltado
  silenciosamente tras el límite Server→Client.
- **vercel/next.js#94075** — React nunca hidrata (el HTML aparece, pero
  `useEffect`/`onClick` no), el loader de Turbopack bloquea en un HMR WS
  fallido; funciona en 16.0.10, roto en 16.2.x. Totalmente silencioso.
- **React 19** — recuperación de mismatch más silenciosa ("parece funcionar
  pero sin handlers/estado"); `suppressHydrationWarning` en `<html>`/`<body>`
  enmascara regresiones de efectos.
- **next-auth** — `useSession()` devuelve `status:'loading'` en el primer
  render tras reload; si el efecto/fetch se salta, el componente queda vacío
  (issues #7666, #13353).

Puesto que aquí se usa **webpack** (no Turbopack), #95932/#94075 aplican sólo
indirectamente; el factor dominante pasa a ser la **compilación SWC-WASM lenta
en dev** y/o un error de hidratación silenciado.

## Diagnostic plan (decision tree)

### A. Instrumentar el spec para capturar TODO lo que ocurre en el navegador

Añadir a `pastor-journey.spec.mjs` (o a un spec de diagnóstico mínimo) antes
del `goto`:

```js
const events = []
page.on('console', m => events.push(`[console.${m.type()}] ${m.text()}`))
page.on('pageerror', e => events.push(`[pageerror] ${e.message}`))
page.on('requestfailed', r => events.push(`[requestfailed] ${r.url()} ${r.failure()?.errorText}`))
page.on('response', r => {
  if (r.request().resourceType() === 'script' && !r.ok())
    events.push(`[script ${r.status()}] ${r.url()}`)
})
```

Dump `events` al final del loop de espera de Step 1. Además, registrar
timing de hidratación:

```js
const probe = await page.evaluate(() => ({
  hasEthereum: typeof window.ethereum !== 'undefined',
  hasNextData: typeof window.__NEXT_DATA__ !== 'undefined',
  btnCount: document.querySelectorAll('button').length,
}))
```

### B. Interpretar según lo observado

| Observación en `events`/probe | Conclusión | Acción |
|---|---|---|
| `[console.info] … useAuthAddress: checking wallet availability` | Hidratación SÍ corre | El problema es timing/mock, no hidratación; revisar por qué no aparece el texto |
| `[console.info] … useAuthAddress: no window.ethereum provider` | `window.ethereum` ausente antes de hidratar | Revisar inyección del mock (`evaluateOnNewDocument`) |
| `[pageerror] … Text content does not match…` / hydration | Mismatch de hidratación React 19 | Aislar el componente que no matchea |
| `[pageerror] … useSession must be wrapped in SessionProvider` | Error de límite cliente/next-auth | Corregir wiring de providers |
| `[requestfailed]` o `[script 4xx/5xx]` en `.js` | Chunk no compilado/servido (SWC-WASM) | Re-aplicar `make swc-wasm` en el dev server; verificar 200 en chunks |
| **Sólo** `[script …]` con 200 pero tarda **mucho** (>30s) | Compilación on-demand fría lenta | Pre-calentar o cambiar estrategia (C) |
| **Silencio total** (sin console/pageerror/requestfailed) | Regresión silenciosa de efectos | Probar `next build && next start`, o pin Next a 16.0.10 |

### C. Regla de decisión principal (causa más probable)

La primera señal a medir es **cuánto tarda en llegar y ejecutarse el chunk del
cliente** y si los logs `useAuthAddress:` aparecen en `console`:

1. Si los logs aparecen **tarde** (más de ~30-60s) → es **compilación
   on-demand fría lenta (SWC-WASM)**. Mitigaciones, en orden:
   - Pre-calentar el dev server antes del E2E (`curl -k https://learn.tg:9001/en`
     y esperar a que el chunk compile; repetir una vez).
   - Subir el timeout del spec (o esperar por el log de hidratación, no por
     `bodyLen`).
   - Para E2E estable, correr contra **build de producción**
     (`next build --webpack` + `next start`), no contra `next dev`.
2. Si hay `[pageerror]`/`[script 4xx]` → corregir el error puntual.
3. Si hay **silencio total** con chunks 200 → regresión de efectos; probar
   `next build && next start` para aislar dev vs prod, y pin de versión.

### D. Pasos de ejecución

1. Añadir la instrumentación (A) al spec y reejecutar contra el dev server:
   ```sh
   cd apps/nextjs
   CHROME_PATH=/usr/local/bin/chrome IPDES=learn.tg PUERTOPRU=9001 CHAIN_ID=11142220 \
     node e2e/specs/pastor-journey.spec.mjs
   ```
2. Volcar `events` y clasificar con la tabla (B).
3. Aplicar la mitigación de (C) y re-ejecutar.
4. Re-ejecutar la suite completa: `CHROME_PATH=/usr/local/bin/chrome make test-e2e`.
5. Ajustar campos de perfil del spec si no mapean exacto (`registration`,
   `denomination`, `position_israel_gaza`, `church_relationship`, etc.).
6. Actualizar `doc/e2e-testing.md` con el spec nuevo, la causa raíz confirmada
   y el workaround.
