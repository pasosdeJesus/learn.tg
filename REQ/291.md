# R-#291: "Build and serve" path — technical courses (adJ, full stack, learn.tg) as the on-ramp to the mission

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/291
**Created:** 2026-10-28
**Status:** Proposal — path, catalogue and phasing. Only F0 is actionable today (a pilot of the
`Web 2.5` course, whose module 1 is already written and executable in `m`). The data model of §7,
the mission course of §5 (B1) and the indicators of §8 need operator decisions before any schema
change. The Spanish name of the path is **"Ruta construir y servir"**; it will keep growing because
it also covers courses about adJ and the full stack, with learn.tg as the worked example.
**Type:** Product / content / data model / documentation
**Priority:** High — it is the first revenue line that is not a donation, and the only one that also
produces maintainers for the platform. Without it the project depends on someone else's calendar.
**Related:** https://github.com/pasosdeJesus/learn.tg/issues/277 (improve the Web3 & UBI course and
the interface-as-manual), https://github.com/pasosdeJesus/learn.tg/issues/265 (several wallets per
user; purchases already record the paying wallet),
https://github.com/pasosdeJesus/learn.tg/issues/289 (transaction ledger),
https://github.com/pasosdeJesus/learn.tg/issues/273 (cluster funds),
https://github.com/pasosdeJesus/learn.tg/issues/161 (GD 10%), and in `m`:

## 1. Objective

1. Publish a **numbered path** of courses with a public page: what each one teaches, for whom,
   what it costs, what it proves, and what comes next.
2. Sell **accompaniment** (cohort, correction, certificate, response time) over material that stays
   free, starting with the technical courses about adJ, the full stack and Web 2.5.
3. Use the technical courses as an **explicit, optional invitation** to the mission courses (Jesus,
   discipleship, mission) — never as bait, and never as a requirement to obtain a certificate.
4. Turn the end of each technical course into a **real contribution** to the platform (a `REQ`
   resolved, a port, a missing test), so the path produces maintainers, not subscribers.
5. Keep learn.tg as **the worked example**: every technical course reads and touches the codebase
   that runs this platform.

## 2. Why a path and not a course

- **Sustainability without a begging cycle.** `m` and learn.tg are built by someone whose hours have
  to be paid. A paid cohort pays them without turning the mission into a fundraising campaign:
  the trade of Acts 18:3, not a collection plate at the door.
- **The relay is the real product.** OpenBSD/adJ + PostgreSQL + Next.js + contracts + wallets is a
  rare combination; whoever learns it here can maintain this platform. No other academy can offer
  that, and it is the only answer to "what happens when the current maintainer stops".
- **The example is already in the repository.** The `m` tutorial
  (`doc/tutorial-contracts-openbsd-1/{en,es}.md`) was written *and made executable*
  (`packages/m/src/tasks/tutorial-contracts-openbsd-1.test.ts`): it reads the files from the
  document and runs every step. A course chapter can be held to the same standard.
- **The audience of a technical course is high-trust and scarce.** Someone who pays to learn Celo
  contracts in Spanish in 2026 is not a casual visitor; treating them as a lead instead of a
  colleague wastes the best audience the project has.

## 3. Principles (non-negotiable)

1. **The software and its documentation stay free.** The code is ISC, the docs are public, the
   tutorial is public and executable. What is sold is time and correction.
2. **The technical course stands on its own.** Complete syllabus, exercises, feedback and
   certificate without ever mentioning the mission courses. If it needs the hook to justify itself,
   it is not a course.
3. **The invitation is explicit, optional and at the end.** One session (or one page): "this is
   why we build this, and here is the next course if you want it". No surprise, no pressure.
4. **Solidarity.** Local currency where possible, scholarships, and a free seat for whoever serves
   without resources (pastors, teachers, students in difficulty). A brother left out for lack of
   money is the model failing, not a business decision.
5. **The course is extracted from the docs, not from a second corpus.** Every session that needs
   material the docs do not have is a signal to write the doc — and then the session.

## 4. The path

| Step | Name | For whom | Paid? | Outcome | Proof |
|---|---|---|---|---|---|
| 1 | **Build** (technical courses, §5 C1–C4) | developers and sysadmins who want to ship | yes (cohort) | a deployed app and a merged contribution | certificate + the contribution link |
| 2 | **Serve** (B1) | anyone, including step-1 graduates | no / solidarity | a biblical frame for the work and its purpose | participation, not a credential |
| 3 | **Keep it alive** (maintainer track) | step-1 graduates who contributed | no | a named contributor with a small area | access to the review queue, `REQ` assignments |

The hinge between 1 and 2 is a **capstone**: the last deliverable of a technical course is a real
contribution (fix a bug, port a patch, write the missing test), and the last session presents
step 2 for whoever wants it. Step 3 is not a course: it is what happens when someone keeps showing
up.

| C4 | **How learn.tg is built** | C2/C3 graduates, funders, curious | 3 sessions | reading the platform: funds, clusters, reputation, scholarships, credentials, the transaction ledger; one small contribution | this repository (`ARCHITECTURE.md`, `doc/`, `REQ/`), REQ 289, 273, 265, 161 |
| B1 | **Jesus, discipleship and mission** | everyone | 4–6 sessions | a biblical frame for technology, work and service | **to write** — the bottleneck of the whole path |

Notes:

- C3 is the one that can start now: module 1 (compile, test and sign, six files, no Hardhat) is
  written, in two languages, and verified by a test.
- C4 is "the example and a half": it is the only course where the student reads a real, funded,
  running platform instead of a toy. It is also the natural bridge between the technical and the
  missional, because it shows *what the platform is for*.
- B1 is intentionally last. A weak course about Jesus damages the mission far more than a missing
  one; it needs a reviewer with theological training and a written script before it opens.

## 6. What exists today (measured 2026-10-28)

| Piece | Where | State |
|---|---|---|
| Course purchase | `premium_course_usuario` (`usuario_id`, `course_id`, `transaction_hash`, `usdt_amount_paid`, `slearn_amount_paid`, `expires_at`, `billetera`) | works; access is derived from this row |
| Payment | `transaction` with `type = 'pay-course'` and `metadata.processPaymentHash`; `wallet` column | works, ledger policy in REQ 289 |
| Course identity | `course_id` references `cor1440_gen_proyectofinanciero` | administrative coupling (see §7) |
| Progress | `guide_usuario` per guide (per account, REQ 265) | works per guide, no roll-up per course |
| Credential | `credential_emission` (`course_id`, `token_id`, `billetera`, `revoked_at`) + the SBT contract | works per course |
| Authoring | `scripts/create-course.sh`, `doc/how-to-create-a-course.md`, `doc/guide-writing.md` | works for free/premium courses with scholarships and a badge |
| Scholarships | vault + SLEARN/USDT flows | works (REQ 289 has the ledger rules) |

Gaps this requirement has to close:

- no **path** entity (nothing says C2 comes after C1, or that B1 exists);
- no **completion roll-up** per course, so "finished the course" cannot be shown or certified;
- no **free/paid/public** attributes on the course itself: the paid fact is a purchase row, the
  free fact is its absence;
- `expires_at` has no written meaning (is a course a subscription or a one-time purchase?);
- a credential proves a course, not a path;
- no public catalogue that explains the path, the price and the next step.

## 7. Proposed data model (additive, to refine)

Keep `premium_course_usuario` as the **purchase** record and add the **access/enrollment** fact, so
a scholarship, a gift or a solidarity seat does not have to fake a payment:

1. `course_meta(course_id, slug, level, language, free boolean, published boolean, price_usdt,
   price_slearn, hours)` — the attributes the catalogue needs, keyed by the existing `course_id`
   while it still points to `cor1440_gen_proyectofinanciero`.
2. `course_path(id, slug, name, position)` + `course_path_step(path_id, course_id, position,
   required boolean)`.
3. `course_enrollment(usuario_id, course_id, source, granted_by, granted_at, expires_at)` where
   `source ∈ {purchase, scholarship, gift, solidarity, staff}`. Purchases keep writing
   `premium_course_usuario`; the enrollment row is what access checks read.
4. `course_completion(usuario_id, course_id, percent, completed_at)` computed from `guide_usuario`
   and refreshed on the last guide; the credential keeps being the on-chain proof.
5. `course_path_completion(usuario_id, path_id, completed_at, credential_token_id)` for the path
   credential, if the path is worth a badge of its own.

Everything is additive: no migration rewrites `premium_course_usuario` or `credential_emission`.
Whether the `cor1440_gen_proyectofinanciero` coupling stays is question 1 of §12.

## 8. Indicators (what "it worked" means)

| Dimension | Indicator | Why |
|---|---|---|
| **Sustain** | hours taught vs. hours paid by the cohort | if it does not pay the hours, it is a donation channel with extra steps |
| **Learning** | completion rate per course (finished guides / enrolled) | a paid course nobody finishes is a refund request |
| **Relay** | graduates who open a `REQ`, a PR or a port within 90 days | the point of the path (step 3) |
| **Mission** | **voluntary** enrolment in B1, and retention | the funnel's real measure |
| **Not a KPI** | conversion from A to B | optimizing it would degrade the technical course and the invitation |

## 9. Phases

| Phase | Scope | Gate |
|---|---|---|
| **F0** | Pilot C3 with the existing material (module 1 is executable). Manual cohort, manual certificate, no schema change. Instrument completion by hand. | the cohort pays the hours |
| **F1** | `course_meta` + `published`/`free` + the path page (`/courses`); C1 and C2 drafted from the `m` docs; both languages. | catalogue live and honest about what is free |
| **F2** | `course_enrollment`, `course_completion`, `course_path*`; the capstone protocol (contribution merged ⇒ course completed); path credential. | completion is computed, not remembered |
| **F3** | B1 written, reviewed by a theology reviewer, opened with solidarity seats; step-3 maintainer track named. | reviewer approves the script |

## 10. Acceptance criteria (draft)

- [ ] A public page lists the path, each course (audience, length, price, deliverable) and what
  comes next, in Spanish and English.
- [ ] A course's completion is computed from `guide_usuario` and shown to the learner.
- [ ] A paid enrolment records the paying wallet (already true) and a granted enrolment records who
  and why (`source`, `granted_by`).
- [ ] The certificate of a course is not conditioned on enrolling in B1.
- [ ] Each technical course closes with a contribution that is merged or linked from the course.
- [ ] Every technical course has at least one **executable** example, verified by a test, the way
  `m`'s tutorial is (`tutorial-contracts-openbsd-1`).
- [ ] The operator has a small dashboard with the five indicators of §8.
- [ ] `expires_at` has a written meaning and the UI states it.

## 11. Risks

| Risk | Mitigation |
|---|---|
| **Extractive framing** ("funnel" heard as bait) | the technical course never mentions B1 until the last session; the certificate is unconditional |
| **KPI drift** | conversion is explicitly not a KPI (§8); the dashboard shows the other four |
| **Theological bottleneck** | B1 opens only with a written script and a reviewer; better one good course than five weak ones |
| **Support load** | capped cohort, fixed office hours, a public channel for the rest |
| **Coupling to `cor1440_gen_proyectofinanciero`** | additive `course_meta` first; decouple only if a second consumer appears |
| **Two languages forever** | every course is written in one language and translated before publishing; the path is not published half-translated |
| **The course steals the engineering time it is meant to fund** | fixed calendar: cohorts in the gaps of the release ritual, no cohort during a migration |

## 12. Open questions for the operator

1. Keep `cor1440_gen_proyectofinanciero` as the course identity (funding/administration) and add
   `course_meta`, or introduce a proper `course` table and leave the administrative link as a FK?
2. B1: enrolment only, or also a credential? (A credential for a mission course has reputational
   and doctrinal consequences.)
3. Prices: USDT only, or local currency with manual reconciliation?
4. Is `expires_at` a subscription to a library or the validity of one course?
5. Who reviews B1, and what is the doctrinal bar (the `m` framework in
   `m/packages/mpdj/ia/alineacion_mejor_marco_operativo.md` is the natural reference)?
6. Does step 3 (maintainer track) grant a named role in the platform, and what does it unlock?

## 13. Out of scope

- Video production tooling and live-classroom features inside the app (a meeting tool is fine).
- The payment flow itself (works: `POST /api/courses/premium/purchase`).
- Reward and scholarship mechanics (REQ 289, REQ 273, REQ 161).
- The `m` side of the same idea (a `m`-repo requirement about *teaching* `m`), except as a source of
  material.
