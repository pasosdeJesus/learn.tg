# F-#295: Crossword submission hangs, the scholarship is never paid and the PWA claims "offline"

## 1. Symptom

A student solves a guide's crossword with the correct answers, presses submit and the button stays
in **"Sending..."** forever. On mobile, after a while the app says **"You are offline. Your answer
was saved and will be sent automatically when the connection returns."** even though the device is
online. No scholarship arrives.

Measured on the development site (2026-11-03, guide 2 of the Global Disciples course): the server
log shows the guide **is** credited —

```
[credential] course=10 user=1166 completed=2/6 wallet=0xd0d6…
[credential] Not at 100% yet: 2/6
```

— and nothing after it, so the request never reaches the end.

## 2. Diagnosis

The order inside `packages/rewards/src/routes/check-crossword.ts` is: validate the answers →
credit the guide (`guide_usuario.points = 1`) → attempt the SBT → read the course vault and pay the
scholarship → respond. The credit and the SBT section run (that is the log above); the hang happens
in the **vault read / scholarship payment**, which are chain calls with no deadline. If the RPC does
not answer, the `await` never settles, the HTTP response is never sent and the browser keeps
"Sending".

The false "offline" message comes from the client: when the request does not come back, the
offline queue assumes a lost connection and stores the answer for later. It should only do that
when the device is really offline (`navigator.onLine === false`) or the failure is a network error,
not when the server is slow.

## 3. What to change

### 3.1 `packages/rewards/src/routes/check-crossword.ts`

- Every chain client uses a deadline: `http(rpcUrl, { timeout: 15000, retryCount: 1 })` (done).
- The scholarship section must be **bounded and non-fatal**: if it times out or fails, the route
  still answers `200` with the guide credited and `scholarship: 'pending'`, and records the reason
  (`scholarship_timeout` / `scholarship_failed`) in the guide event so the operator can retry.
- The response must state clearly which part happened: `points`, `scholarship`, and a message the
  page can show ("guide counted; the scholarship will be retried").

### 3.2 Client

- Only enter the offline queue when the device reports offline or `fetch` fails with a network
  error; a timeout or a 5xx from the site must be shown as an error with a retry, never as
  "you are offline".
- The submit button must always leave the "Sending..." state (success, error or queued).

> **Where the client lives:** the submission and its queue are in this repository, not in the
> `m` package: `apps/web/app/[lang]/[pathPrefix]/[pathSuffix]/test/page.tsx` (submit handler)
> and `apps/web/lib/offline-submit.ts` (the rule, unit-tested). `useOfflineQueue` only replays
> what the page decides to store.

### 3.3 Tests (the gap that let this ship)

- `check-crossword` has **no engine test today**: only `apps/web/app/api/check-crossword/__tests__`
  with mocks. Add engine tests with an injected client:
  1. chain answers → scholarship paid, `200` with amounts;
  2. chain hangs → the route answers within the deadline, guide credited, `scholarship: 'pending'`;
  3. a wrong answer → no credit, no payment.
- Client: a test that a *slow* server does not enqueue the answer as offline, and that a real
  network failure does.

> Implemented: `packages/rewards/src/routes/__tests__/check-crossword.test.ts` (4 cases through
> `deps.crosswordChain`) and `apps/web/lib/__tests__/offline-submit.test.ts`.

## 4. Acceptance criteria

- [x] Submitting a correct crossword always ends: success or a visible error, never "Sending".
      The page posts with a 30 s timeout, the route answers within the chain deadline, and the
      button leaves the state in `finally`.
- [x] With the RPC unreachable, the guide counts and the response arrives in less than ~20 s.
      Every chain call has a 15 s deadline (`withDeadline`) and the section is non-fatal.
- [x] The scholarship, when it cannot be paid, is reported as pending and can be retried.
      `scholarship: 'pending'`, a `userevent` `scholarship_pending` with
      `scholarship_timeout` / `scholarship_failed`, and the page shows it as a warning.
- [x] "You are offline" only appears with the device actually offline.
      `shouldQueueSubmission` queues only when `navigator.onLine` is false or the failure never
      reached the server (`ERR_NETWORK` / `ERR_INTERNET_DISCONNECTED`); a timeout or a 4xx/5xx is
      an error with the submit button available again.
- [x] Engine tests for the three paths above and the client test exist and pass.

## 5. Evidence and how to reproduce

- Dev site, Global Disciples course, guide 2, correct answers, mobile: button stuck, later the
  offline banner; server log as quoted.
- Reproduce with the RPC pointing to an unreachable host (`NEXT_PUBLIC_RPC_URL=https://127.0.0.1:1`)
  and submit a guide: today the request hangs; after the fix it must answer.
