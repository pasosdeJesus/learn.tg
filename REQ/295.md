# F-#295: Crossword submission hangs, the scholarship is never paid and the PWA claims "offline"

## 1. Symptom

A student solves a guide's crossword with the correct answers, presses submit and the button stays
in **"Sending..."** forever. On mobile, after a while the app says **"You are offline. Your answer
was saved and will be sent automatically when the connection returns."** even though the device is
online. No scholarship arrives.

Measured on the development site (2026-11-03, guide 2 of the Global Disciples course): the server
log shows the guide **is** credited —

```
[credential] course=10 user=1166 completed=2/6 wallet=0xd0d6…
[credential] Not at 100% yet: 2/6
```

— and nothing after it, so the request never reaches the end.

## 2. Diagnosis

The order inside `packages/rewards/src/routes/check-crossword.ts` is: validate the answers →
credit the guide (`guide_usuario.points = 1`) → attempt the SBT → read the course vault and pay the
scholarship → respond. The credit and the SBT section run (that is the log above); the hang happens
in the **vault read / scholarship payment**, which are chain calls with no deadline. If the RPC does
not answer, the `await` never settles, the HTTP response is never sent and the browser keeps
"Sending".

The false "offline" message comes from the client: when the request does not come back, the
offline queue assumes a lost connection and stores the answer for later. It should only do that
when the device is really offline (`navigator.onLine === false`) or the failure is a network error,
not when the server is slow.

## 3. What to change

### 3.1 `packages/rewards/src/routes/check-crossword.ts`

- Every chain client uses a deadline: `http(rpcUrl, { timeout: 15000, retryCount: 1 })`, and every
  chain call is wrapped in `withDeadline` (default 15 s, `SCHOLARSHIP_TIMEOUT_MS` overrides it):
  `getActiveVault`, `vaults`, `studentCanSubmit`, both `getStudentGuideStatus` reads and
  `payScholarship`.
- The scholarship section must be **bounded and non-fatal**: if it times out or fails, the route
  still answers `200` with the guide credited and `scholarship: 'pending'`, and records the reason
  (`scholarship_timeout` / `scholarship_failed`) in the guide event so the operator can retry.
- The response must state clearly which part happened: `points`, `scholarship`, and a message the
  page can show ("guide counted; the scholarship will be retried").
- The GD 10% routing (`routeToClusterFunds`, two transfers that wait for receipts) is bounded too
  (`SCHOLARSHIP_ROUTING_TIMEOUT_MS`, default 20 s); on failure it is left in `admin_solves`
  (`gd_cluster_transfer`) for retry and the response still reports the scholarship. This hole was
  found by running the E2E on the GD course (see §7).
- The chain pieces are injectable (`deps.crosswordChain`, `CrosswordChainDeps`) so the engine tests
  can hang the payment without an RPC; production builds the viem clients from the environment.

### 3.2 Client

- Only enter the offline queue when the device reports offline or `fetch` fails with a network
  error; a timeout or a 5xx from the site must be shown as an error with a retry, never as
  "you are offline".
- The submit button must always leave the "Sending..." state (success, error or queued).

> **Where the client lives:** the submission and its queue are in this repository, not in the
> `m` package: `apps/web/app/[lang]/[pathPrefix]/[pathSuffix]/test/page.tsx` (submit handler)
> and `apps/web/lib/offline-submit.ts` (the rule, unit-tested). `useOfflineQueue` only replays
> what the page decides to store.

### 3.3 Tests (the gap that let this ship)

- `check-crossword` has **no engine test today**: only `apps/web/app/api/check-crossword/__tests__`
  with mocks. Add engine tests with an injected client:
  1. chain answers → scholarship paid, `200` with amounts;
  2. chain hangs → the route answers within the deadline, guide credited, `scholarship: 'pending'`;
  3. a wrong answer → no credit, no payment.
- Client: a test that a *slow* server does not enqueue the answer as offline, and that a real
  network failure does.

> Implemented: `packages/rewards/src/routes/__tests__/check-crossword.test.ts` (4 cases through
> `deps.crosswordChain`) and `apps/web/lib/__tests__/offline-submit.test.ts`.

## 4. Acceptance criteria

- [x] Submitting a correct crossword always ends: success or a visible error, never "Sending".
      The page posts with a 30 s timeout, the route answers within the chain deadline, and the
      button leaves the state in `finally`.
- [x] With the RPC unreachable, the guide counts and the response arrives in less than ~20 s.
      Every chain call has a 15 s deadline (`withDeadline`) and the section is non-fatal.
- [x] The scholarship, when it cannot be paid, is reported as pending and can be retried.
      `scholarship: 'pending'`, a `userevent` `scholarship_pending` with
      `scholarship_timeout` / `scholarship_failed`, and the page shows it as a warning.
- [x] "You are offline" only appears with the device actually offline.
      `shouldQueueSubmission` queues only when `navigator.onLine` is false or the failure never
      reached the server (`ERR_NETWORK` / `ERR_INTERNET_DISCONNECTED`); a timeout or a 4xx/5xx is
      an error with the submit button available again.
- [x] Engine tests for the three paths above and the client test exist and pass.

## 5. Evidence and how to reproduce

- Dev site, Global Disciples course, guide 2, correct answers, mobile: button stuck, later the
  offline banner; server log as quoted.
- Reproduce with the RPC pointing to an unreachable host (`NEXT_PUBLIC_RPC_URL=https://127.0.0.1:1`)
  and submit a guide: today the request hangs; after the fix it must answer.

## 7. E2E against the dev site

`apps/web/e2e/specs/crossword-submit-ends.spec.mjs` (browser, with the real chain behind the
server). It walks `CROSSWORD_COURSES` (default `en/web3-and-ubi`, `en/a-relationship-with-Jesus`,
`en/gdcluster`) until it finds a guide whose two scholarships are not paid (the submit button is
disabled once they are) and submits it twice through the UI:

1. **wrong answer** → `200`, `points: 0`, `scholarship: 'not_paid'`;
2. **correct answer** → `200`, `points: 1`, `scholarship` in `paid` / `already_paid` / `pending` /
   `not_paid`.

Both must be answered within `SUBMIT_BUDGET_MS` (default 45 s) and the button must stop saying
"Sending...". The "RPC unreachable" case cannot be forced from the browser (the RPC is the
server's), so it stays covered by the engine test with an injected chain that never answers. When
the wallet has paid every configured guide, the spec prints `[SKIP]` instead of failing.

How to run:

```sh
cd apps/web
CHROME_PATH=/usr/local/bin/chrome make test-e2e-spec SPEC=crossword-submit-ends

# another wallet, or other courses, when the default one already paid its guides:
E2E_WALLET=TEST_PASTOR1 CROSSWORD_COURSES="en/gdcluster" \
  CHROME_PATH=/usr/local/bin/chrome make test-e2e-spec SPEC=crossword-submit-ends
```

Result (2026-11-04, dev site `https://learn.tg:9001`, wallet `0x8427…C5C`,
`/en/a-relationship-with-Jesus/guide2`, 5 clues): the deploy already carries this fix — the
response includes the new fields.

| Step | Result |
|---|---|
| wrong answer | `200`, `points: 0`, `scholarship: 'not_paid'`, answered in **4086 ms** |
| correct answer | `200`, `points: 1`, `scholarship: 'paid'` (0.75 USDT + 0.75 SLEARN), answered in **3812 ms** |
| "Sending..." | left the button ~4.1 s after each click |
| spec | `0 failures`, 17.7 s total |

Second run (same day, `/en/gdcluster/guide2`, 5 clues) **found a remaining hole**: the wrong answer
answered as above (3979 ms), but the correct one never answered — the request stayed open past
25 s and the button past that. The cause was the GD 10% routing (`routeToClusterFunds`, after the
payment and inside the DB transaction) waiting for two receipts with no deadline. Fixed in §3.1
(`SCHOLARSHIP_ROUTING_TIMEOUT_MS`, `admin_solves` for retry) and covered by the engine test
*"answers within the routing deadline when the GD 10% transfer hangs"*; the client timeout went from
30 s to 45 s so it does not abort a bounded response. Re-running the GD case waits for the next
deploy of the dev site.

Third run (2026-11-04, after that redeploy, `E2E_WALLET=TEST_PASTOR1`, `/en/gdcluster/guide2`,
5 clues). The deploy was confirmed from the served chunk of the page
(`app/[lang]/[pathPrefix]/[pathSuffix]/test/page-29491f49745db430.js` carries
`{timeout:45e3}`, the new `submitTimeout` message and the `ERR_NETWORK`-only queue rule).

| Step | Result |
|---|---|
| wrong answer | `200`, `points: 0`, `scholarship: 'not_paid'`, answered in **3946 ms** |
| correct answer | `200`, `points: 1`, `scholarship: 'paid'` (0.93 USDT + 4.65 SLEARN), answered in **23877 ms** |
| "Sending..." | left the button at 24.2 s (previously: never, past 25 s) |
| spec | `0 failures`, 37.9 s total |

The GD course answers much later than the other courses because the same request also sends the
two 10% transfers to the cluster/country fund; they are the part now bounded at 20 s. The same
wallet on `es/redgd` and `en/gdcluster` guide 1 answered in ~0.3 s with `scholarship: 'not_paid'`
(no vault for that course) and `'already_paid'` respectively, which are the other two states.

> `bin/wait-site --expect-build-change` timed out during this deploy because its marker was the
> first chunk of `/[lang]/cluster`, a shared chunk that survived the build. It now reads the
> route's own `page-*.js` chunk (`--path` selects the route), which changes with the code.
>
> Second failure mode, fixed 2026-11-06: when the site was **down** at start (502 while the build
> was replaced) there was no previous marker, so `--expect-build-change` waited for a change that
> could never come and exited only at the timeout (measured: 502 … 200 with the new build at 85 s).
> The first 200 after a downtime now counts as the new build. The script is documented in
> `doc/e2e-testing.md` §3.5 (flags, marker, exit codes and the cheap post-deploy probe).
