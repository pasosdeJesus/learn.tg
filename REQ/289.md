# R-#289: Policy for the `transaction` ledger (and per-destination entries)

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/289
**Created:** 2026-10-27
**Status:** Proposal — policy + implementation/documentation plan. Only the GD 10% case exists today (https://github.com/pasosdeJesus/learn.tg/issues/161, implemented 2026-10-27).
**Type:** Data model / accounting / documentation
**Priority:** Medium — part of the fund ranking is an estimate (`amount * 0.8`) while the rest already uses the real on-chain credit, and no written rule tells a reader which is which.

## 1. Objective

1. Write **one** policy for the `transaction` table: what a row means, what it does not mean, how a split into several destinations is recorded, and which rows are public.
2. Align the donation flows with that policy, as the GD 10% already is: a destination that a public surface aggregates gets its **own row with the real on-chain credit**, never an inferred percentage.
3. Leave the policy in a document (`doc/transaction-ledger.md`) so future code does not have to reverse-engineer it.

## 2. Current state (measured 2026-10-27)

Invariant that already holds in every flow: **one row per token that leaves the user's wallet** (USDT and/or SLEARN; campaigns use the paid token) plus a cashback row when one is minted. The multi-destination split is **not** expanded into rows; it is written as text in `descripcion` and as JSON in `metadata.distribution`, and the contract executes it.

| Operation | Code | Rows written | Split recorded how |
|---|---|---|---|
| Course donation to the vault | `packages/rewards/src/routes/add-donation.ts:146-172` | `donation` usdt/slearn + `donation_reward` | `metadata.distribution` + `processPaymentHash` |
| GD cluster/country donation | `packages/gdcluster/src/routes/gd-donations.ts:176-210` | `donation` usdt/slearn (`subcategoria` `cluster`/`country`) + `donation_reward` | `metadata.distribution` + destination fields |
| Campaign donation | `packages/gdcluster/src/routes/gd-donations.ts:530-551` | `donation` (paid token, `subcategoria='campaign'`) + `donation_reward` | `metadata`: `campaignForwardHash`, `pdjForwardHash`, `reserveForwardHash`, `forwardPending`, raw amounts |
| Premium course (non-GD) | `packages/rewards/src/routes/premium-purchase.ts:255-287` | `pay-course` usdt/slearn + `donation_reward` | `metadata.distribution` + `processPaymentHash` |
| Premium course (GD) | same + `packages/gdcluster/src/lib/gd-cluster-routing.ts` | the above **+ `cluster_contribution`** per token | `distribution` shows `country_fund` 10%; the extra row carries the **real** transfer hash |
| Guide scholarship | `packages/rewards/src/routes/check-crossword.ts:600-641` | `scholarship` usdt/slearn (+ `cluster_contribution` if GD) | `metadata={courseId, guideId}` |
| Referral payouts / pastor bonus | `apps/web/lib/referral-payout.ts`, `packages/rewards/src/lib/pastor-bonus.ts` | `referral_reward`, `referral_bonus`, `pastor_bonus` | own `hash`, no split |

Inconsistencies this requirement fixes:

1. **`rankingFunds` estimates.** `packages/gdcluster/src/routes/gd-ranking.ts:93-126` sums `CASE WHEN hash LIKE '%-fund' AND type='donation' THEN amount ELSE amount * 0.8 END`. No writer produces `%-fund` hashes: the 100% branch is dead code, and the 80% is an assumption that would silently under-report if the fee configuration changes (`ClusterFundsV2._distributeFees`, `feePercentages`) or if a donation were credited at another rate. The exact number is already available on chain: the credited balance after `processDonation`/`processCountryDonation` (`ClusterDonation`/`CountryDonation` events) following the backend's transfer to `ClusterFundsV2` (`gd-donations.ts:128-153`).
2. **The forward hashes are dropped.** `gd-donations.ts` sends `transfer(cfAddress, …)` and `process*Donation` through `sendWithNonce` **without capturing the hashes**, so the ledger has no way to point at the real transfer. The GD 10% path already captures them (`routeToClusterFunds` returns `{usdtHash, slearnHash}`).
3. **Exclusions live in scattered knowledge.** Treasury rows must be filtered by every consumer by hand: done in `apps/web/lib/scores.ts` and `apps/web/lib/user-transactions.ts`; the leaderboard is protected only because `balance_impact` is `0`. A new aggregate that sums `transaction` would count them.
4. **`/api/transparency` sums every type.** `apps/web/app/api/transparency/route.ts:103-108` computes the users' SLEARN as `SUM(balance_impact)` over all rows without an allowlist; today it is only correct because destination rows are `0`. Same antipattern as (3), in the private submodule.
5. **Course vaults and the other destinations are read on chain, not from the ledger.** The vault balance per course comes from `LearnTGVaultsV5.vaults[courseId]`, the churches/referral funds from `/api/churches/fund` and `/api/referrals/fund`, and the pdJ/missional/UBI shares are internal to `SLEARN.processPayment`. No public surface aggregates those destinations from `transaction`, which is why they do **not** get destination rows (§3.7).
6. **No written rule.** Nothing states which `type` values exist, what `amount` vs `balance_impact` mean, that `metadata.distribution` is a plan and not proof, or which destinations need a row.

## 3. Policy (to be documented, `doc/transaction-ledger.md`)

### 3.1 What a row means

- One row = **one token movement of or for the account**, with `balance_impact` carrying the sign. `amount` is the token amount.
- One row per token per operation (at most two: `usdt`, `slearn`; campaigns: the paid token) plus one cashback row.
- `type` is the **class of operation** and is closed by the `transaction_tipo_check` constraint (current values: `scholarship`, `donation`, `donation_reward`, `pay-course`, `ubi-claim`, `conversion`, `pastor_bonus`, `referral_reward`, `referral_bonus`, `cluster_contribution`). Adding a value requires a migration.
- `categoria` groups (`payment`, `donation`, `cashback`, `referral`, `cluster`/`country`, …) and `subcategoria` is the precise kind (`course_purchase`, `course_vault`, `campaign`, …).
- `metadata.distribution` describes the **plan** shown to the user. It is not evidence and must not be summed as accounting.
- `hash` is the **real transfer hash of that token**; `wallet` is the wallet of the account that owns the row; `date` is the operation instant.

### 3.2 Row kinds

- **Movement rows** (user side): `scholarship`, `donation`, `pay-course`, `ubi-claim`, `conversion`, `donation_reward`, `referral_reward`, `referral_bonus`, `pastor_bonus`. `balance_impact` is signed; the outflow rows are the only source of the user's history and score.
- **Destination (treasury) rows**: `cluster_contribution` today. They record that a share of a movement **reached** a fund. Rules:
  - written **only after** the on-chain credit confirms, with the real transfer hash;
  - `balance_impact = 0` (the outflow is already in the originating row, so summing it again would double count);
  - idempotent on the existing unique `(crypto, hash)` (`onConflict(...).doNothing()`);
  - `metadata` identifies destination and origin: `{clusterWallet | countryCode, source: 'course' | 'guide' | 'donation', courseId?, guideId?, grossAmount?, …}`;
  - if the insert fails, the transfer is **not** rolled back: log and queue `admin_solves` (`gd_cluster_ledger`), as `routeToClusterFunds` does today.

### 3.3 Exposure rules (closed list)

| Surface | Movement rows | Destination rows |
|---|---|---|
| User transaction history (`lib/user-transactions.ts`) | yes | **no** |
| Learning score (`lib/scores.ts`) | yes | **no** |
| Leaderboard / metrics / country totals | yes (by their own filters) | **no** |
| Donation history and totals (user) | only `type='donation'` | **no** |
| Referral calculations | only `type IN ('referral_reward','referral_bonus')` | **no** |
| `/api/transparency` users' SLEARN | yes, but must allowlist (today sums all) | **no** |
| Fund ranking (`gdcluster/ranking/funds`) | only `type='donation'` (legacy estimate) | **yes, at 100%** |

Consumers must **allowlist by `type`** when they aggregate; summing every row of a user or of the table is a defect.

### 3.4 What does not belong in `transaction`

- Pending forwards. They live in `metadata.forwardPending` (campaigns), `admin_solves` and the verifier alerts until the forward succeeds.
- On-chain state (fund balances, `processedTx`) — read from the contract.
- Product events (`userevent`), credentials (`credential_*`), enrollments (`premium_course_usuario`).
- **A row per split destination of a normal operation.** A course purchase pays seven destinations (vault, pdJ, cashback, missional, UBI, referral, churches) in two tokens: expanding that into rows would multiply the table by 14 for data nobody aggregates from it.

### 3.5 No invented history

Rows written before a cutover keep the estimate that applied then. The policy forbids rewriting past rows to make them look exact: the ranking keeps the legacy estimate **only** for `donation` rows that have no destination row, and uses the exact row when it exists. One donation is counted once, by one of the two rules.

### 3.6 Contract of the fund ranking

`rankingFunds` answers "how much is in the fund" from destination rows, and falls back to the legacy estimate only for the period before the cutover. The `amount * 0.8` branch disappears once no `donation` row without a destination row remains in the window it reports.

### 3.7 Which destinations get a row (and which do not)

The test is **not** "the operation has a split"; it is **"a public surface publishes this destination's total and reads it from this table"**.

| Destination | Row? | Why |
|---|---|---|
| Cluster / country fund, GD 10% of a purchase or scholarship | **yes**, `cluster_contribution` | `gdcluster/ranking/funds` publishes it and today's source is the ledger (R-#161) |
| Cluster / country fund, direct donation | **yes** (Phase 2) | same ranking, currently estimated as `amount * 0.8` |
| Course vault (purchase remainder or vault donation) | no | the balance is on chain (`LearnTGVaultsV5.vaults[courseId]`); the row would duplicate state nobody sums |
| pdJ, missional, UBI, referral, churches shares of `processPayment` | no | read from the wallets/contract (`/api/churches/fund`, `/api/referrals/fund`, on-chain balances); the per-course revenue is private accounting (`/api/admin/premium-purchases`) |
| Cashback (SLEARN minted) | no, it is its own **movement** row (`donation_reward`) | it is credited to the user, so it is not a destination of a share |
| Campaign forward (campaign wallet, pdJ, reserve) | no (Phase 3) | no public surface aggregates campaigns from `transaction`; hashes stay in `metadata` |

If a new public surface starts publishing a destination from this table, the rule in §3.2 applies to it (real credit, own type or a documented `source`, idempotent, exposed only where intended).

## 4. Implementation plan

**Phase 1 — the policy, written down (no behaviour change).**
- New `doc/transaction-ledger.md` with §3 above, the table of `type` values, the exposure matrix, and the "plan vs evidence" rule.
- Link it from `ARCHITECTURE.md`, `apps/web/lib/README.md` and the documentation list of `AGENTS.md` (§4, as a new numbered item).
- Add a "Related" link in `apps/web/app/api/doc/crossword-reward-flow.md`.

**Phase 2 — GD donations credit a real row.**
- Capture the transfer hashes of `transfer(cfAddress, …)` and of `processDonation`/`processCountryDonation` in `packages/gdcluster/src/routes/gd-donations.ts` (same shape as `routeToClusterFunds`).
- Write one `cluster_contribution` row per token with `source: 'donation'`, `amount` = **the amount credited to the fund** (read from the `ClusterDonation`/`CountryDonation` event, or the fund balance delta per token), `categoria`/`subcategoria` `cluster`/`country`, `balance_impact: 0`, real hash, idempotent.
- `rankingFunds`: sum `cluster_contribution` at 100% (already done); keep `amount * 0.8` **only** for `donation` rows with no companion row; delete the dead `%-fund` branch.
- Tests: a route test asserting the row is written with the event amount and `balance_impact: 0`; a ranking test asserting one donation is counted once and that a fund row is summed at 100%.

**Phase 3 — campaigns (decision, not code).**
- Campaign forwards feed no public fund ranking today, so they stay in `metadata` (documented as such). If a public surface ever aggregates them, §3.2 applies and they get rows with `source: 'campaign'`. Record the decision in the doc.

**Phase 4 — make the exclusions explicit.**
- Replace the ad-hoc `!= 'cluster_contribution'` filters with one shared helper (e.g. `MOVEMENT_TYPES` / `TREASURY_TYPES` in `apps/web/lib/transaction-types.ts`) used by `scores.ts`, `user-transactions.ts` and any new aggregate.
- Apply the allowlist to `apps/web/app/api/transparency/route.ts:103-108` (private submodule: commit it there), which today sums every type and is only right by accident.
- Unit tests for the helper and for the three consumers.

**Phase 5 — documentation sync and audit.**
- Update the money-flow sections of `packages/gdcluster/README.md`, the ledger bullet of https://github.com/pasosdeJesus/learn.tg/issues/161 and this file with the outcome.
- `make type`, `make test-lib`, `make test-gdcluster`, `make test-api`; the private audit of `.crushrules` at `0 findings`.

## 5. Documentation proposal

New file **`doc/transaction-ledger.md`** (English, same voice as `doc/api-security.md`):

1. Purpose and scope (what the table is and is not).
2. Row anatomy: `type`, `categoria`, `subcategoria`, `amount`, `balance_impact`, `hash`, `wallet`, `date`, `metadata`.
3. The "one row per token" rule, with worked examples: a GD purchase (100% payment row + 10% destination row) and a GD donation (80/10/10 plan vs the credited row).
4. Movement vs destination rows, and the `balance_impact = 0` rule.
5. Exposure matrix (which surface reads which `type`).
6. Adding a new `type`: constraint migration, exclusion updates, tests.
7. Failure handling: `admin_solves` and where each retry lives.
8. Anti-patterns: summing all rows, inventing hashes, rewriting history, putting pending work in `transaction`.

`doc/` is the right place: the policy is cross-engine (rewards, gdcluster, the Next host) and outlives a single requirement; `packages/*/README.md` only describes the module that implements it.

## 6. Acceptance criteria

- [ ] `doc/transaction-ledger.md` exists, is linked from `ARCHITECTURE.md`, `apps/web/lib/README.md` and `AGENTS.md`, and every statement matches the code.
- [ ] A GD donation writes one `cluster_contribution` row per credited token (`source: 'donation'`, `balance_impact: 0`, real hash, idempotent), and its `amount` equals the amount the contract credited (event), not a percentage of the donation.
- [ ] `rankingFunds` never adds the same donation twice and no longer contains the `%-fund` branch.
- [ ] No public surface (history, score, leaderboard, metrics, donations, referrals, `/api/transparency`) shows or sums a destination row; the rule is enforced by a shared helper, not by scattered filters.
- [ ] Course vaults, pdJ/missional/UBI/referral/churches shares and campaign forwards still come from their on-chain source; no destination rows were added for them (§3.7).
- [ ] `make type`, `make test-lib`, `make test-gdcluster`, `make test-api` and the private audit are green.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Double counting during the cutover | One rule per row: legacy estimate only when there is no destination row (§3.5); the condition is explicit in the SQL |
| Reading the credited amount on chain fails (RPC) | Keep the donation row and the user's funds intact; queue `admin_solves` and retry from the metadata that already exists (`tokenAddress`, raw amounts) |
| A new `type` without its exclusions | Phase 4 helper plus a test that fails when a `type` is missing from the allowlists |
| JSON consumers depend on `metadata.distribution` | It stays as the user-facing plan; only accounting moves to rows |

## 8. Out of scope

- Rewriting or backfilling historical rows.
- Campaign destination rows (Phase 3 decision).
- Changes to the contracts (`ClusterFundsV2`, `LearnTGVaultsV5`, `SLEARN`).
- `/api/transparency` and the admin dashboards, beyond the allowlist of Phase 4.
