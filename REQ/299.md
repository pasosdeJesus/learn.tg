# R-#299: Invite a pastor by wallet and split the cluster page into a public and a private one

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/299
**Created:** 2026-11-10
**Updated:** 2026-11-12
**Status:** Proposal
**Type:** GD clusters / invitations / UI
**Priority:** Medium — the 6-character code lets any pastor join a cluster without the initiator
accepting, and the workflow depends on sharing a URL that wallet browsers hide.

## 1. Objective

1. Replace the invitation by URL + 6-character code with an invitation the cluster **initiator**
   sends to a pastor, either from the candidate list or by typing the pastor's wallet address. **The
   code disappears**: no column, no route, no UI, no transitional phase — the GD course has no active
   students yet, so nothing has to keep working.
2. Make the invited pastor answer from a notification (**Yes** / **No**), notify the initiator of the
   answer and keep every step in the cluster history.
3. Make the private cluster page progressive and **single**: a pastor belongs to one cluster, so
   `/{lang}/cluster` shows it (invitation card, members, progress, budget, approvals, history); an
   incomplete cluster shows only the invitations card (for the initiator) and the history.
4. Add a **public** page per cluster (its **slug**, churches, total raised, process status and the
   release transaction) linked from the cluster ranking, and keep the current page as the **private**
   one for the member pastors. The pseudonym goes away and **the alias is the slug**: the public
   surface never shows the cluster `name`, only the slug.

## 2. Current state (measured 2026-11-12)

- `POST /api/cluster` creates the cluster and up to **two** invitations taken from
  `GET /api/cluster/candidates` (pastors referred by the initiator,
  https://github.com/pasosdeJesus/learn.tg/issues/163, plus the referrer if they are a pastor); the
  invited pastor is notified through `notifyUser()` (`notifications`).
- `POST /api/cluster/join` accepts the 6-character `clustergd.code` and **adds the caller's church
  directly**. Its only guards are: authenticated `church_relationship = 'pastor'`, registered church,
  type-1 country, no current cluster and the previous cluster did not receive its funds. Nobody
  approves the join, and the page prints the code next to the URL.
- `cluster_invitation` (`20260831100000_cluster_formation`): `clustergd_id`, `invited_pastor_id`,
  `invited_church_id`, `invited_by_id`, `status` (`pending`), `created_at`, `responded_at`, unique
  `(clustergd_id, invited_pastor_id)`; `POST /api/cluster/invitation/accept|reject` already exist.
- UI: two pages. `/{lang}/cluster` is the **formation** page (three states: no cluster / pending
  invitation with accept-reject / member summary that prints the `code` and links to "View cluster
  details"). `/{lang}/cluster/[id]` is the **detail** page, client-rendered by `ClusterPageHost` from
  `GET /api/cluster/[id]` (budget, director, approvals, GD presentation, history). The public ranking
  is `/{lang}/gdcluster/ranking`.
- Measured on `https://learn.tg:9001/en/cluster/52`: the shell has no data (client fetch) and
  `GET /api/cluster/52` answers, **for a member who is not the initiator** (`isInitiator: false`), the
  full record including the 6-character `code`:
  `{"id":52,"name":"Cl2","pseudonym":"Cl2","code":"GL8EZZ","initiator_church_id":171,
  "cluster_wallet":null,"member_count":3,"status":"active","members":[…],"history":[…]}`.
  All three members of cluster 52 joined by code (`church_join` in the history, no invitation event).
  Nobody needs to invite anyone: knowing the code is enough, which is the weakness this requirement
  removes.
- Notifications: `notifications(usuario_id, type, title, content, link, is_read, created_at)`.
- Clusters are only offered in type-1 countries (`isType1Country` in `joinCluster`), and
  `clustergd.pseudonym` already exists (https://github.com/pasosdeJesus/learn.tg/issues/164) and is
  **removed** by this requirement: there are no clusters in production, so nothing depends on it.

## 3. Invitation by wallet (decided)

- **Only the initiator invites**: the authenticated account must be the pastor of
  `clustergd.initiator_church_id`; any other member (or an outsider) gets **403**.
- The initiator has two ways on the private page: the candidate list (as today) and a field to type
  or paste a **wallet address**.
- The wallet path resolves wallet → account → user (`billetera_usuario` → `usuario`) and requires:
  - `church_relationship = 'pastor'` (lead pastor) — otherwise **explicit error**
    (`not_lead_pastor`);
  - the church exists and is verified (`church.registration_verified = true`) — otherwise
    `church_not_verified`;
  - no current cluster (`getChurchCluster`) — otherwise `already_in_cluster`;
  - type-1 country and the previous cluster did not receive its funds — otherwise `wrong_country` /
    `cluster_completed`;
  - it is not the initiator and not already invited in this cluster.
- The response for a wallet that cannot be invited is a **uniform 422 with a reason** (the same
  shape whether the address exists or not), so the endpoint cannot be used to find out which wallets
  are verified pastors.
- **Unique identity**: a cluster's `name` and its public `slug` cannot repeat. `POST /api/cluster`
  (create), `PATCH /api/cluster/[id]` (the pastor changes the alias) and
  `PATCH /api/admin/clusters/[id]` (admin edit) answer **409** with `reason` `name_taken` or
  `slug_taken`; the comparison ignores case
  and surrounding spaces, and the database enforces it with unique indexes (the constraint is the
  source of truth, the API check only gives the friendly reason).
- **The alias is the pastor's**: the slug is suggested at creation from the name (initials, §4) but
  the initiator can edit it before creating the cluster and the pastor can change it later from the
  private page; every change revalidates the uniques. The `name` stays internal and only the
  verifier edits it.
- **Collisions**: the **derived** slug is never rejected, it is suffixed — when `suggestSlug(name)` is
  taken the cluster gets `<base>-<id>` (the base is truncated so the whole slug fits in 40), which is
  unique by construction. A slug the pastor **types** is never rewritten: if it is taken the request
  answers 409 `slug_taken` and they type another (the message offers the suffixed alternative).
- Inviting creates the `cluster_invitation` row (or reopens a rejected one, see below) and a
  notification `type = 'cluster_invitation'` that links to the private page, where the invited pastor
  sees the two buttons: **Yes** and **No**.
- **Rejection**: `status = 'rejected'`, `responded_at` set, the initiator receives a notification
  (`cluster_invitation_rejected`), the row stops counting as a pending invitee and the initiator may
  invite **that same pastor one more time** only (`invite_count` 1 → 2). A second rejection is final
  for that cluster.
- Every step is appended to `clustergd_history` (`invitation_sent`, `invitation_accepted`,
  `invitation_rejected`, `invitation_reinvited`) and mirrored in `userevent`, so the cluster page
  shows them in chronological order.

## 4. Data model

New migration (`bin/m db:mig:make cluster_invitation_by_wallet`; the applied migration is never
edited):

- `cluster_invitation` gains:
  - `invite_count integer not null default 1` (1 = first invitation, 2 = the single re-invite);
  - `invited_wallet varchar(42)` (the address typed, for audit);
  - `origin varchar(20) not null default 'candidates'` (`'candidates'` | `'wallet'`); the rows created
    before this change keep `'code'` as their historical value;
  - optional `response_note varchar(200)` (reason given by the pastor; not published).
- The unique `(clustergd_id, invited_pastor_id)` is **kept**: the re-invite reuses the row (sets
  `status = 'pending'`, `invite_count = 2`, clears `responded_at`) instead of inserting a second one,
  which keeps the pair unique and the history in `clustergd_history`.
- `clustergd.code` is **dropped** (it only served `POST /api/cluster/join`, which is deleted). The
  codes are not needed by any consumer (checked: only the join route, the formation page and
  `GET /api/cluster/[id]` read it).
- `clustergd` gains `slug varchar(120) not null` (the public identifier, used by
  `/{lang}/clusters/[slug]`), loses `pseudonym`, and gets two unique indexes:
  - `clustergd_name_unique` on `lower(btrim(name))`;
  - `clustergd_slug_unique` on `slug`.
- **The suggested slug** (one function, `suggestSlug(name)`, used by the create form and by the
  backfill) is built from the **initials of the words** of the name: lowercase, accents stripped
  (NFD), keep `[a-z0-9]`, drop the rest; a word that starts with a digit contributes its digits
  (`Cl 1 1` → `c11`, `Iglesia Nueva Jerusalén` → `inj`). If the name has a single word the whole word
  is used, and if the result is shorter than 2 characters the full normalized name is used instead.
- **The accepted slug** is validated (not derived) on every write: 2-40 characters, lowercase
  `[a-z0-9]` and hyphens, no leading/trailing hyphen, no doubled hyphen; anything else is rejected
  with `slug_invalid`. A **typed** slug that is taken answers `slug_taken` (§3).
- **Creation with the derived slug**: the endpoint inserts the cluster, computes
  `suggestSlug(name)` and, when that value already exists, writes `<base>-<id>` (truncating the base
  to `40 - len("-<id>")`). The `id` is the row's own, so no retry loop is needed; both steps run in one
  transaction and the unique index is still the last line of defence.
- Backfill in the same migration: every existing cluster gets `suggestSlug(name)`, with `-<id>` when
  it collides (same rule, printed). There are no clusters in production, so the dev rows can also be
  reset.

## 5. Endpoints (gdcluster engine)

| Method | Path | Class | Who |
|---|---|---|---|
| POST | `/api/cluster/invitation/wallet` | authenticated | **only the initiator**; body `{ walletAddress }`; 422 with a `reason` (`not_lead_pastor`, …) |
| POST | `/api/cluster/invitation/accept` / `reject` | authenticated | the invited pastor; on reject it notifies the initiator and applies the re-invite rule |
| GET | `/api/cluster/status` | authenticated | already returns the pending invitations (used by the private page) |
| GET | `/api/clusters` | public | list for the ranking: **slug**, status, total raised (never `name`) |
| GET | `/api/clusters/[slug]` | public | public page: churches (or aggregates), total, status, release transaction |

`GET /api/cluster/candidates` keeps its role for option (1); its `hint: 'invite-by-code'` disappears.
The code is removed end to end with **no compatibility shim**: `POST /api/cluster/join` leaves the
engine registry and `app/api/cluster/join/route.ts` is deleted (404), `clustergd.code` is dropped by
the migration, and `GET /api/cluster/status` stops returning it. `POST /api/cluster` and
`PATCH /api/cluster/[id]` (the pastor's own path) accepts **only `slug`** (plus the existing
`clusterWallet`), revalidating `slug_taken`/`slug_invalid`; `name` is not editable there.
`PATCH /api/admin/clusters/[id]` accepts `name` and `slug`, with the same checks.

## 6. UI

**Private page** `/{lang}/cluster` (the two current pages merge into this one; a pastor belongs to
one cluster, so the `id` in the URL adds nothing). It also carries the **public alias** field (the
slug), editable by any member with the right to edit the cluster, with the validation of §4 and the
`slug_taken` message; the `name` is not editable there:

- The server/client resolves the pastor's cluster from `GET /api/cluster/status` (`hasCluster`) and
  renders one of: creation + invitations, pending invitation with **Yes**/No, or the cluster itself
  (members, invitations, progress, budget, director, approvals, GD presentation, history).
- Cluster with fewer than three churches (not yet active): **only** the invitations card (for the
  initiator) and the history; the progress, budget and approval sections appear once the cluster is
  active, so a cluster being formed is not shown as a half-built dashboard.
- The initiator sees the invitations card **above** the history: candidate list + wallet field + the
  pending invitations with their state (sent / rejected, and the re-invite button after a rejection).
- An invited pastor sees the invitation card with **Yes** / **No**; on rejection the card disappears
  and the answer is notified to the initiator.
- The `code` disappears from the page and from `GET /api/cluster/status`.
- The **rename form** (`handleRename` in `ClusterPage`) becomes an **alias form**: it edits the slug
  (`PATCH /api/cluster/[id]` with `{ slug }`) and never the name. The verifier edits both from the
  admin cluster modal; a new slug is always an explicit choice there too (no automatic
  recomputation), with `slug_taken` when it collides.
- `/{lang}/cluster/[id]` is **deleted** (no redirect): the "View cluster details" button goes away and
  the page itself is `/cluster`. Notifications already point to `/{lang}/cluster`, and the course has
  no active students, so no old link has to keep working. The engine component keeps the `id` prop for
  the public page and for future cross-cluster views; the private page does not pass it.

**Public page** `/{lang}/clusters/[slug]`: the **slug** as the heading (it is the alias; the name is
never rendered), the churches that make up the cluster, the total raised on learn.tg, whether the
process is in progress or finished and, when finished, the transaction that released the funds. The
cluster ranking shows the **slug** in its rows (it stops reading `pseudonym` and `name`) and links
each row to this page. The creation form loses the pseudonym field: name (internal) + invitations,
and it prefills an **editable slug field** with `suggestSlug(name)` (initials), so the initiator sees
and can choose the public alias before creating the cluster.

## 7. Public slug and privacy (https://github.com/pasosdeJesus/learn.tg/issues/164, https://github.com/pasosdeJesus/learn.tg/issues/278)

- `slug` = the **public alias**: lowercase, ASCII, hyphens, **unique** (stored, see §4), suggested
  from the name at creation (its initials) and editable by the initiator then and by the pastor
  later. Changing it makes the old link answer 404, never another cluster's page (nothing needs
  redirects today: there are no students).
- **The name is internal.** It is the source of the slug and the label in the private page, the
  invitations, the notifications and the admin screens; no public endpoint or public page renders it.
- The public page never shows lead pastor names, WhatsApp numbers or church addresses, and never the
  invitations or their reasons.
- Clusters are type-1 only: `createCluster` already checks it and the wallet invitation (§3) checks
  the invited church's country, so removing `joinCluster` does not drop the rule.
- The alias is chosen by the initiator at creation (the initials of the name are only the
  suggestion) and the pastor can change it later, so it is not forced to reveal the name; the default
  is a hint, not a guarantee. Opening clusters to a type-2 country still needs the rule written down:
  the suggested alias must not be pre-filled there (the pastor types one), per
  https://github.com/pasosdeJesus/learn.tg/issues/164 and
  https://github.com/pasosdeJesus/learn.tg/issues/278.
- The wallet-typed invitation is auditable (`invited_wallet`) but the public page does not expose it.

## 8. Acceptance criteria

- [ ] Only the initiator can invite (403 for any other member or outsider), by candidate list or by
      wallet.
- [ ] A wallet that is not a lead pastor, or whose church is not verified, answers an explicit reason
      (`not_lead_pastor`, `church_not_verified`, `already_in_cluster`, `wrong_country`,
      `cluster_completed`) with the same shape for every case (no wallet enumeration).
- [ ] The invited pastor receives a notification and answers Yes/No from the cluster page; on
      rejection the initiator is notified and the pastor leaves the pending list.
- [ ] The same pastor can be invited **one more time** after rejecting (`invite_count` 2); a second
      rejection is final for that cluster.
- [ ] `clustergd_history` shows sent / accepted / rejected / re-invited in order.
- [ ] An incomplete cluster shows only the invitations card and the history; the initiator's card is
      above the history.
- [ ] The public page exists, is reachable from the ranking, shows the **slug** as its heading (never
      the `name`), hides pastor identities and shows the total, the status and the release transaction;
      the ranking rows show the slug and a test asserts that no public response carries `name`.
- [ ] The code is gone end to end, with no shim: `clustergd.code` dropped, `POST /api/cluster/join`
      removed (404) and its route file deleted, `candidates` has no code hint, `GET /api/cluster/status`
      returns no `code`, and the UI has no "share the code" copy left (`noCandidates`,
      `noCandidatesHelp`, `code` i18n keys removed).
- [ ] The private page lives only at `/{lang}/cluster` (formation + invitation + detail in one);
      `/{lang}/cluster/[id]` is deleted (404) and the "View cluster details" button is gone.
- [ ] `name` and `slug` are unique (case and surrounding spaces ignored) at the database level and
      the create, pastor-alias and admin-edit endpoints answer 409 with `name_taken` or `slug_taken`;
      an existing cluster keeps a coherent slug after the backfill.
- [ ] `suggestSlug(name)` returns the initials (`Cl 1 1` → `c11`, `Iglesia Nueva Jerusalén` → `inj`),
      the create form prefills it and lets the initiator edit it, and the pastor can change it later
      (`PATCH /api/cluster/[id]` with `{ slug }`) with `slug_invalid`/`slug_taken` validation.
- [ ] Two clusters with the same name (or whose names give the same initials) end up with different
      slugs: the second gets `<base>-<id>`; a **typed** slug that is taken still answers 409.
- [ ] `clustergd.pseudonym` is gone (column, API responses, ranking, page and i18n) and the public page
      shows the slug, not the name; the pastor edits the slug (alias form) but not the name, the
      verifier edits both, and both paths apply the same uniques.
- [ ] Engine tests for the rules (401/403, non-lead-pastor, re-invite, history) and a browser spec for
      the two pages.

## 9. Out of scope

- More than one cluster per church, bulk invitations, external (email/WhatsApp) notifications.
- On-chain activation by member count (today the third church activates the cluster).
- The GD presentation flow (https://github.com/pasosdeJesus/learn.tg/issues/161,
  https://github.com/pasosdeJesus/learn.tg/issues/220).
