# R-#224: Fix 4 failing dev-site browser specs

**Enlace:** (pendiente — crear issue en GitHub pasosdeJesus/learn.tg)

**Status:** Open — requiere diagnóstico con logs
**Created:** 2026-09-04

---

## 1. Objective

Fix the 4 browser specs that consistently fail on the development site
(`https://learn.tg:9001`, Celo Sepolia) with the official runner
(`bin/m test:e2e <name>`), and add **diagnostics** to pinpoint the root cause
precisely before changing behavior.

The failing specs are unrelated to the campaign donation flow (R-#223); all
its specs are green. They share symptoms around **SIWE authentication
(401/`CredentialsSignin`)** and **Rails-dependent course data**.

## 2. Failing specs and observed symptoms

| Spec | Observed (reproducible with `bin/m test:e2e <name>`) |
|------|------------------------------------------------------|
| `cluster-formation` | SIWE ok, but `GET /api/cluster/status` and `/api/cluster/candidates` → **401**; `/api/admin/clusters` (with verifier token) → **403**; `POST /api/cluster/invitation/accept` → `401 {"error":"Authentication failed"}` |
| `gas-insufficient-panel` | EN panel sometimes missing; ES step: SIWE callback → **401 `CredentialsSignin`**; modal shows "Connect and sign…" instead of the no-gas panel even with mocked `eth_getBalance=0x64` |
| `premium-course-checkout` | Fresh pastor SIWE ok, but the GD course page stays on **"Loading course…"** (`course state: null`); Buy button / CheckoutModal never appear |
| `referral-program` | Fresh referred wallet SIWE → **401 `CredentialsSignin`**; `pendingReferralCode` not stored in localStorage; claim skipped |

## 3. Working hypotheses (to confirm with diagnostics)

1. **Session-token mismatch in `authenticateUser`** (cluster, and others when
   tokens are used for the API): the `token` param (NextAuth CSRF) no longer
   matches `billetera_usuario.token` (rotated by a previous SIWE) and the
   session-cookie fallback (`getToken`) also fails → 401. The doc
   `doc/siwe-auth-flow.md` documents a stale-token fallback; verify which path
   is failing and why.
2. **SIWE 401 `CredentialsSignin` for fresh wallets** (gas-insufficient ES,
   referral-program): nonce/CSRF reuse, domain mismatch (`learn.tg` vs
   `learn.tg:9001`), cookie not forwarded between `csrf` and `callback`
   requests, or NextAuth rejecting the second sign-in of the same browser
   context.
3. **Rails-side session missing for new wallets** (`premium-course-checkout`):
   the Next.js app authenticates, but Rails returns 401/404 for course /
   eligibility endpoints because the wallet has no Rails-side record/session
   (same pattern as `rails-auth.spec.mjs` "token mismatch for new wallets").
4. **Course page data fetch fails silently**: `/[lang]/[pathPrefix]` stuck in
   "Loading course…" because an API (guide/scholarship/purchase-eligibility)
   fails; the page swallows the error → `course state: null`.

## 4. Proposed method: diagnostics first, then targeted fixes

### 4.1 Add diagnostics (no behavior change)

1. **Auth tracing** in `lib/authenticateUser.ts` and the NextAuth
   `authorize()` (gated by env `DEBUG_AUTH=1`, never in prod logs):
   log the reason for failure: `token param present?`, `stored token match?`,
   `session cookie present?`, `session.sub == wallet?`, `domain checked`,
   `nonce match`. Tag with `[auth]` (use `logger` from `@pasosdejesus/m/debug`).
2. **e2e helper** `e2e/helpers/siwe-auth-debug.mjs`: a drop-in for the
   fetch-based SIWE that prints, per step: CSRF status/cookie, callback
   status + **body**, `nextauth` error query param, session status after
   login, and the `token` sent vs the one stored (via `/api/auth/session`).
3. **Network trace in the page-level failures**: capture
   `page.on('requestfailed')`/`response` for `premium-course-checkout` to
   print every API call (`/api/scholarship`, `/api/guide`,
   `/api/courses/…/purchase-eligibility`, Rails `…/proyectosfinancieros…`)
   with status, so "Loading course…" is explained by its first failing call.
4. **Authenticated Rails probe** (extend `rails-health.spec.mjs` or reuse
   `rails-auth.spec.mjs`): after SIWE, call one Rails endpoint and report
   whether the token is accepted — separates "Rails down" from
   "Rails rejects new wallet".

### 4.2 Run and classify

Run each failing spec solo with the diagnostics on and record the exact
failing step/reason:

```sh
cd apps/nextjs
DEBUG_AUTH=1 bin/m test:e2e cluster-formation
DEBUG_AUTH=1 bin/m test:e2e gas-insufficient-panel
DEBUG_AUTH=1 bin/m test:e2e premium-course-checkout
DEBUG_AUTH=1 bin/m test:e2e referral-program
```

Minimal repro via API/curl when possible (avoid browser variability):
- cluster: fresh SIWE → `GET /api/cluster/status?walletAddress=…&token=…` and
  compare the token against `billetera_usuario` (or `/api/auth/session`).
- referral: fresh wallet SIWE → inspect the `credentials` callback response
  and the error URL.

### 4.3 Fix candidates per spec (apply only after root cause is confirmed)

| Spec | Likely fix (pending diagnosis) |
|------|--------------------------------|
| `cluster-formation` | Align token handling in the spec with the session fallback; or fix `authenticateUser` fallback when the token rotated mid-suite; or whitelist verifier actions by session cookie |
| `gas-insufficient-panel` | Make the spec re-auth deterministically (fresh nonce, forwarded cookies) before step ES; ensure the panel assertion waits for `dataLoaded` (avoid the connect prompt) |
| `premium-course-checkout` | Complete the Rails-side registration of the fresh pastor before the page check (or point the page to data available without Rails session); log the failing API and fix/retry it |
| `referral-program` | Fix the fresh-wallet SIWE flow (nonce/domain/cookies) or seed/whitelist the referred wallet; re-check the referral claim rate-limit |
