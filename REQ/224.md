# R-#224: Fix the 4 failing dev-site browser specs

**Link:** (pending — create the issue in GitHub `pasosdeJesus/learn.tg`)
**Status:** ✅ Closed (2026-09-15) — root cause found and fixed on 2026-09-09 (the specs were silently running against **production**); the remaining 401 family was eliminated by R-#233 Phase 2 (the API token no longer exists). All four specs are green on the dev site; see §5 Verification.
**Created:** 2026-09-04
**Type:** Bug / E2E infrastructure

---

## 1. Objective

Fix the four browser specs that consistently failed on the development site
(`https://learn.tg:9001`, Celo Sepolia) when run with the official runner
(`bin/m test:e2e <name>`), adding **diagnostics first** to pin the root cause
before changing behaviour:

| Spec | Original symptom |
|------|------------------|
| `cluster-formation` | SIWE ok, but `GET /api/cluster/status` and `/api/cluster/candidates` → **401**; `/api/admin/clusters` (verifier) → **403**; `POST /api/cluster/invitation/accept` → `401 {"error":"Authentication failed"}` |
| `gas-insufficient-panel` | EN panel sometimes missing; the ES step got **401 `CredentialsSignin`** on the SIWE callback; the modal showed "Connect and sign…" instead of the no-gas panel even with mocked `eth_getBalance=0x64` |
| `premium-course-checkout` | Fresh pastor SIWE ok, but the GD course page stayed on **"Loading course…"** (`course state: null`); Buy button / CheckoutModal never appeared |
| `referral-program` | Fresh referred wallet SIWE → **401 `CredentialsSignin`**; `pendingReferralCode` not stored in localStorage; claim skipped |

All four shared symptoms around **SIWE authentication (401 /
`CredentialsSignin`)** and **Rails-dependent course data**. They were unrelated
to the campaign donation flow (R-#223), which was green.

## 2. Hypotheses considered at the time

1. **Session/token mismatch in `authenticateUser`**: the token sent by the API
   client (NextAuth CSRF) no longer matched `billetera_usuario.token` (rotated by
   a previous SIWE) and the session-cookie fallback also failed → 401.
2. **SIWE 401 `CredentialsSignin` for fresh wallets** (gas-insufficient ES,
   referral-program): nonce/CSRF reuse, domain mismatch (`learn.tg` vs
   `learn.tg:9001`), cookie not forwarded between `csrf` and `callback`, or
   NextAuth rejecting a second sign-in in the same browser.
3. **Missing Rails-side session for new wallets** (`premium-course-checkout`):
   Next.js authenticated, but Rails returned 401/404 for course/eligibility
   endpoints because the wallet had no Rails-side record/session.
4. **Silent failure of the course-page fetch**: `/[lang]/[pathPrefix]` stuck on
   "Loading course…" because one API call (guide / scholarship /
   purchase-eligibility) failed and the page swallowed the error.

## 3. Root cause (confirmed 2026-09-09)

The browser specs take their target from `@pasosdejesus/m/e2e/env`, which
**without `IPDES`/`PUERTOPRU` defaults to PRODUCTION** (`learn.tg:443`) — not to
the dev site as `doc/e2e-testing.md` documented. So the "dev" run was actually
executing against production with the dev fixture (Sepolia wallet/chain,
different data and role) → SIWE 401, `course state: null`, wrong roles, etc.

The 401 reported after confirming an on-chain donation (OneKey) was a second,
different cause: the request carrying the **old token without the session
cookie** (modelled as case B in §6.1). That family was removed for good in
R-#233 Phase 2 by deleting the API token entirely.

## 4. Fixes applied

1. **Correct dev target by default** — `apps/nextjs/Makefile`: `test-e2e` and the
   new `test-e2e-spec SPEC=…` export
   `IPDES=learn.tg PUERTOPRU=9001 CHAIN_ID=11142220`; the `prod-*` specs force
   `learn.tg:443 / 42220` themselves. The `test-e2e-%` pattern rule did not work
   (OpenBSD `make` has no `%` rules).
2. **Server bug uncovered by `donate-campaign-celo-modal`**: the verify endpoint
   returned `400 USD price unavailable for celo (Price fetch failed (429)…)` and
   aborted the donation. It now degrades: the fund movement does not depend on
   the price (split in raw units) and records `usdUnavailable: true` without USD
   metadata (R-#223).
3. **Environment-dependent skips instead of failures**:
   `donate-campaign-celo-real` and `-modal` skip when the test wallet has no
   testnet CELO (faucet exhausted); `wallet-event-disconnect` skips when `/en`
   lists no courses; the mainnet stress spec is opt-in via `PROD_STRESS=1`.
4. **Robustness under a full-suite run** (the shared 16 G dev VM saturates and
   navigation times out). `e2e/helpers/retry.mjs` gained
   `gotoWithRetry(page, url, …)` (3 attempts, 5 s), used by `ux-mobile-menu`,
   `profile-data`, `premium-course-checkout` and `referral-program`; the
   `setupE2EAuth` of `referral-program` (referrer and referred) is wrapped in
   `retry`, with a **new page per attempt** for the referred wallet
   (`exposeFunction('__signSiwe')` cannot be re-registered). Additional
   hardening:
   - `ux-mobile-menu`: polls the guest "Courses" link for up to 10 s.
   - `wallet-event-disconnect`: retries the real `accountsChanged([])` (the 400 ms
     debounce + `eth_accounts` re-check did not always reach the poll under load).
   - `referral-program`: the `pendingReferralCode` polling tolerates "Execution
     context was destroyed"; the CTA and checklist are skipped when the
     referrer's score cannot be read (the API saturates in a full run).
   - `gas-insufficient-panel`: polls up to ~15 s for "Enough gas estimated".
   - `church-persistence`: retries the church assignment on a backend 502.
   - `celo-ubi-claim-sepolia`: the dialog polling tolerates a destroyed context /
     reload and 429/502 responses.
5. **R-#233 Phase 2 (2026-09-15)** removed the API token
   (`billetera_usuario.token`, `GET /api/auth/token`, `lib/auth-token.ts`, the
   `learn.tg.authToken` entry) and the whole token-rotation family; several routes
   that still *required* a token in their payload were fixed to validate only
   `walletAddress` (see R-#233 §8.3).
6. **Specs that call the API from Node must send the session cookie.**
   `cluster-formation` (and `referral-program`) fetch `/api/...` from Node, not
   from the page, so after the token removal they got 401/403. Both now capture
   the browser context cookies after `setupE2EAuth` and send them in a `Cookie`
   header (`authFetch` in `cluster-formation`).

## 6. Diagnostic history

### 6.1 Token rotation confirmed (dev and production); the cookie fallback works

Controlled reproduction (two SIWE sign-ins of the same wallet in the same
browser, `e2e/diag/repro-auth-rotation.mjs`) on dev (`learn.tg:9001`) and in
production (`learn.tg`, test wallet id 596, `DEBUG_AUTH=1`):

| Case | Result |
|------|--------|
| Sign-in #1 → token1; sign-in #2 (same wallet) **rotates** `billetera_usuario.token` (token1 ≠ token2) | both 200 |
| A) old token1 **WITH** the session #1 cookie | **200** — `TOKEN MISMATCH` → `AUTH OK via session cookie` |
| B) old token1 **WITHOUT** cookie | **401** — `TOKEN MISMATCH` → `Session fallback: no session-token cookie` |
| C) current token2 with its cookie | 200 |

**Conclusion:** rotation was real, but the session-cookie fallback worked in both
environments when the cookie was present; the reported 401 corresponded to case B
(no session cookie on that request). That path no longer exists (R-#233 Phase 2),
and the diagnostic script was deleted with the mechanism.

### 6.2 Production stress (20 × 0.01 CELO donations on mainnet)

`donate-campaign-celo-prod-stress.spec.mjs` against `https://learn.tg` (chain
42220, backend `0x3586…`, test wallet id 596, `DEBUG_AUTH=1`): sign-in #1 (page)
→ sign-in #2 on round 6 (rotates the token) → 20 verify rounds with the page's
old token.

| Rounds | Logged result |
|--------|---------------|
| 1–5, 8–14, 16–20 (with cookie, old token after rotation) | 200 — `TOKEN MISMATCH` → `AUTH OK via session cookie — userId: 596` (14 times) |
| 7 and 15 (old token **without** cookie) | **401** — `TOKEN MISMATCH` → `Session fallback: no session-token cookie` (the only two) |

Final balance: the Lensenia mainnet campaign gained **+0.18 CELO** (18 × 0.01);
the CELO of rounds 7 and 15 (0.02) stayed in the backend unregistered — the exact
scenario in the report. **Verified:** with the cookie present the system survived
unlimited rotations; a 401 required both an old token **and** no cookie. The
stress spec was removed with the mechanism (R-#233 Phase 2).

### 6.4 Why the dev run was hitting production

See §3: the shared E2E env helper defaults to production without
`IPDES`/`PUERTOPRU`, so the "dev" run used the dev fixture against production.
Once the Makefile exported the dev target, the four specs and the rest of the
grouped failures became green — which is what closed the original report.
