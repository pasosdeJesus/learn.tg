# R-#197: OpenBSD EDR Fallback — Fix Module Resolution & Tuple/Transfer Bugs

The `contract:test` runner uses `@ethereumjs/vm` as an EDR fallback on OpenBSD
because `@nomicfoundation/edr` has no prebuilt binaries for the platform.
While functional for simple tests, three categories of bugs prevent pre-existing
Hardhat tests from passing and cause false negatives in new tests.

---

## 1. TypeScript Module Resolution

### Problem

The runner (`index.js`, line 187) loads test files with Mocha. Test files import
typechain-generated types:

```typescript
import { CeloUbi } from "../typechain-types/contracts/CeloUbi";
import { LearnTGVaults } from "../typechain-types/contracts/LearnTGVaults.sol/LearnTGVaults";
```

Node.js native `import` cannot resolve `.ts` files without extensions:

```
Error: Cannot find module '...typechain-types/contracts/CeloUbi'
Error: Cannot find module '...typechain-types/contracts/LearnTGVaults.sol/LearnTGVaults'
```

### Root cause

The runner uses Node.js's native ESM loader (`import()`). Node does not
automatically resolve `.ts` extensions or transpile TypeScript. Hardhat's
native runner handles this via ts-node registration, but the EDR fallback
does not.

### Affected tests

- `LearnTGVaults.test.ts` — imports `LearnTGVaults` and `MockUSDT` from typechain
- `CeloUbi.test.ts` — imports `CeloUbi` from typechain

### Fix aplicado (2026-08-05)

**Opción A implementada** en `packages/m/src/tasks/contract-test/index.ts`:
```ts
const tsxRequire = createRequire(path.join(hardhatDir, 'node_modules', 'tsx', 'package.json'))
tsxRequire('tsx/cjs')
```
Registra tsx como loader CJS antes de que Mocha cargue los tests.
tsx resuelve imports `.ts` sin extensión y transpila TypeScript.

También se añadió mock de `hardhat` y módulos relacionados vía `Module._load`
para evitar que los tests importen el `@nomicfoundation/edr` nativo (no
disponible en OpenBSD).

### Resultado
- ✅ LearnTGVaults.test.ts: carga y compila — 34 tests corren (fallan por otros bugs)
- ✅ ClusterFunds.test.ts: carga y compila — 14 passing, 2 failing
- ⚠️ CeloUbi.test.ts: carga pero falla (`Cannot find module` para typechain-types/CeloUbi — el path no incluye `.sol/`)

## 2. Tuple Return Destructuring

### Problem

Solidity functions returning multiple values (tuples) are accessed as named
properties in Hardhat but as indexed arrays in the EDR fallback:

```typescript
// Works in Hardhat, fails in EDR:
const [usdtBal, slearnBal] = await contract.getClusterBalance(clusterWallet);
// TypeError: (intermediate value) is not iterable

// Works in EDR:
const result = await contract.getClusterBalance(clusterWallet);
const usdtBal = result[0];
const slearnBal = result[1];
```

Similarly, struct returns from `getClusterFunds()` fail to destructure:

```typescript
const [, , , verified] = await contract.getClusterFunds(clusterA);
// TypeError: (intermediate value) is not iterable
```

### Root cause

The hre-mock's `HardhatContract._proxy` (hre-mock.js) wraps contract calls with
a Proxy. When a Solidity function returns a tuple, ethers.js v6 returns an array
with named properties. The Proxy in hre-mock may strip or alter the iterable
protocol, making destructuring fail while indexed access works.

### Affected tests

Any test that destructures multi-return Solidity functions.

### Proposed fix

In `hre-mock.js`, the `HardhatContract._proxy` `apply` trap should ensure
returned arrays implement the iterable protocol:

```js
// In the apply trap, wrap tuple returns:
const result = await provider.eth_call(...);
const decoded = decodeFunctionResult({ abi, functionName, data: result });
// Ensure decoded is iterable (has Symbol.iterator)
if (Array.isArray(decoded) && !decoded[Symbol.iterator]) {
  decoded[Symbol.iterator] = Array.prototype[Symbol.iterator];
}
return decoded;
```

## 3. ERC20 Transfer Not Simulated

### Problem

Tests that call `token.transfer(contract, amount)` before `processDonation()`
see zero balance on the receiving contract. The transfer appears to succeed
(no revert) but the recipient's balance doesn't increase.

```typescript
await mockUSDT.connect(donor).transfer(contractAddress, parseUnits('100', 6));
await contract.processDonation(txHash, cluster, donor, amount, 0n);
// Expected: cluster balance = 85
// Actual: cluster balance = 0
```

USDT transfers work (cluster balance is correct for USDT) but SLEARN transfers
fail. The root cause may be:

- **Token deployed twice with same factory:** `MockUSDT` deployed as two
  separate instances. The second instance's bytecode is identical, causing
  the VM to confuse contract addresses or state.
- **State isolation:** The `@ethereumjs/vm` provider may not isolate state
  correctly for contracts with identical bytecode deployed at different
  addresses.
- **Nonce or address collision:** If the factory deploy uses the same nonce,
  the second deployment may fail silently or produce the same address.

### Affected tests

- `ClusterFunds.test.ts` — `processDonation` with SLEARN amount

### Proposed fix

**Option A — Use different bytecode:** Deploy a second MockUSDT instance with
different constructor args (e.g., different initialOwner or token name). Even
a different `initialOwner` should produce a different creation bytecode.

**Option B — Verify deployment addresses:** After deploying the second token,
assert that its address is different from the first. If they're identical,
the VM has a state isolation bug.

**Option C — Track deployed addresses:** In the EdrProvider, maintain a global
nonce counter per signer to ensure each deployment gets a unique address.

## 4. Debugging en curso

### Estado actual (`contract:test` en learn.tg)

| Test file | Passing | Failing | Issue principal |
|-----------|---------|---------|-----------------|
| LearnTGVaults | 0 | 34 | Address checksum mismatch (`0x5FbDB` vs `0x5fbdb`) |
| ClusterFunds | 14 | 2 | ERC20 transfer no simulada (0n vs 170000000) |
| CeloUbi | 0 | 15 | `Cannot find module typechain-types/CeloUbi` |

### Intento: Address checksum (LearnTGVaults)

El contrato devuelve direcciones en formato checksummed (EIP-55, mixed-case)
porque viem's `decodeFunctionResult` las checksumea. Pero
`HardhatEthersSigner.address` devolvía lowercase (las direcciones de
`HH_ACCOUNTS`).

**Fix intentado:** Checksumear `address` en el constructor de
`HardhatEthersSigner` usando `getAddress()` de viem. También en `getAddress()`.

**Resultado:** Sin cambio — los tests de LearnTGVaults siguen fallando con
el mismo error. El `owner.address` del test vs `learnTGVaults.owner()` del
contrato siguen teniendo diferente casing.

**Posible causa:** `loadFixture` puede estar cacheando el valor de `owner`
antes de que el constructor checksumee, o el contrato devuelve la dirección
con un checksum diferente al de viem.

**Próximo paso:** Hacer `console.log` de ambos valores en el runner para
confirmar qué está pasando realmente.

### Intento: `parseEther` (CeloUbi)

Añadido `parseEther` al `HreMock.ethers`. CeloUbi ya no falla con
`parseEther is not a function`, pero falla con `Cannot find module
typechain-types/contracts/CeloUbi`. El path no incluye `.sol/` como sí
lo hace LearnTGVaults.

### Pendiente: ERC20 transfer (ClusterFunds)

Los 2 fallos de ClusterFunds requieren depuración del `@ethereumjs/vm`:
el `token.transfer()` parece ejecutarse sin revertir pero el balance del
receptor no se incrementa. Posiblemente relacionado con el state isolation
del VM cuando hay múltiples instancias del mismo bytecode.
