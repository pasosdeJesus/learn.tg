## 1. Problem

The GoodDollar claim in learn.tg runs entirely through `@goodsdks/citizen-sdk`
(`components/GoodDollarClaimButton.tsx`: `new IdentitySDK(...)`, `new ClaimSDK(...)`,
`claimSDK.claim()`). The SDK is **not just a helper**: it enforces its own client-side
**verification-freshness policy**. When it decides the address needs a fresh face verification
it sends the page to `goodid.gooddollar.org`, throws `Error: User requires identity
verification.`, and the claim never happens — **even for an address the protocol would pay
immediately**.

So a third-party client-side rule can deny a student a benefit they are entitled to, and it can
change without notice. It also makes learn.tg depend on GoodDollar's services
(`goodid.gooddollar.org` for verification, `goodserver.gooddollar.org` for the whitelist sync):
if either is down, the button cannot complete even for an already-verified learner.

This is the root cause of the operator report of 2026-10-01: "en mainnet el botón dice Not
available in testnet" while claiming with the in-app wallet. The **wrong message** was fixed in
R-#271 §9 (the button now names the real cause and offers to unlock a locked in-app wallet); the
**SDK gate still sits in the claim path** and is what this issue removes.

## 2. Evidence — measured on Celo mainnet (2026-10-01)

The real-claim spec reached the button on production and clicked it; the SDK then moved the page
to `goodid.gooddollar.org` and threw `Error: User requires identity verification.`. Decoding the
link's `lz` payload gives the request: `{ account, nonce, fvsig, chain: 42220, rdu }`.

Measured on Celo mainnet for that same address (via the SDK's own production addresses,
`0xC361A6E6…` Identity and `0x43d72Ff1…` UBIScheme):

| Call | Result |
|---|---|
| `getWhitelistedRoot(address)` | the address itself → **whitelisted** |
| `getWhitelistedOnChainId(address)` | **42220** (Celo) |
| `lastAuthenticated(address)` | 21 days ago |
| `checkEntitlement(root)` | `114579521971939197166` → **UBI available today** |

So the demand is not a whitelist, chain or entitlement problem: it is the SDK's own freshness
rule (the operator reports GoodDollar asking for FaceTec more often lately). **The protocol has
no such gate.**

A direct CLI claim proved it with real money: tx
`0x31d264ee2f04e28cd5296d60e37850b23aefc55812e84f41d32d933d6435d358` — status success, `to` the
UBIScheme, input `0x4e71d92d` (`claim()`), and a `Transfer` of **114.579521971939197166 G$** from
the UBIScheme to the verified address. `checkEntitlement` became 0 while `lastAuthenticated`
stayed 21 days old: **the claim needed no FaceTec re-verification**.

## 3. Solution being implemented

Do what the **official GoodDollar browser wallet does** (the reference is
`github.com/GoodDollar/GoodWallet`, analysed below): read the protocol and claim **directly**,
and use GoodID + FaceTec only when verification is genuinely required.

1. Read `IdentityV2.getWhitelistedRoot(address)` (`!= zeroAddress` → whitelisted).
2. If whitelisted, read `UBIScheme.checkEntitlement(root)` (`> 0` → claimable today).
3. Decide with `resolveGoodDollarAction({ chainId, whitelisted, entitlement })`:
   - **`direct-claim`** — `UBIScheme.claim()` signed by the wallet, no GoodID;
   - **`verify`** — sign the fixed FV message (`personal_sign`), redirect to GoodID, and on
     return `syncWhitelist` and re-read;
   - **`nothing-today`** / **`unsupported-chain`** — honest message, no transaction.
4. Keep `@goodsdks/citizen-sdk` **installed but out of the runtime claim path**: it stays only as
   the source the protocol tests cross-check against.

## 5. Wiring the button to `lib/gooddollar-protocol.ts`

Through the hooks the project already has (`usePublicClient`, `useWriteContract`,
`useWalletProvider`):

1. `resolveGoodDollarReason({...})` (unchanged, `lib/gooddollar-reason.ts`). While it is not
   `'ready'` — `no-wallet`, `locked`, `provider-unsupported`, `network-unsupported`, `sdk-error`
   — keep today's message and the unlock dialog and run nothing else.
2. With a signer, read the protocol:
   ```
   chainId = getAppChain().id
   root = publicClient.readContract({ address: GOODDOLLAR_ADDRESSES.identity,
            abi: GOODDOLLAR_IDENTITY_ABI, functionName: 'getWhitelistedRoot', args: [address] })
   whitelisted = root !== zeroAddress
   entitlement = whitelisted
     ? await publicClient.readContract({ address: GOODDOLLAR_ADDRESSES.ubi,
         abi: GOODDOLLAR_UBI_ABI, functionName: 'checkEntitlement', args: [root] })
     : 0n
   ```
3. `resolveGoodDollarAction({ chainId, whitelisted, entitlement })` decides:
   - `unsupported-chain` → honest message (`networkUnsupported` already says mainnet-only), disabled;
   - `nothing-today` → "you already claimed today", disabled;
   - `direct-claim` → `writeContract({ address: GOODDOLLAR_ADDRESSES.ubi, abi: GOODDOLLAR_UBI_ABI, functionName: 'claim' })`, then the success toast;
   - `verify` → sign `goodDollarFvMessage(address)` through the provider (`personal_sign`) to get `fvsig`, then
     `window.location.assign(buildGoodIdVerificationUrl({ account: address, chainId: GOODDOLLAR_CHAIN_ID, fvsig, firstname, returnUrl: window.location.href }))`.
4. On mount, before step 2, read the return: `parseGoodIdReturn(window.location.href)`.
   `verified === true` → `GET ${GOODDOLLAR_SERVICES.backend}/syncWhitelist/{address}`
   and continue with step 2 (the whitelist must be visible now); `verified === false` →
   show `reason` and stop.
5. Read the facts once and report a change instead of failing opaquely:
   `detectProtocolChange({ chainId, identityHasCode, ubiHasCode, ubiPaused, gDecimals })`
   (`getCode` for the two contracts, `paused()`, the G$ `decimals()`); a non-empty result
   is its own message.

Details that matter:

- **`firstname`** for the GoodID link: GoodWallet sends the profile's name; learn.tg has no such
  field, so send the account (or a name if the session ever carries one) and note the choice in a
  comment.
- The verification is a **redirect**, so the only state that must survive is the URL it returns
  (`verified`, `reason`, `chain`) — do not add localStorage.
- `personal_sign` must go through `useWalletProvider()`, never `window.ethereum` directly, so the
  in-app wallet works; the in-app wallet signs while unlocked and its gesture gate is the normal
  path.

## 9. Risks and notes

- If the direct path ever needs the SDK back, the honest fallback is to keep GoodDollar
  **external-wallet only** and say so in the button and in the course, with learn.tg-UBI as the
  in-app path (that is already the course direction).
- GoodDollar can change its contracts or the FV message without notice; `detectProtocolChange()`
  and the tests that cross-check the installed SDK are how the project notices instead of failing
  silently.
- The in-app wallet locks on reload and after an hour of inactivity (R-#246): "locked" is a normal
  state, not an error.
- The claim is an on-chain transaction signed by the wallet: it inherits the gas rule (a little
  CELO for the network fee).

**Two test bugs fixed in both specs** (they made the wallet look "never signed in"):

1. `page.evaluateOnNewDocument("localStorage.clear()…")` runs on **every** document; the SIWE of the
   import does `window.location.reload()`, so the hook wiped the session the import had just created
   and the spec always died in `no session`. Now the specs use an **incognito browser context**
   (clean profile) instead of clearing, which leaves the reload working.
2. After that reload the in-app wallet is **locked** (the key leaves memory) and the button stays in
