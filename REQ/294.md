# R-#294: New proposal to releae gdcluster country funds

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/294
**Created:** 2026-11-01
**Status:** Proposal — needs a new function in the contract (a new `ClusterFunds` version or
an upgrade) and a deployment. Today the country fund is distributed by pdJ among the verified
clusters (a cluster is verified when pdJ presents it to GD).
**Type:** Contracts / GD cluster funds
**Priority:** Medium — it changes how much of the country fund a cluster receives when it
completes the process; the current rule gives the whole balance to the first cluster.

---

## 1. Objective

When **Global Disciples answers the presentation of a cluster**, that cluster receives
**50 % of the balance of its country fund at that moment** instead of the equal split among
all the presented clusters. The other 50 % stays in the country fund for the next cluster.

The condition is objective and already exists: `answered` is the state in which R-#161
releases the funds today. There is no date to schedule and no waiting for pdJ to decide.

## 2. Current behavior (what the app does today)

"Presented in the database (`sent`) = verified in the contract": the backend calls
`setClusterVerification(wallet, true)` when pdJ presents the cluster to Global Disciples, so
several clusters of a country can be verified at the same time (they are shown in green in
the ranking and keep their fund, without the Donate button).

When pdJ records GD's answer (`answered`), the backend calls
`redistributeCountryFunds(countryCode, wallets)` with the presented/verified clusters of the
country: the **whole** country fund is split **equally among them** (each share is credited to
that cluster's fund), and right after that the answered cluster's fund is released to its
wallet (`releaseClusterFunds`). That is the rule in R-#161 and in guides 3 (EN/ES).

This is why the 50 % cannot be enforced today: the deployed contract only splits the fund
equally among N clusters or sends it whole to one recipient; there is no function that moves a
**percentage** of the country fund to one cluster. The available paths are:

| Function | What it does | Who calls it |
|---|---|---|
| `redistributeCountryFunds(countryCode, clusters[])` | Splits the whole country fund **equally among the verified clusters given** and empties it. | `onlyOwner` (the backend, when a cluster completes) |
| `releaseCountryFunds(countryCode, recipient)` | Sends the **whole** country fund to `recipient` and empties it. | `onlyOwner` (available; the app does not call it) |
| `releaseClusterFunds(clusterWallet)` | Sends the cluster fund to the cluster wallet. Requires `fund.exists && fund.verified`. | `onlyOwner` (the backend, at the approval) |

## 3. Proposal

Add to the contract (next version) a function that transfers a percentage of the country fund
to one cluster:

```solidity
function transferCountryFundToCluster(
    string calldata countryCode,
    address clusterWallet,
    uint8 pct
) external onlyOwner whenNotPaused nonReentrant;
```

It moves `pct` (1-50) of the current country balance (USDT and SLEARN, independently) to
`clusterFunds[clusterWallet]` and emits
`CountryFundTransferred(countryCode, clusterWallet, usdtAmount, slearnAmount, pct)`.

Guards:

1. `pct` between 1 and 50 (R-#161 proposes 50 as the value).
2. `countryFunds[countryCode].exists` and `clusterFunds[clusterWallet].exists`.
3. `clusterFunds[clusterWallet].verified` — the cluster was presented to GD
   (`setClusterVerification` set by the backend when pdJ marks `sent`).
4. The cluster has not received its country share before: a per-cluster boolean
   (`countryShareReceived`) set in the same call, so the operation is idempotent.
5. No tokens are transferred when the computed amount is below the minimum (`1e6` USDT or
   `1` SLEARN, the same thresholds as `releaseClusterFunds`).

Order in the backend flow, when pdJ records the answer (the cluster is already verified
since it was presented):

```
transferCountryFundToCluster(countryCode, wallet, 50)   // new
releaseClusterFunds(wallet)
```

If the country transfer reverts (empty fund, already received), the release must **not** be
blocked: log it (`admin_solves` type `gd_country_transfer`) and continue with
`releaseClusterFunds`. The country share is a benefit, not a precondition for the withdrawal.

## 4. Changes in the app (after the contract exists)

- Replace the `redistributeCountryFunds` call in
  `packages/gdcluster/src/lib/cluster-release.ts` (used by the `answered` transition) with
  `transferCountryFundToCluster(..., 50)` (the answered cluster keeps 50 %, the rest stays
  for the next one); keep `releaseClusterFunds` as it is. The distribution call no longer
  needs the list of verified clusters.
- `clustergd.country_fund_received_at` / `country_fund_amount` (USDT) /
  `country_fund_received_slearn`, written by the backend when the transfer confirms; the
  cluster page shows them (today the amounts are only in the history entry).
- Guides 3 (EN/ES): change "the country fund is split equally among the presented clusters"
  to "the cluster receives 50 % and the rest stays for the next cluster".
- R-#161 §"Country fund → cluster fund" becomes this rule.

## 5. Acceptance criteria

- [ ] The contract exposes `transferCountryFundToCluster` with the guards of §3 and the event.
- [ ] A test proves: 50 % moves, the rest stays, `pct > 50` reverts, a second call for the same
      cluster reverts or does nothing, and a non-verified cluster reverts.
- [ ] The backend calls it before `releaseClusterFunds` when pdJ records `answered`.
- [ ] A failure in the country transfer is logged and does not block the release of the
      cluster fund.
- [ ] The cluster page shows the country share received (date and amounts).
- [ ] Both guides describe the 50 % and the operator verifies it on the testnet with two
      clusters: the first keeps half and the rest stays in the country fund for the second.

## 6. Open questions

1. **Keep `redistributeCountryFunds`?** It is the call the app makes today when a cluster
   completes; with the 50 % rule a cluster could receive twice (once by redistribution, once
   by the 50 %). The 50 % call replaces it, so the question is what to do with the general
   tool for pdJ.
2. **50 % of what?** The proposal uses the balance **at the moment of the transfer**. If the
   cluster takes months to approve the withdrawal, the fund may have grown with other
   clusters' 10 %; that is intentional, but a `maxAmount` parameter can cap it.
3. **Country classification.** The cluster's country is `clustergd.country_id`; the contract
   uses the ISO alpha-2 code. The backend maps it with `msip_pais.alfa2` and skips the
   transfer when the country is unclassified.
4. **Which contract version.** `ClusterFundsV2` is deployed; a new function needs a new
   deployment (V3) and a decision about the funds already credited in V2.

## 7. Out of scope

- Automatic release at 100 % of the first-year budget: rejected on 2026-10-22 (the fund is
  released only when every pastor approves).
- Sending the country share to the initiator instead of the cluster fund: rejected, it does
  not solve a conflict between pastors; the cluster mediates or reconfigures first.
