## 1. Donation to a course vault recorded without the "donation received" modal

- **Symptom:** when donating to a course vault, the donation **is recorded** (the
  backend receives it, `/api/add-donation` returns 200) but the **"Donation
  completed" modal is not shown**, with its distribution breakdown
  (`resultDistribution`).
- **Additional symptom (user report):** confirming the payment in the wallet
  **refreshes the whole page**. That reload is what prevents seeing the result
  modal (which lives in `DonateModal` React state): after the reload the state is
  lost, even though the donation was already persisted in the backend.
- **Contrast:** donating to the **Lensenia** campaign does show the modal with the
  breakdown after confirming in the wallet. That is, the `campaign-donation` path
  does not trigger the refresh; the `course-donation` path (course vault, ERC-20
  USDT/SLEARN via `useContractPayment`) does.
- **Refresh hypothesis (to confirm):** `components/WalletEventListener.tsx` calls
  `signOut({ redirect: true, callbackUrl: '/' })` on `accountsChanged([])` or
  `disconnect`; and `ConnectWalletButton` calls `window.location.reload()`. If the
  wallet (mobile / Rabby / OneKey) emits an empty `accountsChanged` or
  `disconnect` during/after the ERC-20 confirmation, the app reloads and the modal
  is lost. It remains to distinguish which of the two triggers fires (log of
  `[WalletEventListener]` or of `accountsChanged`) and why it does not happen in
  the campaign flow.
- **Affected flow (secondary hypothesis):** `components/DonateModal.tsx` →
  `useContractPayment` → `onBackendCallback` → `POST /api/add-donation` → the hook
  calls `onSuccess?.({ increment, usdtHash, slearnHash, ...backendResult })` and
  `DonateModal` sets `setShowResult(true)` + `setResultDistribution(...)`. Since
  the 200 is recorded but the modal is not seen, the suspect is that `showResult`
  is lost due to the reload described above (not necessarily a bug in
  `setShowResult`).
- **Pending diagnosis:** confirm with `[PayDiag]`/console what `/api/add-donation`
  returns (does it include `distribution`?), whether `onSuccess` fires, and which
  wallet event triggers the reload (empty `accountsChanged` vs `disconnect`).

## 1a. Diagnosis — trigger confirmed (2026-09-08, spec `diag-donation-refresh`)

Controlled reproduction on dev (`learn.tg:9001`) with an EIP-1193 provider that
captures handlers and emits the event after opening a course with a vault:

```
[DiagEmit] accountsChanged → 6 handler(s)
[WalletEvtDiag] accountsChanged {"inFlight":false,"sessionAddr":"0x84272a6d", detail:{count:0,empty:true}}
[WalletEvtDiag] accountsChanged -> signOut(redirect:true)
→ page reloads/navigates to "/"  (REPRODUCED)
```

**Conclusion:** the refresh that loses the "Donation completed" modal is the
`signOut({ redirect: true, callbackUrl: '/' })` in `WalletEventListener.tsx`,
triggered by `accountsChanged([])` (and also `disconnect`, same handler). The
backend is NOT the problem: `POST /api/add-donation` returns 200 with the full
`distribution` (verified with `vault-both-donate.spec.mjs`).

**Why the campaign (Lensenia) does show the modal:** its flow
(`handleNativeDonate`) confirms with `eth_sendTransaction` and does not trigger
the `accountsChanged` event on the tested wallet; the ERC-20 flow of
`useContractPayment` does trigger it (or the user confirms in a way that makes
the wallet emit the event).

**Proposed fix (to validate):** in `WalletEventListener`, when the event arrives
with a donation in flight (`window.__donationInFlight === true`, set by
`DonateModal`) **do not** call `signOut(redirect)` if the wallet still reports the
same connected account after the event (re-check `eth_accounts`); or debounce the
`accountsChanged([])` (wait and re-verify `eth_accounts` before signing the
disconnect). Never blindly ignore: a real disconnect must still clear the
session.

## 1b. Fix implemented (2026-09-08)

`components/WalletEventListener.tsx`: the handlers for `accountsChanged([])` and
`disconnect` **no longer blindly sign out**. After the event they wait
`debounceMs = 400` and re-verify with `eth_accounts`:
- if the wallet is still connected (account present) → the event was transient
  (tx confirmation) → **the session is kept** and there is no reload → the result
  modal survives.
- if there is still no account → real disconnect → `signOut({ redirect: true })`
  as before.

Verified by regression E2E: firing `accountsChanged([])` without the account
changing **no longer reloads** the page. Manual validation remains on the dev site
by donating to a vault with a real wallet.
