# R-#221: Security audit — money-related operations

Security audit of the learn.tg sources, with special attention to the
operations that move or grant money (UBI claims, crossword rewards, donations,
premium payments, scholarships, pastor bonus, credential mint, verification
flows that unlock rewards).

**Status:** In progress
**Created:** 2026-09-01 (last reviewed 2026-10-02)

---

## Progress (2026-09-09)

- **Automated API-route audit** (related): `apps/nextjs/bin/audit-api-auth.mjs`
  classifies every sensitive endpoint (DB/files) as public / authenticated /
  **admin-only**, with a `nombre` advisory — **59 passed / 0 failed** re-run 2026-10-02
  (14 public · 16 admin-only · 29 authenticated · 5 advisories; the split moved against the
  2026-09-25 run, which recorded 14 public · 14 admin-only · 31 authenticated). Rules in
  `doc/api-security.md`. It runs in CI (`.github/workflows/ci.yml`).
- **Money endpoints covered by the recent review:**
  - Campaign donations R-#223 (USDT/CELO/USDC/XAUt0/G1001 1001 0 5 10 20: on-chain
    verification of the transfer, server-side recomputation from the receipt,
    automatic split/forwarding, USDT-only SLEARN cashback with reserve
    (`mintAndReserve`), replay protection via `(crypto, hash)` UNIQUE.
  - Premium purchase R-#128/#225: `expectedPrice` computed server-side; minimum
    payment validated against the country price.
- **Existing protections to keep**: `lib/replay-protection.ts`
  (`checkReplayAttack`), `verify-transfer` (receipt logs), ECDSA signatures with
  `recoverAddress` (no malleability), private keys server-side only.
- **Linked critical item** (resolved): root cause of the SIWE 401s
  (rotated CSRF token vs session cookie) — see R-#224; it affected the guarantee
  "every money operation is authenticated" in long-lived/multi-device sessions.

**Revision 2026-09-25:** the route audit was run again: **59 passed / 0 failed** (14 public ·
14 admin-only · 31 authenticated · 5 `nombre` advisories), up from 54 on 2026-09-09.

`checkReplayAttack` with `(crypto, hash)` UNIQUE

receipts. The §2-§7 checkboxes are still **unchecked**: the controls exist and the automated
inventory is done, but the flow-by-flow review (and the §7 report) has not been completed, so
it is **not closable**.

      `doc/api-security.md` §1

### 2. Authentication & authorization
- [ ] Every money route requires a valid session (authenticateUser) — no unauthenticated grants
- [ ] Admin-only operations check the verifier/admin role server-side (pastor-bonus, credentials admin, update-scores)
- [ ] SIWE / verifyMessage: signatures verified correctly (recover address, no signature malleability)

### 3. On-chain payment verification & replay
- [ ] Payments verified on-chain before crediting (hash → receipt, verify-transfer)
- [ ] Replay protection: a tx hash / claim cannot be reused (double-claim, double-spend)
- [ ] Signed messages use nonces/timestamps to prevent replay

### 4. Amount validation (server-side)
- [ ] Amounts recomputed/validated server-side (never trust the client)
- [ ] Min/max limits on UBI, crossword, scholarship, donations, premium
