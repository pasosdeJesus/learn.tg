## 1. Current state

The leaderboard (`/api/leaderboard` → `lib/leaderboard-queries.ts` →
`components/LeaderboardTable.tsx`) shows these columns, all sortable:

| Column | Source |
|---|---|
| Rank, User, Country, [Religion] | `usuario`, `msip_pais`, `religion` |
| Profile Score | `usuario.profilescore` |
| SLEARN | **net balance** (`SUM(balance_impact)` over `transaction`) |
| Scholarship (USDT) | `SUM(amount)` of `transaction` `type = 'scholarship' AND crypto = 'usdt'` |
| UBI (CELO) | `SUM(amount)` of `type = 'ubi-claim' AND crypto = 'celo'` |
| Donations (USDT) | `SUM(amount)` of `type = 'donation' AND crypto = 'usdt'` |
| SBTs | `credential_emission`, filtered by the https://github.com/pasosdeJesus/learn.tg/issues/259 visibility rule |

Default sort is `slearn_balance` desc. `usuario.excluir_leaderboard = true` opts a
user out. The board does not show the **work on the guides**.

## 2. Change requested (operator, 2026-10-02)

The course page draws, in front of each guide, the marks the student earned: a
**checkmark** (passed), the **USDT** scholarship and the **SLEARN** scholarship. The
leaderboard must **add up those three marks across all the student's guides**, in three
columns, with the **main column being the sum** (default order desc). **All courses count**
(every published course, free and paid).

| Column | Meaning | Same rule as |
|---|---|---|
| **Guías aprobadas** (checkmarks) | Guides passed | `/api/guide-status` → `completed` |
| **Guías con beca USDT** | Guides whose USDT scholarship was paid | `receivedScholarship` |
| **Guías con beca SLEARN** | Guides whose SLEARN scholarship was paid | `receivedSlearnScholarship` |
| **Puntaje en Guías / Guide Score** (**main**) | **Sum of the three** | computed in SQL |

- The main column is **"Guide Score"** in English and **"Puntaje en Guías"** in Spanish.
  The SQL key, the API field and `sortBy` are `guide_score`; both the label and the
  identifier were renamed from "Greens"/"Verdes" on 2026-10-02 (see §8).
- These are **counts of guides**, not token amounts. The existing columns (SLEARN
  balance, USDT/SLEARN token amounts, UBI, donations, SBTs) are **kept**.
- The sum is computed in the **SQL query** (the fastest option that keeps sorting and
  pagination correct; a client-side sum would only order the current page).
- The exact meaning of each mark already lives in `app/api/guide-status/route.ts`, and
  the leaderboard must reuse it so the board and the course page always agree:
  - **aprobada**: `guide_usuario.points > 0`;
  - **beca USDT pagada**: `guide_usuario.amountpaid > 0`;
  - **beca SLEARN pagada**: a `transaction` row with `crypto = 'slearn'`,
    `type = 'scholarship'` and `metadata->>'guideId' = actividadpf_id` for that guide.
- A guide that is approved but **not paid** (profile score < 50, empty vault, cooldown)
  counts **1** in "Guías aprobadas" and **0** in the paid columns; that is how the
  course page shows it.
- **SLEARN bonuses are not effort.** Some SLEARN is granted for something other than
  doing guides (the 22-SLEARN pastor bonus is paid when the pastor registers, not for
  guides), which is exactly why the column counts **guides with a SLEARN scholarship**,
  never the SLEARN balance.

## 3. Data and privacy

- New aggregates per user: `guide_approved`, `guide_usdt`, `guide_slearn`, and
  `guide_score = guide_approved + guide_usdt + guide_slearn`.
- **Public surface**: the counts must apply the same visibility rule as `sbt_count`
  (`usuario.mostrar_cursos_publico`, and for **category B** courses only when
  `mostrar_cursos_sensibles_publico` is true), otherwise the board would reveal that a
  student studies category B (sensitive) content. The rule lives in one place
  (`packages/rewards/src/lib/course-privacy.ts`, re-exported by
  `apps/nextjs/lib/privacy-visibility.ts`); reuse it, do not write a new one.
  **Where the rule really lives (verified 2026-10-02):** the canonical module exposes a
  **TypeScript** predicate (`canShowCoursePublicly`) and documents the equivalent SQL
  conditions in its doc comment; it publishes **no SQL fragment**, so a SQL query can
  only restate the rule — "reuse it" holds at the level of the rule, not by importing
  it. The restatement is duplicated inside the same file (SBT subquery
  `lib/leaderboard-queries.ts:48-52`, guide subquery `:71-75`); the tests assert it on
  both, and collapsing the two into a single SQL fragment is recorded in
  https://github.com/pasosdeJesus/learn.tg/issues/252.
  The join is `guide_usuario` → `cor1440_gen_actividadpf` →
  `cor1440_gen_proyectofinanciero`.
- Keep `usuario.excluir_leaderboard` as the opt-out. It applies to the **board**; the
  profile (§9) still publishes the user's guide score, because the opt-out is about
  appearing in the ranking, not about hiding the work.
- Only `nusuario` is exposed; never the real `nombre` (see `doc/api-security.md` §1).

**Label and identifier renamed (2026-10-02).** The column was called "Greens" (EN) and
"Verdes" (ES), and the identifier was `verdes`. In Spanish *verdes* is slang for money and
the board already has columns that are money (SLEARN, Beca USDT, UBI CELO, Donaciones
USDT), so the count read as an amount; and the metaphor was not used anywhere else on the
site (only the board named it). The labels are now **"Guide Score"** / **"Puntaje en
Guías"** and the identifier is **`guide_score`** (SQL alias, JSON field and `sortBy`), so
it matches its siblings `guide_approved` / `guide_usdt` / `guide_slearn`. It is a computed
alias, so there is no migration. **The response field name changed**: a consumer reading
`verdes` must switch to `guide_score` (in the repository the only consumers were the board
and the smoke spec, both updated). The E2E smoke asserts the labels and the fields, so it
must be deployed together with the change.

## 9. The profile shows the same score (2026-10-02)

The operator asked the public profile (`/[lang]/user/[id]`) to show the **guide score**
instead of the SLEARN balance, and to add the **number of referrals**. Both are the same
measure or the same definition as the board, never a second one:

| Change | File |
|---|---|
| The profile's SLEARN balance tile became the guide score tile; a referrals tile was added | `app/[lang]/user/[id]/page.tsx` |
| The response drops `slearn_balance` and adds `guide_score` and `referral_count` | `app/api/user/[id]/route.ts` (submodule `app/api`) |
| `getUserLeaderboardRank` became `getUserLeaderboardStats`, which returns the rank **and** the guide score from the **same** query (one canonical order, one R-#259 rule) | `lib/leaderboard-queries.ts` |
| **The board also gained the referrals column** (the operator's decision, 2026-10-02: the total, published, for every region for now — see below) | `lib/leaderboard-queries.ts`, `types/leaderboard.ts`, `app/api/leaderboard/route.ts`, `components/LeaderboardTable.tsx`, `components/MetricsExplanation.tsx` |

**Opt-out semantics (`excluir_leaderboard`).** The board leaves an opted-out user out;
their profile still publishes the guide score. The base query therefore takes an option to
include them, and the rank uses `ROW_NUMBER() OVER (PARTITION BY (u.excluir_leaderboard IS
NOT TRUE) ...)`: the position of the users who do appear does not change, and the route
reports `leaderboardRank: null` for the ones who opted out (their score is not zeroed).

**Referrals.** `referral_count` is `COUNT(*)` of `referralrelationship` where the user is
the referrer (https://github.com/pasosdeJesus/learn.tg/issues/163), the **total** (pending
and completed together). It is one of the board's columns and it is **public for every
region**, decided by the operator on 2026-10-02 ("es plataforma de cripto"): the platform
already publishes who has which credentials, and the count says nothing about *who* was
invited. The detail (pending, completed, payouts) stays in `/api/referral/stats`, which
authenticates the owner.

**It is not part of the canonical order**: the Rank column keeps ordering by `guide_score`,
so a new referrals column never moves a student's position. The count is computed in its
own subquery grouped by referrer, so the join cannot multiply the rows of `transaction` and
inflate the money aggregates (checked against a local PostgreSQL: the SLEARN total of the
users with referrals is identical with and without the join).
