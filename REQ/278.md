**Link:** https://github.com/pasosdeJesus/learn.tg/issues/278

## 1. Objective

The board and the course page must tell the same story: the **work on the guides**, the
**referrals**, the token columns, and **one global rank** that does not depend on the column
the visitor sorts by. The board is `/api/leaderboard` → `lib/leaderboard-queries.ts` →
`components/LeaderboardTable.tsx`.

## 2. Columns

| Column | Source |
|---|---|
| Rank, User, Country, [Religion] | `usuario`, `msip_pais`, `religion` |
| Guide Score / Approved / Paid USDT / Paid SLEARN | `guide_usuario` + `transaction`, §3 |
| SLEARN | net balance (`SUM(balance_impact)` over `transaction`) |
| Scholarship (USDT) | `SUM(amount)`, `type = 'scholarship' AND crypto = 'usdt'` |
| UBI (CELO) | `SUM(amount)`, `type = 'ubi-claim' AND crypto = 'celo'` |
| Donations (USDT) | `SUM(amount)`, `type = 'donation' AND crypto = 'usdt'` |
| SBTs | `credential_emission`, filtered by the R-#259 rule |

**Aggregates only** (never per row, so that their absence cannot point at anybody): the
`platform_score` that orders the board (§4), the `profilescore` and the total number of
**referrals** (https://github.com/pasosdeJesus/learn.tg/issues/163), which is published as a
total in the board's summary block (`totalReferrals`). The profile score and the platform score
of a student are not published either: only their position.

Default order: `platform_score` desc (§4). `usuario.excluir_leaderboard = true` opts a user
out of the board. Only `nusuario` is exposed, never the real `nombre`
(`doc/api-security.md` §1).

## 3. Guide score — the marks the course page draws

The course page draws, in front of each guide, the marks the student earned: the
**checkmark** (passed), the **USDT** scholarship and the **SLEARN** scholarship. The board
counts them **per guide** with the same rule as `/api/guide-status`, so the two surfaces
cannot disagree:

- **approved**: `guide_usuario.points > 0`;
- **USDT scholarship paid**: `guide_usuario.amountpaid > 0`;
- **SLEARN scholarship paid**: a `transaction` row with `crypto = 'slearn'`,
  `type = 'scholarship'` and `metadata->>'guideId'` = the guide's `actividadpf_id`.

`guide_score` is their sum ("Puntaje en Guías"/"Guide Score"). A guide that is approved but
not paid counts 1 in "approved" and 0 in the paid columns. **All published courses count**,
free and paid. The SLEARN bonus is not effort (22 SLEARN go to the pastor when registering,
not for guides), which is why the column counts **guides with a SLEARN scholarship**, never
the SLEARN balance.

## 4. `platform_score` — the ranking

```
platform_score = 0.35 * n(guide_score)
               + 0.15 * n(referral_count)
               + 0.15 * n(donations_usdt)
               + 0.15 * n(sbt_count)
               + 0.10 * n(slearn_balance)
               + 0.10 * n(profilescore)
```

It **orders** the board (and the profile's rank) and is **not published per row** (§4.1): what
the student sees is the position.

- **`n(x)`: min-max over `ln(1 + max(x, 0))`**, in 0–100 after the weighted sum. One rule for
  all six components. `percent_rank()` was rejected: in skewed components (referrals,
  donations, SBTs) it turned the weight into a binary bonus (the first referral jumped to the
  top percentile). `ln(1 + x)` compresses the tail, and a flat component or a one-row
  population contributes **0** instead of dividing by zero.
- **Population**: the board (`excluir_leaderboard IS NOT TRUE`), computed **before** the
  country filter, so a student's score and rank do not change with the visitor's filter.
- **Canonical order**: `platform_score DESC, usuario_id ASC`. `usuario_id` is unique, so the
  order is total and pagination cannot repeat or skip users. The board's **Rank** column
  (`ROW_NUMBER()` over that order) and the profile's rank (`/api/user/[id]`) use the same
  definition, so they cannot diverge.
- **Cost**: measured at 24 ms over ~570 users (three times the previous query), computed in
  SQL.

### 4.1 Published only as aggregates

`referral_count`, `platform_score` and `profilescore` are **never sent per row** (not on the
board, not on a profile): the referrals appear as the `totalReferrals` aggregate of the board's
summary, the two scores only as the ordering that produces the Rank. The reason is
`doc/api-security.md` §6: if a value were hidden for some rows and shown for others, its absence
would be a public signal.

The region logic survives **inside the order** for the rows whose owner is in region type 2
(`msip_pais.tipo_region`; `NULL` counts as region type 1): their score — and therefore their
position — is computed over the four visible components with the weights renormalized over
0.75, so it carries nothing of `referral_count` or `profilescore`. The owner can still see their
own values in the authenticated `/api/referral/stats` and `/api/profile`.

**Residual exposure (accepted, 2026-10-05).** The four visible components are public, so a
visitor can recompute the score of any row and check its position. For a **region type 2** row
that reveals nothing (its score has no referral or profile term). For a **region type 1** row it
does: two students with the same visible components are ordered among themselves **only** by the
two unpublished terms, so their relative position can suggest who brings more people. The order
keeps the six components (the two weights still count) and that inference is accepted; ordering
everyone by the visible components only — dropping the 0.15 and 0.10 weights — was rejected
because it would stop rewarding referrals and the profile score.

## 5. Referrals

`referral_count` counts the `referralrelationship` rows where the user is the referrer —
the **total** (pending and completed together) — in its own subquery grouped by referrer, so
the join cannot multiply the rows of `transaction`. It is **not published per student**: what is
public is the platform total (`totalReferrals` in the board's summary, scoped to the selected
country when the board is filtered), because the operator wants the platform's referral
activity visible without exposing who brings whom. The detail (pending, completed, payouts)
stays in `/api/referral/stats`, which authenticates the owner.

## 6. Privacy and opt-out

- The counts apply the same visibility rule as `sbt_count`: `usuario.mostrar_cursos_publico`,
  and for **category B** courses only when `mostrar_cursos_sensibles_publico` is true.
  Otherwise the board would reveal that a student studies category B content. The rule lives
  in `packages/rewards/src/lib/course-privacy.ts`, re-exported by
  `apps/nextjs/lib/privacy-visibility.ts`; it is a **TypeScript predicate** with no SQL
  fragment, so the query restates the conditions (SBT subquery and guide subquery). Removing
  that duplication is recorded in https://github.com/pasosdeJesus/learn.tg/issues/252.
- `excluir_leaderboard` applies to the **board**: the profile still publishes that user's
  guide score (the opt-out is about appearing in the ranking, not about hiding the work), but
  not a rank or a platform score, which are defined on the board's population.
- The profile (`/[lang]/user/[id]`) shows the guide score instead of the SLEARN balance. The
  platform score, the profile score and the referrals are not published there either (§4.1); the
  owner reads their own profile score in the authenticated `/api/profile` and `/api/update-scores`.
- **Between surfaces.** The guide columns are shown on the board even in region type 2, while
  the church directory (https://github.com/pasosdeJesus/learn.tg/issues/164) hides
  `guide_score` in region type 2: what the directory hides can be read per student here. It is
  accepted, because the board is individual (it does not expose a church) and the guide counts
  do not reveal category B membership (the rule above), and because the directory's hiding is
  about the church's aggregate.
- The public totals (`getLeaderboardTotals`) aggregate the token amounts and the referrals of
the whole population, region type 2 included: they are aggregates, not per-person data, and
they are part of the transparency surface.

## 10. Out of scope

- Persisting `platform_score` (it is computed on the fly; a materialized view can be added if
  the population grows and the query becomes expensive).
- Exposing the intermediate values of the formula.
- A score history over time.
