# R-#248: Configurable inactivity auto-lock (optional)

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/248

**Status:** Pending — **optional / not a priority**. The fixed auto-lock already
ships (https://github.com/pasosdeJesus/learn.tg/issues/246): **one hour** since
2026-09-19 (`INACTIVITY_LOCK_MS` in
`packages/pdj-wallet-next/src/useInAppWallet.ts`; it was ten minutes until the
operator had to unlock again in the middle of a donation); this requirement is only
about letting the user or the operator change that value.
**Created:** 2026-09-18
**Type:** UX (optional)
**Priority:** Low — the default is enough for the current audience; do this if real
users ask for it or if support sees a concrete problem
**Dependencies:** https://github.com/pasosdeJesus/learn.tg/issues/246

---

### 1. Objective

Make the inactivity timeout of the in-app wallet configurable, instead of the fixed
`INACTIVITY_LOCK_MS` (**one hour** since 2026-09-19; it was ten minutes) of R-#246,
without weakening the defaults for
first-time users.

### 2. What exists today

`packages/pdj-wallet-next/src/useInAppWallet.ts` locks the wallet (drops the key
from memory, `lockReason: 'idle'`) after one hour without pointer, key, touch,
scroll or visibility activity (ten minutes before 2026-09-19: the operator had to
unlock again in the middle of a donation, see R-#246 §10). `WalletEventListener` deliberately does **not** sign the user
out on that lock — only the header ✕ (`'user'`) or deleting the wallet
(`'deleted'`) end the session. The behaviour mirrors OneKey and OKX Web3, where the
user can pick the timeout in the app settings.

### 3. Why it is optional

- The audience is on shared or borrowed phones; a longer timeout is convenient but
  is also the setting most likely to be chosen carelessly.
- Every extra option in the wallet dialog costs attention for a first-time user who
  is already typing a PIN and writing 12 words down.
- The measured need is zero so far: the complaint that started R-#246 was **too
  many** prompts, not too few, and the fix for that was the biometric unlock.

### 4. Design sketch (if it is done)

| Question | Proposal |
|---|---|
| Who can change it | The user, from the wallet dialog (the same panel that enables the fingerprint), never from a hidden global setting |
| Options | 1 min / 1 hour (default) / 4 hours / 1 day / never, as explicit choices (the spectrum Rabby offers in its settings: `useAutoLockOptions` in `src/ui/views/Dashboard/components/Settings/index.tsx` is never / 7 days / 1 day / 4 h / 1 h). Note its stored default is `0` = never, which is the wrong end of the spectrum for a shared phone |
| Where stored | Next to the wallet in IndexedDB (`biometric` store or a small `settings` record); it is not a secret |
| Device-scoped | Yes: it is a device preference, not a wallet property. It must **not** sync (a phone in Sierra Leone and a workstation in the office have different threats) |
| Effect on the session | None: the lock is `'idle'`, so it never signs the user out |
| Effect on the funds gate | None: L1 (a fresh gesture before `eth_sendTransaction`, `eth_signTypedData_v4` and `eth_signTransaction`, implemented 2026-09-19) does not depend on the timeout, so a longer timeout cannot make a transfer or an authorization signature silent. |
| "Never" | Only allowed when a passkey is enrolled; otherwise the PIN would be the only protection and the wallet would stay open on a borrowed phone |

### 5. Acceptance criteria

- [ ] The dialog shows the current timeout and lets the user change it, in Spanish
      and English.
- [ ] The default stays one hour and is what a new wallet gets.
- [ ] The value is stored per device and read at unlock time (no reload needed).
- [ ] `lockReason: 'idle'` keeps not signing the user out; unit test for each
      option, including "never".
- [ ] Moving funds still asks for a fresh gesture with "never" selected.
- [ ] Documented in `doc/pwa-user-guide.md` (what the option does, and why a shared
      phone should keep it short).

### 6. Open questions

1. Is a four-option selector worth it, or is a single "keep unlocked for 1 hour"
   switch enough?
2. Should the operator be able to force a maximum (e.g. ignore "never" on a shared
   kiosk device)?
3. Does the answer change for the learners in Sierra Leone, whose phones are often
   shared? If yes, ask before building.
