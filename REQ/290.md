# R-#290: stable-sl exchange widget inside learn.tg (same origin, session-authenticated)

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/290
**Created:** 2026-10-28
**Status:** Proposal — architecture, session contract and implementation plan. The
exchange logic lives in `stable-sl`; this issue is the **learn.tg side**: hosting
the widget on learn.tg's origin, reusing the NextAuth session, and bridging the
in-app and external wallets.
**Type:** Integration / authentication / deployment / documentation
**Priority:** High — the course already announces "exchanging inside learn.tg is
coming" and the pending item is recorded in
https://github.com/pasosdeJesus/learn.tg/issues/270 §12 ("the **stable-sl widget
inside learn.tg**, so the in-app wallet can exchange without leaving the
platform").

---

## 1. Objective

1. Serve `stable-sl`'s exchange UI under learn.tg's **own origin** at
   `/stable-sl`, so the NextAuth session cookie — the only credential
   (https://github.com/pasosdeJesus/learn.tg/issues/233 Phase 2) — reaches it
   without an iframe, a token or a CSP relaxation.
2. Expose a **session introspection** endpoint (`GET /api/internal/session`)
   that returns the authenticated account (`address`, `usuarioId`,
   `sessionEpoch`, `wallets`) so `stable-sl` can authorize orders and operators
   without duplicating the epoch logic or reading learn.tg's database.
3. Define the **wallet contract**: the in-app wallet (while unlocked) or the
   external wallet, both through `window.ethereum`; the client never reads the
   HttpOnly cookie and never asks for a private key.
4. Preserve every existing invariant: **no API token**, `walletAddress` is an
   untrusted hint, `usuario.session_epoch` revocation, the
   `Sec-Fetch-Site`/`Origin` guard, and **no CSP change**.
5. Update the course guide that announces the exchange as "coming soon" once
   the widget is live.

## 2. Current state (measured 2026-10-28)

- **Authentication is already session-only.** `apps/web/lib/authenticateUser.ts`
  reads the `next-auth.session-token` cookie (or `__Secure-…` under HTTPS),
  verifies it with `getToken({ secret: NEXTAUTH_SECRET })`, then checks `sub`,
  `usuarioId`, `billetera_usuario` and `usuario.session_epoch`. There is no
  `billetera_usuario.token` and no `/api/auth/token` (R-#233 Phase 2).
- **Session shape:** JWT strategy, `maxAge` 30 days, `updateAge` 24 h
  (`apps/web/app/api/auth/auth-options.ts`); claims `sub` (wallet), `usuarioId`
  (account) and `sessionEpoch`. Revocation is
  `UPDATE usuario SET session_epoch = session_epoch + 1`
  (`db/migrations/20261015120000_usuario_session_epoch.ts`).
- **Two wallets, one provider.** The in-app wallet (`@pasosdejesus/m/wallet`,
  vendored) injects itself as `window.ethereum` while unlocked and sets
  `provider.isPdJWallet === true`; the external wallet is the injected provider.
  UI uses `useAuthAddress()`, `useWalletProvider()` and `useWriteContract()`
  (`doc/wallet-auth.md`).
- **Cold-session fallback:** `learn.tg.sessionAddress` in `localStorage`, shared
  by every same-origin page, with `useAuthedApi().ready` to avoid anonymous
  fetches (bug #5719).
- **CSP/CSRF:** `apps/web/proxy.ts` keeps `frame-src 'self'
  https://www.youtube.com` and `frame-ancestors 'none'`, and blocks unsafe
  methods whose `Sec-Fetch-Site`/`Origin` is not same-origin.
- **No widget yet.** There is no `/stable-sl` route; `stable-sl` is a separate
  app in another repository. The pending item is recorded in
  https://github.com/pasosdeJesus/learn.tg/issues/270 §12; the guide says
  "coming soon".
- **stable-sl's side:** https://github.com/pasosdeJesus/stable-sl/issues/16
  chooses the same-origin mode (Mode A), with the standalone mode (external
  wallet only) outside learn.tg.

## 3. Decision and architecture

**Decision (2026-10-28): same origin, no iframe.** A cross-origin iframe cannot
receive the NextAuth cookie; it would need a signed assertion plus a
`postMessage` signing bridge and would relax `frame-src`/`frame-ancestors`.
Serving `/stable-sl` on learn.tg's origin keeps the cookie, the CSRF guard and
the CSP working unchanged.

```
Browser (learn.tg origin)
  ├── /            learn.tg Next.js (session cookie: next-auth.session-token)
  └── /stable-sl   stable-sl app, reverse-proxied, same Host: learn.tg
        │
        ├── GET /api/internal/session  ──> learn.tg (validates the cookie + epoch)
        │                                  returns {address, usuarioId, sessionEpoch, wallets}
        └── exchange UI / API           ──> stable-sl (orders, operator flow)
```

### 3.1 Routing

- Serve stable-sl at `https://learn.tg/stable-sl` through the existing reverse
  proxy, preserving the original host and port:
  `proxy_set_header Host $http_host;` (not `$host`; the port matters on
  `learn.tg:9001`, as `doc/siwe-auth-flow.md` §4 explains).
- NextAuth's cookie is host-only for `learn.tg` and `Path=/`, so the browser
  sends it to `/stable-sl`. **Do not change the cookie domain or path.**
- **Do not route `/stable-sl` through learn.tg's nonce CSP middleware**
  (`proxy.ts` sets `script-src 'nonce-…' 'strict-dynamic'`); stable-sl must
  serve its own CSP for its own HTML. The reverse proxy bypasses the learn.tg
  Next.js app for that prefix, or the middleware must explicitly exclude it.
- Next.js multi-zone (`rewrites`) is a fallback only if the reverse proxy cannot
  be used; verify that the rewrite preserves the cookie and does not inject
  learn.tg's nonce into stable-sl's scripts.

### 3.2 Session contract (`GET /api/internal/session`)

A session-gated, same-origin route (proposed
`apps/web/app/api/internal/session/route.ts`) that reuses the rules of
`lib/authenticateUser.ts` without requiring a `walletAddress` hint:

1. Read the `session-token` cookie; `getToken({ cookieName, secret:
   NEXTAUTH_SECRET })`; reject without `sub` → `401 {error: "auth_required"}`.
2. Resolve the account: `usuarioId` from the token, or `billetera_usuario` by
   `LOWER(billetera) = LOWER(sub)` for tokens minted before R-#265.
3. Compare `sessionEpoch` with `usuario.session_epoch`; a mismatch is `401`
   (`session_revoked`), so a lost phone cancels the widget too.
4. Return `{ address: sub, usuarioId, sessionEpoch, wallets: [addresses of
   billetera_usuario for that account] }` with `Cache-Control: no-store`.
5. No shared secret is needed: the endpoint acts on the caller's own cookie. A
   server-side caller (stable-sl) forwards the `Cookie` header. Never accept a
   `walletAddress` from the body as proof.

Why not `GET /api/auth/session`: it returns `address`/`usuarioId` but not
`sessionEpoch` or the account's wallets, which stable-sl needs for revocation
and for the operator allowlist.

### 3.3 Wallet contract

- **In-app:** `window.ethereum` with `provider.isPdJWallet === true` while
  unlocked; after a reload it is **locked** and must be unlocked through the
  existing dialog (`openInAppWalletDialog`), which is a state, not an error.
- **External:** the injected provider; stable-sl asks it to switch to the app's
  chain with the same pre-flight as `lib/ensure-chain.ts`.
- **Address precedence:** session (`GET /api/internal/session`) → in-app →
  `localStorage` `learn.tg.sessionAddress` (cold-session fallback). The client
  never reads the HttpOnly cookie; it uses the endpoint result and the shared
  `localStorage`.
- **Signing:** a purchase is paid by the platform's backend (it holds the key);
  a sale is signed by the seller's active wallet. No key reaches the widget or
  the operator, and no key is logged.

### 3.4 CSRF and CSP

- stable-sl replicates the `Sec-Fetch-Site`/`Origin` guard for its unsafe
  methods (same-origin requests pass; cross-site ones are rejected), matching
  `apps/web/proxy.ts`.
- stable-sl serves a CSP compatible with same-origin assets; it must not weaken
  learn.tg's own CSP, and learn.tg keeps `frame-ancestors 'none'` (no iframe is
  added in either direction).

### 3.5 Operator allowlist

stable-sl records operators in its own database. `POST /api/operator/*` and
`/operator` require a valid session **and** `operator.wallet` equal to the
session's `sub` or to one of the `wallets` returned by
`GET /api/internal/session`. Revocation follows `session_epoch`; removing an
operator is a stable-sl DB write, not a learn.tg one.

## 4. Implementation plan

**Phase 1 — session endpoint (learn.tg).**
- Add `lib/session-info.ts` with the account/epoch/wallet resolution, and
  `app/api/internal/session/route.ts` built on it (or reuse
  `authenticateUser` with `sub` as the hint).
- Tests: valid cookie returns the account and wallets; no cookie → 401; a
  bumped `session_epoch` → 401; a second wallet of the same account is listed;
  `Cache-Control: no-store`.

**Phase 2 — routing and deployment.**
- Reverse-proxy `/stable-sl` to the stable-sl process with
  `proxy_set_header Host $http_host`; keep the cookie path `/`.
- Verify `https://learn.tg/stable-sl` and `https://learn.tg:9001/stable-sl`
  (the port must be forwarded) serve the widget and that `document.cookie` does
  not expose the session cookie (HttpOnly).
- Ensure `/stable-sl` bypasses learn.tg's nonce CSP; stable-sl serves its own.
- Add a health check and a feature flag (`STABLE_SL_WIDGET_ENABLED`) for the
  rollout.

**Phase 3 — client bridge.**
- `window.ethereum` selection (`isPdJWallet` → in-app, else external), the
  locked state and `learn.tg.sessionAddress` fallback, with
  `useAuthedApi().ready` semantics: wait for the session instead of fetching
  anonymously.
- Chain pre-flight for the external wallet and the in-app wallet created on the
  other network.

**Phase 4 — widget UI and course.**
- Link/route from the Web3 & UBI course to `/stable-sl`; the guide replaces
  "coming soon" with the live flow (buy/sell, Orange Money, operator
  confirmation).
- No iframe: the widget is a normal same-origin page. Keep `frame-ancestors
  'none'`.

**Phase 5 — tests and docs.**
- Node-side e2e: sign in (in-app and external), capture the cookie, call
  `/api/internal/session` and `/stable-sl` with it; bump `session_epoch` and
  assert 401.
- Browser specs: in-app wallet, external wallet, locked wallet, cold session,
  and the widget rendering under `/stable-sl`.
- `make type`, `make test` and the smoke specs stay green.
- New `doc/stable-sl-widget.md` (origin, cookie, endpoint contract, wallet
  bridge, operator check, failure states), linked from `wallet-auth.md` and
  `siwe-auth-flow.md` if the endpoint joins the auth surface.

## 5. Documentation proposal

New **`doc/stable-sl-widget.md`**:

1. Purpose: the exchange inside learn.tg, same origin.
2. Routing: `/stable-sl`, reverse proxy, `Host: $http_host`, cookie path `/`.
3. Session contract: `GET /api/internal/session` (examples, 401 cases,
   `no-store`).
4. Wallet bridge: in-app/external, `isPdJWallet`, locked and cold states.
5. CSRF/CSP: same-origin guard, no iframe, no nonce on stable-sl.
6. Operator check: `operator.wallet` vs `sub`/`wallets`.
7. Failure handling: no session, stale epoch, locked wallet, wrong chain.
8. Anti-patterns: a token in `localStorage`, reading the HttpOnly cookie,
   embedding an iframe, asking for the 12 words.

## 6. Acceptance criteria

- [ ] `GET /api/internal/session` returns `{address, usuarioId, sessionEpoch,
      wallets}` for a valid cookie, with `Cache-Control: no-store`, and
      `401 auth_required`/`session_revoked` otherwise.
- [ ] `https://learn.tg/stable-sl` (and `:9001`) serves the widget on learn.tg's
      origin; the request carries the NextAuth cookie; no iframe is used.
- [ ] `/stable-sl` does not go through learn.tg's nonce CSP; learn.tg's own CSP
      is unchanged (`frame-ancestors 'none'` stays).
- [ ] The in-app wallet (unlocked) and the external wallet both work; a locked
      in-app wallet shows the unlock state; a cold session waits instead of
      fetching anonymously; no key is handled or logged.
- [ ] stable-sl's operator endpoints require a session whose `sub` or one of
      `wallets` is an active `operator.wallet`; others get 401/403.
- [ ] No API token is added and `walletAddress` remains a hint.
- [ ] The course guide no longer says "coming soon".
- [ ] Unit tests for the session helper, Node e2e for cookie + epoch, browser
      specs for in-app/external, and `make type`/`make test` green.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Coupling stable-sl to learn.tg's session secret | Same origin only; share `NEXTAUTH_SECRET` and rotate together; document that both are session issuers. |
| Proxy strips the port (`Host: $host`) | Use `proxy_set_header Host $http_host`; test `:9001` explicitly. |
| `/stable-sl` served through learn.tg's nonce CSP | Bypass the nonce middleware for that prefix; stable-sl serves its own CSP. |
| Epoch revocation not visible to stable-sl | The endpoint reads `usuario.session_epoch` on every call; `no-store`; a bumped epoch is 401. |
| Widget deployment lags learn.tg | Independent deploys behind the proxy; a versioned endpoint contract and a feature flag. |
| The in-app key leaks into stable-sl | stable-sl never receives the key: it only gets the address and asks `window.ethereum` to sign. |
| Operator allowlist drift | stable-sl's DB is authoritative; adding/removing an operator is an audited write with a test. |

## 8. Out of scope

- The exchange logic, the operator flow and the manual mode (stable-sl
  https://github.com/pasosdeJesus/stable-sl/issues/16).
- The standalone mode (stable-sl's own SIWE) and its session.
- Prices, KYC/limits, escrow and cashback (stable-sl requirements).
- A cross-origin iframe widget (discarded; see §3).
