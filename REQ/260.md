## 1. Objective

Turn six MSIP tables into a **base model with guidelines** published by
`@pasosdejesus/m`, instead of tables each app reinterprets on its own:

| Table | What it is | Who uses it |
|---|---|---|
| `usuario` | the learner / person (Devise + msip + learn.tg columns) | learn.tg, sivel3, the Rails backoffice |
| `billetera_usuario` | wallet ↔ person link, `answer_fib`, nonces | learn.tg |
| `msip_pais` | country catalog (ISO names, alfa2/alfa3, coordinates) | learn.tg, sivel3, the backoffice |
| `msip_departamento` | first-level division | learn.tg, sivel3 |
| `msip_municipio` | second-level division | learn.tg, sivel3 |
| `msip_centropoblado` | town / populated centre (what `usuario.city_id`/`verified_city_id` point to — today as plain integers, see §5) | learn.tg, sivel3 |

`m` offers:

- the **base model**: the types of the base columns, the baseline DDL of the six tables, and
  the base queries (read/write helpers for the base part);
- the **guidelines** of use: what a consumer may do, may not do, and must document.

Each consumer **keeps** the base (adopts it, stays on a declared version, runs the
conformance check) and **extends** it as it needs: extra columns on a table, extra tables,
extra triggers, extra indexes. Extending is the expected case, not a deviation: learn.tg
already added ~35 columns to `usuario` in 51 migrations, and that is fine as long as the
base and the guidelines are respected.

The problem being solved is not that learn.tg adds columns — it is that today nobody knows
which part of those tables is shared, so every change is done as if the table were private
and the shared part drifts.

## 3. The base model and the guidelines

### 3.1 What `m` publishes

- **Types**: `Usuario` and `BilleteraUsuario` with the base columns; `Pais`,
  `Departamento`, `Municipio`, `CentroPoblado` with the columns the apps read. The types are
  written so a consumer can **extend** them (exported interfaces, not sealed classes).
- **Baseline DDL** of the six tables: the definition a fresh database starts from, versioned
  (`m` assigns a base-model version and the consumer records which one it is on).
- **Base queries** (the DB handle is injected, never created inside `m`):
  - `getUserByWallet(db, wallet)`, `getUserById(db, id)`;
  - `upsertUserByWallet(db, wallet)` — the SIWE creation/update currently inside
    `authorize()` (`apps/nextjs/app/api/auth/auth-options.ts`), including the
    truncated-address `nusuario`;
  - `ensureWalletLink(db, usuarioId, wallet)`, `answer_fib` set/get;
  - `readProfile(db, userId)` / `updateProfile(db, userId, fields)` with an explicit
    allow-list;
  - `setPrivacyFlags(db, userId, { publicCourses, publicSensitiveCourses })` (R-#259);
  - `isSessionSubject(session, wallet)` — the lowercase session-subject predicate extracted
    from `apps/nextjs/lib/authenticateUser.ts`, with no Next.js import;
  - `listCountries`, `listDepartments(db, paisId)`, `listMunicipalities(db, departamentoId)`,
    `searchTowns(db, { q, municipalityId, departamentoId })` — the cascade
    `msip_centropoblado → msip_municipio → msip_departamento → msip_pais` that
    `app/api/towns/search/route.ts` implements today, honoring
    `fechadeshabilitacion IS NULL`.
- **The guidelines** (3.2) and a **conformance check** (`bin/m db:check` or its successor)
  that reports whether a consumer's database still satisfies them.

Every base query selects only base columns, so a consumer's extra columns never break them;
nothing in `m` writes to, migrates or owns the consumer's database.

### 3.2 Guidelines (numbered, so a consumer can cite them)

1. **The base is additive and shared.** A consumer may add columns, tables, indexes and
   triggers. It may not remove, rename or reinterpret a base column; if the base itself must
   change, `m` publishes a new version and the consumers adopt it.
2. **Extensions must not break the base or another consumer**: new columns are nullable or
   carry a default, and they never change the meaning of a base column.
3. **The primary key of `usuario` is immutable** (27 FKs point at it): no renumbering, no
   re-creation, no `TRUNCATE`. Same for the catalogs' ids.
4. **Wallets are lowercase**, stored and compared with `LOWER(billetera) = LOWER(?)`.
5. **The public name is `nusuario`**, never `nombre`; the base queries never expose `nombre`
   outside the owner-facing profile.
6. **Privacy flags are honored by every query that feeds a public surface** (R-#259): a
   consumer that adds a public listing must respect them.
7. **Triggers are allowed** and are the consumer's responsibility: they must not change the
   result of a base query, and the consumer documents them.
8. **No PII in logs.**
9. **Extensions live in the consumer's own migrations**, never by editing the baseline, and
   are documented where that consumer documents its schema (`doc/usuario-model.md` here).
10. **A consumer declares the base version it is on** and re-runs the conformance check when
    it adopts a new one; the check is part of the consumer's test suite.

### 3.3 What "maintains" means for the consumer

- Apply the baseline (fresh database) or confirm the base part of an existing one.
- Record the base version in the database (a small `m_base_model` row/table, or the version
  the check reads) so drift is detectable.
- Keep its extensions in its own migrations, with the guidelines above and its own doc.
- Adopt a new base version when `m` publishes one (a normal migration, reviewed).

The base model and the guidelines of §3: types (extensible), baseline DDL with a version,

**Columns of the geo tables**: the ones the apps read are base; the rest stay in the table
and `m` documents the criterion (only a base column needs to be typed).

**Integrity finding to decide in step 0:** `usuario` has only **two** FK constraints
(`country_id → msip_pais(id)` and `oficina_id → msip_oficina(id)`). The geographic links the
apps actually use — `pais_id`, `city_id`, `department_id`, `municipality_id` and the
`verified_*` twins — are **plain integers with no FK**. The decision (add the FKs after
cleaning orphans, or keep them unchecked for import compatibility) belongs to the consumer's
migrations, and the base model must not assume an integrity the schema does not have.

Deliverable of step 0: `doc/usuario-model.md` with the three tables above completed column by
column, the count of migrations per group, and the base version learn.tg declares.

## 6. Migration story

- `m` publishes the **baseline DDL** and the version; it ships no migration chain to be
  applied blindly on top of a live consumer database.
- A **fresh learn.tg database** is built from the baseline plus learn.tg's own chain.
- The existing learn.tg migrations are **not rewritten** (CONTRIBUTING: never modify an
  applied migration); they stay as the history of learn.tg's extensions.
- The conformance check verifies the base part (columns, types, the guidelines' invariants)
  and reports; it is not a schema-diff gate that forbids extensions.
- The geographic catalogs are **reference data**: the base model documents where the rows
  come from and how they are refreshed, and exposes no writes.

## 7. Acceptance criteria

- [ ] `m` publishes the base model (extensible types, baseline DDL with a version, base
      queries with tests) and the guidelines, documented in its README; it imports no
      Next.js, no React and creates no DB connection of its own.
- [ ] The conformance check reports a consumer database as compliant when it has the base
      plus its extensions, and reports drift (a removed base column, a changed type, a
      missing base table) without failing because of extensions.
- [ ] learn.tg declares the base version it is on, records it, and runs the conformance check
      in its test suite.
- [ ] learn.tg uses the base helpers in `lib/authenticateUser.ts`, `lib/admin-auth.ts`,
      `app/api/auth/auth-options.ts` and `app/api/profile/route.ts`; the learn.tg-specific
      fields stay as extensions in its own migrations.
- [ ] The geo routes (`countries`, `departments`, `municipalities`, `towns/search`) and the
      admin joins use the base geo queries, with **unchanged HTTP response shapes**
      (`TownAutocomplete` and `CountrySelect` keep working untouched).
- [ ] `searchTowns` returns the same results as today's query for a sample of queries
      (dev data), respecting `fechadeshabilitacion IS NULL`.
- [ ] `doc/usuario-model.md` classifies every table and every `usuario` column (base A/B,
      extensions C), lists learn.tg's extensions and states the base version.
- [ ] `make type`, the full unit suite and `node bin/audit-api-auth.mjs` (0 failed) stay
      green; the Rails backoffice still signs in and works in dev (manual check, documented).
- [ ] A second consumer (sivel3) could adopt the base without learn.tg's extensions: verified
      by reading the guidelines against the baseline, not by migrating sivel3 here.

## 8. Out of scope

- Moving learn.tg's extension columns to a separate table (Part C).
- Removing Devise or any institutional column.
- Migrating sivel3 (this requirement only leaves the base ready for it).
- Rewriting the historical learn.tg migrations.
- Writing to the geographic catalogs (reference data).
- The courses/guides layer (`cor1440_gen_*`).
