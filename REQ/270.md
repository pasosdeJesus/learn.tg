# R-#270: In-app wallet as default + guided migration from external wallets

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/270

**Status:** Proposal
**Created:** 2026-09-29
**Type:** Feature / UX / Onboarding
**Priority:** High — the in-app wallet is already the only path for users without an external wallet, and the target audience (Sierra Leone) is mobile-only
**Dependencies:** R-#236, R-#237, R-#238, R-#244, R-#246, R-#249, R-#256, R-#265, R-#266, R-#269

---

## 1. Objective

Make the in-app wallet the **default** way to operate with learn.tg, while keeping external Web3 wallets (MetaMask, Rabby, OKX, OneKey, Brave) as an explicit alternative. The goal is to reduce friction for the target audience (users in Sierra Leone who do not have an external wallet) and to make the onboarding flow consistent: create a wallet inside the app, sign in, and start using the platform.

The change is **UX-only**. It does not touch the data model, the authentication, or the on-chain logic.

This requirement builds on top of work already done. It does **not** re-implement any of it:

- **R-#236** (`packages/pdj-wallet`): `importWallet({ mnemonic, pin })`, `importWallet({ privateKey, pin })`, `exportMnemonic(pin)`, `exportPrivateKey(pin)`, encryption (AES-256-GCM + PBKDF2 600k), storage (IndexedDB, Memory, File).
- **R-#237** (`packages/pdj-wallet-next`): `useInAppWallet()`, `InAppWalletSetup`, `InAppWalletUnlock`, i18n (en/es).
- **R-#238**: `WalletSelector`, `WalletDialog`, integration with `useAuthAddress`, `useWalletProvider`, `useWriteContract`, `WalletEventListener`.
- **R-#244**: MVP, verified on the dev site.
- **R-#246**: L0/L1/L2 unlock layers, wallet browser detection, funds gate (L1), auto-lock (1 hour).
- **R-#249**: `WalletPanel` (balances, receive, send, collectibles), 3-word backup verification.
- **R-#256**: offline course download, per-wallet entitlement.
- **R-#265** (draft): several wallets per user (link/unlink, principal wallet). **This requirement does not duplicate R-#265.** When R-#265 lands, the in-app wallet is one of the linked wallets, and the default priority still applies.
- **R-#266**: an in-app wallet created on Sepolia can switch to Mainnet and pay. **This requirement does not duplicate R-#266.** The migration guide assumes the user can create the wallet on either network.
- **R-#269**: `PasswordInput` (eye toggle) and the explicit "how do you want to unlock" step with gesture by default. **This requirement does not duplicate R-#269.** The migration guide references the improved create/import flow.

## 3. Design

### 3.1 Default priority

| Situation | What the UI offers |
|---|---|
| No in-app wallet, no `window.ethereum` | Create or import an in-app wallet (as today) |
| No in-app wallet, `window.ethereum` present, **not** a wallet browser | **"Create or import an in-app wallet" (default)** + "Use external wallet" (secondary) |
| No in-app wallet, **wallet browser** (Rabby, MetaMask, OKX, OneKey) | **"Use external wallet" (default)** + "Use in-app wallet" (secondary, with a note that WebAuthn/L1 is not available there) |
| In-app wallet exists | Use it (as today) |
| User arrived with `?iappwallet=1` | Force the in-app option, even in a wallet browser |
| User already signed in with an external wallet | Keep the session; the default only affects new users or users who explicitly choose to switch |

The rule is: **in-app is default unless the browser is the native environment of an external wallet** (R-#246 §4 rule 4). That respects the wallet browsers where the external wallet gives the native experience, and defaults to in-app everywhere else.

### 3.2 Import from an existing external wallet

To migrate from an external wallet to the in-app wallet **without losing the address** (and therefore the history, progress, scholarships and referrals), the user can **import the mnemonic (recovery phrase)**.

- `InAppWalletSetup` already supports importing a mnemonic or a private key (R-#236, R-#237).
- The UI must make this option **visible and clear**: "Already have a wallet? Import your recovery phrase to keep your history."
- The import happens **locally**, in the browser. The mnemonic never leaves the device.
- The mnemonic is encrypted with the user's password (AES-256-GCM + PBKDF2 600k, R-#236 §5).
- After importing, the user is prompted to **back up the phrase again** (the 3-word verification of R-#249 applies).
- The `PasswordInput` with the eye toggle (R-#269) and the "how do you want to unlock" step with gesture by default (R-#269) apply to the import flow.

### 3.3 Guided migration from external wallets

For users coming from MetaMask, Rabby, OKX, OneKey or Brave, add a short guide.

**Two formats:**

1. **`doc/pdJ-wallet-migration.md`** — the complete Markdown guide, with screenshots, detailed steps, and security warnings. Linked from the site and from the WhatsApp message.
2. **WhatsApp message** — a short, emoji-friendly version that the operator can send to users to invite them to migrate.

#### 3.3.1 Markdown guide (`doc/pdJ-wallet-migration.md`)

Structure:

- **Why migrate:** keep the same address, keep history, progress, scholarships, referrals.
- **Before you start:** security warnings (never share the phrase, write it on paper, do not store in photos or notes).
- **How to export the recovery phrase from each wallet:**
  - MetaMask: Settings → Security & Privacy → Reveal Secret Recovery Phrase.
  - Rabby: Settings → Security → Reveal Recovery Phrase.
  - OKX Web3: Settings → Security → Recovery Phrase.
  - OneKey: Settings → Backup → Recovery Phrase.
  - Brave Wallet: Settings → Backup → Reveal Recovery Phrase.
- **How to import it into learn.tg:**
  - Open learn.tg → "Use in-app wallet" → "Import recovery phrase".
  - Paste the 12 words.
  - Create a password (8+ characters).
  - Choose how to unlock (fingerprint/Face ID by default, R-#269).
  - Confirm the 3-word backup verification (R-#249).
- **What stays and what changes:**
  - Stays: same address, same history, same scholarships, same referrals.
  - Changes: the wallet now lives inside learn.tg, unlocked with the gesture.
- **What if something goes wrong:** recovery with the 12 words, support contact.
- **Security warnings (repeated at the end):**
  - "Your recovery phrase never leaves your device. learn.tg never sees it."
  - "Never share your recovery phrase with anyone. Not even with learn.tg."
  - "If you lose your recovery phrase, you lose access to your funds."
  - "Write it down on paper. Do not store it in a photo, a note, or email."

#### 3.3.2 WhatsApp message

A short, emoji-friendly version that the operator can send to users. The message does **not** contain the phrase, only the instructions. It ends with a link to the Markdown guide.

Draft:

```

Si tienes MetaMask, Rabby, OKX u otra billetera, puedes importar tu frase semilla en la billetera de learn.tg y seguir usando la misma dirección. Así conservas tu progreso, becas y referidos.

📝 Pasos:
1️⃣ Abre tu billetera externa.
2️⃣ Busca "Configuración" → "Seguridad" → "Revelar frase de recuperación".
3️⃣ Copia las 12 palabras.
4️⃣ En learn.tg, toca "Usar billetera de la app" → "Importar frase".
5️⃣ Pega las 12 palabras y crea una contraseña.

⚠️ Importante:
```

The WhatsApp message is stored in the same doc (`doc/pdJ-wallet-migration.md`, section "Mensaje para WhatsApp") so the operator can copy it directly.

### 3.4 Payment modals

`DonateModal` and `CheckoutModal` currently show a generic "Connect Wallet" or "Unlock your in-app wallet" notice. The change:

- If no wallet exists: **"Create or import an in-app wallet" (default)** + "Use external wallet" (secondary).
- If an in-app wallet exists but is locked: keep the current behavior (unlock with the gesture, R-#246).
- If an external wallet is being used: keep the current behavior.
- If a wallet browser is detected: external wallet default (as in §3.1).

### 3.5 Header

The wallet pill (R-#249) already opens `WalletPanel` when the in-app wallet is unlocked, or `WalletDialog` when it is locked. When no wallet exists, it opens `WalletDialog` to create or import. The external wallet remains accessible from inside the dialog.

### 3.6 Respect existing users

- A user who already signed in with an external wallet keeps their session. The default only affects **new users** or users who explicitly choose to switch.
- No data is migrated automatically. Importing the mnemonic is the user's explicit choice.
- The external wallet remains fully functional as an alternative.
- When R-#265 lands (several wallets per user), the in-app wallet becomes one of the linked wallets; the default priority still applies, and the user can link the external wallet too.

## 4. Scope

**In scope:**

- Change the priority in `WalletSelector` (in-app default, external secondary).
- Change the priority in `DonateModal` and `CheckoutModal`.
- Improve the import UI in `InAppWalletSetup` (make it visible, clear, with warnings).
- Create `doc/pdJ-wallet-migration.md` (Markdown guide + WhatsApp message).

- Add short security warnings in the UI.
- Respect wallet browsers (external default there).
- Respect existing users (no forced change).

**Out of scope:**

- Multiple wallet addresses per user (R-#265).
- Changing the network of an in-app wallet (R-#266).
- Password eye toggle and unlock choice (R-#269).
- Changes to the data model (`billetera_usuario`, `authenticateUser`).
- Changes to the SIWE flow.
- Changes to the on-chain logic.
- Forcing users with an external wallet to switch.

## 6. Risks

- **Users may be confused by the choice.** Mitigation: clear labels, the in-app option first, and a short explanation of why.
- **Users may import a mnemonic insecurely.** Mitigation: prominent warnings, local-only import, no server transmission, the guide repeats the warnings.
- **Users may send the recovery phrase through WhatsApp.** Mitigation: the WhatsApp message explicitly says "never share your recovery phrase, not even with learn.tg", and the message itself never contains a phrase.
- **Wallet browsers may behave unexpectedly.** Mitigation: detect them explicitly (R-#246 §3) and give the external wallet priority there.
- **Existing users may see a different UI.** Mitigation: the change only affects new users or users who choose to switch; the session persists.
- **R-#265 may land first.** Mitigation: this requirement references R-#265 and does not duplicate it; the priority still applies when both land.
