# R-#270: In-app wallet as default + guided migration from external wallets

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/270

**Status:** Proposal
**Created:** 2026-09-29
**Type:** Feature / UX / Onboarding
**Priority:** High — the in-app wallet is already the only path for users without an external wallet, and the target audience (Sierra Leone) is mobile-only
**Builds on (already landed):** R-#236, R-#237, R-#238, R-#244, R-#246, R-#249, R-#256, R-#266, R-#269. **Related, still open:** R-#265 (several wallets per user, draft).

---

## 1. Objective

Make the in-app wallet the **default** way to operate with learn.tg, while keeping external Web3 wallets (MetaMask, Rabby, OKX, OneKey, Brave) as an explicit alternative. The goal is to reduce friction for the target audience (users in Sierra Leone who do not have an external wallet) and to make the onboarding flow consistent: create a wallet inside the app, sign in, and start using the platform.

The change is **UX-only**. It does not touch the data model, the authentication, or the on-chain logic.

## 2. What already exists (do not duplicate)

This requirement builds on top of work already done. It does **not** re-implement any of it:

- **R-#236** (`packages/pdj-wallet`): `importWallet({ mnemonic, password, storage })` / `importWallet({ privateKey, password, storage })` — the option is **`password`** (renamed from `pin`, `packages/pdj-wallet/src/wallet.ts:194`), `exportMnemonic(password)`, `exportPrivateKey(password)`, encryption (AES-256-GCM + PBKDF2 600k), storage (IndexedDB, Memory, File).
- **R-#237** (`packages/pdj-wallet-next`): `useInAppWallet()`, `InAppWalletSetup`, `InAppWalletUnlock`, i18n (en/es).
- **R-#238**: `WalletSelector`, `WalletDialog`, integration with `useAuthAddress`, `useWalletProvider`, `useWriteContract`, `WalletEventListener`.
- **R-#244**: MVP, verified on the dev site.
- **R-#246**: L0/L1/L2 unlock layers, wallet browser detection, funds gate (L1), auto-lock (1 hour).
- **R-#249**: `WalletPanel` (balances, receive, send, collectibles), 3-word backup verification.
- **R-#256**: offline course download, per-wallet entitlement.
- **R-#265** (draft): several wallets per user (link/unlink, principal wallet). **This requirement does not duplicate R-#265.** When R-#265 lands, the in-app wallet is one of the linked wallets, and the default priority still applies.
- **R-#266**: an in-app wallet created on Sepolia can switch to Mainnet and pay. **This requirement does not duplicate R-#266.** The migration guide assumes the user can create the wallet on either network.
- **R-#269**: `PasswordInput` (eye toggle) and the explicit "how do you want to unlock" step with gesture by default. **This requirement does not duplicate R-#269.** The migration guide references the improved create/import flow.

## 3. Design

### 3.1 Default priority

| Situation | What the UI offers |
|---|---|
| No in-app wallet, no `window.ethereum` | Create or import an in-app wallet (as today) |
| No in-app wallet, `window.ethereum` present, **not** a wallet browser | **"Create or import an in-app wallet" (default)** + "Use external wallet" (secondary) |
| No in-app wallet, **wallet browser** (Rabby, MetaMask, OKX, OneKey) | **"Use external wallet" (default)** + "Use in-app wallet" (secondary, with a note that WebAuthn/L1 is not available there) |
| In-app wallet exists | Use it (as today) |
| User arrived with `?iappwallet=1` | Force the in-app option, even in a wallet browser |
| User already signed in with an external wallet | Keep the session; the default only affects new users or users who explicitly choose to switch |

The rule is: **in-app is default unless the browser is the native environment of an external wallet** (R-#246 §4 rule 4). That respects the wallet browsers where the external wallet gives the native experience, and defaults to in-app everywhere else.

**Safeguard when an external provider is present.** A desktop Chrome with MetaMask is not a "wallet browser", so rule 2 would default to "create in-app" for a user who may already have history (progress, scholarships, referrals). To avoid handing them an empty wallet, when `window.ethereum` is available the create screen must (a) keep the external offer as a first-class, visible option, (b) show "Already have a wallet? Import your recovery phrase" with the link to §3.3.2, and (c) never create a wallet without an explicit click. The two-button shape (in-app first) is preferred over deciding for the user.

**`?iappwallet=1` in a wallet browser** forces the in-app option, but WebAuthn/L1 is not available there (R-#246): the wallet works with the password (L0) and the UI must say it before creating.

**MiniPay is out of scope.** We are not pursuing a MiniPay listing (its rules and infrastructure are not ours to meet); the direction is the **PWA** and, later, a mobile app. Do not add MiniPay-specific branches in this work: the existing `isMiniPay` hints stay as they are and the wallet-browser detection covers Rabby/MetaMask/OKX/OneKey/Brave only.

### 3.2 Import from an existing external wallet

To migrate from an external wallet to the in-app wallet **without losing the address** (and therefore the history, progress, scholarships and referrals), the user can **import the mnemonic (recovery phrase)**.

- `InAppWalletSetup` already supports importing a mnemonic or a private key (R-#236, R-#237).
- The UI must make this option **visible and clear**: "Already have a wallet? Import your recovery phrase to keep your history."
- The import happens **locally**, in the browser. The mnemonic never leaves the device.
- The mnemonic is encrypted with the user's password (AES-256-GCM + PBKDF2 600k, R-#236 §5).
- After importing, the user is prompted to **back up the phrase again** (the 3-word verification of R-#249 applies).
- The `PasswordInput` with the eye toggle (R-#269) and the "how do you want to unlock" step with gesture by default (R-#269) apply to the import flow.

### 3.3 Guided migration from external wallets

For users coming from MetaMask, Rabby, OKX, OneKey or Brave, add a short guide. Three
deliverables: the source documents, the **public pages that serve them**, and the
WhatsApp message.

**When the address is preserved (state it in the guide):** the in-app wallet derives at
the standard BIP44 path (`m/44'/60'/0'/0/0`, `accountFromMnemonic(mnemonic, 0)`), the same
path MetaMask/Rabby/OKX/OneKey/Brave use for **account #1**. It is **not** preserved when
the external wallet used a BIP39 passphrase (extra word) or when the user needs an account
beyond #1 (only index 0 is derived, R-#236). Cover both cases with a known vector in the
unit tests (`HARDHAT_MNEMONIC` → `0xf39F…9226`).

#### 3.3.1 Source documents

| File | Content |
|---|---|
| `doc/migration-in-app-wallet/en.md` | English guide: steps per wallet, security warnings, what changes |
| `doc/migration-in-app-wallet/es.md` | Spanish translation |
| `doc/migration-in-app-wallet/whatsapp.md` | The short and long WhatsApp messages (EN/ES), for the team; **not** served |

A folder per document (instead of a `.es.md` suffix) keeps the translations together and avoids inventing a suffix convention if more languages are added later.

**Screenshots:** they age fast; keep them optional ("when available") or link each
wallet's own documentation. If included, they live under `public/img/migration/` so that
the PWA image cache (`/img/*`, CacheFirst) stores them for offline reading.

Guide outline (both languages):

- **Why migrate:** keep the same address, keep history, progress, scholarships, referrals.
- **Before you start:** security warnings (never share the phrase, write it on paper, do not store in photos or notes).
- **How to export the recovery phrase from each wallet:**
  - MetaMask: Settings → Security & Privacy → Reveal Secret Recovery Phrase.
  - Rabby: Settings → Security → Reveal Recovery Phrase.
  - OKX Web3: Settings → Security → Recovery Phrase.
  - OneKey: Settings → Backup → Recovery Phrase.
  - Brave Wallet: Settings → Backup → Reveal Recovery Phrase.
- **How to import it into learn.tg:**
  - Where (added 2026-09-30, operator feedback after reading the English guide): in a
    normal browser, **Chrome** on Android or **Safari** on iPhone/iPad, **not** inside
    the browser of MetaMask/OKX/OneKey/Rabby (there the page offers the external wallet
    first and the fingerprint/Face ID unlock is not available); the wallet is not a
    separate app, it lives in the learn.tg page. The guide also says to **type** the
    12 words by hand when the external wallet is on a computer (never by WhatsApp/email).
  - Open learn.tg in that browser → tap "Use in-app wallet" → "Import an existing
    wallet" (button "Import wallet") → paste the 12 words in "Recovery phrase".
  - Create a password (8+ characters).
  - Choose how to unlock (fingerprint/Face ID by default, R-#269).
  - Confirm the 3-word backup verification (R-#249).
- **What stays and what changes:**
  - Stays: same address (and therefore the same funds), same history, same scholarships, same referrals.
  - Changes: the wallet now lives inside learn.tg, unlocked with the gesture.
- **Two things that surprise users (explain them):**
  - The in-app wallet **locks when the page reloads** (the key leaves memory): it is
    unlocked again with the gesture or the password, it is not lost.
  - Do not use **two signers for the same address** (the imported wallet and the external
    one) **for learn.tg**: keep using the external wallet for other DApps, but for
    learn.tg use only the in-app one, to avoid confusion with the session state.
- **What if something goes wrong:** recovery with the 12 words, support contact.
- **Security warnings (repeated at the end):**
  - "Your recovery phrase never leaves your device. learn.tg never sees it."
  - "Never share your recovery phrase with anyone. Not even with learn.tg."
  - "If you lose your recovery phrase, you lose access to your funds."
  - "Write it down on paper. Do not store it in a photo, a note, or email."

#### 3.3.2 Served pages (public, no auth)

The guide is read from a WhatsApp message, so it must be a normal **public** page (no
session, no database, no API):

| Language | Route | Renders |
|---|---|---|
| English | `/en/migration-in-app-wallet` | `doc/migration-in-app-wallet/en.md` |
| Spanish | `/es/migracion-billetera-app` | `doc/migration-in-app-wallet/es.md` |

- One thin server component (`components/migration/MigrationGuide.tsx`) picks the
document by `lang` with `readFile` and renders it with the same remark pipeline as the
guides (`remark-parse` + `remark-gfm` + `remark-rehype`, `allowDangerousHtml`); the two
page files are one-liners.
- Language-specific slugs follow the existing precedent (`/en/referrals` +
`/es/referidos`, `components/Header.tsx`); the Spanish one mirrors the wallet copy ("Usar
billetera de la aplicación").
- **No redirects for now, and keep the slug stable.** A redirect is only worth it for a
link already sitting in someone's phone; since no message has gone out with another
slug, adding `migracion-billetera-en-app` / `migracion-billetera-aplicacion` /
`in-app-wallet-migration` today is dead weight. If a message is ever sent with a
different slug, add that single redirect then. (The header has no automatic path
switcher, so per-language slugs are safe: it is the existing pattern of
`/en/referrals` + `/es/referidos`.)
- The page is under `/{lang}/*`, so the PWA page cache (`next.config.ts`
`runtimeCaching`, NetworkFirst without age expiry) stores it: the guide is readable
offline after the first visit, with no extra work.
- Links that invite the user to act append `?iappwallet=1` (§3.1), so the in-app option is
forced even in a wallet browser.

### 3.4 Payment modals

`DonateModal` and `CheckoutModal` currently show a generic "Connect Wallet" or "Unlock your in-app wallet" notice. The change:

- If no wallet exists: **"Create or import an in-app wallet" (default)** + "Use external wallet" (secondary).
- If an in-app wallet exists but is locked: keep the current behavior (unlock with the gesture, R-#246).
- If an external wallet is being used: keep the current behavior.
- If a wallet browser is detected: external wallet default (as in §3.1).

### 3.5 Header

The wallet pill (R-#249) already opens `WalletPanel` when the in-app wallet is unlocked, or `WalletDialog` when it is locked. When no wallet exists, it opens `WalletDialog` to create or import. The external wallet remains accessible from inside the dialog.

### 3.6 Respect existing users

- A user who already signed in with an external wallet keeps their session. The default only affects **new users** or users who explicitly choose to switch.
- No data is migrated automatically. Importing the mnemonic is the user's explicit choice.
- The external wallet remains fully functional as an alternative.
- When R-#265 lands (several wallets per user), the in-app wallet becomes one of the linked wallets; the default priority still applies, and the user can link the external wallet too.

## 6. Risks

- **Users may be confused by the choice.** Mitigation: clear labels, the in-app option first, and a short explanation of why.
- **Users may import a mnemonic insecurely.** Mitigation: prominent warnings, local-only import, no server transmission, the guide repeats the warnings.
- **Users may send the recovery phrase through WhatsApp.** Mitigation: the WhatsApp message explicitly says "never share your recovery phrase, not even with learn.tg", and the message itself never contains a phrase.
- **Wallet browsers may behave unexpectedly.** Mitigation: detect them explicitly (R-#246 §3) and give the external wallet priority there.
- **Existing users may see a different UI.** Mitigation: the change only affects new users or users who choose to switch; the session persists.
- **R-#265 may land first.** Mitigation: this requirement references R-#265 and does not duplicate it; the priority still applies when both land.
- **A user with an external wallet may create a fresh in-app wallet** (rule 2) and see empty progress. Mitigation: the §3.1 safeguard (the external offer stays visible, the import offer links to the guide, no wallet is created without an explicit click).
- **The imported address may differ** from the external one (a BIP39 passphrase, or an account beyond #1) and the user may think their history was lost. Mitigation: the guide states both cases and the unit test proves the standard one.
- **`detectWalletBrowser` over-reports MetaMask, inverting rule 2.** It returns true when `ethereum.isMetaMask === true` even with a desktop user agent (inherited from the old ad-hoc copy in `components/ui/qr-code-dialog.tsx`), and non-MetaMask providers set that flag for compatibility (Brave's wallet does, per the helper's own comment). Measured 2026-09-29: the provider of `installCoreWalletMock` (`e2e/helpers/in-app-wallet.mjs:109`) makes a plain desktop Chrome render the external-primary header of §3.1, where this requirement wants the in-app option first; the E2E case "con proveedor (navegador común)" only passes because it injects a provider without that flag. Mitigation: decide whether `isMetaMask` stays a signal or the UA marker becomes mandatory for MetaMask (keeping `isOkxWallet`/`isOneKey`), then re-run `lib/__tests__/wallet-browser.test.ts`, `components/__tests__/WalletSelector.test.tsx` and `make test-e2e-spec SPEC=in-app-wallet-default` against the dev site. Still open as of 2026-09-29.

## 10. Full E2E run of 2026-09-29 against the dev site: the single failure it left

Recorded here at the operator's request because it is the evidence behind the criteria of
§5, even though the failing spec exercises other code and the failure is **not** a defect
of this requirement's logic.

**The run.** `make test-e2e` (12 s between specs), `IPDES=learn.tg PUERTOPRU=9001
CHAIN_ID=11142220` (`https://learn.tg:9001`), deployment `433b7580`, log
`/tmp/e2e-dev.log`:

- **38 specs, 384 checks OK, 1 spec failed** with 1 failing check:
  `e2e/specs/offline-course-download.spec.mjs` (33.9 s). It fails inside the suite and
  also when run alone, so it is not suite load.
- `e2e/specs/in-app-wallet-default.spec.mjs` (new in this work): **9/9 OK**.
- `e2e/smoke/migration-guide.spec.mjs` (new in this work): OK.

Failing check (`e2e/specs/offline-course-download.spec.mjs:281`):

```
[FAIL] La guía sin conexión no mostró su contenido (You are offline. Your progress will be saved locally. Learn through games ☰ 0x8427...0c5c ✕ Use in-app wallet In this browser the in-app wallet has no fingerpri)
```

**Why it is not this requirement's logic.** The spec was created on 2026-09-22 and last
touched on 2026-09-25; the code it exercises (`lib/offline-guide-db.ts`,
`lib/hooks/useCachedGuide.ts`, `app/[lang]/[pathPrefix]/[pathSuffix]/page.tsx`) was last
touched on 2026-09-25. The sibling specs `offline-guide`, `offline-crossword` and
`offline-two-courses` pass on the same deployment.

**What it is: a readiness heuristic in the spec that the header text of §3.1 pushed over
its threshold.** Before reading the offline page, the spec waits for the document to grow
past 200 *characters*:

```js
await page.waitForFunction(() => (document.body?.innerText || '').length > 200, { timeout: 30000 })
const offlineText = await page.evaluate(() => document.body.innerText)
```

Measured on the deployed site on 2026-09-29 with a temporary probe, now deleted
(`/tmp/guide4-probe.log`), going offline and navigating to the never-visited
`/en/web3-and-ubi/guide4`:

| Moment | Body text | Cached guide painted |
|---|---|---|
| t = 104 ms | 289 characters | no (`Loading guide...`) |
| t = 516 ms | 3362 characters | yes (`Course: Web3 & UBI ... Showing the saved copy: your device is offline. Introduction ...`) |

The body crosses the 200-character threshold **before** the guide is painted, because the
shell alone already carries 289 characters: this requirement added the two pieces of
header below, which render here because the spec's injected provider declares
`isMetaMask: true` (`e2e/helpers/in-app-wallet.mjs:109`) and `detectWalletBrowser` then
treats a plain desktop Chrome as a wallet browser (see the risk in §6):

| Piece of the offline header added by this requirement | Characters |
|---|---|
| "Use in-app wallet" (`wallet-use-in-app`) | 17 |
| Wallet-browser note (`wallet-browser-note`) | 103 |
| Same shell without those 120 characters and their separator (approximate) | ~168 |

Without them the shell stays under the threshold, so the wait kept polling until the
cached guide appeared: that is why the spec passed before this work and fails now, and
also why the offline reading itself is fine (at 516 ms the guide renders with its
"Showing the saved copy" notice).

**Where the fix belongs:** in the spec (R-#256,
https://github.com/pasosdeJesus/learn.tg/issues/256), not here. It waits for a guide
marker instead of a character count; the exact change, together with the misdetection of
§11.1 and the test that pins it, is in §11.

## 11. Proposed solution for the findings of §10

Two changes, in this order. 11.1 is this requirement's own code and rule 2 asks for it;
11.2 is a spec of R-#256. Both are needed: 11.1 alone would turn
`offline-course-download` green again just by shortening the shell, which would hide the
brittleness instead of fixing it.

### 11.1 `detectWalletBrowser`: MetaMask and Rabby need their own signal

`lib/wallet-browser.ts:19` treats `ethereum.isMetaMask === true` as "wallet browser" even
with a desktop user agent. That is the wrong question: §3.1 rule 2 asks whether the
browser *is* the wallet's native environment, while third-party providers set
`isMetaMask` for compatibility (the helper's own comment, `:8`, says Brave does; Rabby
sets it too, and today Rabby is detected **only** through that flag because the user-agent
list is `['okx', 'onekey', 'metamask', 'trust wallet']`).

Proposed change:

- Keep the user-agent markers and the explicit provider flags, and add the ones that
  replace the blanket `isMetaMask`:
  - user agent: `okx`, `onekey`, `metamask`, `trust wallet`, **plus `rabby`** (missing
    today) and the `; wv` (Android WebView) marker;
  - provider: `isOkxWallet`, `isOneKey`, **plus `isRabby`** (Rabby exposes it).
- Drop `eth?.isMetaMask === true` as a standalone signal (`:19`). A desktop Chrome with
  the MetaMask extension is then a normal browser: in-app first, external second, which is
  rule 2 and the §3.1 safeguard.
- Keep the `isBrave` short-circuit first, as today.

**Residual risk and how to close it.** A wallet browser whose marker we do not know would
default to in-app there, and that is the milder of the two errors: §3.1 already covers it
with the secondary button and `?iappwallet=1`, whereas the opposite error tells a desktop
user with an extension to use MetaMask and hides the path this requirement recommends.
Before shipping, the operator should open learn.tg inside each in-app browser (MetaMask,
Rabby, OKX, OneKey, Brave) on a phone and record `navigator.userAgent` together with the
`is*` flags of `window.ethereum`; whatever that measurement returns goes into the user
agent list (or the flags) with a unit test per wallet.

**Tests that move with it:** `lib/__tests__/wallet-browser.test.ts` (desktop user agent +
`isMetaMask: true` → `false`; MetaMask/Rabby user agent → `true`; `isRabby`,
`isOkxWallet`, `isOneKey` → `true`; Brave → `false`), `components/__tests__/WalletSelector.test.tsx`,
and the E2E case of 11.3.

### 11.2 The offline specs must wait for the guide, not for a character count

`e2e/specs/offline-course-download.spec.mjs:262` (the same shape at `:116`, on the course
page) waits for the body to exceed 200 characters, which the shell crosses on its own once
the header is long. Replace it with a wait on a guide marker, keeping the `/offline`
phrase so the diagnostics still tell the two pages apart:

```js
await page.waitForFunction(
  () => /Showing the saved copy|Comprehension Questions|Introduction|Your progress is saved and will sync when the connection returns/.test(document.body?.innerText || ''),
  { timeout: 30000 },
)
```

The classification below it (`isFallback` / `looksLikeGuide`) stays as it is.

`e2e/specs/offline-guide.spec.mjs` deserves the same treatment: `waitBodyContent`
(`:49-60`) and `bodyLength` accept any body over 200 characters. In the run of
2026-09-29 it reported 307 characters for a page whose shell measured 130 in the same flow
(probe of 2026-09-29, `/tmp/guide1-probe.log`) and 4829 with the guide painted and its
`[aria-label="Guide text"]` section filled (4446 characters). So the threshold is met while
the page is still filling in: it means "more than the shell", not "the guide is readable".
Waiting for `Showing the saved copy` (or for that section to be non-empty) makes the check
mean what its name says.

This is R-#256's file, so it lands as its own small change, recorded in that requirement.

### 11.3 Close the E2E hole that let the false positive through

`e2e/specs/in-app-wallet-default.spec.mjs` case 2 ("con proveedor (navegador común)")
injects a provider **without** `isMetaMask`, which is why it passed while the real
desktop-extension case was inverted. Change that case to inject the provider **with**
`isMetaMask: true` and a desktop user agent, and keep asserting that the in-app option is
primary; leave the wallet-browser case with a MetaMask/Rabby user agent. The case then
fails before 11.1 and passes after it, so it pins rule 2 instead of describing the mock.

### 11.4 Order, verification, and alternatives rejected

1. 11.1 + 11.3 together (the fix and the test that pins it): `make type`, `make test-lib
   test-components`, then `make test-e2e-spec SPEC=in-app-wallet-default` against the dev
   site and `make test-e2e-spec SPEC=offline-course-download` to confirm the shell shrank.
2. 11.2 on its own: `make test-e2e-spec SPEC=offline-course-download` and
   `make test-e2e-spec SPEC=offline` until green, then one full `make test-e2e`.
3. Alternatives considered and rejected:
   - **Raise the spec's threshold** (200 → 1000): only moves the race; a short guide or a
     longer shell breaks it again.
   - **Shorten the offline header to please the spec** (drop the note): the note is
     required copy (§3.1, R-#246 §3); the product does not follow the test's needs.
   - **A fixed pause before reading**: slow and flaky, and the project already avoids
     pauses in E2E.
   - **Keep `isMetaMask` and give the in-app option priority inside wallet browsers too**:
     contradicts §3.1 rule 3 and R-#246 §3.
