# #155: Cluster/Country Funds & Operations (Actualizado)

Unified implementation for cluster/country funds, donations, GD contact tracking, and yield strategy for idle funds.

## Dependencies
- #152 (Profiles of Church / GD Cluster — includes `cluster` table)
- #154 (Ranking de Clústeres y Países)
- #161 (GD course — prerequisite for contact)
- Existing SLEARN and USDT contracts
- SLEARN contract: `ClusterFunds` MUST be whitelisted in SLEARN (restricted transfers)
- Existing LearnTGVaultsV3 contract
- `transaction` table (existing) — records all value movements. CHECK constraint must accept:
  - `subcategoria` values `'cluster'` and `'country'` for `type='donation'`
  - `type` values `'aave_deposit'` and `'aave_withdrawal'` (Phase 2)
- `m_hdi` table — Human Development Index by country and year (used for donation metrics)

**Note on SLEARN whitelist:** SLEARN has restricted transfers (only sender or receiver authorized). `ClusterFunds` must be added to `authorizedTransfers` in SLEARN via `addAuthorizedTransfer()` by the SLEARN admin (DEFAULT_ADMIN_ROLE). Without this, SLEARN donations will fail.

## 1. Contract Design: `ClusterFunds.sol`

### 1.1 Purpose
- Receive and manage USDT and SLEARN donations for clusters and countries
- **Country donations:** If clusters exist in the country → split equally among them. If no clusters → accumulate in country fund for future distribution
- When a new cluster forms in a country with accumulated funds → redistribute country funds equally among all clusters (including the new one)
- **Yield (Phase 2):** pdJ can deposit idle USDT in AAVE V3 while funds wait for GD contact; yield stays with the fund (70% cluster, 30% pdJ)
- Provide transparency through events

**Phase 2 note:** AAVE yield implementation (Section 4) is Phase 2 — not required for the Global Disciples pilot. The contract will be upgraded to support AAVE after the pilot.

### 1.2 Relationship with Existing Contracts

| Contract | Relationship |
|----------|--------------|
| `LearnTGVaultsV3` | Receives SLEARN from vaults for scholarships |
| `SLEARN.sol` | Can mint SLEARN for donations to clusters |
| `USDT` | Receives USDT donations for clusters |
| `AAVE V3 on Celo` | Yield generation for idle funds (Phase 2) |

### 1.3 Contract Functions

#### Donation Functions

Donations follow the calldata-stuffing pattern: users send USDT/SLEARN via `transfer()` to the contract. The backend verifies on-chain and calls `processDonation()` to allocate.

| Function | Description |
|----------|-------------|
| `processDonation(bytes32 txHash, address clusterWallet, uint8 pdjPercentage)` | Process a verified incoming donation: split USDT/SLEARN between cluster and pdJTreasury |
| `processCountryDonation(bytes32 txHash, string countryCode, uint8 pdjPercentage)` | Process a verified incoming donation to a country fund |

**`pdjPercentage`:** Fijo en 15%. Configurable por admin (no por donante) mediante `setPdJPercentage()`.

**Replay protection:** Each `txHash` is recorded on-chain after processing. `require(!processedTx[txHash], "Already processed")`.

#### Transfer Functions

| Function | Modifier | Description |
|----------|----------|-------------|
| `redistributeCountryFunds(string countryCode)` | `onlyAdmin` | Called by backend when a new cluster forms. Distributes country fund equally among all clusters in that country. Uses ratio-based calculation to avoid gas costs. Requires `getClusterCount(countryCode)` to know how many clusters exist. |
| `releaseClusterFunds(address clusterWallet, uint256 usdtAmount, uint256 slearnAmount)` | `onlyAdmin` | Transfer USDT/SLEARN from contract to cluster's `multisig_address`. Called by learn.tg backend (signed with `PRIVATE_KEY`). Requires `clusterFunds[clusterWallet].verified == true`. |
| `releaseCountryFunds(string countryCode, address recipient, uint256 usdtAmount, uint256 slearnAmount)` | `onlyAdmin` | Transfer USDT/SLEARN from country fund to a specific recipient (e.g., new cluster startup funds). Recipient must be a valid address in that country (verified by backend). |

**Note:** No `withdrawFunds` function. `releaseClusterFunds` transfers directly to the cluster's `multisig_address`. No two-step release+withdraw needed.

#### Admin Functions

| Function | Modifier | Description |
|----------|----------|-------------|
| `setPdJTreasury(address pdjTreasury)` | `onlyAdmin` | Set pdJ treasury wallet — pdJ's portion of donations and yield is sent here |
| `setPdJPercentage(uint8 percentage)` | `onlyAdmin` | Set the fixed percentage for pdJ (default 15%). Valid values: 0-30, steps of 5. 0% only allowed for admin use, not for donors. |
| `setClusterVerification(address clusterWallet, bool verified)` | `onlyAdmin` | Mark cluster as verified (required before `releaseClusterFunds`) |
| `getClusterCount(string countryCode)` | `view` | Returns the number of clusters in a country (used by `redistributeCountryFunds`) |

#### View Functions

| Function | Description |
|----------|-------------|
| `getClusterBalance(address clusterWallet)` | Get USDT and SLEARN balance of a cluster |
| `getCountryBalance(string countryCode)` | Get USDT and SLEARN balance of a country |
| `getClusterFunds(address clusterWallet)` | Get all fund information for a cluster |
| `getCountryFunds(string countryCode)` | Get all fund information for a country |

## 3. Contact with Global Disciples

### 3.1 Checkbox-Based Tracking

Contact with GD happens outside the platform. The platform tracks progress via **checkboxes** that cluster members and pdJ mark manually.

```mermaid
flowchart TB
    A[Cluster completes GD course] --> B[Cluster marks: ✅ Sent email to GD]
    B --> C[pdJ marks: ✅ pdJ contacted GD]
    C --> D[Wait for GD response]
    D --> E[pdJ marks: ✅ GD responded]
    E --> F[pdJ marks: ✅ Release funds]
    F --> G[Funds transferred to cluster wallet via ClusterFunds.releaseClusterFunds]
```

### 3.2 Checkbox Permissions

| Checkbox | Who can mark | Description |
|----------|-------------|-------------|
| ✅ Cluster sent email to GD | Cluster (any pastor) | Cluster confirms they contacted GD |
| ✅ pdJ contacted GD | pdJ (admin) | pdJ confirms parallel contact |
| ✅ GD responded | pdJ (admin) | GD confirmed contact with cluster |
| ✅ Release funds | pdJ (admin) | Triggers `releaseClusterFunds()` on-chain |

### 3.3 Status Display (derived, not stored)

Status is derived from checkboxes — no `status` column:

| Checkboxes marked | Display in Ranking |
|-------------------|-------------------|
| None | "⏳ Pendiente" |
| Cluster sent only | "✅ Clúster envió" |
| Cluster + pdJ sent | "✅ Ambos enviaron" |
| + GD responded | "✅ Contacto confirmado" |
| + Released | "💰 Fondos liberados" |

### 3.4 Contact Tracking Storage

```sql
CREATE TABLE gdcontact (
    id SERIAL PRIMARY KEY,
    cluster_id INTEGER REFERENCES cluster(id) UNIQUE,
    cluster_sent_at TIMESTAMP,        -- cluster marked: "we sent email"
    pdj_sent_at TIMESTAMP,            -- pdJ marked: "pdJ contacted GD"
    gd_responded_at TIMESTAMP,        -- pdJ marked: "GD responded"
    released_at TIMESTAMP,            -- pdJ marked: "release funds" → triggers releaseClusterFunds()
    release_reason VARCHAR(50),       -- 'gd_confirmed' (Phase 1) or 'timeout' (Phase 2)
    course_completed_at TIMESTAMP,    -- When cluster completed GD course
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_gdcontact_cluster_id ON gdcontact(cluster_id);
```

### 3.5 Fund Release

When pdJ marks the ✅ Release funds checkbox:

1. Backend calls `ClusterFunds.releaseClusterFunds(clusterWallet, usdtAmount, slearnAmount)`
2. If funds were in AAVE (Phase 2), contract withdraws first, distributes 30% yield to pdJ Treasury and 70% to cluster
3. Contract transfers USDT/SLEARN to the cluster's `multisig_address`
4. `gdcontact.released_at` is set to NOW
5. Event logged in `userevent` (`funds_released`)

### 3.6 Who Calls `redistributeCountryFunds`?

`redistributeCountryFunds` is called by the **learn.tg backend** (signing with `PRIVATE_KEY`) **after** a new cluster is successfully created in the database (via #152). The backend detects that the cluster belongs to a country that has accumulated funds and calls the function.

## 4. Yield Strategy for Idle Funds (Phase 2 — Post-Pilot)

This section is **Phase 2** and will be implemented **after** the Global Disciples pilot, not before. The contract will be upgraded to support AAVE in Phase 2.

### 4.1 Overview

Funds in `ClusterFunds` sit idle while waiting for GD contact + release (weeks to months). Since pdJ custodies these funds, pdJ can put them to work safely.

**Yield Distribution:**

| Recipient | % | Purpose |
|-----------|-----|---------|
| Cluster/Country Fund | 70% | Added to the same fund, visible in ranking |
| pdJ Treasury | 30% | Covers operational costs (servers, APIs, development) |

**Design principle:** Most yield stays with the cluster that generated it. pdJ takes a smaller share to cover real operational costs — transparent and visible in the dashboard.

### 4.2 Implementation

| Aspect | Decision |
|--------|----------|
| **Protocol** | AAVE V3 on Celo (USDT only) |
| **Who deposits** | pdJ admin (backend signed with `PRIVATE_KEY`) |
| **Who holds aUSDT** | `ClusterFunds` contract (not a separate wallet) |
| **When to deposit** | After donation, before release (admin-triggered or automatic) |
| **When to withdraw** | Automatically when `releaseClusterFunds()` is called |
| **Yield tracking** | On-chain balance difference tracked per cluster/country |

### 4.3 Transaction Table for AAVE

All AAVE operations are recorded in the existing `transaction` table:

```sql
-- AAVE deposit
INSERT INTO transaction (
    usuario_id, wallet, crypto, type, amount, balance_impact, date, hash,
    categoria, subcategoria, metadata
) VALUES (
    :usuario_id, :wallet, 'USDT', 'aave_deposit', :amount, -:amount, NOW(), :hash,
    'aave', 'deposit', '{"cluster_id": 1}'
);

-- AAVE withdrawal
INSERT INTO transaction (...) VALUES (
    :usuario_id, :wallet, 'USDT', 'aave_withdrawal', :amount, :amount, NOW(), :hash,
    'aave', 'withdrawal', '{"cluster_id": 1, "yield": 0.15}'
);
```

**Note:** Requires adding `'aave_deposit'` and `'aave_withdrawal'` to the `transaction` type CHECK constraint.

### 4.4 Events

| Event | Description |
|-------|-------------|
| `YieldGenerated(address indexed clusterWallet, uint256 yieldUsdt)` | Yield earned from idle funds |
| `YieldDistributed(address indexed clusterWallet, uint256 clusterShare, uint256 pdjShare)` | Yield split between cluster and pdJ |
| `ClusterDonation(address indexed donor, address indexed clusterWallet, uint256 usdtAmount, uint256 slearnAmount)` | Donation to cluster |
| `CountryDonation(address indexed donor, string countryCode, uint256 usdtAmount, uint256 slearnAmount)` | Donation to country |
| `CountryFundsRedistributed(string countryCode, uint256 usdtAmount, uint256 slearnAmount, uint8 clusterCount)` | Country funds distributed equally |
| `ClusterFundsReleased(address indexed clusterWallet, uint256 usdtAmount, uint256 slearnAmount)` | Funds released to cluster |
