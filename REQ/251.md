# R-#251: Wallet PIN policy and KDF calibration

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/251

**Status:** Pending — open question from the wallet/session review (2026-09-19).
Nothing is implemented: the PIN is digits-only with a fixed PBKDF2 work factor.
**Created:** 2026-09-19
**Type:** Security / UX
**Priority:** Medium — the stored record is the only thing an offline attacker
needs, and the user is allowed to choose a 6-digit secret against it.
**Dependencies:** https://github.com/pasosdeJesus/learn.tg/issues/236 (core wallet),
https://github.com/pasosdeJesus/learn.tg/issues/246 (unlock layers),
https://github.com/pasosdeJesus/learn.tg/issues/249 (backup verification)

---

## 1. Objective

Raise the cost of an offline attack against the stored wallet record and let the
user pick a stronger secret than six digits, **without** making the first-time flow
harder for a low-end phone.

## 2. What exists today (verified 2026-09-19)

- `packages/pdj-wallet/src/wallet.ts:87` validates the PIN with `/^\d{6,}$/`:
  **digits only**, minimum six. A six-digit secret is a 10^6 search space.
- KDF: PBKDF2-SHA256 with a **fixed** 600,000 iterations, 16-byte random salt,
  AES-GCM-256 with a 12-byte random IV per record (`src/crypto.ts:1-3`, `:40-96`).
  The iteration count is stored in the record, so old records stay readable.
- Measured cost of one derivation: ~110 ms on this VM (`doc/pdj-wallet-testing.md`
  probe section); the operator's target phones are Infinix-class.
- The record holds the private key **and** the recovery phrase (the phrase cannot
  be derived from the key), so the PIN protects both.
- The UI label says "PIN (6 or more digits)"; nothing tells the user that the 12
  words are the real recovery.

## 3. Risks

| Risk | Detail |
|---|---|
| Offline brute force of the record | 10^6 candidates at ~110 ms on a phone ≈ 30 hours single-threaded, but PBKDF2 is GPU-friendly; a small GPU cluster tries millions per second |
| Shoulder surfing / guessing on the device itself | Six digits are easy to observe and easy to guess (birthdays, 000000) |
| No user guidance | Most users do not know the phrase is what actually protects the funds if the PIN is guessed |

PBKDF2-SHA256 is the right choice here: it is native in WebCrypto, so it costs no
download and no battery-hungry WASM on the phones this project targets. Argon2id
would be better against GPUs but has no WebCrypto implementation; keep it as a
future option behind a size/CPU measurement, not as a default.

## 4. Proposal

1. **Accept a passphrase.** Change the rule to "at least 8 characters, anything
   printable" and keep a 6-digit PIN as one allowed shape (so existing wallets and
   habits keep working). Normalize with Unicode NFKD + trim (and optional
   case-folding only if the field is explicitly a PIN) so a legitimate user does
   not lock themselves out over a space or a composed accent.
2. **Calibrate the work factor on the device.** At creation, measure one
   derivation and pick the highest iteration count that stays within a budget
   (~300-500 ms), with a **floor of 600,000** (never below today's value) and a
   ceiling (~5,000,000) so a slow phone cannot hang. The count already lives in
   the record, so mixed records keep working.
3. **Upgrade on unlock.** If a record's iteration count is below the current
   target, re-encrypt it after a successful unlock (the plaintext is in memory at
   that moment). No user-visible step.
4. **Set expectations in the UI.** The PIN field says what is accepted, a short
   hint says the 12 words are the recovery, and (with R-#249) the backup test
   happens before the wallet counts as created.
5. **Keep the failure messages honest.** "Wrong PIN or corrupted data" is fine
   (it must not distinguish the two), but the help text should say what to do.

## 4b. Comparison with the Rabby source review (2026-09-19)

From `/var/www/adJ-ia/Rabby` (see R-#246 §14 for the full review):

- Rabby does not derive its biometric wrapping key from a KDF over a user secret
  at all: it HKDF-SHA256s the WebAuthn **userHandle** of a resident credential and
  uses that AES-GCM key to wrap the vault *password*
  (`src/ui/utils/biometric.ts`). Whatever layer we add, this requirement keeps the
  PIN as the only secret the user owns and the 12 words as the recovery.
- Rabby keeps `exportedKey` + `salt` from `@metamask/browser-passworder` in
  `browser.storage.session` while unlocked so later writes do not re-derive the key
  (`src/background/utils/password.ts`), and clears them on lock. We deliberately do
  **not** export the derived key: every encryption asks for the PIN again. Keep it
  that way here; if a future convenience path stores a derived key, it must be
  non-extractable and cleared on lock, and this requirement must say so.
- Their password policy is a normal extension password (min length enforced in the
  UI), not a numeric PIN; our `assertPin` (`/^\d{6,}$/`) is stricter about shape and
  weaker about entropy, which is exactly what item 1 above proposes to fix.

## 5. Acceptance criteria

- [ ] A passphrase of 8+ characters (letters, digits, symbols) creates and unlocks
      a wallet; a 6-digit PIN still works.
- [ ] Normalization is documented and tested (leading/trailing spaces, NFKD).
- [ ] The iteration count is calibrated within the floor/ceiling bounds and stored
      in the record; a unit test asserts the floor.
- [ ] A record below the current target is transparently re-encrypted on unlock
      (test: open an old record, assert the stored count went up and the wallet
      still unlocks with the same secret).
- [ ] The UI states the accepted secret shapes and points at the 12 words as
      recovery, in English and Spanish.
- [ ] `doc/pwa-user-guide.md` and `packages/pdj-wallet/README.md` updated.

## 6. Open questions

1. Is a minimum of 8 characters too much friction for the first-time flow, or is
   the 6-digit PIN (kept as an option) what most users will pick anyway?
2. Should the app refuse the classic weak PINs (000000, 123456, birthdays)?
3. Do we want an "unlock with the 12 words" shortcut in the dialog (today recovery
   means import), to reduce the cost of a forgotten passphrase?
