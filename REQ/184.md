# R-#184: In-App Wallet — Self-Custodied Wallet for learn.tg

**Created:** 2026-07-13
**Updated:** 2026-09-14
**Status:** Proposal
**Type:** Feature
**Priority:** High
**Dependencies:** R-#14 (`@pasosdejesus/m/wallet`), E-#177 (Two-Layer Strategy), R-#176 (Post-Quantum Identity), R-#227 (Session-first auth)

---

## 1. Objective

Create a **PWA-native, self-custodied wallet** that lets new users generate a wallet directly in the browser — no app store, no extension, no server storage. The user receives a seed phrase and controls their keys from day one.

The In-App Wallet is designed to be:

- **The primary onboarding path** for users without an external wallet (Seria/Falaba, Sierra Leone)
- **Interoperable** with external wallets (Rabby, MetaMask, OneKey, OKX Web3) via a standard BIP39 seed phrase
- **Multi-chain ready** for the Two-Layer Strategy (E-#177): Celo today, Cardano in the future, with preparation for post-quantum (SPHINCS+)
- **Offline-first**, so it works in low-connectivity contexts (PWA + IndexedDB)

---

## 2. Motivation

Many users arrive at learn.tg **without a wallet**. Today they must:

1. Leave learn.tg → go to Play Store / App Store
2. Install Rabby (or another wallet)
3. Return to learn.tg, connect, and sign in

This friction loses users. A built-in wallet eliminates the bounce and lets users start learning immediately. It also aligns with our educational mission: the user learns seed phrases by **using** one from the start.

Additionally, R-#184 is designed to be the **bridge between Celo (operational layer) and Cardano (resilience layer)** as defined in E-#177.

## 3. Design

### 3.1 Wallet Creation (Client-Side Only)

```
┌─────────────────────────────────────────────────────┐
│  Browser / PWA                                       │
│                                                      │
│  1. crypto.getRandomValues() → 128-bit entropy       │
│  2. BIP39 → 12-word seed phrase                      │
│  3. BIP32/BIP44 → private key → address              │
│  4. Show seed phrase to user (once, never again)     │
│  5. User confirms they saved it (3-word verification)│
│  6. Sign SIWE message with derived private key → auth │
│                                                      │
│  Nothing leaves the browser — no server knows        │
│  the seed phrase or private key.                     │
└─────────────────────────────────────────────────────┘
```

---

### 3.2 Multi-Chain Derivation (E-#177 Alignment)

The same seed phrase derives keys for multiple chains:

| Chain | Curve | Derivation Path | Purpose |
|-------|-------|-----------------|---------|
| **Celo (EVM)** | secp256k1 | `m/44'/52752'/0'/0/0` | Daily operations, course, scholarships |
| **Cardano** | Ed25519 | `m/1852'/1815'/0'/0/0` | Resilience layer (future) |
| **Post-Quantum (SPHINCS+)** | SPHINCS+ | *To be defined (CIP-0197 or custom)* | Identity (#176, future) |

**Principle:** One seed phrase, multiple wallets.

---

### 3.3 Storage

| What | Where | Encrypted? |
|------|-------|------------|
| Seed phrase | User's paper / device | N/A |
| Private key | Session-only memory (or IndexedDB encrypted with user PIN) | Optional PIN (AES-256-GCM + PBKDF2) |
| Public address | `billetera_usuario` (same as any wallet) | N/A |

No server-side storage of private material. The private key can optionally be stored in IndexedDB encrypted with a user-chosen PIN for session persistence (avoids re-entering seed phrase every visit).

### 3.5 Auth Flow

The derived private key signs SIWE messages exactly like an external wallet. No change to `/api/auth/callback/credentials` — the backend sees a valid SIWE signature and proceeds normally.

**Implementation with viem:**

```typescript
// External wallet (uses window.ethereum)
const externalWalletClient = createWalletClient({
  chain: celo,
  transport: custom(window.ethereum),
});

// In-App Wallet (uses local private key)
const inAppAccount = privateKeyToAccount('0x...');
const inAppWalletClient = createWalletClient({
  account: inAppAccount,
  chain: celo,
  transport: custom({ request: async () => {} }), // No external transport
});
```

**Key point:** When a local `account` is passed to `createWalletClient`, viem signs **locally** with that private key. It does not delegate signing to `window.ethereum`.

---

### 3.6 Seed Phrase Verification

After showing the 12-word seed phrase, the user must confirm they saved it by:

1. Selecting 3 random words from the phrase in the correct order
2. Or typing 3 random words

If the user fails, the wallet is not created and the phrase is discarded.

---

### 3.7 Bridge to External Wallets

The In-App Wallet is a **stepping stone**, not a dead end:

| Migration | How |
|-----------|-----|
| **In-App → External** | Export seed phrase → Import in Rabby/MetaMask/OneKey |
| **External → In-App** | Export seed phrase from external wallet → Import in In-App Wallet |
| **Change external wallet** | Connect with new wallet (Connect Wallet) |

The seed phrase is standard BIP39 and compatible with any wallet that supports BIP39.

---

### 3.8 Offline-First Design (PWA)

The In-App Wallet is designed to work **offline-first**:

| Feature | Offline Support |
|---------|-----------------|
| **Wallet generation** | ✅ Yes (all client-side) |
| **SIWE signing** | ✅ Yes (local signing) |
| **Auth session** | ✅ Yes (session stored in IndexedDB) |
| **Transaction signing** | ✅ Yes (local signing) |
| **Synchronization with learn.tg** | ⏳ When connection is available |

This makes the In-App Wallet the ideal companion for the PWA in low-connectivity contexts (Seria/Falaba).

---

### 3.9 Future: Post-Quantum Preparation

Following E-#177 and R-#176, the In-App Wallet is designed to be:

- **Compatible with SPHINCS+** when the post-quantum identity layer is implemented
- **Prepared for Cardano** with Ed25519 derivation
- **Ready for CIP-0197** (Post-Quantum ZK Signatures for HD Wallets) when it becomes standard

For the MVP, the wallet uses secp256k1 (Celo) and Ed25519 (Cardano) derivation. SPHINCS+ support will be added when a standard derivation path emerges.

## 5. Out of Scope (MVP)

- Native mobile app (PWA only)
- Storing seed phrase server-side
- Sending transactions from the In-App Wallet (SIWE auth only — user switches to external wallet for UBI claims and scholarships)

## 7. Acceptance Criteria

### Wallet Creation
- [ ] User clicks "Create Wallet" → sees 12-word seed phrase
- [ ] User confirms phrase (3-word verification) → wallet is "connected" (address derived, no server roundtrip)
- [ ] User can sign in (SIWE) with the derived key
- [ ] Private material never leaves the browser (verify via Network tab)
- [ ] Works in PWA standalone mode
- [ ] Seed phrase can be imported into Rabby/MetaMask/OneKey and yields same address

### Multi-Chain Derivation
- [ ] Same seed phrase derives a secp256k1 key for Celo
- [ ] Same seed phrase derives an Ed25519 key for Cardano (when implemented)
- [ ] Architecture is prepared for SPHINCS+ (future)

### Detection and Connection
- [ ] If `window.ethereum` exists and In-App Wallet exists → show both options
- [ ] If `window.ethereum` exists and no In-App Wallet → show "Connect Wallet" + "Create In-App Wallet"
- [ ] If `window.ethereum` does not exist and In-App Wallet exists → show "Connect In-App Wallet"
- [ ] If `window.ethereum` does not exist and no In-App Wallet → show "Create In-App Wallet"
- [ ] User can migrate from In-App Wallet to external wallet by exporting seed phrase
- [ ] User can migrate from external wallet to In-App Wallet by importing seed phrase
- [ ] UI clearly shows available options based on the scenario

### Security
- [ ] Private key is encrypted in IndexedDB with user PIN (AES-256-GCM + PBKDF2)
- [ ] If user loses PIN, they can recover by re-entering seed phrase
- [ ] Private material never leaves the browser

### Offline-First
- [ ] Wallet generation works offline
- [ ] SIWE signing works offline
- [ ] Session persists in IndexedDB
- [ ] Synchronization happens when connection is available
