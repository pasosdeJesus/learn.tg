# R-#292: Protocol to retire a course

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/292
**Created:** 2026-10-31
**Status:** Proposal — a **procedure** for V5 (runnable today, the operator executes it) and the
protocol for V6, whose deployment is undated (R-#293).
**Type:** Operations / contract accounting
**Priority:** High — course 106 was "retired" by withdrawing its 8 USDT without zeroing its
books, and that single omission travelled through four vault versions (R-#221).

## 1. What "retiring a course" means

A course is retired when **all** of this is true:

1. it is no longer sold: hidden from the catalog and the purchase API refuses it;
2. it no longer pays scholarships;
3. its recorded balance is **0**, and the tokens that backed it are either returned to the
   owner or left as unallocated float of the pool;
4. its row and its history stay: `premium_course_usuario`, `transaction`, the donations and
   `guidePaid` all point at the same `courseId`, and `getStudentGuideStatus` must keep
   resolving for the historical record.

Retiring is **not** deleting the course row, and it is not "withdraw the money and forget the
number": the number is the part that has to be cleaned.

## 2. Who does it and how

The owner of the vault (the `admin` operational wallet) sends the transactions with
`bin/m eng:opwallet:*`; they are `onlyOwner` calls on the vault. The agent may prepare and
verify the commands, but **does not move real tokens** (AGENTS §6): the operator runs them.

## 3. Today — `LearnTGVaultsV5` (deployed, there is no `retireCourse`)

The vault address comes from `apps/contracts/deployments/LearnTGVaults/V5/<network>.json`
(mainnet: `0x4d1607A8AEfCdF7B24208E5ceA1e55085781Fc3B`). `<id>` is the `courseId`
(`cor1440_gen_proyectofinanciero.id`).

### 3.1 Stop selling

- In the database set **both** `conBilletera` and `sinBilletera` to false for the course. That
  is the catalog filter (`app/api/course-catalog`) and, since 2026-10-30, the purchase gate
  (`canPurchasePremiumCourse` answers `course_not_offered`).
- If a payment could be in flight, `pause()` SLEARN for the window
  (`bin/m eng:opwallet:send --name admin --to <SLEARN> --function "pause()"`) and unpause it at
  the end. Do **not** leave it paused.

### 3.2 Measure (read-only)

```sh
cd apps/web
make vault-check ARGS="--network celo --json"      # per-course books, Σ and held
bin/m eng:opwallet:call --name admin --to <V5> --function "vaults(uint256)" --args "<id>"
```

Write down:

- `recorded` = the course's `balanceUsdt` / `balanceSlearn`;
- `float` = `held − Σ (every other course's balance)`: the part of the pool that is not owed to
  another course. It is the **maximum** that can be returned to the owner.

If `Σ books > held`, stop and run R-#221's cleanup first: a course with a phantom cannot be
retired cleanly until the books of the whole vault are consistent.

### 3.3 Zero the books first

```sh
bin/m eng:opwallet:send --name admin --to <V5> \
  --function "setVaultBalance(uint256,uint256,uint256)" --args "<id>,0,0"
```

This does not move tokens: it drops the course's claim and leaves the tokens as float. The
trace on chain is `VaultBalanceSet(<id>, 0, 0)`.

### 3.4 Verify before touching the money

```sh
make vault-check ARGS="--network celo"      # must be OK (Σ ≤ held)
```

If it fails, the course was not the only phantom: stop and reconcile.

### 3.5 Decide what happens to the money

- **Leave it in the pool** (the default when other courses still need it): nothing else to do.
  The tokens are now unallocated float and other courses can use them.
- **Return the backed part to the owner**:

  ```sh
  # USDT has 6 decimals, SLEARN 2. Amount = min(recorded, float).
  bin/m eng:opwallet:send --name admin --to <V5> \
    --function "emergencyWithdrawUSDT(uint256)" --args "<amount>"
  bin/m eng:opwallet:send --name admin --to <V5> \
    --function "emergencyWithdrawSLEARN(uint256)" --args "<amount>"
  ```

  V5 does not enforce the float: the operator has to compute it (3.2) and never exceed it.
  Withdrawing more than `float` is exactly how another course is left without money.

### 3.6 Verify again and record

```sh
make vault-check ARGS="--network celo"      # must stay OK
```

Keep in the issue (and in `db/chain-state/` if the retirement happens inside a migration): the
course id and network, `recorded` before, `float`, the amount withdrawn, and the hash of the
`setVaultBalance` and of each withdrawal. The vault is kept (`exists = true`); never call
`createVault` again for that id.

### 3.7 Pitfalls (each one has already happened in this project)

| Pitfall | What it causes |
|---|---|
| withdrawing without zeroing the book | the 106 case: the number survives every migration (R-#221) |
| zeroing and forgetting the check | a later `setVaultBalance` can restore a phantom; `Σ ≤ held` is the guard |
| withdrawing more than `float` | another course cannot pay its next scholarship |
| deleting the course row | `premium_course_usuario`, `transaction` and `guidePaid` lose their parent |
| reusing the `courseId` for a new edition | the retired vault's history mixes with the new one; create a new course |

## 4. Future — `LearnTGVaultsV6` (written, not deployed; R-#293)

The same decisions, in one transaction:

```sh
# sendToOwner = true returns min(recorded, float) to the owner;
# sendToOwner = false leaves the backed part as float.
bin/m eng:opwallet:send --name admin --to <V6> \
  --function "retireCourse(uint256,bool)" --args "<id>,true"
```

What the contract does: sends `min(recorded, float)` of each token to the owner, writes off
whatever has no tokens behind it, sets the course balance **and** the per-guide amounts to 0,
sets `retired = true`, updates `totalRecordedUsdt/Slearn` and emits
`CourseRetired(id, sentUsdt, sentSlearn, unsentUsdt, unsentSlearn)`.

From then on the course is closed for business at the contract level:

- `recordCourseFunds` reverts ("Course is retired"): the January mistake cannot repeat, even if
  the catalog flags are wrong;
- `payScholarship`, `setAmountPerGuide` and `setVaultBalance` revert for that course;
- the only calls left are `retireCourse` again (idempotent: it sweeps whatever arrived before
  the flag) and `emergencyWithdraw*` of the float;
- `createVault` refuses an existing id, so a new edition needs a new `courseId`.

Verification is the same `make vault-check` (on V6 it also cross-checks `accountingState()`
against the scanned sum) and `retired` must be true; `accountingBroken` must stay false.

During the V5→V6 migration (`apps/web/db/migrations/next/20261030_contract-to-v6.ts`) retired
courses are simply not recreated: the script only creates vaults for courses with a balance or
with `guidePaid` pairs, and it refuses to restore a course that is retired in the target.

## 5. Record to keep for every retirement

| Field | Why |
|---|---|
| network, courseId, date | identify the case |
| `recorded` USDT/SLEARN before | the claim being removed |
| `float` at that moment | bounds what could be returned |
| amount actually withdrawn (USDT/SLEARN) | matches the token balance change |
| hash of `setVaultBalance`/`retireCourse` and of each withdrawal | audit on Blockscout |
| `make vault-check` before and after | proves the invariant |
