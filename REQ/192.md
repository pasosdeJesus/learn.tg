## Phase 2 Features

### 1. Registration Photo Verification (Admin)

When a pastor declares a church, they upload a `registration_photo`. The admin must be able to verify this document during the interview.

**Admin UI:**

| Field | Action |
|-------|--------|
| Registration photo | View photo (opens in new window) |
| Registration number | View/edit |
| `registration_verified` | Toggle `true`/`false` |

**Endpoint:** `PATCH /api/admin/church/[id]`

**Process:**
1. Admin views the registration photo via `/api/user/id-photo/[churchId]?side=registration`
2. Admin confirms document is valid
3. Admin sets `registration_verified = true`
4. Church is marked as "verified" on public page

### 2. Pastor Wallet (Phase 2)

**Objective:** Add a wallet address field to the pastor's church record so the church can receive funds.

**Field:** `church.wallet_address` VARCHAR(42)

**Where to collect:**
- Pastor dialogue when declaring a church
- Admin can edit via `/api/admin/church/[id]`

**Why:** Required for clusters and country funds (R-#155).

### 3. Church Curation and Deduplication (Phase 2)

**Problem:** Users may declare duplicate churches (same name, same city) multiple times.

**Solution:** Admin interface for merging duplicates (already in R-#190).

**Additional:**
- Notification when duplicate is detected (future)
- Auto-suggestion of existing churches when user types a name

### 4. SLEARN Bonus (On-Chain) — from the churches fund

Replace the `POST /api/admin/pastor-bonus` stub with a real SLEARN transfer from
the **churches fund** (`churchesWallet` in `SLEARN.sol`).

**Eligibility (updated 2026-08-14):**
- Pastor (`church_relationship = 'pastor'`).
- Pilot country: Colombia or Sierra Leone (`usuario.pais_id` in `[170, 694]`).
- Non-Zionist: `usuario.position_israel_gaza = 'no'`.
- **Profile score > 90** (`usuario.profilescore > 90`).
- Verified church: `church.registration_verified = true` (the verifier confirmed
  the church's registration document).
- Not paid before (no previous bonus in `transaction`).
- **While funds last**: the churches fund must hold ≥ 22 SLEARN.

> Note: eligibility was simplified to `profile score > 90` instead of requiring
> each verified field separately (the score already covers name, country, email,
> WhatsApp/Telegram, location, place of worship, GoodDollar and the interview).

**Notification:**
- To the verifier: `PATCH /api/admin/church/[id]` and `PATCH /api/admin/user/[id]`
  return the bonus result (`{ bonus: { awarded, amount, hash } }`) and the admin
  modal shows a toast when it is awarded.
- To the pastor: a row is inserted in the `notifications` table (R-#162 phase 1)
  and can be read via `GET /api/notifications`.

**Automatic trigger:** the bonus is awarded automatically once the data is
verified (no manual button):
- `PATCH /api/admin/user/[id]` — after verifying the pastor's data.
- `PATCH /api/admin/church/[id]` — after verifying the church registration
  (`registration_verified = true`).
Both call `awardPastorBonus()`, which validates the full eligibility.

**Source of funds:**
- The bonus comes from the **churches fund** (`SLEARN.churchesWallet`), which
  receives 5 % of `processPayment` (`_distributeChurches`). NOT from the main
  backend wallet.
- The backend signs with `CHURCHES_WALLET_PRIVATE_KEY` (the `churchesWallet`
  key), not with `PRIVATE_KEY`.

**Reading the fund balance (new):**
- Endpoint `GET /api/churches/fund` returning the `churchesWallet` SLEARN (and
  USDT) balance, so a pastor can see how much is left.

**Pastor landing page (onboarding):**
- Pages `/gdcluster/pastors` (EN) and `/redgd/pastores` (ES) with the
  `GdPastoresLanding` component.
- They show: the GD course invitation, requirements (pastor + pilot country +
  score > 90 + registration document + non-Zionist), the 22 SLEARN bonus and the
  churches fund balance (SLEARN).
- They include the **onboarding path** for a new pastor: (1) Web3 & UBI course
  for wallet and platform, (2) complete the profile + propose an interview (over
  90 points and 22 SLEARN awarded automatically when the documents are verified),
  (3) claim the daily UBI, (4) optional crosswords to earn USDT/SLEARN, (5) GD
  course payable in SLEARN/USDT (if USDT is scarce in Sierra Leone →
  `stable-sl.pdJ.app`).
- A "why the GD course matters" section without revealing the content (it is
  unlocked on payment).

**Requirements:**

1. **Get pastor wallet**: Query `billetera_usuario.billetera` for the pastor's
   wallet address.
2. **Validate eligibility**: pilot + complete profile + church registration
   verified + non-Zionist + not paid.
3. **Check fund balance**: read `SLEARN.balanceOf(churchesWallet)` ≥ 22e2.
4. **Transfer SLEARN**: `SLEARN.transfer(pastorWallet, 22e2)` signed with
   `CHURCHES_WALLET_PRIVATE_KEY`.
5. **Wait for confirmation** + **Store tx hash** + **Handle errors**.

**Technical Details:**

- **Contract**: SLEARN (ERC-20, 2 decimals) on Celo
- **Amount**: 22 SLEARN (= 2200 in contract units, `22 * 10^2`) — was 44
- **Network**: Determined by `NEXT_PUBLIC_NETWORK` env var
- **Churches fund**: `NEXT_PUBLIC_CHURCHES_WALLET_ADDRESS` +
  `CHURCHES_WALLET_PRIVATE_KEY` (the fund key, not the backend one)
- **Library**: `viem` (already in dependencies)

**Real implementation:** `packages/rewards/src/lib/pastor-bonus.ts` (engine `@learn-tg/rewards`, https://gitlab.com/pasosdeJesus/m/-/work_items/35 — `isEligiblePastor` +
`awardPastorBonus`), invoked from `PATCH /api/admin/user/[id]` and
`PATCH /api/admin/church/[id]` when the data is verified.

**Edge Cases:**

- **Insufficient SLEARN balance**: Return error, log, do NOT record as paid
- **Network timeout**: Retry once, then fail with clear message
- **Pastor has no wallet**: Return error "pastor has no wallet address"
- **Already paid**: Check `transaction` table for existing bonus to avoid duplicates

**Dependencies:**

- `viem` (already installed)
- `packages/rewards/src/lib/deployments.ts` (`getSlearnAddress`)
- `SLEARNAbi` from `@/abis/SLEARN.json`
- `@pasosdejesus/m/blockchain` for SLEARN_ADDRESSES
- `erc20Abi` from `viem` or hardcoded
