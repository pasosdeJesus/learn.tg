# R-#203: Web3 Engine System — Modular Course Plugins

Design a pluggable "engine" system inspired by Rails engines and `m eng:credentials`.
Each course or feature group ships as a self-contained module with its own database
schema, API routes, frontend components, smart contracts, and tests. Compilable
independently, pluggable into learn.tg.

---

## Motivation

The GD cluster course (`gdcluster`) currently mixes course content with a dedicated
smart contract (`ClusterFunds`), donation system, ranking, and contact tracking.
As more courses add their own contracts and logic, learn.tg needs a modular
architecture where each course engine can be:

- **Developed in isolation** — compile and test independently
- **Added or removed** without touching core learn.tg
- **Namespaced** — no collisions between engines (API, DB, routes)
- **Versioned** — engines can evolve independently of the host app

## Inspiration

| Source | Pattern |
|--------|---------|
| Rails engines | Self-contained gems with migrations, routes, views, tests |
| `m eng:credentials` | Plugin system: `eng:credentials:*` commands, isolated blockchain logic |
| `@pasosdejesus/mpdj` | PdJ-specific plugin that extends `m` without modifying it |
| Remix IDE plugin system | Each plugin declares `profile`, `methods`, `events` |

## Namespace Conventions

| Layer | Pattern | Example |
|-------|---------|---------|
| API | `/api/{engine}/...` | `/api/gdcluster/ranking/clusters` |
| Pages | `/[lang]/{engine}/...` | `/en/gdcluster/ranking` |
| DB tables | `{engine}_*` prefix | `clustergd`, `gdcontact` |
| Components | `{Engine}*` prefix | `GdDonateModal`, `GdContactTracker` |
| Contracts | Engine-specific directory | `engines/gdcluster/contracts/` |

## Integration Points

### 1. Database

Engine migrations run alongside core migrations. The host app's migration runner
discovers engines via `engines/*/db/migrations/` and runs them in dependency order.

```typescript
import { discoverEngines } from '@/lib/engines'
for (const engine of discoverEngines()) {
  await runMigrations(engine.db.migrations)
}
```

### 2. API Routes

Engine API routes are mounted at build time:

```
engines/gdcluster/api/gdcluster/  →  app/api/gdcluster/
```

Engines register themselves at startup:

```typescript
// engines/gdcluster/index.ts
export function register(host: EngineHost) {
  host.addRoutes('/api/gdcluster')
  host.addPages('/gdcluster')
}
```

### 3. Frontend Pages

```
engines/gdcluster/pages/[lang]/gdcluster/  →  app/[lang]/gdcluster/
```

### 4. Smart Contracts

Each engine has its own Hardhat project. Compiled and deployed independently.

```sh
cd engines/gdcluster/contracts
pnpm hardhat compile
pnpm hardhat run scripts/deploy.ts --network celoSepolia
pnpm hardhat test
```

### 5. Components

```typescript
import { GdDonateModal } from '@/engines/gdcluster/components/GdDonateModal'
```

### 6. Tests

```sh
pnpm test                           # core + all engines
pnpm test --engine gdcluster        # single engine
cd engines/gdcluster && pnpm test   # engine in isolation
```

## Migration Path

### Phase 1 — Namespace existing GD code (current)

Move existing GD code to `engines/gdcluster/` directory without full engine
infrastructure. Just reorganize files. API and pages keep working.

### Phase 2 — Engine manifest + discovery

Add `engine.json`, implement `discoverEngines()`, create engine registry.

### Phase 3 — Build tooling

Scripts to compile engines independently, run engine-specific tests.

### Phase 4 — Generic engine template

`pnpm create engine my-course` generates scaffold.

- [ ] GD cluster code lives under `engines/gdcluster/`

- [ ] Adding/removing an engine does not break core learn.tg
