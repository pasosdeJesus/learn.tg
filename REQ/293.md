# R-#293: LearnTGVaultsV6 (the accounting guard)

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/293
**Created:** 2026-10-31
**Status:** Proposal — written and tested, **not deployed**. No date for the deployment or for the V5→V6 migration.
**Type:** Contracts / accounting / migration
**Priority:** High — a course whose recorded balance exceeds the vault's tokens can leave later
students unpaid, and the course 106 case (R-#221) already left 8.040910 USDT of phantom books.

## 1. Objective

1. Make the per-course books of the scholarship vault **self-enforcing**: no function may
   leave the sum of the courses above the tokens the vault holds.
2. Give the operator the call that was missing in January 2026: retire a course **and** clean
   its books (and optionally return the tokens) in one transaction.
3. Keep the migration of the vault repeatable, resumable and auditable, so nobody ever again
   runs a balance restore twice.
4. Leave the code and the tests of the next version apart from the versions in production, so
   nothing under `next/` is mistaken for live code.

## 3. Why (the problem this version fixes)

`LearnTGVaultsV5` keeps one token balance but **per-course bookkeeping**:

- `recordCourseFunds` adds to `vaults[courseId].balanceUsdt/Slearn` (only the SLEARN
  contract can call it).
- `payScholarship` requires **that course's** recorded balance to be ≤ the contract's
  **whole** token balance, then pays and subtracts.
- `setVaultBalance` (a migration helper, `onlyOwner`) sets a course's balance requiring
  only **that amount** ≤ the whole balance. It never looks at the sum of the courses.
- `emergencyWithdrawUSDT/SLEARN` move tokens out **without touching** the per-course
  balances. This is not hypothetical: on 2026-01-13 a test deposit of 10 USDT went into the
  already-retired course 106, the 8 USDT that stayed in the vault were withdrawn 1 min 41 s
  later (`emergencyWithdrawUsdt(8000000)`, `0x6f22cc3a…c548600e0e2`, block 56 437 614) and
  the course kept its 8 USDT on the books, because the contract accepted the deposit and had no
  way to zero a balance.

So the recorded balances can add up to more than the contract holds. On Celo mainnet
(2026-10-28, block ≈ 81 410 000) they did:

| | Recorded (sum of courses) | Held | Difference |
|---|---|---|---|
| USDT, as found (106 = 8) | 21.236402 | 13.195492 | **−8.040910** |
| USDT with 106 zeroed | 13.236402 | 13.195492 | **−0.040910** |
| SLEARN | 819.23 | 834.29 | +15.06 |

The gap was the retired course **106** ("W e b 3 e IBU --retirado"), which carried a
recorded balance of **8 USDT** (zeroed since) and a per-guide amount of 0.000001. Those 8 USDT
were real: `deposit(106, 10000000)` put 8 USDT into V2 on 2026-01-13 21:04:31 (block 56 437 513)
— a test deposit into a course that was already retired — and `emergencyWithdrawUsdt(8000000)`
took them back to the owner at 21:06:12 the same day (block 56 437 614). The withdrawal could
not zero the book, so the number stayed; no `CourseFundsRecorded` event exists for 106.

Every migration then did exactly what it was written to do: drain the tokens, read the
per-course numbers from the old vault and restore them in the new one with `setVaultBalance`.
That is why the same 8 USDT appear in every version:

| Version | Sum of books | Tokens held | Over |
|---|---|---|---|
| V2 (before its sweep) | 16.248137 | 8.248137 | 8.000000 |
| V3 (`0x34b0…4728`, before its sweep) | 19.418021 | 11.418021 | 8.000000 |
| V4 (`0x42dc…0479`, before its sweep) | 20.265825 | 12.224915 | 8.040910 |
| V5 (after its setup) | 20.262753 | 12.224915 | 8.037838 |

A `totalRecordedUsdt` updated by the setters and compared against
`token.balanceOf(address(this))` would have stopped the first migration that copied the
phantom, and `retireCourse` gives the operator the call that was missing in January.

The extra **0.040910** (V4 8.040910 against 8.000000 in V2 and V3) is not an emergency
withdrawal: V4 has exactly two, both during the 2026-08-12 migration (12.224915 USDT and
301.12 SLEARN, which went straight into V5). It comes from running the V3→V4 migration
**twice**: `setVaultBalance` is not idempotent (it re-applies the snapshot), so the second run
(2026-06-10 09:10:32) undid three movements made after the first one (2026-06-09 18:44:07): a
record of 0.50909 for course 103, a record of 0.21 for course 107 and a payout of 0.76 for
course 2, netting 0.040910 of extra books. V6 rejects that second run (`_assertSolvent` in
`setVaultBalance`) and the runbook forbids re-running a balance restore.

Impact: nobody is owed that money (the course is retired and pays 0.000001 per guide),
but the books overstate the fund, and a course whose recorded balance exceeded the global
balance would make `payScholarship` **revert**. The invariant `Σ recorded ≤ held` is the
one to enforce.

## 4. What V6 implements

**Decision (operator, 2026-10-22): one contract per course is not practical; the fix is to do
the accounting well in the contract.** The contract keeps a single vault and makes the books
self-enforcing.

1. **Two accumulators.** `uint256 public totalRecordedUsdt; uint256 public
   totalRecordedSlearn;`, changed only by the four functions that touch `vaults[]`:
   `recordCourseFunds` (`+=`), `payScholarship` (`-=` exactly what it deducts),
   `setVaultBalance` (`total - old + new`) and `retireCourse` (`-=` the removed amounts).
   Each one ends with

   ```solidity
   function _assertSolvent() internal view {
       require(totalRecordedUsdt <= usdtToken.balanceOf(address(this)), "Accounting: USDT");
       require(totalRecordedSlearn <= slearnToken.balanceOf(address(this)), "Accounting: SLEARN");
   }
   ```

   O(1): do **not** iterate `vaults` (there is no course list and the gas would be unbounded).
2. **`emergencyWithdraw*` can only take the unallocated float:** `require(amount <=
   balanceOf(this) - totalRecordedX, "Withdrawal would break accounting")`. For a real
   emergency there is `forceEmergencyWithdraw*` with an explicit step, which sets
   `accountingBroken = true`, emits it, and makes `payScholarship` revert until the owner
   reconciles. A migration therefore zeroes the books first (`setVaultBalance` or
   `retireCourse`), withdraws, and declares the balances again in the new vault; the contract
   cannot silently keep paying against money that left.
3. **`retireCourse(courseId, bool sendToOwner)`**: retires the course and cleans its books in
   one call, so the second half cannot be forgotten (this is exactly the course 106 case). It
   also sets a `retired` flag in the vault: from then on the course **cannot take funds**
   (`recordCourseFunds` reverts, so the January mistake cannot repeat), cannot pay and cannot
   be repriced; the only operations left are `retireCourse` again and the emergency withdrawals,
   so whatever it still holds can always be swept. Since there is **one** token balance, "the
   course's money" is its recorded balance and it can only be paid from the float left after
   covering the other courses: it sends `min(recorded, float)` to the owner when `sendToOwner`
   is true, writes off whatever has no tokens behind it, or (with `false`) leaves the backed
   part in the pool as float. It keeps `exists = true`, zeroes the per-guide amounts and emits
   `CourseRetired(courseId, sentUsdt, sentSlearn, unsentUsdt, unsentSlearn)`. The operational
   protocol is R-#292.
4. **A view for the off-chain check.** `accountingState() returns (heldUsdt, heldSlearn,
   totalRecordedUsdt, totalRecordedSlearn, accountingBroken)`, read by
   `apps/web/bin/check-vault-balances.mjs` (target `make vault-check`); the script also
   **fails when the accumulator differs from the scanned per-course sum**, because that is a
   contract bug, not rounding.
5. **Tests** (`apps/contracts/test/next`): a migration that declares more than it holds
   reverts; an emergency withdrawal above the float reverts; `forceEmergencyWithdraw` sets the
   flag and blocks `payScholarship`; `retireCourse` keeps the invariant and blocks payment of
   that course; the totals stay exact across `recordCourseFunds` + `payScholarship`.
6. **Migration script.** `apps/web/db/migrations/next/20261030_contract-to-v6.ts`, outside
   `db/migrations` so `db:migrate` cannot run it by accident, with its own README. It is
   idempotent and resumable: the snapshot, the drained amounts, the pending step and every
   transaction hash live in a journal under `db/chain-state/` (the helper
   `apps/web/lib/chain-state.ts`, no project imports, candidate for
   `@pasosdejesus/m/blockchain/chain-state`), separate from `db/backups/`, which holds
   gitignored database dumps. Its order answers the two accidents above: preflight (target
   empty, source solvent), journal, `pause()` on SLEARN, zero the source books, drain, send the
   same amounts to V6, create the vaults, **then** `setVaultBalance` (V6 refuses a balance the
   tokens cannot back), repoint SLEARN, copy `guidePaid`, assert `accountingState()` and only
   then `unpause()`.

### 4.1 What the counter does and does not fix

It fixes the drift that exists today: from V6 on, no `setVaultBalance`, `recordCourseFunds`,
`payScholarship`, `retireCourse` or `emergencyWithdraw*` can leave the books above the tokens, so
a migration that declares 20.26 while holding 12.22 reverts instead of shipping, and the
retired-course phantom becomes impossible once `retireCourse` is used. What it does not do is
give each course its own tokens: the guard checks the **sum**, so a migration can still assign
the pool to different courses while the total matches. **That limit is accepted**: a contract
per course (or a clone per course) would be the only true segregation and was discarded as
impractical — deploy and migration per course, a `courseId -> vault` registry, and more
addresses to verify. A per-course balance inside one contract is not possible with a single
ERC-20 balance, and a hash of the totals would be only an audit anchor, not enforcement.

## 5. Until V6 is deployed

- Deploy with `cd apps/contracts && bin/next/deployLearnTGVaultsV6` (writes
  `deployments/LearnTGVaults/V6/<network>.json`); the operator runs it.
- **Do not call `setVaultBalance` outside a migration.** It is not a general admin tool.
- After **any** `setVaultBalance` or `emergencyWithdraw*`, run
  `cd apps/web && make vault-check ARGS="--network celo"` and require it to pass.
- The known phantom is already zeroed with `setVaultBalance(106, 0, 0)` (V6: `retireCourse(106,
  true)`); that leaves a **0.040910 USDT** residual (0.037838 declared above the tokens in the
  V5 setup plus 0.003072 of rounding), accepted by the script's built-in tolerance (0.05 USDT /
  0.50 SLEARN, in `apps/web/bin/check-vault-balances.mjs` — deliberately not a flag).
- Retiring a course today follows R-#292. The guard is also the reason the script exists:
  without it, only a post-migration check can catch a bad migration. The script already
  understands V6: it accepts `VERSION` 5 or 6 and, on V6, compares `accountingState()` with the
  scanned sum and fails when the contract reports `accountingBroken`.
