### 2. Changes

**Current state before this REQ (verified 2026-09-15):** `next-pwa@^5.6.0` was
already a dependency of `apps/nextjs`, and `next.config.ts` already wrapped the

**`next.config.ts`:** ✅ done

- `disable: pwaDisabled`, with `pwaDisabled = process.env.NEXT_PUBLIC_PWA_DISABLE === '1'`.
  **The PWA is generated in development too** (decided 2026-09-15), so the install
  flow can be tried on the dev site (`learn.tg:9001`); `NEXT_PUBLIC_PWA_DISABLE=1`
  turns it off in a build. Careful: in `next dev`, next-pwa still forces
  `NetworkOnly` and logs *"Build in develop mode, cache and precache are mostly
  disabled... offline support is disabled"*, while regenerating the worker on
  every compile (*"GenerateSW has been called multiple times"*), so **offline is
  only testable on a production build**. (An earlier revision of this REQ gated it
  on `pwaEnabled = NODE_ENV === 'production'`; the code no longer does.)
- `register: false`, and the registration lives in the app
  (`components/ServiceWorkerRegistrar.tsx`, mounted in `app/RootLayoutClient.tsx`):
  next-pwa's `register: true` injects `register.js` into the webpack `main.js`
  entry, which the App Router does not have, so the worker was generated and
  served while nothing registered it (found on the dev site 2026-09-15: `/sw.js`
  200, `getRegistrations()` empty, no registration code in any client chunk, and
  a manual `register('/sw.js')` working). Verified locally: 1 registration,
  activated, page controlled.
- `nextConfig.env.NEXT_PUBLIC_PWA_ENABLED` is `'1'` unless the build was disabled
  (`pwaDisabled`), and the registrar also honours `NEXT_PUBLIC_PWA_DISABLE`; when
  the flag is off the registrar **unregisters leftover workers and clears their
  caches** (a browser must not keep running stale code).
- `make pwa-clean` (run by `all`, `prod` and `bin/dev`) deletes the generated
  `public/sw.js` and the `workbox-*` / `fallback-*` / `worker-*` artifacts before
  a build, so nothing stale is served when the PWA is off. To retire a worker that
  is already deployed, `make pwa-kill-switch` copies `scripts/pwa-kill-switch.js`
  over `public/sw.js` (R-#243).
- Keep `skipWaiting: true`.
- `fallbacks: { document: '/offline' }` (typed as `PWAConfig['fallbacks']`
  because the published type demands all five fallback keys).
- `additionalManifestEntries: [{ url: '/offline', revision: null }]`: workbox
  only serves a document fallback that is **precached**, and `/offline` is a
  server-rendered route, so it must be added explicitly. The page is static (no
  user data), so `revision: null` is acceptable; a redeploy refreshes it with
  the service worker update.
- Extend `runtimeCaching`:
  - Static assets (`/_next/static/*`): `CacheFirst`, 7 days (already present).
  - Pages (`/en/*`, `/es/*`): `NetworkFirst`, 24 hours, 5 s network timeout.
  - API GET (`/api/*` with GET): `NetworkFirst`, 1 hour.
  - API mutations (`/api/*` with POST/PATCH/DELETE): `NetworkOnly`.
  - Images of the guides and icons (`/img/*`, `/icons/*` with
    png/jpg/jpeg/svg/webp/gif): `CacheFirst`, 30 days (R-#241 asks for the guide
    images to be available offline too).
- Keep the existing `diligent-records` entry (it caches another app served by
  this same Next app at `/[lang]/diligent-records`). will be cached (NetworkFirst, diligent-cache, 30 days) once the tool exists (R-#258). The entry in runtimeCaching is already planned.
- `public/sw.js`, `public/workbox-*.js` and their `.map` stay out of git
  (`.gitignore`).

### 4b. Offline course content (free and purchased) — requested 2026-09-19

> **Moved (2026-09-21):** this whole scope is now
> https://github.com/pasosdeJesus/learn.tg/issues/256: it needs its own
> data model, server contract and UI, so it is no longer a checklist item of this
> requirement. What stays here is the record of the origin and the design notes below.
> The `diligent-records` item of §2 moved to
> https://github.com/pasosdeJesus/learn.tg/issues/258 (the accounting tool of the
> business course).

**What the operator asked for:** what stays offline should be the content of the
**free courses** (guides *and* their crosswords) and of the courses the user **has
paid for** (also with crosswords), and that content should **refresh when there is
a connection**.

**Feasible: yes, and most of the pieces exist.** Today's behaviour:

| Piece | Where | Offline today |
|---|---|---|
| Guide body (markdown) | `lib/offline-guide-db.ts` + `lib/hooks/useCachedGuide.ts` (IndexedDB, key `lang/prefix/suffix`) | yes, for a **visited** guide (R-#241) |
| Crosswords | `/api/crossword?courseId=…` GET cached by the service worker (`learntg-api-get`, NetworkFirst 5 s / **1 h**) | only while that entry lives |
| Pages | `runtimeCaching` `/en/*` and `/es/*` (NetworkFirst / 24 h) | yes, for a visited page |
| Submissions | `lib/offline-queue-db.ts` + `useOfflineQueue` (replayed on `online`) | queued and replayed (R-#242) |

So the gaps are (a) there is no **explicit** "this course is available offline"
state, (b) the crossword relies on a 1-hour HTTP cache entry instead of the same
durable store as the guide, (c) nothing revalidates the stored copy when the
content changes, and (d) the paid content sits in the **generic** `/api/*` GET
cache, where the user cannot see or delete it.

**Design**

1. `lib/offline-course-db.ts` (IndexedDB, next to `offline-guide-db`): one record
   per course — `{ courseId, lang, prefix, revision, savedAt, guides: [{ sufijoRuta,
   markdown, crossword }] }` — plus a small index for "courses downloaded on this
   device". Extend the existing guide store rather than duplicating it.
2. One authenticated endpoint, `GET /api/course-offline?courseId=…`, returns the
   course in a single round trip: the guide list, each guide's markdown and its
   crossword payload, and a `revision` (a hash of the course's guide rows and
   `updated_at`). **The server decides entitlement**: free courses answer for any
   visitor, premium courses only when the wallet has access
   (`premium_course_usuario`), reusing the existing check. The client never decides
   what is downloadable.
   **It covers the whole course, not only what was visited** (asked 2026-09-19):
   the download writes every guide of the course and its crossword, so a user who
   never opened guide 4 can read it and answer its crossword in airplane mode. That
   is possible because the crossword payload is generated server-side from the
   guide's own markdown (`/api/crossword` parses it with
   `lib/remarkFillInTheBlank.mjs`), not from anything the user had to see first.
   **The offline crossword travels without the solution** (decided 2026-09-19): the
   payload this endpoint returns has the grid layout (cells, numbers, which words
   they belong to), the previous input of that wallet and the clues
   (`number`, `clue`, `direction`, `row`, `col`) — **no `letter` in the grid cells
   and no `word` in the placements**, so nobody can read the answer in DevTools and
   pass the crossword by copying it. The **online** crossword
   (`GET /api/crossword` + inline `mistakesInCW` feedback) is **not** changed by
   this requirement; the offline payload is a different response of the new
   endpoint.
3. **Offline answering and review (decided 2026-09-19).** Offline the app only
   presents the crossword: the grid, the clues, the answers the user types and a
   submit button. The submit is **queued** (R-#242) and takes effect when the
   connection returns; then `POST /api/check-crossword` validates it and answers as
   it does today (`mistakesInCW` plus `message`, and the payment when the answers
   are right and the wallet qualifies). The result — **"correct, you received X
   USDT/SLEARN" or "these words have a problem"** — is delivered to the user as a
   **notification** (`notifications` table, R-#162 phase 1), because the user may
   have already left the crossword page when the queue drains. The app must also
   reflect the result on the guide/course progress once it arrives.
4. **One obstacle to fix with this feature.** `POST /api/check-crossword` compares
   the submission against `billetera_usuario.answer_fib`
   (`packages/rewards/src/routes/check-crossword.ts:152-159`), a **per-wallet
   column that `GET /api/crossword` overwrites** each time the app shows a guide
   online (`app/api/crossword/route.ts:239`). So the validation currently depends
   on the client having fetched that very guide online first: a guide downloaded
   but never opened online (or a guide opened after another one) would be checked
   against the wrong answers, and an all-offline course would be a lottery. Fix:
   have `check-crossword` derive the expected answers from the guide markdown
   itself, exactly as `/api/crossword` does, instead of trusting the column (keep
   `answer_fib` for the legacy flow if that helps the rollout). **This does not
   change the online behaviour**: same request, same validation, same
   `mistakesInCW`/`message` response; only the source of the expected answers moves
   to the same markdown the crossword was built from. It is a prerequisite of the
   offline courses and also removes a fragile coupling in the online case.
5. **When the download happens.** Two options, to decide with the operator:
   (a) an explicit button per course (predictable data usage), or (b) an automatic
   prefetch of the courses the wallet has access to when the course page is opened
   online, with the explicit button still there for a whole course and for
   "download everything I can read". The audience pays for data on low-end phones,
   so (a) plus "download my courses" (bounded) is the safer default; the prefetch
   must be visible and cancellable.
6. UI on the course page: **Descargar para leer sin conexión** (with size estimate),
   then "downloaded · update · delete"; the state lives in the course page and in
   the guide list (an offline badge per guide).
7. **Refresh:** on `online` (and at least once every 24 hours) the client compares
   `revision` for every downloaded course; if it changed, it rewrites the store and
   shows "el contenido se actualizó" (a stale copy must never be served silently).
   The page cache and the `/api/*` entries keep their `NetworkFirst` behaviour, so
   online reading is always fresh.
8. **Security and privacy (deliberate trade-off):**
   - The explicit store is per device and per signed-in wallet; it is **cleared on
     Disconnect and on deleting the wallet**, and the panel offers "borrar contenido
     descargado". A shared phone in airplane mode can read what that wallet
     downloaded, so the UI says so before downloading a paid course.
   - Add `NetworkOnly` entries for `/api/course-offline`, `/api/crossword` and
     `/api/guide` **before** the generic `/api/*` GET rule, so the paid copy is only
     the explicit, deletable one and not an invisible hour-long HTTP cache entry.
     **Order matters:** this entry and the explicit store ship together, otherwise
     the offline crossword (R-#242) loses its only source while offline.
9. **Rewards:** unchanged in the online path; the offline submission is queued
   (R-#242) and validated by the server when the connection returns, so a modified
   local copy of the puzzle cannot mint a reward (the payload has no answers, and
   the payment needs the server).

**Acceptance criteria (new):**

- [ ] A free course can be downloaded and read offline, guides **and** crosswords,
      after installing the PWA — including guides the user **never opened online**.
- [ ] The offline crossword payload carries **no answers**: no `letter` in the grid
      cells and no `word` in the placements (a DevTools inspection shows the layout
      and the clues only).
- [ ] Offline the user fills the crossword and presses submit: the button queues the
      answer, says it is saved and that it will be reviewed when there is a
      connection, and nothing is validated locally.
- [ ] On reconnect the queue drains, `POST /api/check-crossword` validates it, and
      the user gets the result as a **notification**: right (with the prize paid, or
      "both already paid") or wrong (naming the words with a problem), plus the
      guide/course progress updated.
- [ ] `POST /api/check-crossword` validates a guide the user never fetched online
      (answers derived from the guide markdown, not from
      `billetera_usuario.answer_fib`), **without changing** the online response.
- [ ] A purchased course can be downloaded and read offline while that wallet has
      access; another wallet on the same device does not see it.
- [ ] The stored copy is revalidated at least once every 24 hours when there is a
      connection: if a guide's content or answers changed, the copy is refreshed and
      the user is told.
- [ ] Disconnect and "delete wallet" remove the downloaded courses.
- [ ] Downloaded paid content is not readable from the generic HTTP cache (the
      `/api/*` rule no longer applies to it).
- [ ] Unit tests for the store and the revision comparison; E2E: download a free
      course online → airplane mode → open a guide, answer its crossword and submit
      → back online → the queued answer is validated and the notification arrives.
