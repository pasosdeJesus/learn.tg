# R-#247: Content Security Policy for learn.tg

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/247

**Status:** Pending — proposal (design agreed 2026-09-18). Nothing is implemented:
the app serves no `Content-Security-Policy` header today.
**Created:** 2026-09-18
**Type:** Security
**Priority:** High — it is the control that makes the threat model of
https://github.com/pasosdeJesus/learn.tg/issues/246 pointless
**Dependencies:** https://github.com/pasosdeJesus/learn.tg/issues/246 (the in-app
wallet keeps a private key in the page), https://github.com/pasosdeJesus/learn.tg/issues/227
(the `middleware.ts` origin checks already protect the cookie-authenticated APIs)

---

### 1. Objective

Make it **much harder for foreign script to run on learn.tg**, because everything
the in-app wallet does today — unlock, sign a SIWE message, move funds — is
JavaScript in our own origin. A strict Content Security Policy is the only control
that stops that script from running in the first place; the layers of R-#246 (PIN,
WebAuthn gesture, PRF) reduce what a script could do *if* the key is available, but
they cannot stop it from being loaded.

> **Priority confirmed by the 2026-09-19 wallet review:** while the key lives in the
> page, a CSP is what makes "the key is only usable by our own code" a property
> instead of a promise. The L1 gate of R-#246 is the second half (and today it only
> covers `eth_sendTransaction`; typed-data and raw signing are pending there). Roll
> it out report-only first, as §4 proposes.

### 2. Why now (threat model)

R-#246 §7 records what an attacker needs to reach the wallet: **no privilege on the
user's device at all** — just code executing in the `learn.tg` origin. The ways that
happens, in order of likelihood:

1. An XSS in our own code (a field, a guide body rendered as HTML, an unescaped
   attribute).
2. A compromised dependency in the bundle (the app ships a large `node_modules`).
3. A poisoned build or a compromised static asset/CDN.

The app currently sends only HSTS, `X-Content-Type-Options: nosniff`,
`X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection` (deprecated, no effect in modern
browsers) and `Referrer-Policy` (`apps/nextjs/next.config.ts` §headers). A CSP is
the missing piece, and it is also what makes the R-#246 decision "do not store the
key in the page" verifiable rather than aspirational: with a strict policy, a
plain XSS cannot exfiltrate anything.

### 3. Scope

**In scope:** a real policy for the Next.js app (`apps/nextjs`), rolled out in
report-only first, then enforced; a way to observe violations from real users; the
documentation of what each directive costs.

**Out of scope:** rewrite the app to remove inline styles or third-party scripts;
protect the Rails admin (`:3500`); MiniPay (not a market for this project).

**Platforms:** the policy must work on the priority mobile stack of R-#246 §3
(Chrome Android, Safari iOS, and the Rabby/MetaMask/OneKey/OKX in-app browsers).
Those WebViews are Chromium-based but can be older, so every directive must be
verified against the oldest engine in the matrix (Chromium 96–99 was still in the
StatCounter sample for Opera).

### 4. Proposal

Phase 1 — **report only**, on the development site, so nothing breaks:

```
Content-Security-Policy-Report-Only: <policy>; report-uri /api/csp-report
```

Phase 2 — **enforce** once the report shows only known-good sources, then keep the
report endpoint to catch regressions.

Starting policy (to be tuned with the reports, not guessed):

| Directive | Value | Why |
|---|---|---|
| `default-src` | `'self'` | Baseline deny |
| `script-src` | `'self' 'nonce-<per request>' 'strict-dynamic'` | Next injects inline hydration scripts; a per-request nonce from `middleware.ts` (which already exists) is the supported path, and `strict-dynamic` keeps dynamic imports working without listing every chunk |
| `style-src` | `'self' 'unsafe-inline'` | Tailwind + inline styles from React; removing `'unsafe-inline'` here is a later, separate step (it is far less dangerous than in `script-src`) |
| `img-src` | `'self' data: blob:` | Icons, QR codes, credential SVGs |
| `font-src` | `'self'` | The app uses system fonts |
| `connect-src` | `'self'` plus the RPC hosts (`https://forno.celo.org`, `https://forno.celo-sepolia.celo-testnet.org`) and the Alchemy endpoints used for campaign balances | `fetch`/XHR and WebSocket |
| `worker-src` | `'self' blob:` | The service worker (`public/sw.js`) and Next's workers |
| `manifest-src` | `'self'` | `manifest.webmanifest` |
| `frame-ancestors` | `'none'` | Replaces `X-Frame-Options` (Rails admin pages are not covered by this policy) |
| `base-uri` | `'self'` | Prevents `<base>` hijacking |
| `form-action` | `'self'` | No form should post elsewhere |
| `object-src` | `'none'` | No plugins |
| `upgrade-insecure-requests` | — | The site is HTTPS-only |

Phase 3 — **Trusted Types** (`require-trusted-types-for 'script'`), only after
React/Next are known to work with it; treat as a separate step because it can break
`dangerouslySetInnerHTML` (the guide body and the course outline use it).

### 5. How to know it is safe to enforce

1. Ship report-only and add a small collector (`app/api/csp-report`) that logs
   `document-uri`, `violated-directive` and `blocked-uri` — **never** the full URL
   query string (it can carry a wallet address).
2. Drive the app on the dev site with the existing E2E specs (landing, guide,
   profile, donation modal, in-app wallet, biometric unlock, offline specs) and by
   hand on a phone; every blocked resource shows up in the report.
3. Watch for the classic breakages: Next's inline scripts without a nonce, the
   service worker registration, the Solana/BTC-era dead code if any remains, fonts,
   the QR library and the wallet's WASM (if the SWC WASM fallback is used on
   OpenBSD, `wasm-unsafe-eval` may be needed **for the build only**, not in the
   browser).
4. Enforce on the dev site first, then ask the operator to deploy to production
   only after a full manual pass on a phone.

### 6. Acceptance criteria

- [ ] `Content-Security-Policy-Report-Only` served on the dev site with the policy
      of §4 and a nonce generated per request in `middleware.ts`.
- [ ] A report collector that stores/logs violations without personal data.
- [ ] A report from real navigation (all wallet-related E2E specs plus a manual
      pass on Chrome Android) with **no** unexpected violation, or with each one
      explained and fixed.
- [ ] Policy enforced on the dev site; the app works: landing, course, guide,
      offline banner, in-app wallet create/unlock/sign, donation modal, biometric
      unlock.
- [ ] The policy is documented in `doc/api-security.md` (or a new `doc/csp.md`)
      together with **how to change it** and what each exception is for.
- [ ] `frame-ancestors 'none'` verified to not break any legitimate embedding
      (there is none known).
- [ ] A regression test (or an E2E assertion) that the header is present in
      production, so a future `next.config.ts` edit cannot silently drop it.

### 7. Open questions

1. Where should the policy live: `next.config.ts` `headers()` (static, no nonce) or
   `middleware.ts` (dynamic, nonce)? The nonce requires the middleware path, which
   already exists for the CSRF checks.
2. Do we need `'unsafe-eval'` for anything in production (viem/ethers, the QR
   library)? Measure, do not assume.
3. Report endpoint: log only, or persist in `userevent` (it already exists and is
   the natural place for a `csp_violation` event)?
4. Should production enforce in the same rollout as the dev site, or wait one
   release?
