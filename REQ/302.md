# R-#302: Parche equivalente a vercel/next.js#100607 para los code frames del binding WASM

> *"El prudente ve el peligro y se refugia"* (Proverbios 27:12)

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/302
**Created:** 2026-11-19
**Updated:** 2026-11-19
**Status:** En curso — parche aplicado y verificado en el repro; pendiente prueba a fondo en
learn.tg y seguimiento upstream
**Type:** Dependencia / parche de plataforma (Next 16 + WASM en OpenBSD/adJ)
**Priority:** Alta — sin el parche, cualquier error de `next dev` o `next build` en OpenBSD/adJ
se sustituye por el error del binding WASM y la causa real no se ve.

## Summary (EN)

learn.tg carried a workaround that coerced `codeFrameColumns` options in
`dist/{esm/,}shared/lib/errors/code-frame.js`. This requirement replaces it with the
normalization proposed in [vercel/next.js#100607](https://github.com/vercel/next.js/pull/100607):
the WASM `loadWasm` wrapper fills the napi defaults and strips `undefined` fields before
`serde_wasm_bindgen`, without touching the native path. The patch was applied to learn.tg
(Next 16.3.5), verified against the issue reproduction (4/4 shapes render) and against a real
`next dev` 500 (`ENOENT` and its code frame reach the console). A thorough test plan and the
remaining acceptance items are below.

## 1. Origen y problema

En OpenBSD/adJ no hay binarios nativos de SWC, así que Next 16 usa el fallback
`@next/swc-wasm-nodejs`. El binding WASM deserializa `CodeFrameOptions` de forma estricta:
rechaza `color` booleano y `maxWidth`/`language`/`highlightCode`/líneas en `undefined`. Next
pasa justamente esas formas desde el dev overlay, el formateador de diagnósticos de TypeScript
y el lector de `jsconfig.json`, así que **todos** los code frames fallan y el error real se
reemplaza por:

```
invalid type: boolean `false`, expected enum CodeFrameColorMode
invalid type: unit value, expected usize
```

- Reporte: [vercel/next.js#99348](https://github.com/vercel/next.js/issues/99348).
- Fix propuesto: [vercel/next.js#100607](https://github.com/vercel/next.js/pull/100607)
  (abierto, sin fusionar ni publicar al 2026-11-19).
- Parche anterior de learn.tg: [R-#267](https://github.com/pasosdeJesus/learn.tg/issues/267), sobre
  `dist/{esm/,}shared/lib/errors/code-frame.js`. Funciona para las formas booleanas, pero no
  cubre `color` numérico, `'Warning'`/`'Info'`, ni `undefined` explícito en
  `language`/`highlightCode`/líneas; muta las opciones del llamador, fuerza `maxWidth` a 100
  (napi usa 240) y también afecta al camino nativo.

El parche nuevo replica la conversión de napi **sólo en el wrapper WASM**
(`loadWasm` de `dist/build/swc/index.js` y su copia ESM), así que el camino nativo queda
intacto.

## 2. Cambios aplicados (2026-11-19)

- Nuevo `apps/web/patches/next@16.3.5-pr100607.patch`:
  - añade `getCodeFrameOptions()` con los defaults y el mapeo de napi (`color`
    `false`/`true`/`0`/`1`/`2`/`'None'`/`'Error'`/`'Warning'`/`'Info'`, `maxWidth` 240,
    `linesAbove`/`linesBelow` 2/3, `highlightCode` según color y `language`
    `'javaScript'`/`'css'`);
  - llama al binding con `removeUndefined(location)` y
    `removeUndefined(getCodeFrameOptions(options))`;
  - cambia únicamente el wrapper WASM en CJS y ESM; el camino nativo no cambia.
- Eliminado `apps/web/patches/next@16.3.5.patch` (el workaround anterior).
- `pnpm-workspace.yaml`: `patchedDependencies.next@16.3.5` apunta al parche nuevo.
- `pnpm-lock.yaml`: actualizado el `patch_hash` (los demás cambios del lockfile son sólo ese
  hash).
- `apps/web/Makefile`: `next-patch-check` verifica `function getCodeFrameOptions` en
  `dist/build/swc/index.js` y `dist/esm/build/swc/index.js` (antes buscaba el marcador del
  parche viejo en `code-frame.js`) **y ejecuta el arnés nuevo**
  `apps/web/bin/check-next-codeframe.mjs`: carga los bindings wasm reales y renderiza 8 formas
  (dev overlay, TypeScript, `color` `'None'`/`0`/`2`, campos `undefined`, `language` `css` y
  `javascript`, `message`). Antes la guarda sólo probaba que el parche *entró*, no que
  *funcione*. Las formas viven en `apps/web/lib/next-codeframe-check.mjs`, que comparten el
  script y la **prueba de regresión** `apps/web/lib/__tests__/next-codeframe-wasm.test.ts`
  (corre en `make test-lib`, dentro de `make test`, y se omite donde no hay binding wasm).
- Referencias actualizadas en `apps/web/CONTRIBUTING.md`, `apps/web/README.md`,
  `doc/e2e-testing.md` y `doc/environments.md`.
- En `m`, `doc/next16-openbsd.md` describe las dos formas del parche y el estado del PR.

El parche se aplica **sólo** con `pnpm install`; no se edita `node_modules` a mano. Para
regenerarlo, ver §7.

## 3. Verificación ya ejecutada

- `pnpm install` en learn.tg aplicó el parche sin error (3m 7s) y `make next-patch-check`
  terminó en verde.
- Repro del issue (`../wasm-code-frame-columns`, Next 16.4.0-canary.51 + wasm
  16.4.0-canary.51) con el equivalente del parche: **4/4 formas renderizan** (antes fallaban
  3/4). Sin el parche vuelve a fallar 3/4.
- `npm run dev -- -p 3100` con el parche y `GET /trigger-error`: el log muestra el `ENOENT`
  real y el code frame (`> 16 | const missing = await readFile(...)`), sin
  `invalid type ... CodeFrameColorMode`.
- Contra learn.tg (Next 16.3.5 + `@next/swc-wasm-nodejs@16.3.1`), invocando
  `codeFrameColumns` con las formas del repro: dev overlay, TypeScript, `jsconfig`, control y
  opciones explícitamente `undefined` renderizan. Sin el parche fallan las tres primeras.
- El `node_modules` del repro se restauró después de la prueba para que siga reproduciendo el
  fallo.

### 4.2 Code frames con WASM (determinista) — automatizado

Es parte de la **suite de regresión**: `apps/web/lib/__tests__/next-codeframe-wasm.test.ts`
vive en `lib/__tests__` (lo corre `make test-lib` y por tanto `make test`) y se omite con
`describe.skipIf` donde no hay binding wasm. La forma de la prueba está en
`apps/web/lib/next-codeframe-check.mjs`; `node bin/check-next-codeframe.mjs` (y
`make next-patch-check`, que lo encadena) usa el mismo módulo para un chequeo rápido sin
levantar Vitest. Sin el parche esas formas lanzan `invalid type ...`. Las formas manuales de
abajo siguen sirviendo para inspeccionar la salida.

Con `NEXT_TEST_WASM=1` y `NEXT_TEST_WASM_DIR=$PWD/node_modules/@next/swc-wasm-nodejs`,
invocar `next/dist/shared/lib/errors/code-frame` con estas formas y comprobar que **ninguna
lanza** y que la primera línea contiene el código:

- `{ color: false, maxWidth: undefined }` (dev overlay sin TTY);
- `{ color: true }` (diagnóstico TypeScript / `jsconfig`);
- `{ color: 'None' }` y `{ color: 0 }`;
- `{ color: false, maxWidth: 240, language: undefined, highlightCode: undefined,
  linesAbove: undefined }` (el parche debe rellenarlos).

Repetir sin el parche (o con el archivo del parche revertido en una copia) y confirmar que las
formas anteriores fallan con `invalid type ... CodeFrameColorMode`/`usize`: así la prueba
distingue el parche de una casualidad.

## 6. Riesgos y límites

| Riesgo | Mitigación |
|---|---|
| El parche toca `dist/` y depende de la versión de Next | Regenerarlo en cada bump (`pnpm patch next@<versión>`), actualizar hash y `make next-patch-check`; no copiar el parche de 16.3.5 a 16.4.x sin revisar el contexto |
| `ERR_PNPM_PATCH_FAILED` al instalar | No editar `node_modules` a mano; revisar que el parche tenga cabeceras `diff --git` y aplicar sobre el paquete limpio |
| El PR no se fusiona o cambia | Mantener el parche mientras tanto; el issue #99348 y el PR son la referencia; retirarlo cuando haya release |
| Se pierde la cobertura WASM en CI | Pedir que las pruebas del PR corran con `NEXT_TEST_WASM=1`; mientras tanto, el chequeo de §4.2 es la regresión local |
| El parche nativo se ve afectado | El cambio está sólo en `loadWasm`; verificar en CI Linux con §4.5 |

## 7. Regenerar el parche

1. `cd apps/web && pnpm patch next@16.3.5` (crea una copia editable).
2. Aplicar en `dist/build/swc/index.js` y `dist/esm/build/swc/index.js` la normalización de
   §2 (helper + `removeUndefined`).
3. `pnpm patch-commit <directorio>` y mover/renombrar el parche a
   `apps/web/patches/next@16.3.5-pr100607.patch`.
4. Actualizar `patchedDependencies` en `pnpm-workspace.yaml` si cambia el nombre; `pnpm install`
   y `make next-patch-check`.
5. No editar `node_modules` a mano: pnpm usa enlaces duros y el store queda sucio.
6. Comprobar con `node bin/check-next-codeframe.mjs` **y** con
   `pnpm vitest run lib/__tests__/next-codeframe-wasm.test.ts`: si el binding wasm de la
   versión nueva nombra distinto alguna variante (`javaScript`, los modos de `color`), fallan y
   dicen cuál forma; es lo primero que se rompe al subir Next o `@next/swc-wasm-nodejs`.
