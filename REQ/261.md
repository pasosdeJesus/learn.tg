## 1. Objective

Let learn.tg talk about **`Curso` and `Guia`** instead of
`cor1440_gen_proyectofinanciero` and `cor1440_gen_actividadpf`, through **one wrapper
module**, with **no change to the database**:

1. A single module (`lib/courses.ts`) is the only code that knows the physical table
   names. Everything else imports the wrapper.
2. The engines (`packages/rewards`) receive the wrapper as an **injected port**, so they do
   not import app internals (the rule they already follow) and stop carrying the SQL.
3. A **cheap static check** fails the build/PR when the physical names appear outside the
   allowlist, so the rule is enforced instead of remembered.
4. The **wire format does not change**: the JSON the frontend already consumes keeps its
   current field names. This is a rename of the *code entity*, not of the API.

Deliberately **not** done here: no view, no table rename, no new database object, no change
in the Rails engine or in sivel3.

## 3. Design

### 3.1 `apps/nextjs/lib/courses.ts` — the only door

```ts
import type { Kysely } from 'kysely'
import type { Cor1440GenProyectofinanciero, Cor1440GenActividadpf, DB } from '@/db/db'

// learn.tg names for the two shared tables. The physical names live ONLY here.
export type Curso = Cor1440GenProyectofinanciero
export type Guia = Cor1440GenActividadpf

export const CURSOS = 'cor1440_gen_proyectofinanciero'   // uso interno del módulo
export const GUIAS = 'cor1440_gen_actividadpf'

export const cursos = (db: Kysely<DB>) =>
  db.selectFrom('cor1440_gen_proyectofinanciero as curso')

export const guias = (db: Kysely<DB>) =>
  db.selectFrom('cor1440_gen_actividadpf as guia')
```

plus the queries the inventory actually needs, each one named in learn.tg terms:

| Function | Replaces the call site |
|---|---|
| `listCursos(db, filtros)` | `course-catalog/route.ts` |
| `cursoPorId(db, id)` | `course-catalog/[id]`, `course-access.ts`, `credential.ts`, `scholarship.ts`, `courses/premium/price` |
| `cursoPorPrefijo(db, prefijo)` | `guide-utils.ts`, `guide/route.ts` |
| `cursoDeGuia(db, guiaId)` | `check-crossword.ts`, `scholarship.ts`, `course-catalog/[id]` |
| `guiasDeCurso(db, cursoId)` | `guide-status/route.ts`, `course-catalog/[id]`, `guide/route.ts` |
| `guiaPorId(db, id)` / `guiaPorSufijo(db, cursoId, sufijo)` | `guide-utils.ts`, `guide/route.ts` |
| `joinCurso(db, …)` | the `innerJoin`/`leftJoin as c` of `transparency`, `user/[id]`, `courses/premium/mine`, `credential.ts` |

Rules for the module:

- It may use Kysely or raw `sql` (the raw spots move here too); callers never see either.
- It returns **rows** (`Curso`, `Guia` or the subsets the API needs), never query builders,
  except the two `cursos()`/`guias()` helpers for the joins.
- It does not authenticate, does not write HTTP and holds no policy: `course-access.ts`
  keeps its decisions and asks the wrapper for the rows.
- The API JSON keeps the current column names (`titulo`, `prefijoRuta`, `porPagar`…):
  renaming the wire format or the columns is a separate, breaking decision and is out of
  scope.

### 3.2 The engines get a port, not an import

`packages/rewards` already receives everything via `RewardsDeps` (`db`, `authenticateUser`,
`backend`, `routeReward`, `canPurchasePremiumCourse`, `updateUserAndCoursePoints`…). The
wrapper is added the same way:

```ts
export interface CoursesPort {
  cursoPorId: (db: any, courseId: number) => Promise<{ id: number } | undefined>
  cursoDeGuia: (db: any, guiaId: number) => Promise<{ id: number; cursoId: number } | undefined>
  guiasDeCurso: (db: any, cursoId: number) => Promise<Array<{ id: number; nombrecorto: string | null; sufijoRuta: string | null }>>
}
```

`createRewardsApp(deps)` receives `courses: CoursesPort`, and the three reward routes stop
carrying the SQL. The implementation lives in learn.tg (`lib/courses.ts`) and the engine keeps
its invariant: **no `@/lib` import** (`m` work item 35 D2).

### 3.3 Enforcement: the rule must fail, not be remembered

New check `apps/nextjs/bin/audit-course-tables.mjs`, in the style of
`bin/audit-api-auth.mjs` (which the project already runs before every PR):

- scans `apps/nextjs/{app,lib,components}` and `packages/*/src`, excluding tests;
- fails if `cor1440_gen_proyectofinanciero` or `cor1440_gen_actividadpf` appears outside an
  explicit allowlist: `lib/courses.ts`, `packages/rewards/src/index.ts` (the port type),
  `db/db.d.ts`, `db/migrations/**`, `db/structure.sql`, `__tests__/**`;
- prints every offending `file:line` and exits 1.
- Documented in `CONTRIBUTING.md` next to the API audit (and in CI where that one runs), so
  a new call site is caught in review.

### 3.4 Extensions enter through the wrapper

When R-#259 adds `contenido_sensible` to the courses table:

- the migration is a learn.tg one, as today (`apps/nextjs/db/migrations/`);
- the wrapper exposes it (`cursoPorId` returns it, `Curso` gains the field) and that is the
  only place the visibility rules read it;
- the check keeps the physical name confined, so the extension does not spread.

This is the pattern for every future learn.tg-only course field.

### 3.5 What we deliberately do not do

| Alternative | Why not |
|---|---|
| A view `curso` (or `learntg.curso`) in the database | `SELECT *` in a view is expanded **at creation**, so every column added to the base table requires recreating it (a migration per change); writes are only auto-updatable when simple; `INSERT … ON CONFLICT` does not work on views and no FK can reference one. A read-only view for reports is a legitimate *addition* later, not the app's model |
| Renaming the tables | The `cor1440_gen` gem, its Rails models and migrations, the `fk_rails_*` constraint names, both `structure.sql` files and sivel3 all depend on the names. That is the end game, when no Rails consumer is left |
| Aliasing in the ORM types only (`DB['curso']`) | It would emit `FROM curso`, which does not exist. The SQL alias (`… as curso`) is per query, and that is exactly what the wrapper emits |

## 4. Acceptance criteria

- [ ] `lib/courses.ts` exists, exports `Curso`, `Guia` and the queries of §3.1, and is the
      only non-allowlisted place that mentions the physical names.
- [ ] The 19 references of §2 are served by the wrapper (app routes and `lib/`) or by the
      port (engines); no behavioural change: same rows, same HTTP bodies.
- [ ] `RewardsDeps` gains `courses: CoursesPort`; `packages/rewards` imports no app
      internals; its tests inject a fake port (as they already do for the other deps).
- [ ] `node bin/audit-course-tables.mjs` reports `0 offending files` on this tree, and fails
      (exit 1) when a new call site is introduced outside the allowlist (tested by adding a
      temporary file).
- [ ] The API response shapes for the touched routes are byte-identical for the existing
      tests (course catalog, guide, guide-status, transparency, premium price/mine,
      user/[id], check-crossword, credential, scholarship).
- [ ] `make type`, the full unit suite and `node bin/audit-api-auth.mjs` (0 failed) stay
      green.
- [ ] `CONTRIBUTING.md` documents the check next to the API audit; the wrapper's purpose and
      the "physical names live here" rule are stated in the module header and in
      `ARCHITECTURE.md` (§Web3 Engines or a new short note on the courses layer).
- [ ] `contenido_sensible` (R-#259) is added through the wrapper, not beside it (checked when
      that requirement lands).

## 5. Out of scope

- Renaming the tables, the columns or the JSON fields (a separate, breaking decision).
- Creating views or any other database object in the shared schema.
- Touching `cor1440_gen`, `servidor/` or sivel3.
- Moving courses into an `m` base model: if that ever happens (the R-#260 pattern), this
  wrapper is the seam that makes it a one-module change instead of 19 edits.
- The learner/geo model (R-#260) and the privacy rules themselves (R-#259).
