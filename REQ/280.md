# R-#280: Calendar doesn't allow to delete appointments

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/280

**Status:** implemented (2026-10-06) — pending `make type` / affected suites and the deploy.
**Type:** Bug fix (admin calendar)
**Related:** `components/admin/CalendarWidget.tsx`, `app/api/admin/calendar/block/route.ts`,
`lib/admin-fetch.ts`, `lib/admin-auth.ts`, `doc/admin-guide.md`

---

## 1. Symptom

In the verifier dashboard (`/{lang}/admin`), hovering an appointment shows a ✕ to delete
it. Clicking it switches the calendar to `Loading…` and then the **same appointment
reappears**, undeleted. The same happened when creating a block from the calendar.

- **Report:** operator, learn.tg, 2026-10-06 (`https://learn.tg/en/admin`).

## 2. Cause

`CalendarWidget` read the calendar through `adminFetch` (which appends the verifier
`wallet`), but **deleted through a raw `fetch` without the wallet**:

```ts
await fetch(`/api/admin/calendar/block?uid=${encodeURIComponent(uid)}`, { method: 'DELETE' })
```

`authenticateAdmin(db, wallet)` (`lib/admin-auth.ts`) requires both a valid SIWE session
**and** `wallet` in `NEXT_PUBLIC_VERIFIER_WALLET`; with an empty `wallet` it returns
`null`, so the route answered **403** and never called `deleteEvent`. The widget ignored
the response (`await fetch(...)` with no status check) and re-fetched, so the event came
back. The "Create block" dialog had the same defect (raw `fetch` for the POST).

The route also answered `200 { success: false }` when the CalDAV delete did not
succeed, which would keep the failure invisible even with the wallet fixed.

## 3. Fix

- `components/admin/CalendarWidget.tsx`: both the delete and the block now use
  `adminFetch` (the standard same-origin mechanism, R-#233: it appends the `wallet`
  identity hint and throws on a non-OK response), and the widget shows the error message
  instead of silently refetching.
- `app/api/admin/calendar/block/route.ts`: the `DELETE` returns a non-OK status
  (`502`) when `deleteEvent` fails, so a failed deletion is not reported as success.

## 4. Acceptance criteria

- [x] The ✕ deletes the appointment and it does not come back after the refresh.
- [x] A failed deletion shows an error instead of silently reappearing.
- [x] Creating a block works with the verifier session.

  event and clicking ✕ calls `adminFetch` with the `DELETE` and the `uid` (not a raw
