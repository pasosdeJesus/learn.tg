# R-#280: Calendar doesn't allow to delete appointments

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/280

**Status:** implemented (2026-10-06), including the follow-up (§6: the appointment still came back because the service worker cached `/api/admin/*`). Code, tests and docs green; pending the development-site pass and the deploy (operator).
**Type:** Bug fix (admin calendar)
**Related:** `components/admin/CalendarWidget.tsx`, `app/api/admin/calendar/block/route.ts`,
`lib/admin-fetch.ts`, `lib/admin-auth.ts`, `doc/admin-guide.md`

---

## 1. Symptom

In the verifier dashboard (`/{lang}/admin`), hovering an appointment shows a ✕ to delete
it. Clicking it switches the calendar to `Loading…` and then the **same appointment
reappears**, undeleted. The same happened when creating a block from the calendar.

- **Report:** operator, learn.tg, 2026-10-06 (`https://learn.tg/en/admin`).

## 2. Cause

`CalendarWidget` read the calendar through `adminFetch` (which appends the verifier
`wallet`), but **deleted through a raw `fetch` without the wallet**:

```ts
await fetch(`/api/admin/calendar/block?uid=${encodeURIComponent(uid)}`, { method: 'DELETE' })
```

`authenticateAdmin(db, wallet)` (`lib/admin-auth.ts`) requires both a valid SIWE session
**and** `wallet` in `NEXT_PUBLIC_VERIFIER_WALLET`; with an empty `wallet` it returns
`null`, so the route answered **403** and never called `deleteEvent`. The widget ignored
the response (`await fetch(...)` with no status check) and re-fetched, so the event came
back. The "Create block" dialog had the same defect (raw `fetch` for the POST).

The route also answered `200 { success: false }` when the CalDAV delete did not
succeed, which would keep the failure invisible even with the wallet fixed.

## 3. Fix

- `components/admin/CalendarWidget.tsx`: both the delete and the block now use
  `adminFetch` (the standard same-origin mechanism, R-#233: it appends the `wallet`
  identity hint and throws on a non-OK response), and the widget shows the error message
  instead of silently refetching.
- `app/api/admin/calendar/block/route.ts`: the `DELETE` returns a non-OK status
  (`502`) when `deleteEvent` fails, so a failed deletion is not reported as success.

## 6. Follow-up: the appointment still came back (operator, 2026-10-06)

After the fix above was deployed, the operator reported: clicking ✕ showed no feedback,
the appointment reappeared on the calendar refresh, and deleting it again answered
**"Failed to delete event"** (no server console error); reloading `/{lang}/admin`
finally showed it gone.

**Cause.** The generic service-worker rule cached every `/api/*` **GET** with
`NetworkFirst` and a **5 s** timeout (`next.config.ts`). The events endpoint lists the
whole verifier calendar and then fetches **one `.ics` per event**: measured against the
real server it takes **~16 s** (112 events → 15.7 s just fetching the `.ics`). So the
list requested right after the `DELETE` blew past the 5 s timeout and the worker served
the **cached** list, still containing the appointment. By the time the operator clicked
again the appointment was already gone, so the server answered the CalDAV `DELETE` with
`404` → `502 "Failed to delete event"`. A full reload later fetched a fresh list, hence
the appointment "disappeared".

**Fix.**

- `next.config.ts`: `/api/admin/*` GET is `NetworkOnly` (declared before the generic
  `/api/*` rule). Admin responses are per-verifier and changing, so they must never be
  served from the cache (nor left on the device).
- `components/admin/CalendarWidget.tsx`: on a successful delete the row is removed from
  the local list at once and **no immediate re-list** is issued (the slow server listing
  was what brought the row back); a success toast confirms the action and a destructive
  toast reports a failure.
- `lib/caldav.ts` (`deleteEvent`): a `404`/`410` from Radicale counts as already-deleted
  (idempotent), so a second click over an appointment that is gone is not an error.

**Residual (out of scope).** The listing is still slow (~16 s: it fetches one `.ics` per
event for the whole calendar before filtering to the next 7 days). It no longer breaks the
delete, but a time-range CalDAV query is a separate performance follow-up.
