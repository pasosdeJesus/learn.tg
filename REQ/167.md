# R-#167: Fix Session Persistence Across Page Navigation (Partial Login)

After connecting wallet (OneKey) at `https://learn.tg/`, signing SIWE, and navigating to `/en`, the user sees: _"Partial login. Please disconnect your wallet and connect and sign again."_ The problem repeats when navigating between courses, guides, and landing pages, degrading UX especially on mobile and PWA in Sierra Leone.

**Merged Issues:** R-#167 + R-#173 (same root cause, same fix).

## Symptom

1. Open `https://learn.tg` in a new tab
2. Activate OneKey → reload
3. Connect wallet → confirm → sign SIWE
4. Click on English → `/en` shows "Partial login"

The E2E test with Puppeteer + simulated SIWE (R-#172) **does not reproduce** the bug — it only occurs with a real wallet (OneKey). See [R-#172](172.md) for test details.

## Root Cause

**Known NextAuth bug:** `useSession()` returns `status: 'unauthenticated'` after client navigation (`<Link>`, `router.push()`), even with a valid `next-auth.session-token` cookie.

- [NextAuth discussion #5719](https://github.com/nextauthjs/next-auth/discussions/5719) — 37 participants
- [NextAuth issue #9504](https://github.com/nextauthjs/next-auth/issues/9504)

**Mechanism:** `SessionProvider` does not automatically re-fetch the session on client navigation. Its internal polling (`refetchInterval`) only fires periodically, not on `router.push()`. When the component mounts on the new route, `useSession()` receives the initial context state (`null`) before the poll runs.

**Why the E2E doesn't reproduce it:** The test simulates SIWE via direct POST and verifies the cookie, but does not mount `SessionProvider` nor run `useSession()` in the React client.

**Why it does happen with OneKey:**
1. Wagmi reconnects on mount → `address` populated
2. `RainbowKitSiweNextAuthProvider` detects wallet → triggers SIWE
3. SIWE completes → cookie set
4. But `SessionProvider` does not notify `useSession()` immediately
5. The guard runs before `useSession()` reflects the new session
6. `sessionStatus === 'unauthenticated'` (not `'loading'`) → the loading guard does not protect

### What We Learned

1. **`reconnectOnMount={false}` alone is not viable** — wagmi loses the address after navigation and the guard blocks everything
2. **The root cause is not wagmi, it's NextAuth** — `useSession()` returns `'unauthenticated'` after client navigation even with a valid cookie
3. **learn.tg's two-layer auth model provides flexibility** — UI layer (session) and API layer (token DB) are decoupled; read-only pages do not need session

## Solution

**Relax the "Partial login" guard on read-only pages** (courses, guides, landing):

```tsx
// Current (3 conditions, very strict):
if ((session && !address) || (address && !session) || 
    (address && session && session.address && 
     address.toLowerCase() !== session.address.toLowerCase()))

// Proposed (2 conditions, allows address without session):
if (address && session && session.address && 
    address.toLowerCase() !== session.address.toLowerCase())
```

**Rationale:**
- If wallet is connected (`address`) and session matches → renders normally
- No wallet (`!address`) → the page shows public content without user data
- Wallet connected without session (`address && !session`) → NextAuth bug case, renders and the session resolves on its own
- Write operations are protected at the API layer via `authenticateUser()` → `billetera_usuario.token`
- We only block if BOTH addresses exist and do NOT match (real mismatch)

**Modified files:**
- `app/[lang]/page.tsx` — courses landing (useEffect guard + render guard)
- `app/[lang]/[pathPrefix]/page.tsx` — course page (render guard)
- `app/[lang]/[pathPrefix]/[pathSuffix]/page.tsx` — guide page (render guard)
- `lib/hooks/useCourse.ts` — course fetch hook (data-fetching guard)
- `app/[lang]/[pathPrefix]/[pathSuffix]/test/page.tsx` — crossword (guard + loading)

**Do not modify:** `app/[lang]/profile/page.tsx` — the profile needs the token from `billetera_usuario` for writes via `authenticateUser()`.

### Fix Detail in `test/page.tsx` (crossword)

**Problem:** If NextAuth returns `'unauthenticated'` after navigation (bug #5719) but wagmi has `address`:
1. The crossword load was skipped (`!session` on line 110) → empty grid
2. The guard showed "Connect Wallet" even though the wallet WAS connected

**Fix:**
1. `!session` removed from the loading condition — the crossword loads with `getCsrfToken()` which works without an authenticated session
2. Guard relaxed: only blocks if `!address` (no wallet) or address mismatch
3. Submit security is maintained: `/api/check-crossword` uses `authenticateUser()` which validates `walletAddress + token` against `billetera_usuario`

## Considered Alternatives (future)

| Alternative | Feasibility | Note |
|-------------|-------------|------|
| `SessionUpdater` with `update()` on navigation | High | `useEffect(() => update(), [pathname])` — attacks root cause, but adds requests per navigation |
| Custom `SessionProvider` that re-fetches on `usePathname()` | Medium | Solves root but adds complexity — [community pattern](https://github.com/nextauthjs/next-auth/discussions/5719) |
| `RainbowKitAuthenticationProvider` with manual status | Medium | Breaks wallet↔SIWE coupling |
| Pass session from server component | Low | Requires large refactor |
| NextAuth v5 with `auth()` | Low | Requires version migration |

### Discarded
- Defer SIWE verification — RainbowKit handles it automatically
- localStorage session cache — XSS risk, duplicates NextAuth
