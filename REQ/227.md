### Reported regression (2026-09-12): card in "cooldown" and 0% with a new wallet — RESOLVED

- **Symptom (students with a new wallet, e.g. Rabby):** on the first connect the
  course "A relationship with Jesus" appears in **"cooldown"** and at **0%
  progress**; disconnecting and reconnecting shows it normally.
- **Root cause:** the course page (`app/[lang]/page.tsx`) took the wallet **only
  from `session?.address`**. With the cold-session bug (#5719) after login,
  `session.address` arrives empty even though the address is in
  `localStorage['learn.tg.sessionAddress']`. Without a wallet there was no token,
  so the listing and the progress were requested **anonymously**
  (`/api/scholarship?courseId=…` without `walletAddress`/`token`); the anonymous
  response brings a falsy `canSubmit` and 0% → the card is painted as "cooldown".
  Reconnecting warmed the session and everything returned to normal. It is the
  same underlying pattern as the token regression above (session identity on the
  home page), now on the **address** side, not the token side.
- **Applied fix:**
  - `app/[lang]/page.tsx`: `const wallet = session?.address || address || null`
    (session **or** `useAuthAddress`/localStorage). It keeps `connectedHint`
    (authenticated session ∥ address ∥ localStorage) → if the user appears
    connected and there is still no wallet, it **waits** instead of querying
    anonymously. The `/api/scholarship` loop **never** queries without
    wallet+token (it returns so the effect re-runs).
  - `lib/hooks/useCourse.ts`: same fallback (`address || session?.address`) for
    the Rails listing/detail and the per-guide `guide-status` under a cold
    session.
  - `components/CourseStatistics.tsx`: the "cooldown" text requires
    `canSubmit === false` (previously `!canSubmit`, which also showed it for
    `null`/unknown).
  - `packages/rewards/src/routes/scholarship.ts`:
    `let canSubmit: boolean | null = walletAddress ? false : null` — an anonymous
    query returns `null` (unknown), not `false` (confirmed cooldown).
- **Tests:** `components/__tests__/CourseStatistics.test.tsx` (`null` does **not**
  show cooldown; `false` does) and
  `app/api/scholarship/__tests__/route.test.ts` (anonymous → `canSubmit: null`).
- **New E2E regression:** `e2e/specs/fresh-wallet-first-connect.spec.mjs` (new
  wallet + SIWE; phase A with a freshly obtained dedicated token = control,
  phase B with the legacy CSRF as first-login fallback). In **production, before
  the fix**, it reproduced the bug (`ANONYMOUS 4/6`, "cooldown?: YES"); after
  deploying the fix it passes on **dev** (`learn.tg:9001`) and in **production**
  (`learn.tg`, 0 anonymous in A and B, no cooldown) — see "Production — VERIFIED"
  below. In production the listing is served on port `:3250` (unreachable from
  the VM): use `MOCK_COURSE_LIST=1`.
- **Token self-recovery (2026-09-12):** if the stored token is obsolete (e.g.
  `GET /api/auth/token` failed on the first login and the legacy CSRF remained),
  the course list and course detail return Rails `401` and the page ended up
  empty / in error. Now `lib/auth-token.ts` exposes `refreshApiToken()` (requests
  a new DEDICATED token through the session cookie and stores it) and
  `app/[lang]/page.tsx` + `lib/hooks/useCourse.ts` retry **once** with the new
  token on a `401` — reusing the session instead of degrading to anonymous
  queries. Unit test in `app/[lang]/__tests__/page.test.tsx` (401 →
  `/api/auth/token` → retry with the new token).

### OWASP analysis (2026-09-12)

Contrast of the current scheme with the OWASP cheat sheets. References: CSRF
Prevention, Session Management, REST Security, HTML5 Security, JSON Web Token and
Secrets Management (`https://cheatsheetseries.owasp.org/cheatsheets/`).

**Aligned**

- **The nonce/CSRF is no longer an API credential** — *CSRF Prevention*: "A CSRF
  Token is not an access token". This is exactly what Phase 1 changed.
- **The session is the primary credential, in an `HttpOnly; Secure; SameSite=Lax`
  cookie** with the `__Host-`/`__Secure-` prefix (*Session Management*). Verified
  in production: `HttpOnly; Secure; SameSite=Lax`.
- **Session identifier regenerated on authentication** (anti session-fixation,
  *Session Management*): NextAuth issues a new cookie on each login.
- **Do not share `NEXTAUTH_SECRET` with Rails** (Phase 2 recommendation) — *JSON
  Web Token*: "A different secret must be used for each (issuer, audience) pair…
  one audience can forge a token"; *REST Security*: "a compromise of any service
  also compromises all other services sharing the same key".
- **Server-side authorization on every request** (`authenticateUser`) +
  Origin/Sec-Fetch-Site as defense in depth.

**Deviations (inherited; Phase 2 must close them)**

1. **Token in the URL/query** (`?walletAddress=…&token=…` to Rails and to Next
   routes such as `/api/scholarship`, `/api/guide`). *REST Security*: "Passwords,
   security tokens, and API keys should not appear in the URL, as this can be
   captured in web server logs". → move to a header (`Authorization`/`X-Api-Token`)
   or eliminate it (session). **Tracked in R-#233.**
2. **Token in `localStorage`** (`learn.tg.authToken`). *HTML5 Security* / *Session
   Management*: "Do not store authentication tokens, session IDs, JWTs… in
   `localStorage`… a single XSS discloses every token". → stop persisting it once
   Rails accepts the session. **Tracked in R-#233.**
3. **Rotation on every login of a long-lived API token.** The mandatory rotation
   of *Session Management* applies to the **session ID** (complied); for **API
   tokens** OWASP asks for **short expiry + revocation** (`jti`/denylist), not
   rotating on every login. The current token does not expire. **Since 2026-09-14
   `authorize()` no longer rotates it** (intermediate step); expiry/revocation
   remains in R-#233.

**Conclusion:** the direction (session-first, cookie, CSRF out as a credential)
**is the recommended one**; what remains are the vestiges of the legacy scheme
(credential in the query and in `localStorage`), tracked in R-#233. "Stop rotating"
is a compatible intermediate step, but OWASP would prefer the API token **not to
exist on the client**.

## 1. Objective

Change API authorization so that **the NextAuth session (JWT in an HttpOnly
cookie) becomes the primary mechanism**, and stop using the **SIWE nonce/CSRF
as a persistent authentication token** (the `billetera_usuario.token`
column). CSRF remains only as the SIWE handshake nonce.

Direct motivation: real users get **401 "Unauthorized"** right after
confirming an on-chain transaction (reported on donations with the OneKey
wallet), and several E2E specs fail for the same reason (R-#224). Root cause:
the token **rotates on every SIWE sign-in** — logging in with the same wallet
from another tab/device invalidates the token of an already-open page, so a
money operation already signed on-chain stays unregistered. That must not
happen.

## 2. Context / Constraints

- **We already moved away from RainbowKit + wagmi** due to the session-loss
  problems documented in [issue #167](https://github.com/pasosdeJesus/learn.tg/issues/167)
  (session persistence — partial login with SIWE+NextAuth+OneKey/RainbowKit)
  and [issue #168](https://github.com/pasosdeJesus/learn.tg/issues/168)
  (RainbowKit QR crash), replaced by the in-house
  `ConnectWalletButton`/`useAuthAddress` implementation ([issue #186](https://github.com/pasosdeJesus/learn.tg/issues/186) — `doc/wallet-auth.md`).
- **RainbowKit/wagmi is not coming back.** The fix lives in the session layer
  (NextAuth + `authenticateUser`), keeping the in-house wallet hooks.
- Ecosystem reference pattern: the official SIWE+NextAuth example
  (RainbowKit `with-next-siwe-next-auth` / Auth.js) validates
  `siweMessage.nonce === csrfToken` **only inside `authorize()`** and then
  authorizes with the session; it never persists CSRF as an API token.
- OWASP CSRF Cheat Sheet: *"A CSRF token is not an access token"*; rotating
  the token on every login is an anti-pattern that hurts UX without a security
  gain; and tokens must not travel in URL/query params (log-leak risk).

## 3. Design decisions

| Decision | Rationale |
|---|---|
| **Session first, DB token as fallback (transition)** | `authenticateUser` validates the session cookie (JWT, `sub` = wallet, signed with `NEXTAUTH_SECRET`); if there is no cookie it falls back to the `billetera_usuario` token — old specs/tools keep working during the migration |
| **CSRF stays only for the SIWE login** | The dual use goes away: the nonce is no longer persisted as an API credential (stop populating `billetera_usuario.token`, then migrate/drop the column) |
| **Identity = session `sub`; request `walletAddress` only routes** | Prevents impersonation: the wallet param must match the session `sub` (and exist in `billetera_usuario`) |
| **CSRF for mutating APIs without a token in the body** | Same-origin + JSON/fetch: `SameSite=Lax` (session cookie) + `Origin`/`Sec-Fetch-Site` checks on unsafe methods; NextAuth keeps its internal CSRF for `/api/auth/*` |
| **Money operations resilient to 401** | Payment/donation verifies of already-signed on-chain txs must be retryable (idempotent via the `(crypto, hash)` UNIQUE constraint); if the session expired, re-authenticate by cookie and retry — never lose the hash record |
| **No wallet libraries reintroduced** | `wallet-auth` (R-#186) stays; only the way the server decides who the user is changes |

## 4. Specification

### 4.1 `authenticateUser` (new order)

1. Request has `token`/`walletAddress`: if the session cookie is valid and its
   `sub` == wallet (lowercase) → OK (no DB-token lookup).
2. No session → validate the DB token as a **legacy fallback** (same code as
   today), with gated logging to detect residual usage.
3. `401` responses always carry a reason in logs (tag `[auth]`, no PII,
   enabled via `DEBUG_AUTH=1`).

### 4.2 SIWE login

- Kept: CSRF as the nonce of the signed message (step 2 of the flow in
  `doc/siwe-auth-flow.md`), domain/chain/signature verification in
  `authorize()`.
- Change (implemented): step 7 stores a **dedicated random API token**; the
  CSRF/nonce is never persisted as an API credential. Since 2026-09-14 the token
  is **not rotated on re-login**: `authorize()` reuses the existing dedicated
  token on update (generates one only on insert or for a legacy non-dedicated
  value).

### 4.3 CSRF layer for mutations (same origin)

Middleware/helpers for unsafe methods on cookie-authenticated routes:
- `Origin` (when present) == expected origin; if absent, fall back to
  `Referer`; reject when `Sec-Fetch-Site: cross-site` and the method is not
  safe.
- Session cookies: `Secure; HttpOnly; SameSite=Lax` (+ `__Host-` prefix in
  production if the proxy allows it); `NEXTAUTH_SECRET` stable across
  deploys/redeploys (rotating it invalidates every session).

### 4.4 Money routes (priority)

- `donations/{slug}/verify`, `add-donation`, `gdcluster/donations/verify`,
  `premium/purchase`, `claim-*`, `scholarship`, `pastor-bonus`: authorize by
  session; if a 401 happens after an on-chain confirmation, the client must
  **re-authenticate and retry the verify** (idempotent); if the backend
  already recorded the hash it responds without duplicating.

### 4.5 Compatibility / migration

- During the transition `authenticateUser` accepts both paths (env flag
  `AUTH_SESSION_ONLY=1` to force session-only and measure dependencies).
- E2E/specs: fetch-based SIWE flows already keep cookies → keep passing; the
  ones sending only `token` (no cookie jar) are updated to session/cookie.
- Docs to sync: `doc/siwe-auth-flow.md` (drop "CSRF = API token"),
  `doc/wallet-auth.md`, `doc/api-security.md`, R-#224.
