# #196: LearnTGVaultsV5 — Flexible Scholarship Split

Modify `LearnTGVaultsV4` to V5, allowing the backend to specify amounts for referrer and learn.tg destination. The contract performs the transfers without calculating percentages.

---

## 1. Changes from V4 to V5

### 1.1 Version Change

```diff
- uint256 public constant VERSION = 4;
+ uint256 public constant VERSION = 5;
```

### 1.2 New Parameters in `payScholarship`

```diff
function payScholarship(
    uint256 courseId,
    uint256 guideId,
    address student,
    bool isPerfect,
    uint8 profileScore,
+   address referrer,
+   uint256 referrerUSDT,
+   uint256 referrerSlearn,
+   address learnTgWallet,
+   uint256 learnTgUSDT,
+   uint256 learnTgSlearn
) external onlyOwner vaultExists(courseId) {
```

### 1.3 Validation

```solidity
// 1. Base amounts
uint256 actualUSDT = (vault.amountPerGuideUsdt * profileScore) / 100;
uint256 actualSlearn = (vault.amountPerGuideSlearn * profileScore) / 100;

// 2. Total deductions must not exceed scholarship
uint256 totalDeductionsUSDT = referrerUSDT + learnTgUSDT;
uint256 totalDeductionsSlearn = referrerSlearn + learnTgSlearn;
require(totalDeductionsUSDT <= actualUSDT, "USDT deductions exceed scholarship");
require(totalDeductionsSlearn <= actualSlearn, "SLEARN deductions exceed scholarship");

// 3. Self-referral prevention
if (referrer != address(0)) {
    require(referrer != student, "Cannot refer yourself");
}

// 4. Student receives the remainder
uint256 studentUSDT = actualUSDT - totalDeductionsUSDT;
uint256 studentSlearn = actualSlearn - totalDeductionsSlearn;
```

### 1.4 Transfers

```solidity
// Student (remainder)
if (studentUSDT > 0) usdtToken.transfer(student, studentUSDT);
if (studentSlearn > 0) slearnToken.transfer(student, studentSlearn);

// Referrer (if any)
if (referrer != address(0) && referrerUSDT > 0) {
    usdtToken.transfer(referrer, referrerUSDT);
}
if (referrer != address(0) && referrerSlearn > 0) {
    slearnToken.transfer(referrer, referrerSlearn);
}

// learn.tg wallet (if any)
if (learnTgWallet != address(0) && learnTgUSDT > 0) {
    usdtToken.transfer(learnTgWallet, learnTgUSDT);
}
if (learnTgWallet != address(0) && learnTgSlearn > 0) {
    slearnToken.transfer(learnTgWallet, learnTgSlearn);
}
```

## 2. Backend Usage Examples

### Example 1: Global Disciples (10% referrer, 10% cluster)

```typescript
const scholarshipUSDT = 1.00
const scholarshipSlearn = 5

const referrerUSDT = referrer ? scholarshipUSDT * 0.10 : 0
const referrerSlearn = referrer ? scholarshipSlearn * 0.10 : 0

// 10% to learn.tg wallet → backend will send to ClusterFunds
const learnTgUSDT = scholarshipUSDT * 0.10
const learnTgSlearn = scholarshipSlearn * 0.10

await vaultV5.payScholarship(
    courseId, guideId, student, isPerfect, profileScore,
    referrer, referrerUSDT, referrerSlearn,
    process.env.NEXT_PUBLIC_ADDRESS,  // learn.tg wallet
    learnTgUSDT, learnTgSlearn
)

// Backend then calls ClusterFunds.processDonation()
```

### Example 2: No referrer, no destination

```typescript
await vaultV5.payScholarship(
    courseId, guideId, student, isPerfect, profileScore,
    address(0), 0, 0,
    address(0), 0, 0
)
// Student receives 100% of scholarship
```

### Example 3: Only referrer (10%)

```typescript
await vaultV5.payScholarship(
    courseId, guideId, student, isPerfect, profileScore,
    referrer, referrerUSDT, referrerSlearn,
    address(0), 0, 0
)
// Student receives 90%, referrer 10%
```

## 3. Migration: V4 → V5

Following the pattern established in `20260607_contract-to-v4.ts` (V3→V4) and
`20260531000000_contract-to-v3.ts` (V2→V3).

### Migration file

`db/migrations/YYYYMMDD_contract-to-v5.ts`

### Steps

| Step | Action | Details |
|------|--------|---------|
| 1 | **Drain V4** | `emergencyWithdrawUSDT(balance)` + `emergencyWithdrawSLEARN(balance)` from the V4 contract back to the deployer wallet |
| 2 | **Transfer to V5** | `usdt.transfer(V5, usdtBalance)` + `slearn.transfer(V5, slearnBalance)` — send drained tokens to the new V5 contract |
| 3 | **Migrate vaults** | For each course in `cor1440_gen_proyectofinanciero`, read vault from V4 (`amountPerGuideUsdt`, `amountPerGuideSlearn`), create vault in V5 via `createVault(courseId, perUSDT, perSLEARN)` |
| 4 | **Restore balances** | For each vault, call `setVaultBalance(courseId, usdtBalance, slearnBalance)` on V5 with the original V4 balances |
| 5 | **Migrate guidePaid** | Aggregate `transaction` table (type=`scholarship`, crypto=`usdt`|`slearn`) by `(usuario_id, guideId)`. For each pair, read `getStudentGuideStatus` on V4, call `setGuidePaid` on V5 with the same values. Idempotent — skips if V5 already has the record. |
| 6 | **Update env** | Set `NEXT_PUBLIC_DEPLOYED_AT_V4` = old V4 address (archive), `NEXT_PUBLIC_DEPLOYED_AT` = new V5 address (active) |

### Key differences from V3→V4

- V3→V4 involved a dual-token model (USDT + SLEARN); V4 already has this. V5 keeps the same token model but changes the `payScholarship` signature.
- The `setGuidePaid` function exists in V4 and is expected to exist in V5 with the same signature (migrating cumulative paid amounts per guide).
- The `vaults` mapping structure should remain compatible (V4 and V5 use same fields: `amountPerGuideUsdt`, `amountPerGuideSlearn`, `isActive`, etc.).

### Lessons learned from V3→V4 migration issues

The V3→V4 migration (`20260607_contract-to-v4.ts`) required 4 follow-up fix migrations:

| Fix migration | Problem | Root cause |
|---|---|---|
| `20260722180000_deduplicate_scholarship_usdt` | Duplicate `transaction` rows: `sync` entries from V3 and `deep-scan` entries from the migration aggregator overlapped | The migration created new `transaction` rows without checking for pre-existing sync entries |
| `20260722190000_fill_missing_hashes` | `transaction.hash` was NULL for migrated entries | `setGuidePaid` on-chain calls were not recorded with their transaction hash in the DB |
| `20260723000000_fix_transaction_dates` | `transaction.date` had wrong dates (some off by months) | Dates were derived from `new Date()` at migration time instead of from on-chain event timestamps |
| `20260723010000_fill_missing_hashes_v1` | Additional NULL hashes from older V1 contract transactions | First pass only covered a subset; V1-era transactions were missed |

**Rules for V4→V5 migration:**

1. **No duplicates**: Before inserting a `transaction` row for a migrated `guidePaid` record, check if a `scholarship` transaction already exists for the same `(usuario_id, guideId)` pair. If it does, skip — don't create a duplicate.
2. **Record hashes**: After each `setGuidePaid` on-chain call, immediately record the transaction hash and the on-chain timestamp in the `transaction` row.
3. **On-chain timestamps**: Use the block timestamp from the transaction receipt (`waitForTransactionReceipt` returns a receipt with `blockNumber`; query the block for its timestamp), not `new Date()`.
4. **Export blockchain history before migration**: Run `bin/m db:console` to dump all scholarship transactions with their hashes as a CSV backup, in case any are missed and need filling later.

### Prerequisites

- V5 contract deployed and its address available via `getV5Address()` in `lib/deployments.ts`
- V4 address still available in env or deployments
- `PRIVATE_KEY`, `NEXT_PUBLIC_RPC_URL`, `NEXT_PUBLIC_USDT_ADDRESS` set in `apps/.env`
- SLEARN token address retrievable from V4 contract
