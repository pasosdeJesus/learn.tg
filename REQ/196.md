# #196: LearnTGVaultsV5 — Flexible Scholarship Split

Modify `LearnTGVaultsV4` to V5, allowing the backend to specify amounts for referrer and learn.tg destination. The contract performs the transfers without calculating percentages.

## 1. Changes from V4 to V5

### 1.1 Version Change


### 1.3 Payment Strategy: Per-Token All-or-Nothing

V5 mantiene pagos parciales **entre tokens** (USDT hoy, SLEARN mañana) pero cada token es **todo o nada**:

- **USDT**: Si `vault.balanceUsdt >= actualUSDT` → paga las 3 partes (student + referrer + learnTg). Si no, no paga USDT ni registra `guidePaidUSDT`.
- **SLEARN**: Ídem independiente.
- Esto es más estricto que V4 (que permitía partial dentro de un mismo token), pero más simple y predecible para el backend.

### 1.4 Validation

```solidity
// 1. Base amounts (profileScore-adjusted)
uint256 actualUSDT = (vault.amountPerGuideUsdt * profileScore) / 100;
uint256 actualSlearn = (vault.amountPerGuideSlearn * profileScore) / 100;

// 2. Si referrer es address(0), sus montos deben ser 0
//    (el backend garantiza esto; si no, las deducciones excederían la beca)

// 3. Total deductions must not exceed scholarship
uint256 totalDeductionsUSDT = referrerUSDT + learnTgUSDT;
uint256 totalDeductionsSlearn = referrerSlearn + learnTgSlearn;
require(totalDeductionsUSDT <= actualUSDT, "USDT deductions exceed scholarship");
require(totalDeductionsSlearn <= actualSlearn, "SLEARN deductions exceed scholarship");

// 4. Self-referral prevention
if (referrer != address(0)) {
    require(referrer != student, "Cannot refer yourself");
}

// 5. Student receives the remainder
uint256 studentUSDT = actualUSDT - totalDeductionsUSDT;
uint256 studentSlearn = actualSlearn - totalDeductionsSlearn;
```

### 1.5 Transfers (per-token all-or-nothing)

```solidity
// Pay USDT if not already paid AND vault has enough
if (!alreadyPaidUSDT && actualUSDT > 0 && vault.balanceUsdt >= actualUSDT) {
    vault.balanceUsdt -= actualUSDT;
    guidePaidUSDT[courseId][guideId][student] = actualUSDT;

    if (studentUSDT > 0) usdtToken.transfer(student, studentUSDT);
    if (referrer != address(0) && referrerUSDT > 0) {
        usdtToken.transfer(referrer, referrerUSDT);
    }
    if (learnTgWallet != address(0) && learnTgUSDT > 0) {
        usdtToken.transfer(learnTgWallet, learnTgUSDT);
    }
    paidUSDT = actualUSDT;
}

// Pay SLEARN if not already paid AND vault has enough
if (!alreadyPaidSLEARN && actualSlearn > 0 && vault.balanceSlearn >= actualSlearn) {
    vault.balanceSlearn -= actualSlearn;
    guidePaidSLEARN[courseId][guideId][student] = actualSlearn;

    if (studentSlearn > 0) slearnToken.transfer(student, studentSlearn);
    if (referrer != address(0) && referrerSlearn > 0) {
        slearnToken.transfer(referrer, referrerSlearn);
    }
    if (learnTgWallet != address(0) && learnTgSlearn > 0) {
        slearnToken.transfer(learnTgWallet, learnTgSlearn);
    }
    paidSlearn = actualSlearn;
}

// Cooldown only if something was paid
if (paidUSDT > 0 || paidSlearn > 0) {
    studentCooldowns[courseId][student] = block.timestamp;
    emit ScholarshipPaidV5(...);
} else {
    emit ScholarshipInsufficientFunds(...);
}
```

## 2. Backend Usage Examples

### Example 1: Global Disciples (10% referrer, 10% cluster)

```typescript
const scholarshipUSDT = 1.00
const scholarshipSlearn = 5

const referrerUSDT = referrer ? scholarshipUSDT * 0.10 : 0
const referrerSlearn = referrer ? scholarshipSlearn * 0.10 : 0

// 10% to learn.tg wallet → backend records pending transfer to ClusterFunds
const learnTgUSDT = scholarshipUSDT * 0.10
const learnTgSlearn = scholarshipSlearn * 0.10

const tx = await vaultV5.payScholarship(
    courseId, guideId, student, isPerfect, profileScore,
    referrer || '0x0000000000000000000000000000000000000000',
    referrerUSDT, referrerSlearn,
    process.env.NEXT_PUBLIC_ADDRESS,  // learn.tg wallet
    learnTgUSDT, learnTgSlearn
)

// Register pending cluster transfer for admin resolution
if (learnTgUSDT > 0 || learnTgSlearn > 0) {
    await db.insertInto('admin_solves').values({
        type: 'cluster_transfer',
        metadata: { txHash: tx, learnTgUSDT, learnTgSlearn, courseId, guideId },
        solved_at: null
    }).execute()
}
```

### Example 2: No referrer, no destination

```typescript
await vaultV5.payScholarship(
    courseId, guideId, student, isPerfect, profileScore,
    '0x0000000000000000000000000000000000000000', 0, 0,
    '0x0000000000000000000000000000000000000000', 0, 0
)
// Student receives 100% of scholarship
```

### Example 3: Only referrer (10%)

```typescript
await vaultV5.payScholarship(
    courseId, guideId, student, isPerfect, profileScore,
    referrer, referrerUSDT, referrerSlearn,
    '0x0000000000000000000000000000000000000000', 0, 0
)
// Student receives 90%, referrer 10%
```

### 2.1 ClusterFunds Flow (Non-Atomic, Traceable)

El pago a `learnTgWallet` y la transferencia posterior a `ClusterFunds` no es atómico, pero es trazable mediante la tabla `admin_solves`:

1. `payScholarship` envía fondos a `learnTgWallet` (NEXT_PUBLIC_ADDRESS)
2. Backend inserta registro en `admin_solves` con `type='cluster_transfer'`, `solved_at=null`
3. Admin dashboard muestra registros pendientes (`solved_at IS NULL`)
4. Admin ejecuta `ClusterFunds.processDonation()` manualmente o vía script
5. Admin marca `solved_at = NOW()` en el registro

#### 3.2.4 Qué NO se bloquea

- Login / autenticación
- Perfil de usuario (lectura/escritura)
- Rankings de clústeres y países
- Donaciones a clústeres/países (ClusterFunds)
- Navegación de cursos (lectura)
- Guías ya completadas (lectura)

Solo se bloquean **nuevas becas** (payScholarship) y **verificación de crucigramas** que disparen pago.

### 3.3 Migration Script Design

**Archivo:** `db/migrations/YYYYMMDD_contract-to-v5.ts`

**Principio:** Leer estado directamente del contrato V4 (on-chain), NO de la tabla `transaction`. Esto evita los 4 problemas de V3→V4.

```
1. Exportar CSV de respaldo (hashes + timestamps de V4)
2. Drenar V4: emergencyWithdrawUSDT + emergencyWithdrawSLEARN → deployer
3. Transferir tokens → V5: usdt.transfer(V5) + slearn.transfer(V5)
4. Crear vaults en V5: leer vaults de V4 on-chain, createVault en V5 (idempotente)
5. Restaurar balances: setVaultBalance en V5 con valores de V4
6. Migrar guidePaid:
   - Leer getStudentGuideStatus de V4 para cada (user, guide)
   - Llamar setGuidePaid en V5 (idempotente — verifica si V5 ya tiene registro)
   - Guardar hash + block.timestamp de cada tx (NO new Date())
7. Actualizar .env: DEPLOYED_AT_V4 = V4 (archivo), DEPLOYED_AT = V5 (activo)
```

**Por qué no usar `transaction` table:** La migración V3→V4 agregó desde `transaction` y generó:
- Duplicados con sync entries existentes
- Hashes NULL (no se capturaron durante la migración)
- Fechas incorrectas (new Date() en vez de block.timestamp)

Leyendo directo de V4 evitamos todo esto. La única fuente de verdad es el contrato.

## 6. GD Course Scholarship Routing

For the Global Disciples course (IDs 10 `/gdcluster`, 11 `/redgd`), 10% of
each scholarship is routed to the student's cluster or country fund via
`ClusterFunds`. The student receives 90% (100% − 10% cluster − 0% referrer).
When #163 implements referrals, it becomes 80% (100% − 10% cluster − 10%
referrer).

### 6.1 Routing Logic

Resolved automatically in `lib/gd-cluster-routing.ts`:

1. **Church cluster**: student's church (`usuario.church_id`) belongs to a
   GD cluster (`church_clustergd`) → 10% to `church.cluster_wallet` via
   `ClusterFunds.processDonation()`.
2. **Country fund**: no church/cluster, but student's country is in pilot
   (`PILOT_COUNTRIES`) → 10% to country fund via
   `ClusterFunds.processCountryDonation(countryCode)`.
3. **Sierra Leone fallback**: otherwise → 10% to `"SL"` country fund.

If auto-routing fails, falls back to `admin_solves` for manual processing.

### 6.2 Implementation

In `check-crossword/route.ts`, when V5 is active and course is GD:

```typescript
learnTgUSDT = (fullUSDT * score * 10n) / 10000n  // 10% of scholarship
learnTgSlearn = (fullSlearn * score * 10n) / 10000n
learnTgAddr = NEXT_PUBLIC_ADDRESS
```

After `payScholarship`, `routeToClusterFunds()` handles approve + 
`processDonation`/`processCountryDonation` automatically.

### 6.3 Course Card Display

The scholarship card on the course page must reflect the split:

| Course type | Referrer | Card shows |
|-------------|----------|------------|
| Standard | No (0%) | "Up to 1 USDT/scholarship" |
| Standard | Yes (10%) | "Up to 0.90 USDT after 10% referral" |
| GD | No (0%) | "Up to 0.90 USDT (10% to cluster fund)" |
| GD | Yes (10%) | "Up to 0.80 USDT (10% cluster + 10% referral)" |
