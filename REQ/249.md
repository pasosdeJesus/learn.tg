> **Relation to the packages (asked 2026-09-19): should this have been part of
> R-#236/R-#237?** Partly yes and partly no. What belongs to the packages is
> already there: create/import/unlock/delete, the encrypted record, the provider
> and `exportMnemonic`/`exportPrivateKey`, all `@learn-tg/pdj-wallet` (R-#236) and
> `@learn-tg/pdj-wallet-next` (R-#237). What does **not** belong there is a panel:
> balances need the app's token addresses, the RPC client and the same gas panel
> the donation modal uses, and the NFTs need a Blockscout call. Keeping it in

> into a framework-agnostic package. The one item that did fit in the core
> originally, the **3-word seed verification**, is moved here (acceptance criteria)
> because it is a backup UX check, and the panel is where "do you really have the
> words?" belongs now that the wallet shows them once.

### 1. Objective

Make the in-app wallet a place the user can **look at and act from**: tapping the
wallet pill in the header opens a panel that shows the balances of the wallet,
lets the user copy the address, receive and send, and — where the wallet holds
them — shows the NFTs.

Today the pill opens `WalletDialog`, which is only about creating, importing,
unlocking, deleting and (since R-#246) enrolling the fingerprint. Once unlocked it
shows the address, a delete button and the fingerprint switch: nothing about the
money.

### 2. What the operator asked for (2026-09-18, mobile Chrome, dev site)

> "Al presionar la píldora de la billetera debería mostrar un modal de billetera
> con saldos, al menos con saldos de CELO, USDT y SLEARN, botones para enviar y
> recibir, un icono para copiar la dirección, también debería poder presentar los
> NFT que el usuario tenga, por ahora solo red CELO."

Read as requirements:

| # | Requirement |
|---|---|
| 1 | The header pill opens a **wallet panel** (not just the unlock form) |
| 2 | Balances of **CELO**, **USDT** and **SLEARN** at least |
| 3 | **Send** and **receive** actions |
| 4 | An icon/button to **copy the address** |
| 5 | Show the user's **NFTs**, Celo network only for now |

### 3. Scope

**In scope:** the panel, the balances, copy, receive, send (native CELO and the
ERC-20s the app already knows: USDT, SLEARN) and the NFT listing on Celo.

**Out of scope (for now):** other chains (the operator said "solo red CELO"),
swaps, bridges, transaction history with filters, gas top-up flows (the donation
modal already has the gas panel), fiat on/off ramps, and the Rails admin.

**Platforms:** mobile first, in the priority order of
https://github.com/pasosdeJesus/learn.tg/issues/246 §3 (Chrome Android, Safari
iOS, then the wallet in-app browsers). Desktop gets the same code; it is not the
target (R-#246 §3).

### 4. Design sketch

**4.1 Where it lives**

`WalletDialog` keeps its job (create/import/unlock/enroll fingerprint) and the
panel is its **unlocked** state, or a sibling dialog opened from the same pill. The
second option is cleaner: the unlock flow is a security surface, the panel is a
wallet UI, and mixing them makes the first one harder to reason about (and to test).

| State | What the pill opens |
|---|---|
| No wallet, or wallet locked | the current `WalletDialog` (create / unlock / fingerprint) |
| Wallet unlocked | the new **wallet panel** |

**4.2 Balances**

- CELO: `eth_getBalance` (already used by the donation modal).
- USDT and SLEARN: ERC-20 `balanceOf` with the addresses already resolved through
  `@learn-tg/rewards/lib/deployments` (no address hardcoded, per the project rule).
- Read through the same provider resolution as the rest of the app
  (`useWalletProvider`), and refresh when the panel opens, after a transaction and
  when the chain changes. Show a skeleton while loading and never a `NaN`.
- Format with the token decimals that already exist in the app (CELO 18, USDT 6,
  SLEARN 2) and show the symbol; the fiat value is out of scope (there is no price
  feed for SLEARN and adding one is a separate decision).

**4.3 Receive**

- Show the address as text **and** as a QR code (there is already a QR dependency
  in the app for the Self verification flow; reuse it, do not add another).
- Copy button with a confirmation (`Copied`), and the same address checksummed as
  in the rest of the UI.

**4.4 Send**

- Form: destination address, amount, token selector (CELO / USDT / SLEARN), and a
  "max" that leaves gas on native CELO.
- Validation before signing: valid EIP-55 address (checksum warning if the user
  typed a mixed-case address that does not match), sufficient balance, and the same
  gas handling the donation modal already has (`useGasEstimation`,
  `GasInsufficientPanel`).
- Signing goes through the existing provider, so it **inherits the layer L1 gate**
  of R-#246: moving funds asks for a fresh fingerprint. With the panel this becomes
  the most common way to move money, so the confirmation must be explained in the
  UI ("confirma con tu huella"), not a surprise.
- Result screen: hash + explorer link + "Done", like the donation modal.

**4.5 NFTs (Celo only)**

- Read-only listing from a public API (Blockscout on Celo is already used in the
  app for explorer links and needs no key; Celoscan is the alternative with a key).
  Candidate: the address's NFT list, then metadata (name, image, collection).
- Lazy: load the first screenful only when the panel opens, with a "show more", and
  never block the balances on the NFT call failing.
- Degrade silently: if the API is down or the user has none, the section says so
  and the rest of the panel keeps working.
- The images come from third-party hosts: if
  https://github.com/pasosdeJesus/learn.tg/issues/247 (CSP) is enforced first, its
  `img-src` must allow those hosts or the images must be proxied.

### 5. Acceptance criteria

- [ ] Tapping the pill with an unlocked wallet opens the panel; with a locked
      wallet it opens the unlock flow first.
- [ ] The panel shows CELO, USDT and SLEARN balances with correct decimals, and
      survives one of the three calls failing.
- [ ] Copy button copies the checksummed address and confirms it.
- [ ] Receive shows the address and a scannable QR code.
- [ ] Send works for CELO, USDT and SLEARN to a valid address, refuses an invalid
      one with a clear message, refuses an amount above the balance, and asks for
      the fingerprint (L1) before signing.
- [ ] NFTs on Celo are listed for an address that has them, with a clear empty
      state, and the section failing does not break the balances.
- [ ] Everything works on Chrome Android at 360×640 (the MiniPay-adjacent minimum
      the project already designs for) and in English and Spanish.
- [ ] Unit tests for the balance/format helpers and for the send validation;
      E2E spec for "open panel → read balances → copy address", tolerant of a slow
      first load (see the cold-compile note in
      https://github.com/pasosdeJesus/learn.tg/issues/246 §11).
- [ ] `doc/wallet-auth.md` and the user guide document the panel.
- [ ] **Backup confirmation (moved from
      https://github.com/pasosdeJesus/learn.tg/issues/184 on 2026-09-19):** after
      the 12 words are shown, ask for three of them (random positions) before the
      wallet counts as backed up; today `WalletDialog` only requires pressing "I
      saved them", so a user who copied nothing loses the wallet on the next
      device. Keep the order the wallet used for the words, accept the words in any
      case, and never show the phrase again after this step.

### 6. Open questions

1. Where do the balances come from: the wallet's own RPC calls, or the backend
   (which already knows the address and could cache them)? Own calls keep the panel
   working offline-ish and avoid trusting the server; the backend could be faster.
2. Is a fiat estimate needed? It requires a price source for SLEARN (its value is
   defined by the reserve rules of the white paper, not a market).
3. NFTs: which API exactly (Blockscout vs Celoscan) and do we cache them?
4. Send: do we need a contact/address book, or is a plain address enough for now?
5. Should the panel also offer "lock now" and "delete wallet" (today in
   `WalletDialog`), so the security actions live with the wallet UI?
