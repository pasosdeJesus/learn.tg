## 1. Qué se rompe

En **OpenBSD/adJ** Next 16.3.5 no tiene bindings nativos de SWC
(`next-swc does not have native bindings for platform openbsd/x64`) y usa el paquete
WASM `@next/swc-wasm-nodejs`. Su export `codeFrameColumns(source, location, options)`
deserializa `options` con `serde`: `color` debe ser el **enum** `None|Error|Warning|Info`
y `maxWidth` un **número**.

Next, en cambio, pasa:

- `color: false` / `color: true` (booleano) en `next/dist/next-devtools/server/shared.js`
  (`getOriginalCodeFrame`, con `process.stdout?.isTTY ?? false` por defecto), en
  `lib/typescript/diagnosticFormatter.js` y en `build/load-jsconfig.js`.
- `maxWidth: undefined` cuando la salida **no es una terminal** (el `next dev` que arranca
  `bin/dev` escribe en un archivo: `process.stdout.columns` no existe), y en
  `getOriginalCodeFrame` siempre que se lo llame con un booleano.

Con eso el binding lanza y **el error real desaparece**:

```
Error: invalid type: boolean `false`, expected enum CodeFrameColorMode
Error: invalid type: unit value, expected usize
```

Efectos medidos en este VM: en `next dev` el overlay del error no se pinta y la consola del
servidor no muestra ni el `console.error` del route ni la página de error (por eso existe
`apps/nextjs/lib/server-errors.ts` + `instrumentation.ts`, el paliativo de
https://github.com/pasosdeJesus/learn.tg/issues/252). En `next build`, un `tsconfig.json`
mal formado o un diagnóstico de TypeScript fallarían al construir el mensaje.

## 2. Evidencia (2026-09-27)

En `/tmp/learn-tg-server-errors.log`, con el parche **anterior** aplicado (que sólo
normalizaba `color`), la traza es la misma pero con el otro error:

```
[2026-09-27T11:02:36.986Z] onRequestError GET /api/guide?courseId=103&... 
Error: Error: invalid type: unit value, expected usize
    at Module.codeFrameColumns (…/next/wasm/@next/swc-wasm-nodejs/wasm.js:12:22)

    at codeFrameColumns (…/next/dist/shared/lib/errors/code-frame.js:23:40)
```

Es decir: el parche de la sesión anterior arreglaba el booleano de `color` y dejaba vivo el
`maxWidth: undefined`. La causa que se estaba reportando era, de nuevo, invisible (el 500
real era `error: remaining connection slots are reserved for roles with the SUPERUSER
attribute` de PostgreSQL).

## 3. El arreglo

`apps/nextjs/patches/next@16.3.5.patch` normaliza las dos opciones en
`dist/{esm/,}shared/lib/errors/code-frame.js`, el único módulo por el que pasan todos los
llamadores:

```js
if (options.color === false) {
    delete options.color;          // el default de ambas rutas es "sin color"
} else if (options.color === true) {
    options.color = 'Error';       // true era Error tambien en la ruta nativa
}
if (typeof options.maxWidth !== 'number') {
    options.maxWidth = 100;        // stdout.columns no existe sin terminal
}
```

Detalle importante: **no** se traduce `false` a `'None'`. El enum del binding nativo
(`NapiCodeFrameColorMode`) sólo tiene `Error|Warning|Info`, así que `'None'` sería válido para
wasm y un `InvalidArg` en nativo; borrar la propiedad deja el default en las dos rutas
(verificado en la verificación de §5). Ese matiz es la razón por la que el parche no se limita
a "convertir el booleano en enum".

Cosas que **no** hace: no toca el binding WASM, ni el comportamiento cuando la salida sí es
una terminal (`process.stdout.columns` manda), ni los colores ANSI (`color: true` sigue
pintando).

Se declara en `apps/nextjs/package.json`:

```json
"pnpm": { "patchedDependencies": { "next@16.3.5": "patches/next@16.3.5.patch" } }
```

`pnpm install` lo re-aplica (queda registrado en `pnpm-lock.yaml`), así que un checkout
nuevo en OpenBSD ya trae el arreglo.

## 4. Criterios de aceptación

- [x] `codeFrameColumns` con las opciones reales de Next (booleano en `color`,
      `maxWidth: undefined`) devuelve el marco de código en vez de lanzar.
- [x] `color: false` → sin colores; `color: true` → con colores ANSI; `maxWidth` explícito
      se respeta.
- [x] El parche se aplica con `pnpm install` sin `ERR_PNPM_PATCH_FAILED` y deja los dos
      archivos exactamente como los genera el parche.
- [x] Un 500 de una ruta deja de perderse: el error real queda visible.
- [x] No cambia el comportamiento del sitio (parche sólo del motor, en `node_modules`).
- [x] En `next dev`, un 500 real vuelve a mostrar su causa con marco de código, sin la traza
      del binding (§5).

## 6. Pendiente / notas

- **Cómo se aplica y se comprueba.** Se aplica solo con `pnpm install` (lo toma de
  `pnpm.patchedDependencies`). Para hacerlo a mano y verificar que quedó:

  ```sh
  cd apps/nextjs
  make next-patch        # pnpm install --frozen-lockfile + comprobación
  make next-patch-check  # sólo comprueba (falla si node_modules trae el parche viejo)
  ```

  `make all` y `make prod` ya ejecutan `next-patch-check` antes de compilar: abortan con
  instrucciones si el parche no está aplicado, igual que `build-guard` hace con el dev
  server.
- **Cómo se regenera** (no editar `node_modules` a mano: pnpm usa enlaces duros y el store
  queda sucio, `ERR_PNPM_PATCH_FAILED`):
  1. quitar `pnpm.patchedDependencies` de `package.json` y `pnpm install` (deja el archivo
     original);
  2. guardar el original, hacer el cambio, y generar el diff con
     `diff -u --label a/dist/... --label b/dist/... original nuevo`;
  3. reponer `patchedDependencies` y `pnpm install`;
  4. comprobar que el archivo instalado coincide con el editado (`diff`).
- **Actualizar Next** invalida el parche: si algún día hay bindings nativos en OpenBSD (o
  Next normaliza estas opciones — el arreglo de fondo sería que pasara `color: 'None'` y un
  `maxWidth` numérico), se borra el parche y esta entrada se cierra. Un parche que ya no
  aplica **no** pasa desapercibido: `pnpm install` falla con `ERR_PNPM_PATCH_FAILED` y
  `make next-patch-check` lo dice.
- **El paliativo se queda.** `lib/server-errors.ts` + `instrumentation.ts` siguen siendo
  útiles: registran en stderr y en `/tmp/learn-tg-server-errors.log` los errores que no
  pasan por el overlay (rutas de streaming, `unhandledRejection`). Lo que cambia es que el
  overlay vuelve a mostrar la causa.
- **¿Vale la pena en producción?** No es urgente y no cambia el runtime: el overlay es de
  `next dev` y el sitio sirve `next build`/`next start`. Lo que sí cambia es el **momento de
  compilar en OpenBSD**, que corre en la misma máquina: si hay un error de `tsconfig.json` o
  un diagnóstico de TypeScript, sin el parche el mensaje se pierde en la traza del binding.
  Como el parche entra con el `pnpm install` normal (el de `make all`), lo razonable es
  dejarlo puesto en todos los entornos y **no** agregar un paso de despliegue especial; el
  único efecto de no tenerlo es un mensaje de error peor.

````markdown
Title: WASM: codeFrameColumns rejects `color: boolean` and `maxWidth: undefined`, which the napi binding and Next's own callers accept

### Summary

On the WASM fallback build (`@next/swc-wasm-nodejs`), every code frame requested by Next's
own call sites throws before rendering:

```
Error: invalid type: boolean `false`, expected enum CodeFrameColorMode
Error: invalid type: unit value, expected usize
```

Both come from `serde_wasm_bindgen` deserializing the JS options object into
`next_code_frame::CodeFrameOptions`. The native (napi) binding accepts the exact same
options because it normalizes them first, so this is a divergence between the two bindings,
not a platform problem. As a result, on the WASM path Next cannot render a code frame for
**any** error, and the real cause of a 500 or a build error is replaced by the error above.

### Environment

- next 16.3.5 (`@next/swc-wasm-nodejs`), also reproduced while debugging a project on
  OpenBSD/adJ, which has no native bindings for `openbsd/x64` and therefore always uses the
  WASM fallback.
- Source level checked against `canary` on 2026-09-27: `crates/wasm/src/lib.rs`
  (`code_frame_columns`), `crates/next-code-frame/src/frame.rs`, and
  `crates/next-napi-bindings/src/code_frame.rs`.
- Affects any user of the WASM fallback (unsupported platform, or a failed native download),
  not only OpenBSD.

### Minimal reproduction (any OS, ~1 minute, no app needed)

```sh
mkdir next-wasm-codeframe && cd next-wasm-codeframe
npm i next@16.3.5 @next/swc-wasm-nodejs@16.3.1
```

```js
// repro.cjs
const path = require('path')
const swc = require('next/dist/build/swc')

// Force the WASM bindings. They are the default where there are no native ones
// (unsupported platform, or a failed native download); this makes the repro run on
// any OS. `loadWasmRawBindings` reads it (the same switch `run-tests` uses).
process.env.NEXT_TEST_WASM_DIR = path.join(__dirname, 'node_modules', '@next', 'swc-wasm-nodejs')

const { codeFrameColumns } = require('next/dist/shared/lib/errors/code-frame')
const source = 'const a = 1\nconst b = ;\n'
const location = { start: { line: 2, column: 11 } }

;(async () => {
  await swc.loadBindings()

  for (const [label, options] of [
    // exactly what getOriginalCodeFrame() (dev overlay) passes when stdout is not a TTY:
    // colors = process.stdout?.isTTY ?? false, maxWidth = undefined
    ['1. dev overlay', { color: false, maxWidth: undefined }],
    // exactly what lib/typescript/diagnosticFormatter.ts and build/load-jsconfig.ts pass:
    ['2. ts diagnostic / jsconfig', { color: true }],
    // the maxWidth half: color is a valid enum value, maxWidth stays undefined because the
    // JS wrapper fills it from process.stdout.columns (absent when piped / in CI):
    ['3. maxWidth', { color: 'None' }],
    // control: both acceptable -> renders
    ['4. control', { color: 'Error', maxWidth: 80 }],
  ]) {
    console.log('--- ' + label + '  ' + JSON.stringify(options))
    try {
      console.log(String(codeFrameColumns(source, location, options)).split('\n')[0])
    } catch (e) {
      console.log('THROW: ' + e.message)
    }
  }
})()
```

```

Output on next 16.3.5 (wasm bindings):

```

THROW: Error: invalid type: boolean `false`, expected enum CodeFrameColorMode
--- 2. ts diagnostic / jsconfig  {"color":true}
THROW: Error: invalid type: boolean `true`, expected enum CodeFrameColorMode
--- 3. maxWidth  {"color":"None"}
THROW: Error: invalid type: unit value, expected usize
--- 4. control  {"color":"Error","maxWidth":80}
  1 | const a = 1
```

Notes:

- With the native bindings none of this fails: `NapiCodeFrameOptions` takes
  `color: Option<Either<CodeFrameColorMode, bool>>` and `max_width: Option<u32>`, so the
  boolean and the missing width are normalized there (`crates/next-napi-bindings/src/code_frame.rs`).
  That asymmetry, not the option shapes themselves, is the bug.
- Case 3 does not need a pipe if the caller passes `maxWidth: undefined` explicitly, which the
  dev overlay does.
- User-visible effect: in any dev server running with these bindings, an error that needs a
  code frame surfaces as `invalid type: boolean \`false\`, expected enum CodeFrameColorMode`
  instead of the real cause. We hit it with a 500 on an app route: the overlay and the server
  console showed only that message, and the actual error had to be recovered from a separate
  error log.

Even more isolated (calls the wasm binding directly, bypassing the JS wrapper, so it pinpoints
the deserialization rather than the call site):

```js
const swc = require('next/dist/build/swc')
await swc.loadBindings()
const bindings = swc.getBindingsSync()

bindings.codeFrameColumns(Buffer.from('const a = 1\nconst b = ;\n'), { start: { line: 2, column: 11 } }, { color: false })
// Error: invalid type: boolean `false`, expected enum CodeFrameColorMode

bindings.codeFrameColumns(Buffer.from('const a = 1\n'), { start: { line: 1, column: 1 } }, { color: 'None', maxWidth: undefined })
// Error: invalid type: unit value, expected usize

bindings.codeFrameColumns(Buffer.from('const a = 1\n'), { start: { line: 1, column: 1 } }, { color: 'None', maxWidth: 80 })
// -> renders correctly
```

### Analysis

The two bindings take different paths over the same public options contract:

- **napi** — `crates/next-napi-bindings/src/code_frame.rs`:

  ```rust
  #[napi(object)]
  #[derive(Default)]
  pub struct NapiCodeFrameOptions {
      pub lines_above: Option<u32>,
      pub lines_below: Option<u32>,
      pub max_width: Option<u32>,
      pub color: Option<Either<NapiCodeFrameColorMode, bool>>,
      pub highlight_code: Option<bool>,
      pub message: Option<String>,
      pub language: Option<String>,
  }
  ```

  and the conversion normalizes and defaults:

  ```rust
  impl From<NapiCodeFrameOptions> for CodeFrameOptions {
      fn from(opts: NapiCodeFrameOptions) -> Self {
          let color = match opts.color {
              None | Some(Either::B(false)) => CodeFrameColorMode::None,
              Some(Either::A(NapiCodeFrameColorMode::Error)) | Some(Either::B(true)) => {
                  CodeFrameColorMode::Error
              }
              ...
          };
          CodeFrameOptions {
              max_width: opts.max_width.unwrap_or(DEFAULT_MAX_WIDTH) as usize,
              ...
          }
      }
  }
  ```

  This matches the generated type: `color?: NapiCodeFrameColorMode | boolean`,
  `maxWidth?: number`
  (`packages/next/src/build/swc/generated-native.d.ts`).

- **wasm** — `crates/wasm/src/lib.rs`, `code_frame_columns` (~lines 228-238) deserializes the
  JS value straight into `CodeFrameOptions`:

  ```rust
  #[wasm_bindgen(js_name = "codeFrameColumns")]
  pub fn code_frame_columns(
      source: Box<[u8]>,
      location: JsValue,
      options: JsValue,
  ) -> Result<Option<String>, JsError> {
      let location: next_code_frame::CodeFrameLocation = serde_wasm_bindgen::from_value(location)?;
      let options: next_code_frame::CodeFrameOptions = serde_wasm_bindgen::from_value(options)?;
      ...
  }
  ```

  but `CodeFrameOptions` (`crates/next-code-frame/src/frame.rs`) has no `Either<_, bool>` and no
  `Option` on these two fields:

  ```rust
  #[derive(Debug, Clone, Copy, Deserialize)]
  pub enum CodeFrameColorMode { None, Error, Warning, Info }

  #[derive(Debug, Clone, Deserialize)]
  #[serde(rename_all = "camelCase", default)]
  pub struct CodeFrameOptions {
      pub lines_above: usize,
      pub lines_below: usize,
      pub color: CodeFrameColorMode,
      pub highlight_code: bool,
      pub message: Option<String>,
      pub max_width: usize,
      pub language: Language,
  }
  ```

  `serde(rename_all = "camelCase", default)` applies defaults to *missing* fields, but it does
  not make an enum accept a boolean, nor `usize` accept an explicit `undefined` — hence the two
  errors. The wasm `.d.ts` even types the options as `any`, so nothing rejects these shapes at
  the JS boundary.

Next's own callers use exactly the shapes the napi path documents:

- `packages/next/src/next-devtools/server/shared.ts` → `getOriginalCodeFrame()` passes
  `{ color: <isTTY>, maxWidth }` where the default is `process.stdout?.isTTY ?? false` and
  `maxWidth` is `undefined` when called with a boolean.
- `packages/next/src/lib/typescript/diagnosticFormatter.ts` → `{ color: true }`.
- `packages/next/src/build/load-jsconfig.ts` → `{ message, color: true }`.

So 100% of code frames fail on the WASM path: the dev overlay, `next build` TypeScript
diagnostics, and the `jsconfig.json` parse error path.

### Suggested fix

Either is fine and small:

1. In `crates/wasm/src/lib.rs`, deserialize into a tolerant option struct (the mirror of
   `NapiCodeFrameOptions` plus its `From` conversion) before calling `render_code_frame`, or
2. Make `CodeFrameOptions` tolerant (`color: Option<Either<CodeFrameColorMode, bool>>`,
   `max_width: Option<usize>`) and default them where they are used.

Option 1 keeps the tolerance in one place per binding boundary; option 2 makes the crate
accept what the JS types already allow.

### Impact

- `next dev` on the WASM fallback: the dev overlay cannot render the frame, so an unrelated
  binding error replaces the real one — the same class of problem that #85592 fixed for
  `@babel/code-frame` ("throwing RangeErrors when rendering errors, hiding the original
  issue").
- `next build` on the WASM fallback: TypeScript diagnostics and `jsconfig.json` errors fail
  with the serialization error instead of the actual diagnostic.
- #85592 lists this as a known review risk ("environments where native bindings behave
  differently (e.g. WASM fallback path)"); this report is that case.

### Workaround

We coerce the options in `packages/next/src/shared/lib/errors/code-frame.ts` with a pnpm patch:
`color: false` → delete the property (the default on both bindings), `color: true` → `'Error'`,
and `maxWidth: undefined` → a number. Note that the native enum has no `None` variant, so
`'None'` would not be a portable value to substitute for `false`. Happy to send this as a PR if
that is the preferred place for the fix.
````
