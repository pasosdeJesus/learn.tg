## 1. What breaks

On **OpenBSD/adJ**, Next 16.3.5 has no native SWC bindings
(`next-swc does not have native bindings for platform openbsd/x64`) and therefore uses the
WASM package `@next/swc-wasm-nodejs`. Its `codeFrameColumns(source, location, options)`
export deserializes `options` with `serde`: `color` must be the **enum**
`None|Error|Warning|Info` and `maxWidth` a **number**.

Next, however, passes:

- `color: false` / `color: true` (boolean) in `next/dist/next-devtools/server/shared.js`
  (`getOriginalCodeFrame`, with `process.stdout?.isTTY ?? false` as the default), in
  `lib/typescript/diagnosticFormatter.js` and in `build/load-jsconfig.js`.
- `maxWidth: undefined` when the output **is not a terminal** (the `next dev` started by
  `bin/dev` writes to a file: `process.stdout.columns` does not exist), and in
  `getOriginalCodeFrame` whenever it is called with a boolean.

With that the binding throws and **the real error disappears**:

```
Error: invalid type: boolean `false`, expected enum CodeFrameColorMode
Error: invalid type: unit value, expected usize
```

Effects measured on this VM: in `next dev` the code frame cannot be painted. The server
console replaces the real error with the binding error, and on a page error the overlay paints
the message and the call stack but no frame (measured 2026-09-27 in the reproduction
repository); the earlier measurement on learn.tg, with a 500 on an API route, saw no error at
all in the overlay or the console. That is why `apps/nextjs/lib/server-errors.ts` +
`instrumentation.ts` exist, the workaround of
https://github.com/pasosdeJesus/learn.tg/issues/252. In `next build`, a malformed
`tsconfig.json` or a TypeScript diagnostic would fail when the message was being built.

## 2. Evidence (2026-09-27)

In `/tmp/learn-tg-server-errors.log`, with the **previous** patch applied (the one that only
normalized `color`), the trace is the same but with the other error:

```
[2026-09-27T11:02:36.986Z] onRequestError GET /api/guide?courseId=103&... 
Error: Error: invalid type: unit value, expected usize
    at Module.codeFrameColumns (…/next/wasm/@next/swc-wasm-nodejs/wasm.js:12:22)
    at Object.codeFrameColumns (…/next/dist/build/swc/index.js:1114:32)
    at codeFrameColumns (…/next/dist/shared/lib/errors/code-frame.js:23:40)
```

That is: the previous session's patch fixed the `color` boolean and left `maxWidth:
undefined` alive. The cause that was being reported was, again, invisible (the real 500 was
PostgreSQL's `error: remaining connection slots are reserved for roles with the SUPERUSER
attribute`).

## 3. The fix

`apps/nextjs/patches/next@16.3.5.patch` normalizes both options in
`dist/{esm/,}shared/lib/errors/code-frame.js`, the only module every caller goes through:

```js
if (options.color === false) {
    delete options.color;          // the default on both paths is "no color"
} else if (options.color === true) {
    options.color = 'Error';       // true was Error on the native path too
}
if (typeof options.maxWidth !== 'number') {
    options.maxWidth = 100;        // stdout.columns does not exist without a terminal
}
```

Important detail: `false` is **not** translated to `'None'`. The native binding's enum
(`NapiCodeFrameColorMode`) only has `Error|Warning|Info`, so `'None'` would be valid for
wasm and an `InvalidArg` in native; deleting the property leaves the default on both paths
(verified in §5). That nuance is why the patch is not limited to "converting the boolean
into an enum".

What it does **not** do: it does not touch the WASM binding, nor the behavior when the
output *is* a terminal (`process.stdout.columns` rules), nor ANSI colors (`color: true`
still paints).

It is declared in `apps/nextjs/package.json`:

```json
"pnpm": { "patchedDependencies": { "next@16.3.5": "patches/next@16.3.5.patch" } }
```

`pnpm install` re-applies it (it is recorded in `pnpm-lock.yaml`), so a fresh checkout on
OpenBSD already carries the fix.

- [x] `codeFrameColumns` with the options Next really passes (boolean in `color`,
      `maxWidth: undefined`) returns the code frame instead of throwing.

      respected.
- [x] The patch applies with `pnpm install` without `ERR_PNPM_PATCH_FAILED` and leaves both
      files exactly as the patch generates them.
- [x] A 500 in a route stops being lost: the real error stays visible.

      `node_modules`).
- [x] In `next dev`, a real 500 shows its cause with a code frame again, without the
      binding trace (§5).

## 6. Pending / notes

- **How it is applied and checked.** It is applied only by `pnpm install` (which takes it
  from `pnpm.patchedDependencies`). To do it by hand and verify it stuck:

  ```sh
  cd apps/nextjs
  make next-patch        # pnpm install --frozen-lockfile + check
  make next-patch-check  # check only (fails if node_modules carries the old patch)
  ```

  `make all` and `make prod` already run `next-patch-check` before building: they abort with
  instructions when the patch is not applied, just like `build-guard` does with the dev
  server.
- **How it is regenerated** (do not edit `node_modules` by hand: pnpm uses hard links and the
  store is left dirty, `ERR_PNPM_PATCH_FAILED`):
  1. remove `pnpm.patchedDependencies` from `package.json` and run `pnpm install` (this
     leaves the original file);
  2. save the original, make the change, and generate the diff with
     `diff -u --label a/dist/... --label b/dist/... original new`;
  3. restore `patchedDependencies` and run `pnpm install`;
  4. check that the installed file matches the edited one (`diff`).
- **Updating Next invalidates the patch**: if one day there are native bindings on OpenBSD
  (or Next normalizes these options — the real fix would be for it to pass `color: 'None'`
  and a numeric `maxWidth`), the patch is deleted and this entry is closed. A patch that no
  longer applies does **not** go unnoticed: `pnpm install` fails with
  `ERR_PNPM_PATCH_FAILED` and `make next-patch-check` says so.
- **The workaround stays.** `lib/server-errors.ts` + `instrumentation.ts` are still useful:
  they log to stderr and to `/tmp/learn-tg-server-errors.log` the errors that do not go
  through the overlay (streaming routes, `unhandledRejection`). What changes is that the
  overlay shows the cause again.
- **Is it worth it in production?** It is not urgent and it does not change the runtime: the
  overlay belongs to `next dev` and the site serves `next build`/`next start`. What does
  change is the **moment of compiling on OpenBSD**, which runs on the same machine: if there
  is a `tsconfig.json` error or a TypeScript diagnostic, without the patch the message is lost
  in the binding trace. Since the patch comes in with the normal `pnpm install` (the one in
  `make all`), the reasonable thing is to keep it in every environment and **not** add a
  special deploy step; the only effect of not having it is a worse error message.
- **Upstream report.** Filed: https://github.com/vercel/next.js/issues/99348, with the public
  reproduction repository the `reproduction-template` requires
  (https://github.com/vtamara/wasm-code-frame-columns). The issue text, field by field, is kept
  in §8. If it is accepted, this requirement closes by deleting the patch and its entry in
  `patchedDependencies`.

### Field 7 — Additional context

```markdown
The two bindings take different paths over the same public options contract:

- **napi** — `crates/next-napi-bindings/src/code_frame.rs` declares the tolerant shape and
  normalizes it in `impl From<NapiCodeFrameOptions> for CodeFrameOptions`:

  `color: Option<Either<NapiCodeFrameColorMode, bool>>`, `max_width: Option<u32>`
  (`None | Some(Either::B(false))` → `CodeFrameColorMode::None`, `Some(Either::B(true))` →
  `CodeFrameColorMode::Error`, `max_width.unwrap_or(DEFAULT_MAX_WIDTH)`). This matches the
  generated type (`color?: NapiCodeFrameColorMode | boolean`, `maxWidth?: number`).

- **wasm** — `crates/wasm/src/lib.rs`, `code_frame_columns` deserializes the JS value straight
  into `CodeFrameOptions` with `serde_wasm_bindgen::from_value`, and
  `crates/next-code-frame/src/frame.rs` has no `Either<_, bool>` and no `Option` on those fields:

  ```rust
  pub enum CodeFrameColorMode { None, Error, Warning, Info }

  #[derive(Debug, Clone, Deserialize)]
  #[serde(rename_all = "camelCase", default)]
  pub struct CodeFrameOptions {
      pub color: CodeFrameColorMode,
      pub max_width: usize,
      // …
  }
  ```

  `serde(default)` applies to *missing* fields: it does not make the enum accept a boolean nor
  `usize` accept an explicit `undefined`. The wasm `.d.ts` types the options as `any`, so nothing
  rejects these shapes at the JS boundary.

Next's own callers use exactly the shapes the napi path documents:

- `packages/next/src/next-devtools/server/shared.ts` → `getOriginalCodeFrame()` passes
  `{ color: <isTTY>, maxWidth }`, with `process.stdout?.isTTY ?? false` as the default and
  `maxWidth` filled from `process.stdout.columns` (undefined when stdout is not a TTY, which is
  the case for `next dev` writing to a log or in CI).
- `packages/next/src/lib/typescript/diagnosticFormatter.ts` → `{ color: true }`.
- `packages/next/src/build/load-jsconfig.ts` → `{ message, color: true }`.

100% of code frames fail on the WASM path: the dev overlay, `next build` TypeScript diagnostics
and the `jsconfig.json` parse error path.

Suggested fix, either is fine and small: (1) in `crates/wasm/src/lib.rs`, deserialize into a
tolerant option struct (the mirror of `NapiCodeFrameOptions` plus its `From` conversion) before
calling `render_code_frame`; or (2) make `CodeFrameOptions` tolerant
(`color: Option<Either<CodeFrameColorMode, bool>>`, `max_width: Option<usize>`) and default them
where they are used. Option 1 keeps the tolerance at one place per binding boundary; option 2
makes the crate accept what the JS types already allow.

Impact: `next dev` on the WASM fallback cannot render the frame, so an unrelated binding error
replaces the real one — the same class of problem that #85592 fixed for `@babel/code-frame`
("throwing RangeErrors when rendering errors, hiding the original issue"), and #85592 lists this
exact risk ("environments where native bindings behave differently (e.g. WASM fallback path)").
`next build` fails with the serialization error instead of the actual TypeScript or
`jsconfig.json` diagnostic.

Versions: reproduced on `next@16.3.5` (with `@next/swc-wasm-nodejs@16.3.1`) and on
`next@16.4.0-canary.51` (with `@next/swc-wasm-nodejs@16.4.0-canary.51`); the source check above
is against `canary`.

Workaround while it is unfixed: a pnpm patch over
`packages/next/src/shared/lib/errors/code-frame.ts` that coerces the options before calling the
binding (`color: false` → delete the property, the default on both bindings; `color: true` →
`'Error'`; `maxWidth: undefined` → a number). Note that `'None'` is not portable: the native
enum has no `None` variant, so deleting the property is what keeps both paths working. Happy to
send this as a PR if that is the preferred place for the fix.
```
