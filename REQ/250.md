# R-#250: Session lifetime and revocation for wallet sessions

**Link:** https://github.com/pasosdeJesus/learn.tg/issues/250

**Status:** Pending — open question from the wallet/session review (2026-09-19).
Nothing is implemented: the NextAuth session has no explicit lifetime and no way
to be revoked server-side.
**2026-09-25 (relación con el criterio "SIWE sin conexión" de la PWA):** este requisito es la
mitigación elegida para el único caso real que quedaba —estar **sin red** más que la vida de la
sesión (30 días)— y la opción decidida por el operador fue **A: sin protocolo nuevo**
(https://github.com/pasosdeJesus/learn.tg/issues/234 §4.9). Con red la sesión ya se renueva sola
(NextAuth re-emite la cookie; `updateAge` por defecto 24 h), así que lo que falta aquí sigue
siendo la **decisión** de duración explícita y la **revocación** del lado del servidor; el otro
lado del caso (no perder las respuestas guardadas cuando el 401 llega) ya quedó cubierto: la
cola conserva la respuesta sin gastar intentos y avisa "vuelve a firmar".
**Created:** 2026-09-19
**Type:** Security / Session
**Priority:** Medium — the amounts are small and the credential is HttpOnly, but
the audience is on shared phones and the session outlives the wallet key by a
month.
**Dependencies:** https://github.com/pasosdeJesus/learn.tg/issues/233 (session-only

## 1. Objective

Give the session a **known, deliberate lifetime** and a way to **end it
server-side**, so that losing a phone, lending it, or leaking a cookie stops being
valid for a month.

## 2. What exists today (verified 2026-09-19)

- `app/api/auth/auth-options.ts:244` declares `session: { strategy: 'jwt' }` with
  **no `maxAge`**, so NextAuth applies its default **30 days** (a dev-site run
  returned `expires: 2026-10-19`).
- The session cookie (HttpOnly JWT, `sub` = wallet) is the **only** credential
  (R-#233 Phase 2); `authenticateUser` validates it and compares `sub` with the
  requested wallet (`lib/authenticateUser.ts`).
- Sign-out is client-side: `signOut()` clears the cookie. A JWT cannot be revoked
  before it expires, so a stolen cookie is valid until then.
- The wallet key is a separate lifetime: it lives in memory and locks after
  `INACTIVITY_LOCK_MS` (one hour, R-#246); the session does not follow it.
  Sensitive writes already need the unlocked wallet (no wallet client → no write),
  which is what makes a long session tolerable today.

## 3. Risks

| Risk | Effect with 30 days |
|---|---|
| Borrowed/shared phone (the measured audience) | Whoever picks it up keeps the account: profile, scores, referrals and every write the wallet allows |
| Cookie leaked (XSS, extension, profile copy) | Valid until expiry; nothing to revoke from the server |
| Lost device | Only the wallet key expiry of one hour matters; the session survives a month |
| Support/KYC action needed (R-#221) | No lever: the operator cannot cut a session |

## 4. Proposal

1. **Explicit lifetime.** Set `session.maxAge` (start with **7 days**) and
   `updateAge` so the cookie slides only with real activity, not on every request.
   Write both in `auth-options.ts` so the value is reviewed, not inherited.
2. **Server-side revocation without a session store.** Add a
   `session_epoch` (integer) to `usuario`; the JWT carries the value it was issued
   with, and `authenticateUser` rejects a token whose epoch is older. Bumping the
   column invalidates every session of that user (lost phone, support request,
   detected abuse) with one UPDATE. Optionally re-issue the epoch on wallet unlock
   so the normal flow keeps working.
3. **Decide the interaction with the wallet lock.** Document the rule explicitly
   (today implicit): the session identifies the user, the unlocked wallet
   authorizes value; a signed-in user with a locked wallet can read but not write.
   If that rule is accepted, a shorter session is not needed for writes.
4. **Documentation.** `doc/siwe-auth-flow.md` (new "Session lifetime" section) and
   `doc/api-security.md`; mention in `doc/pwa-user-guide.md` that closing the app
   does not sign the user out, but disconnecting the wallet does.

## 5. Acceptance criteria

- [ ] `session.maxAge` is explicit (7 days, adjustable) and `updateAge` is set.
- [ ] An expired cookie gets 401 from a protected route (test, no real waiting:
      issue a token with a past `exp` and call `authenticateUser`).
- [ ] Bumping `session_epoch` for a user makes their existing cookie answer 401 on
      the next request, without a server-side session store.
- [ ] Wallet unlock (or an explicit action) re-issues the session so normal users
      are not signed out mid-course.
- [ ] The "signed in but wallet locked" rule is written down and covered by a test
      (read works, write answers the documented error).
- [ ] Both docs updated; no behavior change for the external-wallet flow.

## 6. Open questions

1. 7 days, or 24 hours with a silent renewal while the wallet is unlocked?
2. Is `session_epoch` enough, or is a per-device identifier wanted (so one phone
   can be cut without touching the others)?
3. Should the operator be able to cut a session from the admin UI (R-#221)?
