# R-#253: Transfer confirmation policy (grace window + new destinations)

## 1. Objective

Decide how a transfer is confirmed once the in-app wallet is **unlocked**:

- Too strict (a gesture for every move) is what the operator rejected as
  unusable.
- Too loose (a fixed one-hour window with no other check) lets a hostile flow drain
  the whole balance to any address for an hour.

The chosen middle ground keeps the device gesture as the real barrier while removing
the friction for the common case.

## 2. Decision

1. **Grace window of 15 minutes.** After the user verifies with the device — an L1
   assertion **or** an L2 biometric unlock (`evaluatePrf`) — a transfer to an
   address the wallet **already used** does not ask again for 15 minutes
   (`USER_VERIFICATION_GRACE_MS`).
2. **A new destination always asks**, even inside the window. The address is
   remembered **only after a successful broadcast**, per wallet, in `localStorage`
   (`destinations.ts`; max 200, `localStorage` unavailable ⇒ memory only).
3. `lockWallet()` / `deleteWallet()` clear the window (and the idle auto-lock, one
   hour, calls `lockWallet()`), so after inactivity the next move asks again.
4. Applies to `eth_sendTransaction` through the in-app provider. For an ERC-20
   transfer the destination is the **recipient in the calldata**
   (`transfer`/`transferFrom`), not the token contract
   (`extractDestination`).

## 3. Threat analysis (why this balance)

| Scenario | Does the grace window matter? |
|---|---|
| **Remote attacker without code execution in the app origin** | No: it cannot reach the provider, the IndexedDB record or the signing API. |
| **Stolen phone, screen unlocked** | Yes: with the old rule the thief could drain through the UI with no gesture; now only to addresses already used, and only 15 minutes. A new address forces the gesture. |
| **Code execution in the same origin** (XSS, hostile extension, automated browser agent) | Barely: while the wallet is **unlocked** the account also lives in module memory (`getUnlockedAccount()`), so such an attacker can sign directly and bypass the provider. The decisive control is **L2 + the auto-lock**, not L1. |
| **AI / automation** | It cannot forge WebAuthn (the platform authenticator needs a physical factor), so it cannot create a *new* destination silently. It does shorten the time-to-exploit, which is why the window is 15 minutes and a new destination is always gated. |

Consequence documented for the operator: on a stolen *unlocked* device, money can be
moved **to a known address** within the 15 minutes without a gesture. The password is
never stored and the 12 words remain the recovery.

## 4. Implementation

| Where | What |
|---|---|
| `packages/pdj-wallet/src/web-authn.ts` | `USER_VERIFICATION_GRACE_MS = 15 min`; `markUserVerified` / `hasRecentUserVerification` / `clearUserVerification` |
| `packages/pdj-wallet/src/web-authn.ts` | `assertUserVerification` and `evaluatePrf` mark the verification (L1 and L2) |
| `packages/pdj-wallet/src/destinations.ts` (new) | `isKnownDestination` / `rememberDestination` / `clearDestinations`, per wallet |
| `packages/pdj-wallet/src/provider.ts` | `extractDestination(tx)`; `requireFundsConfirmation({ destination })` (a new destination ignores the window); the destination is remembered after `eth_sendRawTransaction` succeeds |
| `packages/pdj-wallet/src/wallet.ts` | `lockWallet` / `deleteWallet` call `clearUserVerification` |
| `packages/pdj-wallet/src/index.ts` | exports the new helpers |

## 5. Acceptance criteria

- [x] A transfer to an address already used does not ask for the gesture within 15
      minutes of a verification (L1 or L2).
- [x] A transfer to a **new** address always asks for the gesture, even inside the
      window.
- [x] The destination is remembered only after a successful broadcast; an address
      becomes "known" only after that.
- [x] For ERC-20 transfers the destination is the calldata recipient, not the token
      contract.
- [x] `lockWallet()` clears the window (idle auto-lock ⇒ next move asks).
- [x] Unit tests: `destinations` (5), `user-verification` (5), `provider`
      `extractDestination` (3), `funds-confirmation` (new/known destination, cancel,
      grace).
- [x] EN/ES user text says when the gesture is asked.

## 6. Out of scope / future

- **Amount cap per window** (move silently only up to X USD/hour): needs prices and
  a product decision.
- **Whitelist UX** (let the user see/remove remembered destinations): `destinations`
  is per wallet and capped, but the app does not expose it yet.
- **Session lifetime** (R-#250) is the other half of the exposure window.
- For balances that matter, a native/hardware wallet is still the recommendation;
  the in-app wallet runs the key in the browser realm while unlocked.
