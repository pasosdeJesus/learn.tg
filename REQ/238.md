# R-#238: Integrate In-App Wallet in learn.tg


**Link:** https://github.com/pasosdeJesus/learn.tg/issues/238

**Status:** Implemented (2026-09-15, branch `mvppwa`, deployed to the dev site
that day) — the MVP subset tracked by R-#244 is wired: `WalletSelector` mounted
in `Header`, `WalletDialog` with the create/import/unlock/delete/SIWE flow,
hooks extended, `WalletEventListener` lock handling done and `doc/wallet-auth.md`
updated. The `in-app-wallet` E2E spec passes on the dev site (R-#244 §10).
**Created:** 2026-09-15
**Type:** Feature / Integration
**Priority:** High (blocks R-#242)
**Dependencies:** R-#236, R-#237

### 1. Objective

Integrate the in-app wallet into learn.tg's authentication flow, alongside the existing external wallet support. Create `WalletSelector` so users can choose between in-app and external wallets. Extend the wallet hooks (`useAuthAddress`, `useWallet`, `useWriteContract`) to work with the in-app wallet provider.

### 2. Changes

**New component `components/WalletSelector.tsx`:** ✅ created (header state only)

- `'use client'`.
- Uses `useInAppWallet()` and `useAuthAddress()`.
- **Signed in** (a `sessionAddress` exists, i.e. the NextAuth session is the
  credential, R-#233 Phase 2): short address + "Disconnect" (clears
  `sessionAddress`, locks the wallet, `signOut`). The decision is deliberately
  based on the **session**, not on `isInAppUnlocked`: after SIWE the wallet is
  locked again, so keying the header off the lock state made it ask to unlock
  right after signing in.
- Not signed in: a button that opens `WalletDialog`
  ("Unlock your in-app wallet" / "Sign in with in-app wallet" / "Use in-app
  wallet", depending on `status` and `isInAppUnlocked`). While the wallet status
  or the NextAuth session is still resolving (`loading`) the button reads
  **"In-app wallet"** and is disabled: claiming "Use in-app wallet" (or "Unlock
  your in-app wallet") before knowing whether a wallet/session exists is what
  made the operator think the sign-in had been lost.
- The address is shown as a `bg-gray-100` pill with a **ghost** "Disconnect"
  (the previous `outline` buttons were white on the white header), and the
  "Use external wallet" button is ghost too.
- `window.ethereum` is detected **after mount** (effect), not during render: the
  old `typeof window !== 'undefined' && !!window.ethereum` branch rendered the
  button only on the client and produced a **hydration mismatch**
  (confirmed by `fresh-wallet-first-connect`, whose diff showed the
  `wallet-use-external` button).

**New component `components/WalletDialog.tsx`:** ✅ created

- The whole flow lives in a modal, not in the header: create/import with a PIN,
  the **12 words for manual backup** with a confirmation step, unlock, delete the
  wallet, and the **SIWE sign-in** (`lib/in-app-siwe.ts`).
- Why: the operator's manual test on 2026-09-15 found (a) the header showed
  `InAppWalletSetup`/`InAppWalletUnlock` inline and unreadable, (b) creating a
  wallet appeared to do nothing because those components had their **own copy of
  the hook state**, and (c) the flow never signed in, so pages showed "Partial
  login… connect and sign again" while authenticated calls answered 401.
- `useInAppWallet()` now keeps a single module-level store
  (`useSyncExternalStore`) shared by every instance, so components and consumers
  agree.
- **The flow restarts when the modal closes**: `recovery`, `pin`, `confirm`,
  `mnemonic` and the error are cleared on close. Without it, reopening the modal
  after creating a wallet landed on the recovery-phrase screen (the operator hit
  this on 2026-09-15) and the wallet looked impossible to unlock.
- After `create` the modal shows the 12 words and the sign-in button ("I saved
  them, sign in"); `unlock` and `import` sign in immediately.

**Extend `lib/hooks/useAuthAddress.ts`:** ✅ done

- Add `inAppAddress` from `useInAppWallet()`.
- `address = sessionAddress || inAppAddress || storedAddress`.
- `isWalletAvailable = isInAppUnlocked || window.ethereum.eth_accounts().length > 0`.
- Add `isInAppUnlocked` and `isSessionLoading` (`useSession().status ===
  'loading'`) flags.

**New `lib/hooks/useWalletProvider.ts`:** ✅ done — the single place that resolves
the effective EIP-1193 provider (in-app while unlocked, else `window.ethereum`).

**Extend `lib/hooks/useWallet.ts`:** ✅ done (consumes `useWalletProvider`)

- `usePublicClient` and `useWalletClient` use `getInAppWalletProvider()` when the in-app wallet is unlocked, falling back to `window.ethereum`.

**Extend `lib/hooks/useWriteContract.ts`:** ✅ done (consumes `useWalletProvider`)

- Use `getInAppWalletProvider()` when the in-app wallet is unlocked, falling back to `window.ethereum`.

**Extend `components/WalletEventListener.tsx`:** ✅ done

- Watch `useInAppWallet().status`: a transition **away from** `unlocked`
  (locked, deleted) counts as a disconnect.
- On that transition: clear `sessionAddress` (localStorage) and call
  `signOut({ redirect: true, callbackUrl: '/' })`.
- A wallet that is already locked when the page loads does **not** sign out (no
  transition happened), so a locked wallet keeps the session.

**Update `components/Header.tsx`:** ✅ done

- Replace `ConnectWalletButton` with `WalletSelector`.

**Update `doc/wallet-auth.md`:** ✅ done

- Document the in-app wallet flow.
- Document `WalletSelector`.
- Document the provider EIP-1193.

### 3. Acceptance criteria

- [x] `WalletSelector` exists and renders correctly in all states (9 component
  tests in `components/__tests__/WalletSelector.test.tsx`, including the neutral
  label while the wallet status or the session is loading; `Header`/`Layout`
  tests mock it).
- [x] `WalletDialog` covers the second series of fixes: 8 tests, including
  "starts a fresh flow when it is closed and reopened".
- [x] `useAuthAddress` returns the in-app address when unlocked (and reports
  `isSessionLoading`).
- [x] `usePublicClient` and `useWalletClient` work with the in-app wallet (both
  take the provider from `useWalletProvider`).
- [x] `useWriteContract` works with the in-app wallet.
- [x] `WalletEventListener` signs out when the in-app wallet is locked (3 new
  unit tests in `components/__tests__/WalletEventListener.test.tsx`, 8 total).
- [x] User can create an in-app wallet and sign in via SIWE — verified on the dev
  site (branch deployed 2026-09-15): `make test-e2e-spec SPEC=in-app-wallet` →
  0 failures in 17.7 s (R-#244 §10), and 2 of 3 independent re-runs passed in
  ~12 s (R-#245 §5). The spec is `e2e/specs/in-app-wallet.spec.mjs` (R-#245 §5).
- [x] User can use an external wallet (existing flow preserved) — `WalletSelector`
  delegates to `ConnectWalletButton` when there is a `window.ethereum`;
  `fresh-wallet-first-connect` passed against the dev site on 2026-09-15
  (0 failures, 43.7 s: the page uses the session wallet and makes no anonymous
  `/api/scholarship` calls), and `wallet-event-disconnect` keeps covering the
  disconnect path.
- [x] `doc/wallet-auth.md` updated.
- [x] Header + modal flow verified end to end **on a local `bin/dev` instance**
  (2026-09-15, Chrome via Puppeteer, `BASE_URL=http://localhost:4000`): after
  creating and closing the modal, the header reads "Sign in with in-app wallet";
  unlocking signs in, the header shows the address pill + "Disconnect" and keeps
  it **across reloads** (the previously observed "reverts to Unlock your in-app
  wallet" came from the deployed build, where the header keyed the state off
  `isInAppUnlocked`), reopening the modal starts a fresh flow, and no hydration
  error appears. Script: `/var/www/adJ-ia/tmp/wallet-dialog-repro.mjs`
  (throwaway; see `doc/environments.md` §Local run modes 4).
- [x] E2E `fresh-wallet-first-connect`: the dev site now serves this branch
  (2026-09-15) — re-run on 2026-09-15 against the dev site: **0 failures in
  43.7 s** (no anonymous calls; the page uses the session wallet).
